## 总结

**这一版可审查性改善，部分分类更合理，但仍不能当成准确、完整的最终情况目录。**

- 确定改善：逐成员证据可直接核对；部分正常处理被拆开；参数 JSON 错误单列；过程案卷不再使用自行设定的“可疑数量 ≥10”阈值冒充密度。
- 明确未解决：无约束类仍混入有约束成员；跨轮缺失仍一概描述为发起澄清；同参重试类仍将未提供缓存证据的成员说成缓存短路。
- 新版具体遗漏：知识轴 R88 的保单查询超时没有进入对应类别，尽管该 ref 已在知识召回类出现。
- 部分原来的杂项类别被并入更大的“规则违规”“收尾失当”，名字更宽了，但不是更具体的语义聚合。
- 摘录真实只证明出处，不证明类名与共同说明受到支持。R52 是直接反例：摘录中的“范围约束”与该类“无附加约束”当面冲突。

## 关键发现

### 1. 有约束案例仍落入“无附加约束”的正常类

位置：意图理解 / sound / 单对象明确查询的对象字段子问题完整映射。

该类共同说明宣称“无附加约束、指代或歧义情形”，但：

- R52/#31 的入类摘录直接包含“‘先列清单’的范围约束”。
- R17/#26 的完整 reason 明确说保留了业务客户号及当前核对范围约束，摘录只取了对象字段部分。
- R59/#33 完整 reason 明确说“完整保留……约束条件”，摘录避开了这句话。

这与相邻“复合/带约束请求的约束与格式要求完整保留”边界不一致。R66/#34 已移入带约束类，是局部改善，但另外三个反例仍在。

### 2. 历史缺失类继续把所有后果概括成“被迫澄清”

位置：上下文管理 / problematic / 跨轮历史与实体上下文未注入致指代失效。

R157/#52 确实支持“上一轮查询关注点未传入”，属于这类的上位共同情况。但同案例 R160 明确记录：模型实际调用 policy_detail，获取数据后作答，“未发生多余重复或澄清”。

所以本类成员不是都缺少实体，也不是都发起澄清。应把共有部分限定为“历史实体或任务关注点未传入”；澄清是部分案例的后果。意图轴已经把 #52 拆成“改单继承……未继承”，但上下文轴没有相应收紧说明。

### 3. “仅走澄清”与成员摘录直接矛盾

位置：规划与路由 / problematic / 多轮追问仅走澄清、未覆盖必要取数。

- R134/#48 支持“实际调用序列仅触发 ask_clarify”。
- R155/#51 的摘录却是“未执行保单与条款查询，仅获取客户全量明细画像并尝试澄清”。它执行过客户查询，并不是仅调用澄清工具。

两例真正的共同点是“遗漏了必要的保单/产品查询”，而不是“只走澄清”。建议去掉标题里的“仅走澄清”，在说明中区分两种路径。

### 4. 知识轴漏掉一个独立情况，不是漏掉整条记录

R88/#37 的完整 reason 同时包含：

1. 保单查询服务两次超时失败；
2. 产品条款检索返回其他产品内容。

当前仅进入“产品知识库召回无关产品、目标条款未召回”，没有进入“保单查询接口超时致子问题数据未取得”。因此该超时类当前显示 6 例，少覆盖了这条明确支持其含义的记录。

上一版 R88 同时进入服务失败和召回错误两类，本版在这一点上退步。协议允许同一 ref 多归属，不存在被迫二选一的限制。

### 5. 同参重试不等于已证实缓存短路

位置：规划与路由 / problematic / 同名同参重发未被拦截且失败结果被缓存吞掉。

R6/#24、R55/#31 有缓存命中的明确证据；R90/#37 的摘录及完整轴 reason 只支持重复调用未被拦截，没有提供写入缓存、毫秒返回或未触达后端的证据。

此外 R90 原文本身先称“不可重试失败”，又称前次提示“可稍后重试一次”、未声明不可重试。应保留这个输入口径的待核查边界，而非统一包装成确定的同一种机制。

### 6. 更宽的类名解决了字面错配，却留下过粗分类

“工具选择违反分工或准入规则”同时放入：
- 保单需求误调客户搜索；
- 清单需求未走卡片入口；
- 使用未经确认的保单号；
- 删除条件扩大范围；
- 无必要地发起澄清。

现在不再把 R54/#31 的 policy_search 误叫 customer_search，这点改了；但将原“其他工具决策违规”并进来后，形成六成员的规则违规大类，仍缺少更具体的共同操作或失败机制。

“失败分支的收尾与整合失当”同样把清空事实、错误引用校验覆盖答复、未写 gaps、直接拼装字段/密文等不同情况放在一起。可作粗粒度检索目录，不适合直接当作一个可定位、可修复的故障类别。

### 7. 工具解析/检索类的根因表述过强

位置：工具执行 / problematic / 检索/解析缺陷致返回错对象或应查未查。

R63 有解析层缺陷依据；R91 对其中“有明确产品代码仍仅返回候选”的情况明确写着“原因未定位（工具或数据待查）”。共同说明却将应查未查统称为“工具解析/检索自身缺陷”。

应保留现象级表述及未定位边界，不能用一个成员的确定归因覆盖另一个成员的未知原因。

## 对本次优化的判断

不能因为类别从 44 变成 50、或全部 207 条摘录通过出处校验，就说聚类质量整体已经提高。

目前能确认的收益是：
1. 一部分具体类别边界改进；
2. 摘录与共同说明的矛盾更容易被人工发现；
3. 某些原先混在一起的正常模式与格式问题被区分。

目前仍缺的是模型是否真正用完整 reason 检查了自己的共同说明，而不是先写一个宽泛总结、再摘一句看似相关的真原文。语义遗漏也不能通过“每个 ref 至少引用一次”来检测。

本次只新增审阅报告，未修改代码、Prompt、配置、原判定或聚类结果，未调用真实模型。
