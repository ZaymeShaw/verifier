# 同执行 A/B 轨迹：两份 llmtracing 既有判词的证据核对

性质：助理人工核对草案，非独立专家 gold；不计算准确率。仅使用已有结果，无模型调用、无业务调用、无实现修改。

## 范围与版本

证据：`report/business-trace-provider-ab-20261001/traces.json` 中 `llmtracing`。边界为 `non_streaming_http_llm_probe`，不是最终用户界面观察。

待核对结果：`report/business-trace-llmtracing-transcript-20261001/ab-llmtracing-r1.json`（R1）与 `ab-llmtracing-r2.json`（R2）。下文 axis / obligation / link_id 均可在 `axes.results[].output.results[]` 定位。主轴位置为 `judge.reasoning_summary` 与 `judge.fulfillment_assessments[].downstream_impact`。

两份结果均早于“t*.final 是调用方实收响应”的提示词澄清。当前代码已有该说明；历史错误不能直接算作当前版本仍复现。先前单轴复跑没有在本组报告中保存完整可复核结果，不能视为整链修复验证。

只核对同一条完整轨迹的两次 llmtracing 判词，不拿 Agno 判词当答案，不声称这是两个独立业务样本。标签正确与推理/引用正确分别评价。

## 2. 需要修正或进一步校准的判断

### F01｜两次 context_memory 把已有 HTTP 实收误判为缺证

- R1 / delivered_intact / t1.final：
  > 对话稿仅记录了系统落库输出 t1.final，缺少调用方客户端实收记录。
- R2 同样要求“用户终端实际展示或收到的最终答复内容”。
- 核对：该轨迹的 final 来源为 verifier HTTP 调用方的 extracted_output；应用边界是非流式 HTTP。不能把“未观察最终 UI”当作“没有 API 调用方实收”。
- 分类：证据角色误认，导致虚假的 insufficient_evidence；不是业务系统缺证。
- 版本边界：提示词已补说明，本次只确认旧结果的问题，不声称新版本仍错。共享 delivered_intact 文本仍要求“落库与实收”，需后续校准其是否引入本场景不需要的第三端。
- R1 主轴能够识别这一错误并纠正，但不能因此认为过程轴的错误无影响。

### F02｜两次主轴都把 API 证据扩大成实际 UI 展示事实

- R1 downstream_impact：
  > 前端与业务用户直接看到内部工具名、推理过程和未解析的JSON代码块。
- R2 downstream_impact：
  > 导致下游前端直接向用户展示了系统的内部思考与调试代码块。
- 核对：现有材料只证明 answer 字段如此；没有浏览器/UI 渲染或用户实收证据。
- 分类：问题本身发现正确，但影响描述越界。
- 可接受表述：API 返回内容不符合成品答复要求；若下游直接展示，会影响可读性。不能写成已观察到 UI 展示。
- 用户确认“最终结果不应混杂”并不自动证明前端已原样展示，也未确认这项单独必须阻塞整案。

### F03｜R1 为污染结果补出了不可见的处理机制

- R1 reasoning_summary：
  > 导致网关组装t1.final……时无法正常解析AgentOutput，将三轮思考文本与原始代码块全部拼接到顶层answer中。
- 核对：对话稿可比较模型输出与业务响应，证明混杂；看不到解析器运行结果，也未证明是“网关”负责业务 answer 组装。
- 分类：不可支持的精确归因。可能与其他 provider 的调查结果相似，也不能作为 llmtracing-only 证据下的已知事实。
- 可接受表述：最终 answer 包含多个调用中的过程文本与代码块；是哪一步如何组装，当前材料不足以确定。
- R2 没有同样具体的“网关解析失败”断言，但仍有 F02 的影响越界。

### F04｜两次 arrives_intact 用单侧证据证明双侧无损

- R1：以 `t1.c2.m4/t1.c3.m6`（模型收到的工具消息）及 call 头证明“原样无损传递”。
- R2：输入引用是 `t1.c1.response/t1.c2.response`（发起工具调用的参数），输出引用是收到的 tool 消息，却说工具产出的事实未丢失、未改义。
- 核对：工具请求不是工具的原始执行结果。这里只看到模型收到的结果，没看到业务工具产出、传递前的独立一端。
- 分类：无损结论证据不足，引用位置存在但证据类型不对。
- 可接受结论：模型输入中可见这些工具结果；至于业务侧原始结果到模型输入之间是否发生改写，当前无法核对。若另一个传递边界（例如上一请求消息是否在下一请求保留）有两端，则可以独立判定该边界。
- 不建议为了通过校准把整个 context_memory 一律设为缺证；只限制无证据的这项断言。

### F05｜“看不到控制步骤”被表述成“没有控制步骤”

- R1 planning / branch_condition：
  > 本轮无独立的 Condition/Router/Loop 等工作流控制步骤，全流程由 Agent 模型调用驱动。
- R2 引用 gap.visibility 说明非模型内部路由不可见，却仍用“未出现”支撑 not_applicable。
- 核对：llmtracing 的可见范围不允许断言整条业务链没有控制步骤。
- 分类：适用性边界不清。R1 的“全流程”断言明确过强；R2 若仅指当前可见模型片段，not_applicable 可以是范围结论，但不能据此排除隐藏控制步骤。
- 建议校准规则：明确结果针对可见范围还是全业务路径。只有正面证据支持未发生时，才把它算作整案 not_applicable；不可见不能自动等同未发生。也不要求模型虚构隐藏分支。

### F06｜多调用共用一组引用，造成逐调用归属失真

- R2 model / output_faithful 展开为 c1、c2、c3 三条结果，却每条都带 c1、c2、c3 的全部输入输出。
- R2 model / tool_decision 对 c1 的引用包含 c2/c3 的系统材料与 c3 工具结果；已有 flags 明确标记了部分后时点 source_refs。
- 核对：自然语言观察可能整体正确，但不代表每条结果的所有引用均属于该次调用。当输出被展开成“义务×位置”后，证据归属失去原来的对应关系。
- 分类：引用质量问题，不等于三个 pass 都应改成 fail。应拆分每次调用实际适用的证据，或明确分组内每个位置的证据映射。
- 当前 `_flag_model_sources` 只检查 source_refs 的先后顺序，不检查全部 evidence.input 是否属于该次输入；没有 flags 也不是证据充分的保证。

## 3. 不应据此制造的新问题

- customer_detail 参数中的 `customer_ids: []` 在此模型实际看到的 schema 中没有 minItems 限制。因此不能用隐藏后端的数组约束倒推模型违反了可见 JSON Schema。两次判词说参数结构符合可见 schema，并不因工具后来报错而必然错误。
- 模型提示词明确要求 answer_draft/gaps 为业务可读正文，并限制内部词和来源转述。模型自己的 gaps 是否违反这条要求，与业务后处理是否允许把顶层 gaps 泛化，是两个不同契约问题。
- P06 顶层 gaps 泛化尚无明确字段消费契约，不计漏报或误报；不能因为旧主轴负面描述该变化就把它变成 gold。
- 两次主裁决均 not_fulfilled，有出生年月目标未达成这一独立依据。发现推理瑕疵不等于必须把最终标签反转为 fulfilled。

## 4. 优先修正方向（未实施）

1. 先校准证据角色：真实 HTTP 实收、模型输出、工具请求、模型收到的工具消息不能互相冒充；只验证有两端的实际传递边界。
2. 主轴区分观察事实、潜在影响和根因假设。发现污染，不应自动生成“UI已展示/网关解析失败”的故事。
3. 明确可见范围内不适用与整案不可见的区别，避免缺证被说成没有。
4. 逐调用证据归属独立核对，不以存在合法编号替代语义支持。

以上均是通用六轴的证据约束，不是 Insurance 特例。修复应先以这些既有结果构造回归检查，再申请小规模模型复跑确认行为；本轮不修改实现、不新增 gold，也没有新的模型费用。
