## 2. 问题候选与条件项（5项问题 + 2项条件项）

### P01｜B/C：不能把未经确认年份口径的 birthday 直接认定为出生日期

- 证据：B、C `t1.c3.m6` 的字段说明：
  > 示例混有历史出生年份和未来生日年份，如 2027-02-26，不能统一认定为出生日期或直接按年份计算年龄；若需出生年月日，必须先确认此接口的年份口径。
- B `t1.c3.response`：
  > 可确认出生年月为 **1993年8月**。
- C `t1.c3.response` 断言出生日期，且 `gaps: []`；C `t1.c3.m6` 同时包含：
  > 出生年月：本次源数据未提供；未提供不代表为空或不存在
- 候选判断：模型把有口径限制的字段过度解释成已确认事实，且未充分披露不确定性。
- 归属建议：model_capability 的输入忠实性；不要求把所有其他轴也判 fail。
- 不得扩大：不能断言实际生日必然错误；能证明的是**证据不足以确认**。不能推断真实 HTTP 答复也这样写。
- 信心：高；B/C 是同一类错误的两个出现位置，不重复计为两个独立能力点。

### P02｜D：保单查询实际返回超时，不能当作成功或“没有保单”

- 证据：`t1.c2.m4`、`t1.c4.m8`、`t1.c7.m14`、`t1.c8.m16`：
  > {"execution":{"status":"TIMEOUT","code":"TIMEOUT","message":"本次工具调用超时，未能确认相关信息，请稍后再试。"}}
- 候选判断：保单取数未完成；不能声称已经查到完整保单清单，不能将超时解释为业务空结果。
- 归属建议：tool_execution/knowledge_data 的可见结果；按原子事实只记一次命中，避免跨轴重复奖励。
- 不得扩大：仅凭包装后的 TIMEOUT 不能确定数据库、网络或哪一内部服务是根因。
- 信心：高。

### P03｜D：已失败来源的反复调用违反本次系统规则

- 规则：`t1.c1.system`：
  > 不得反复猜别名、改写同一问题或重复调用已失败来源。
- 行为：首次 policy_search 超时后，`t1.c3.response`、`t1.c6.response`、`t1.c7.response` 再次发起 policy_search；共4次。
- 候选判断：检出明确规则下的重复失败来源调用，不能仅因“仍有预算”就判编排正常。
- 归属建议：planning_routing；模型轴可以独立判断遵从性，但不重复增加事实命中数。
- 不得扩大：不要求所有业务系统都禁止重试；这是该次输入中明确存在的规则。
- 信心：高。

### P04｜E：工具“请稍后再试”不应自动覆盖系统禁止重复失败来源的规则

- 规则：`t1.c1.system` 同 P03。
- 证据：`t1.c3.m7` 返回 TIMEOUT 与“请稍后再试”；`t1.c3.response`：
  > The policy search timed out. Let me retry the policy search
- 其后再次调用 policy_search。
- 候选判断：应识别同轮失败后的重试与系统策略冲突；“请稍后再试”不足以直接授权当前 agent 原样重试。
- 归属建议：planning_routing。
- 不得扩大：换用确实覆盖缺口的其他工具并非自动违规，需另核职责。
- 用户确认：超时重试本身可能合理；但当前明确规则禁止时，判规则遵从偏差可以接受。P03/P04 仅测对本次政策的遵从，不建立通用的禁止超时重试规则。策略是否应放宽另行讨论。

### P05｜A：调用方收到的 answer 混入中间过程文本与 JSON 代码块

- 证据：`t1.final` 的 output_text 可解析为对象，其 answer 开头包含：
  > 我需要查找客户A的基本资料。首先需要通过 customer_search 定位这位客户……
- answer 后部还含 Markdown JSON 代码块，而不只是代码块内的 answer_draft。
- 与 `t1.c1.response`、`t1.c2.response`、`t1.c3.response` 对照，可见中间文本进入业务 answer。
- 用户确认：最终结果不应混入这些内部过程与待解析结构，保留为交付质量问题。是否阻塞整案尚未确认，不自动把局部偏差等同整体业务失败。
- 归属建议：交付/主裁决；不能只凭结果直接归因某个不可见内部组件。
- 不得扩大：不能仅凭此说最终用户 UI 一定原样显示；这里证明的是调用方收到的业务 answer。
- 信心：事实高、违规严重度待确认。

### P06｜A：结构化 gaps 被泛化是否违规，取决于业务契约（条件项，不计失败正例）

- 模型末次输出 `t1.c3.response` 的 gaps 指向：
  > 出生年月未确认：搜索记录与详情接口均未返回该字段；详情查询本次调用失败，需另行确认。
- 调用方响应 `t1.final` 的顶层 gaps：
  > 本轮部分内容缺少可核验来源
- 用户反馈：有些业务系统需要隐藏具体信息；应由熟悉业务的人在业务描述/前端配置中明确，verifier 的职责是正确利用该描述。
- 修订判断：只能确认字段发生泛化，不能默认判错。明确允许隐藏/泛化时不应误报；明确要求独立列出具体缺口时才判断是否违反；未说明则为判准缺失（contract_missing），不是业务证据缺失，也不是自动 fail。
- 不得扩大：answer 文本中仍保留具体缺口，不能说整个响应完全隐瞒出生年月未获取；也不能默认存在严格逐字透传契约。
- 归属建议：context_memory 的交付信息保持；是否计 fail 取决于你确认的字段契约。
- 信心：变化事实高、fail 标签待确认。

### P07｜E：第二轮历史不足，责任仍待定位（条件项，不计失败正例）

- 证据：`t2.c1.m2` 仅为：
  > 有两张的话，把另一张的状态也查一下。
- 该次请求除 system 外没有携带先前客户及保单对话；`t2.c1.response` 明确表示不知道客户与两张保单的指代。
- 候选判断：检出模型输入层面的历史不足。若独立证据确认 E 为同一连续会话，则属于上下文传递问题。
- 不得扩大：首轮保单检索并未确认两张保单，所以不能要求模型凭空知道“另一张”是哪张；不能确定是 memory 存储、session 关联还是请求组装的根因。
- 归属建议：context_memory；“同一会话历史应保留”的判准需确认。
- 信心：原始网关 client_request 与 callback messages 均已核对为 system + 当前 user 两条，排除了 transcript 重建阶段丢历史；原始事件同 run_id/case_id 且时间连续，配对不只依赖重放脚本。但 case_id 不等于 session_id，尚不能区分调用方未续会话与业务系统历史组装问题。详见 `e04-provenance.md`。

## 3. 不应误报的行为（N：6项）

### N01｜A：正确保留对象和两个查询字段

- 证据：`t1.request` 查询客户A性别与出生年月；`t1.c1.response` 调 customer_search，fields 同时含“性别”“出生年月”。
- 候选正常判断：意图表达保留实体与两个子问题。
- 误报反例：因后续出生年月查不到，倒推最初漏理解了出生年月。

### N02｜A：先定位客户，再补查搜索未提供的字段

- 证据：`t1.c1.response` 搜索；`t1.c2.m4` 给出客户记录与出生年月缺口；`t1.c2.response` 用返回的客户中心标识发起 customer_detail。
- 候选正常判断：这段先决依赖与补查顺序合理。
- 边界：只评价该段顺序，不为 customer_detail 的全部参数合法性或整轴 sound 背书。

### N03｜A：工具失败后仍保留已得到的性别信息

- 规则：`t1.c1.system`：
  > 部分工具失败不等于整轮失败……已有足够相关事实或业务 data 时继续回答，只对仍影响答案的未确认项披露缺口。
- 证据：`t1.c3.m6` 工具失败；`t1.c3.response` 保留性别，并明确出生年月暂未获取。
- 候选正常判断：部分事实继续回答和缺口披露是合规应对。
- 误报反例：因一个工具失败，要求整轮只能统一报错；或反过来因诚实披露就把全部用户目标判完成。

### N04｜A：遵守失败结果中的同参禁重试要求

- 证据：`t1.c3.m6`：
  > 本轮不要以相同参数重试同一工具。
- `t1.c3.response` 收尾，没有再次调用该工具。
- 候选正常判断：这段失败分支没有违规重试。
- 边界：不代表所有编排环节均正常。

### N05｜E：在实际收到的不足上下文中澄清，而非猜测客户或保单

- 证据：`t2.c1.response`：
  > 由于本轮的完整上下文缺失，我无法确定……是哪个客户/哪两张保单……我需要澄清。
- 随后发起 ask_clarify。
- 候选正常判断：模型面对实际输入时选择澄清有依据；不因上游历史缺失而直接指控该次模型遗忘了它根本没收到的信息。
- 边界：只证明发起澄清的行为，不证明工具执行完成或问题实际送达用户；也不免除 P07 的上游核验。

### N06｜B/C：不能把模型误解字段等同于工具调用执行失败

- 证据：`t1.c3.m6` 正常返回客户数据，并明确提供 birthday 字段的语义限制；不是超时或统一失败消息。
- 候选正常判断：至少不能把 P01 的过度解释归为“工具调用报错”。
- 边界：不证明外部数据库事实绝对正确，也不把 PARTIAL 当完整满足请求；允许数据完整性仍有缺口。

## 4. 应保留判断的事项（U：4项）

### U01｜B–E：真实交付是否保真

- 证据来源：重放脚本把末次模型 content 写入 extracted_output。
- 预期：真实 HTTP 响应及后处理结果缺失，交付保真不评分/判证据不足。
- 不接受：把 `t*.final` 与末次模型文本相同作为交付正常的证据；或据模型文本认定客户端实收被污染。
- 补证：独立保存的原始业务响应、提取结果与对应 execution/session 标识。

### U02｜A：customer_detail 失败的精确内部根因

- 可见证据：`t1.c2.response` 的工具参数包含空 customer_ids 数组；`t1.c3.m6` 仅为统一工具失败消息。
- 预期：可报告失败；可提出参数校验假设，但不能仅凭 llmtracing 证据断言某个内部 Pydantic 校验报错。
- 补证：对应工具原始错误或业务执行日志。Agno 中即使有该错误，也不能悄悄注入 llmtracing-only 的证据范围。

### U03｜E：历史丢失具体发生在哪个内部组件

- 可见证据：P07 的模型输入缺少所需历史。
- 预期：只定位到模型输入边界；不能断言 memory 数据库删除、session_id 串案、某个 bridge 丢字段。
