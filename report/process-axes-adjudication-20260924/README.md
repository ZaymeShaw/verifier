# 过程六轴边界裁定范例（2026-09-24）

评测产物：`verifier-llm_probe-cases-20260924-212317.xlsx`（insurance-agno-e2e，32 条 live）
六轴定义基准：`~/Downloads/process-axes-v3.md`（v3）
被测系统：insurance-qa-agent（`~/WorkSpace/package/insurance_qa_agent/insurance-qa-agent`），运行库 `~/.insurance-qa-agent-real/runtime-real.db`

本文是一次「逐格核对六轴结论」的范例：边界说不清的地方，一律回到原始记录和外部依赖直接取证后再裁定，不凭轴的理由文字猜。

---

## 1. 判准口径

### 1.1 被测对象是大模型系统

模型负责理解、决定调什么工具、整合结果；系统负责给模型正确的信息、工具和规则，并把模型的输出如实交付给用户。六轴是**定位工具**，沿着这条链问「哪一环坏了」：

用户原话 → 意图理解 → 规划与路由 → 工具执行 → 知识与数据 → 模型整合 → 系统交付（上下文管理）

### 1.2 每个轴只问自己那一环

| 轴 | 只问这一环 | 不管 |
|---|---|---|
| intent_understanding | 系统内部表达（门控参数、任务表述、工具参数）里的对象、字段、约束、子问题、指代是否与用户原文一致 | 理解对了之后的一切 |
| planning_routing | 路由、拆解、工具顺序、失败分支、重试、结束时机；系统按设计跑但设计不对也算 | 工具本身、上下文拼装、模型逐次输出 |
| tool_execution | 工具/后端/子 agent（含工具内部的解析模型）自身有没有做对：报错、超时、残缺、返回对象与参数不符 | 该不该调、参数从哪来、数据源有没有 |
| knowledge_data | 每个子问题需要的数据，外部源给了没有；对象/版本/时点对不对。**没数据就是 problematic**，注明原因类型 | 调用怎么发、失败怎么处置 |
| model_capability | 只看上下文正常的调用：输出是否忠实于输入、工具调用决策是否与输入一致、输出契约是否遵守 | 输入本身缺的东西 |
| context_memory | 系统拼上下文、传状态、用缓存、注入历史、截断，**以及模型输出往下游投影（bridge/finalize）**时，有没有把信息弄丢、改义、用旧 | 模型拿到完整上下文后做得对不对 |

### 1.3 结论用词

- **nf（problematic）**：被测系统在该环有缺陷。
- **fail**：评测本身跑不下去，例如上游模型限流导致整条链路没跑起来。
- 查不到不等于正常，要分轴看：保单号不存在时，知识轴判 nf；模型如实说查不到，模型能力轴判正常。

### 1.4 什么叫判得准

按「用例 × 轴」逐格核对：

1. **事实对**：引用的记录真实存在，描述与原始记录一致。
2. **归位对**：问题落在该轴那一环。一个根因让几环都真坏了，几轴都判 nf 是对的，不强行去重；只有「这一环其实没坏」时，才算归错。
3. **口径对**：nf 表示这一环确实有缺陷；环境导致跑不下去的记 fail。
4. **一致**：同类情况在不同用例里判法相同。

## 2. 取证方法

边界不清时按下面顺序取证，每条裁定至少落到其中一项：

1. **被测系统运行库**：`agno_runs.run_data` 里的 `step_results`（门控/agent_input/agent/agent_bridge/finalize 各步内容）、`step_executor_runs[].messages`（模型每次实际收到的消息和输出）、`tools[]`（工具参数与返回原文）。对照「模型写了什么」和「用户最终拿到什么」。
2. **被测系统源码**：找到结果背后的具体机制，例如拦截规则、兜底话术、终止钩子，确认是设计行为还是偶发。
3. **直连外部依赖**：绕过被测系统，直接用同样的请求去问知识库、解析服务，区分「库里没有」「检索排错」「解析错了」。

## 3. 逐条裁定

### 3.1 条款检索拿错产品（B02、E01、E02、F01）

- **现象**：问安佑福、鑫瑞优享的等待期或免责，`product_knowledge` 返回的 5 条正文全部是其他产品。
- **取证**：
  - 直连 `chunk_context_search`（source=product_wiki），用全称+险种代码、全称+维度、关键词三种方式各取前 10 条，都没有安佑福和鑫瑞优享的任何条款。
  - 源码 `app/tools/real/product_rag.py` 注明「名称提示不等于产品 ID 级过滤」，只做语义召回。
  - 返回的 hint 写着「产品『平安安佑福…』相关知识仅供参考」，把别家产品的条款标成了目标产品。
- **裁定**：

| 轴 | 结论 | 理由 |
|---|---|---|
| knowledge_data | nf | 库里没有该产品条款 |
| tool_execution | nf | 没有如实返回空，而是把他产品内容标成目标产品交给模型 |
| model_capability | 正常 | 四条里模型都识别出是他产品，没有借用 |
| context_memory | 不判 | 系统只是如实转交了工具结果 |

- **现表对照**：知识轴全对；工具轴对 3 条，漏了 F01；上下文轴在 E01、C09 判 nf，归错轴。

### 3.2 通用问答答非所问（B17、C09）

- **现象**：问「年缴保费和累计已交保费的区别」，`general_qa` 返回的都是「趸交与年交的区别」。
- **取证**：直连 `faq_context_search`（source=askbob），换三种问法各取前 10 条。库里有「已交保费」相关条目，但没有任何一条解释年缴保费与累计已交保费的区别。
- **裁定**：两条都是知识缺失，knowledge_data 判 nf。
- **现表对照**：B17 对；C09 知识轴判了正常，同一问题记到了上下文轴，判错且前后不一致。

### 3.3 用未确认保单号调详情被拦（B17、B01）

- **现象**：`policy_detail` 返回「该保单号既非用户本轮明确提供，也不是保单搜索或会话已确认结果」。
- **取证**：
  - 保单号来自 `customer_search` 返回的客户画像（polNoInfo）。
  - 系统提示词只写「只能用用户明确提供、候选或会话已确认的 ID」。
  - 准入钩子 `app/tools/hooks.py` `_selection_error` 实际只认用户原话和 `policy_search` 结果。
- **裁定**：模型按提示词这样理解说得通，工具也按设计拦截，两边都不是主因。问题在**系统告诉模型的规则和工具实际执行的规则不一致**，属于编排设计，planning_routing 判 nf。tool_execution 判正常。
- **现表对照**：
  - 工具轴判 nf，判错；规划轴判了正常，漏判。
  - B01 模型轴的契约 nf 可以保留：英文开场白、JSON 外包裹代码块、字段名外泄都站得住；但「用了未确认 ID」这一条理由不成立。

### 3.4 保单搜索假空（B17 第一次调用）

- **现象**：同一个人，查「乐欣凡名下的保单，关注年缴保费和累计已交保费字段」返回 0 条；后来查「乐欣凡的保单」返回 3 条。
- **取证**：直连保单搜索解析服务 `policy-search-parse`，第一句被解析为 `prem_method_desc EQ 年缴`，人名丢了。
- **裁定**：工具内部的解析模型理解错了，tool_execution 判 nf。模型在查询里多写了「关注…字段」，有次要责任。
- **现表对照**：工具轴把这次空结果当成「契约允许的未命中」放过，漏判。
- **注意**：该解析服务不稳定。复现时「乐欣凡的保单」这句返回了 1001（解析失败），与评测运行时的结果不同。

### 3.5 姓氏加生日月份筛选失败（D01）

- **现象**：`customer_search` 三次都返回「未能可靠解析本次筛选条件或排序，尚未执行客户查询」。
- **取证**：
  - 直连客户解析服务：能正确解析出性别=女、生日月份 12-01~12-31；「姓平」被解析为 `searchClientName MATCH 平 match_mode=prefix`。
  - 被测系统本地适配层 `app/tools/real/customer_parser.py` `_condition` 只接受 `suffix`，于是整条查询被拒。
  - 「按客户号升序」在解析服务这一步就被丢掉（sort 为空）。
- **裁定**：

| 轴 | 结论 | 理由 |
|---|---|---|
| tool_execution | nf | 工具说明写着支持按姓名、性别、生日月份查，实际做不到 |
| knowledge_data | nf 可保留 | 原因类型应写「查询未执行」，而不是「数据源没有」 |
| model_capability | 正常 | 换三种说法重试后澄清 |

- **现表对照**：工具轴判了正常，判错。

### 3.6 最终答复是检索原文拼接（B10）

- **现象**：用户拿到的是「qa_pair qa-document-01: · qa_answer:【标题】…」原样拼接的退保问答。
- **取证**：
  - 模型只被调用一次，同时发起了 `policy_search` 和 `general_qa`，这一步是对的。
  - `policy_search` 返回 OVERLOADED，是被测系统自己的本地容量闸，由评测并发触发。
  - `app/tools/hooks.py` `capacity_hook` 按设计抛出 `StopAgentRun`，终止模型循环。
  - 第二条 assistant 消息就是错误信封本身，桥接层把问答事实直接渲染成卡片输出。
- **裁定**：planning_routing 判 nf：一个工具繁忙就终止整个模型循环，已经拿到的另一半数据没人整合，原文直接露给用户。线上高峰期同样会触发，所以按系统行为评，不记 fail。
- **现表对照**：规划轴判「失败分支有产出」「结束时机合理」，漏判。

### 3.7 模型的正确答复被换成套话（E01 第三轮）

- **现象**：用户拿到「暂时无法确认相关信息，请补充更完整的信息后再试，或转人工渠道办理。」
- **取证**：
  - 模型实际输出的是「未能取得安佑福等待期与免责的可核实内容，请勿以其他产品条款推断，建议以合同原文为准」，这是对的。
  - 模型没有引用任何事实，因为能引的只有他产品。
  - `app/runtime/agent_bridge.py` 的「无引用不放行」规则（D16）把整段答复替换成 `_UNCITED_BUSINESS_ANSWER`。
- **裁定**：模型输出往下游投影时被系统改义，context_memory 判 nf。用户根本不需要补充信息，这句话会误导用户。
- **现表对照**：六个轴都没发现。当时的上下文轴查的是「检索内容不相关」。

### 3.8 已确认、不再展开的两类

- **负例**（neg-wrong-empno、neg-unknown-policy）：知识轴判 nf、模型能力轴判正常，现表正确。
- **上游模型限流**（F02、F05、F20、K，`RateLimitError: Maximum concurrency limit of 3`）：记 fail，不计入各轴。

| 用例 | 该判 nf 的轴 | 现表 |
|---|---|---|
| B02/E01/E02/F01 条款拿错产品 | 知识、工具 | 知识对；工具漏 F01；上下文在 E01 归错 |
| B17/C09 问答答非所问 | 知识 | C09 归错到上下文 |
| B17/B01 准入拦截 | 规划（提示词与准入规则不一致） | 工具判错，规划漏判 |

| E01 答复被换成套话 | 上下文（桥接层改义） | 漏判 |

## 5. 本次暴露的两个系统性盲区

1. **工具内部的解析模型出错看不见。** 解析错了常表现为 EMPTY 或 AMBIGUOUS，工具轴一律当成契约内的业务结果放过。判工具执行时，要拿同一 run 内的其他调用或直连结果去核对这个「空」是真空还是假空。
2. **模型输出之后被系统改坏看不见。** 桥接层和 finalize 如何处理模型答复，是 v3 上下文轴的职责；但当前 `context_memory.py` 只判模型输入的充分性、相关性、组织，偏离了 v3。判上下文轴时，必须对照 agent 步骤的模型原文和 finalize 的最终答复。

## 6. 局限

- 「知识库没有该产品条款」是多种查法都召回不到得出的结论，没有逐条遍历全库。
- 工具内部的解析服务是模型，结果不稳定，复现结果可能与评测运行时不同。
