## 测法

对 30 条冻结 trace（25 条 clean + 5 条 frozen 快照）各构建一次案卷，然后按同一种「会被塞进 prompt 的 payload」口径比较：

- **现在**：`build_chunks` 逐段展开正文（`{case_overview, chunk}`），即组织者今天真实收到的东西；
- **清单**：同一 `case_overview` + 每段只给 `{id, kind, turn, scope, at, chars, field_status, copy_of, parent_ref, ref, summary}`；
- **瘦身清单**（测量用投影，未落代码）：去掉空键、每字段只留 80 字头条预览、字段状态正常就不写状态。

轴视图按 `output.selection.refs` + `build_axis_view` 重建（结果文件里的 `view` 只是计数，不是视图本体）。

## 诚实结论：B1 未完全达标

验收线是「压缩率 ≥60%；引用 100% 可达」。实际：

**压缩率**
- 轴视图：全过（最差 −65.8%，>160k 的 47 个视图清零）。
- 组织者：**平均过、逐样本不过**。清单口径 9/30 样本压缩不到 60%，其中 **2 个样本清单反而比现在大 47.8%**；瘦身口径仍有 5/30 不到 60%，最差只降 15.5%（无样本退化）。
- 原因是清单行太肥：160 字预览 × 每字段 + 11 个键，在小案卷上比正文还长；瘦身后剩下的地板是 `case_overview` 骨架（19k～24k，两边都要发）。

**可达性**
- 99.86%，不是 100%。那 1 条真不可达不是清单的问题，是**案卷真的没登记这类材料**：本轮最终回答（`run.content` / `extracted_output`）没进案卷，案卷 `kind` 里只有 `definitions/messages/model_calls/reasoning/runs/sessions/states/steps/tool_calls`，没有任何 output 类编号。轴想引用「第 2 轮最终回答」只能自己编一个 `turn2/final_output`。

### 实测挖出的平台缺陷（均已修，各带测试）

1. **端点回 200 但产出不可用 → 被记为成功、不切端点**（最严重）：整理阶段两次拿到空产出，六轴全部静默降级成
   `not_evaluable`，表面像「诚实缺证」。修：`llm_client._usable_structured()` 在重试循环内部预检，不可用即
   `record_failure` 并切端点。
2. **中转站把上游 4xx 当 200 回吐成 JSON**：实测主端点返回
   `{"error": {"code": 400, "message": "User location is not supported for the API use."}}` 被当成模型产出。
   修：`provider_error_body()` 增认「只含一个 error 键」的 JSON 错误体。
3. **工具调用消息带 pydantic 对象 → 调用记录整条丢失**：`save_context` 抛错被吞，用了工具的调用在 context store
   查不到。修：`_extract_messages` 过 `_json_safe()` 拍平。

### 补测：调用记录落档 + 端点工具能力（第 5、6 个缺陷）

补上第一条诊断（落档失败不再静默）后，真根因浮出来：**记录里出现机器绝对路径 → 路径契约抛
`PathContractError` → 整条调用记录消失**。模型把记录编号当文件路径写成 `tool_args.path = /Users/...`。
这不是新问题——旧批次有一次实测的轴记录目录（`axes-1ad8ddab76ad:replay-snap-cash-value`）整个是空的，
同一个原因。修法：`portable_artifact.redact_forbidden_paths()` 用**同一套谓词**隐去会被拒的绝对路径
（相对引用 `turn1/records/run` 原样保留），`_track_context` 不再静默失败。

第二条：**本地 cursor 桥（fallback1）不支持 tool calls**（把工具调用拼成正文 `___TOOL_CALL___` 标记、
拼错工具名、第二次直接吐 JSON 数组），却一直在降级链里吃废产出 → 整理阶段两次尝试全废 → 六轴全缺证。
修法：`LlmEndpoint.tool_calls` + `serves(needs_tools=)` + `LLM_FALLBACK_1_TOOL_CALLS=false`。
实测同一只跑整理轴的探测：`llm_attempts: 1`、直接打到 fallback2 拿真产出、`axes_without_evidence: []`。

## 读取粒度修正 + 每轴材料需要（B3 收尾）

改前实测到的口子：整理员按 12k 结构图下钻、只读了 `session_state` 的 3 个片段，
视图却把 **29.7k 整棵子树**倒给 4 个轴。修正三处同口径：

1. 超过单条上限（12000）的记录：只给「逐字读过的片段 + 其余部分结构图 + 说明」；
2. **读到结构图不算读到正文**：这种编号不可引用（`evidence_audit.shape_only` 单独留痕）；
3. **每轴声明依赖哪几类记录**（`AxisSpec.needs`）：写进整理员 prompt，并在审计里报「某轴没拿到它依赖的类别」。

第 3 条的必要性来自一个实测事实：**轴的检查集是从材料推出来的**——上下文轴的 checks 是
「每个 `model_calls` 三项」，没选到 `model_calls` 时它的 6 项检查整体塌缩成 1 项，轴静默降级成
`not_evaluable`（像诚实缺证，实为选材失误）。

## requires 前置 + 完整读取 + 端点兜底（2026-09-22，三样本实测）

用户裁定：**需求方（六个轴）用业务语言讲清「我要判断什么、需要看到什么证据」（不含检查项/字段名等实现细节），
侦探（整理员）看得到案卷全部细节，自己把需求映射成具体编号。** 本条方向落地为 `AxisSpec.requires` →
`downstream_questions.requires`（替换原来的类别级 needs 提示；`needs` 只留作程序侧塌缩审计）。
同时修了两处工作条件：路由器兜底（全部端点各试过一次后，未进冷却的端点各再给一次机会）、`TOOL_CALL_LIMIT` 48→64。

| 样本（最缺证） | 基线旧实现 | needs 版（b3-full） | requires 版 |
|---|---|---|---|
| baseline-insured-name | 六轴全有结论 | 缺证 11 | **缺证 1**；tool=sound（补上「还要能看到本轮超时/时限上限」这句需求后回到 sound） |
| ctx-ref | tool/context/knowledge 均 not_evaluable | 缺证 21 | **缺证 4**；tool/intent/planning/knowledge=sound |
| ctx-cache | 六轴全 sound | 六轴全 not_evaluable | 缺证大幅下降；但仍出现整理员引 46 个未读编号被闸门剔除（b3f） |

残留缺证根因（同批实测）：

1. **单节点 12000 字上限卡住「整页工具回填」**（`messages/3` 40921 字）：侦探读它只能拿到结构图，轴也只能看到结构图
   → 缺证。旧实现整棵倒出所以能判。**已修**：侦探可带 `full=true` 申请一次完整读取（上限 80k），
   回执算读过正文，轴视图 `read_paths` 带上整段，去留由轴视图预算（160k）决定。
2. **轴口径**：context_memory 的 sufficiency 规则要求「完整请求缺失必须缺证」，而案卷自己声明了
   `gap.exact_model_request`。旧实现把「重建输入 + token 校对」当充分证据判 sound。要由轴拥有者定口径，程序不代答。
3. **整理员行为**：引用检索片段/父编号（没有正文回执）→ 闸门剔除 → 整轴塌缩。已在工具说明与整理员 prompt 里写明
   「检索片段/清单摘要/结构图都不算读过」「引用要精确到你读的那一段」。

**可复现性（重要）**：ctx-cache 同代码连跑两次（b3g1/b3g2）→ g1 tool=sound/context=not_evaluable，
g2 tool=not_evaluable/context=problematic。**同输入下 2 个轴翻转**，单样本判定有 ±2 轴噪声；
30 样本对比的 43 处降级 / 19 处升级要按这个噪声地板读（共 180 个轴位）。
