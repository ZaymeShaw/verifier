## 1. 缺证项到底缺在哪

29 条 case 共 162 个 `insufficient_evidence` 检查项。一项可有多个原因；括号内是"唯一原因"的项数。

| 类别 | 项数（唯一） | 性质 |
|---|---:|---|
| 程序剔除"视图外编号" | 71（37） | **不是缺证**。模型引用了没有读取回执的编号，旧程序把结论降为缺证。W3 已改为只标注 |
| `exact_model_request`（原始模型请求被脱敏） | 82（29） | 平台永久限制 |
| 案卷里有、本轴没读到 | 47（8） | **不是缺证**。选材召回或 3 次补查预算不够，属分析轴/补查能力问题（W2 召回） |
| `raw_backend_http`（没有后端原始报文） | 10（4） | 平台永久限制 |
| 缺判准（单工具耗时阈值、SLA） | 6（5） | 不是证据问题，是协议没定判准 |
| `state_transitions`（没有逐次状态变化） | 7（2） | 可补采候选 |
| `source_documents` | 3（0） | 平台永久限制 |
| `history` | 1（1） | 单轮 case 的 history 为 `empty`，本来就没发生，不该算缺口 |
| 其他 | 14（4） | 多为"某段正文没进初始视图"，同"没读到" |

**结论：约 2/3 的缺证与"证据真的拿不到"无关**。程序剔除已在 W3 修掉；"没读到"要靠分析轴召回和补查预算解决。

## 2. 平台缺口的实际状况

五类缺口在全部 30 份案卷里都出现，是 provider 固定声明，不随 case 变化：

| 缺口 | 状态 | 实际影响 |
|---|---|---|
| `exact_model_request` | unverified | 89 次模型调用的原始输入**全部**脱敏。其中 66 次有经 token 校验的重建输入（verified），23 次（5 条 case）重建失败或缺消息 |
| `raw_backend_http` | unsupported | 工具正文可见，但拿不到下游原始请求/响应 |
| `state_transitions` | unsupported | session_state 只有运行末态，看不到每一步的状态变化 |
| `source_documents` | unsupported | 不访问外部文档 |
| `history` | empty / 有值 | 单轮时是"未发生"，不是缺口 |

重建失败集中在：multi-policy-anjinning 8 次、customer-profile 5 次、A01 4 次、agg-paid-prem 3 次、C08 3 次。原因是持久化消息缺失（messages 计数 0），或 assistant 消息与 LLM span 数对不上。

## 4. 已做的程序改动（W2 容错 + W3 不改结论）

- **分析轴失败时整条阻断，原因可见。** 失败写明三类原因：`[运行环境]`（端点、限流、超时）、`[轴实现]`（分析两次都产不出可用结构）、`[需补材料]`（业务 Trace 缺失）。被阻断的六轴会写出上游失败原文。去掉了"分析轴没给案卷时六轴全判缺证"的旧兜底，以及 `insufficient` 这个整理结论。
- **端点容错。**
  - 修了公共客户端的一个缺陷：没试过的端点都在冷却时，请求直接报 `no untried llm endpoint remains`，不会去重试已试过但仍健康的端点。
  - 扩展轴没有可用端点时按 30s、60s、120s 退避等待；生产请求仍然快速失败。
- **程序不改已判出的问题。**
  - fail 永不被降级。
  - 引用没有读取回执时只写进 `flags`，本轴内格式重试也保留已读回执。
  - 只保留一条协议约束：pass 或 not_applicable 没有引用、或检查范围为空时，记为缺证（v3：检查范围为空不得判 sound）。
  - pass 可以附带不影响结论的范围限制。
- **导出。** "扩展轴明细"的"引用"列输出引用编号、缺口和程序标注。

测试：相关的 11 个测试文件加分析轴、业务 Trace 测试全部通过。全量测试有 17 项失败，其中我这次改动涉及的已全部修复；剩余 11 项都是原有失败，与本次无关（缺历史 api-check 文件、`.env.example` 过期、schema 渲染、两条已不存在的保险 case）。

另外删掉了一条旧测试：它测的是已删除的兜底分支，而且运行时会真实调用模型端点。
