# 结果：现行六轴 vs 「本应/实际」新方案（8 个真实 case，Gemini 3.8 flash medium，各两遍）

线路：primary 中转，`gemini-3.8-flash-medium`，两臂同模型、同冻结输入。评判清单 gold.json（22 hard / 7 soft，跑之前冻结）。
**这是 8 个 case 的小样本，没有统计显著性；差距小于归类噪声的，不下结论。**

## 一句话

在修掉新方案第一版程序检查的 bug 后，新方案**召回不低于现行**（第二遍更高）、**误报率更低**、**清单外真问题明显更多**，
代价是**证据引用的可核对性差很多**（58–62% vs 98%）、请求数和 token 更多；耗时与现行相当（见文末「耗时更正」）。
改程序检查是看过第一遍结果之后做的（见 CORRECTION-3.md），所以三种口径都列出，不只列有利的。

## 引用可核对性（triage_rules §6 / F1）

| 臂 | 引用能在案卷里解析的比例 |
|---|---|
| 现行 | 98% |
| 新·v1 / 仅模型 / 模型+v2 | 58–62% / 47–49% / 58–62% |

新方案的模型条目引用的是模型自己编的单位 id（`exp_`/`item_` 等内部定位符），不是案卷记录 id。
这是新方案目前**最大的实质缺点**：问题能说清，但「点过去看原始记录」做不到。不能在这一点上为新方案开脱。

现行臂的请求数里有大量连接重置/校验被拒后的重试。墙钟差异主要来自现行臂的整案重跑，不是方案本身快（见文末「耗时更正」）。
现行 pass2 的墙钟没有可靠数字，不比。

## 没拿到合格记录的轴（两臂都有，都按「没产出」处理，没有再加轮次）

- 现行：pass1 1 个（D01 context_memory），pass2 4 个（4 个 case 的 model_capability，连接重置或「应发生单位不能用未发生跳过」被自己校验拒收，4 轮用完）。
- 新方案：pass1 2 个、pass2 1 个，均是某批输出结构校验被拦，无重跑。
这些轴上的问题两臂都没算进去，所以两臂召回都被低估；不对称之处是现行丢得多一点。

## 抽查（我在不看来源臂的情况下手工判 71 条 = 35%）

- verdict 一致 60/71 = **.845**；gold 对应一致 66/71 = **.93**（空与 none 视为同义）。
- 11 条分歧：5 条是我判「无法判断」、模型判误报或真问题（需要核原始记录，我没做）；3 条工具 `customer_detail` 报错
  （我判真问题 CP-1，模型判误报）；2 条 D01「本轮已停止查询」（模型判真，我判误：这一轮确实因预算停止）；
  1 条提示词内两套冲突约束（我判真，模型判误）。
- 分歧分布在两臂：现行 5 条、新方案 6 条，没有单向偏倚；没有按我的标签重算全量指标，所以上表仍是模型归类的数字。
- 归类用的是和被测同一个模型（Gemini 3.8 flash）。它不是独立评审，只是一致性检查。

## 偏离与更正（跑的过程中发生的）

1. CORRECTION-1/2（派发方）：输出结构注入、不带 response_format、不设 max_tokens。旧记录都已归档为 INVALID。
2. **CORRECTION-3（我，看过第一遍结果之后）**：新方案第一版程序检查有 bug（在轴视图里找下游请求，把「看不到」当「没送达」；缺口出处检查口径不全），
   改成 v2 并三种口径同时报告。这是事后改判据，需要按此理解 v2 一栏。D01 那条「已停止查询」v2 仍判没达到，我没有为了好看去改规则。
3. `classify_blind.py` 初版会把已归类的 id 整批重发并覆盖旧标签，覆盖了 27 条：15 条从原始应答还原，12 条用重新归类的标签并标 `relabeled_after_overwrite`。
   重新归类后有 5/15 与原标签口径不同（约 1/3），说明**归类本身噪声大**，小于约 10 个百分点的差距不应解读。
4. 现行臂记账判据：连接重置后的重试曾被判成「记账不符」从而作废记录，改为按成功尝试计数，影响 3 个轴（有效 → 无效反转为有效）。
5. dump 回退只找 b 轮，现行臂实际重跑到 d，已对齐。
6. 现行臂并发竞争、deepseek 余额不足导致的旧记录已作废（INVALID-*），不计入。
7. 程序 v2 条目与 pass 无关，在两遍里各出现一次（14 条），对「新·模型+v2」口径的两遍都计了；两遍的程序部分因此是完全相同的，不增加稳定性证据。

## 能得出什么、不能得出什么

能：
- 「本应/实际」两阶段 + 程序逐字检查，召回不低于现行，误报不更高，并能抓到现行稳定漏掉的编排层问题。
- 新方案的价值有一半来自**程序检查**（模型+v2 比仅模型多 3 个 hard 命中、多 8 个清单外真问题），这一半可以脱离「本应/实际」框架单独搬到现行方案。

不能：
- 不能说「本应/实际」的模型部分本身更强：仅模型口径 hard 召回低于现行（.50/.59 vs .64/.50，互有胜负）。
- 不能说新方案证据更好：引用可核对性明显更差。
- 8 个 case、单一模型、两遍，一致性数字很粗。

## 耗时更正（2026-10-11）

前文「新方案墙钟快 3 倍」是错的。两臂并行方式相同：3 个 case 同时跑，case 内六轴串行、轴内批次串行。现行 4772s 里包含失败轴的整案重跑（b/c/d 轮）与连接重置退避。
按「每个 case 六个轴各自耗时之和」（不含重跑轮次）比：

| 臂 | 遍 | 中位 | 均值 | 最长 |
|---|---|---|---|---|
| 现行 | 1 / 2 | 626 / 733s | 596 / 691s | 1030 / 1032s |
| new3 | 1 / 2 | 687 / 548s | 679 / 547s | 912 / 742s |
| new4 | 1 / 2 | 576 / 509s | 582 / 553s | 820 / 818s |

结论：单个 case 的六轴耗时三者相当（新方案每批两次调用，但每次推理更少，抵消了）；新方案的实际优势是现行臂这次失败重跑多，不是方案本身更快。
