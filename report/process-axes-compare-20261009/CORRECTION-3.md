# 更正 3：新方案臂程序判定条目换成 v2（事后更正，派发方接管后）

**时间**：2026-10-10，pass1 两臂结果和盲测归类出来之后。**这是看过结果之后的更正**，所以三种口径都报，不只报更正后的。

## 为什么改

pass1 新方案臂误报里，程序条目占 11/24（46%），模型条目 7/31（23%）。逐条核对发现 v1 程序检查（new_arm.program_entries）本身有缺陷：

1. **工具返回送达**：只在「本轴本批的材料视图」（full_view(dossier, links_batch, …)）里找下一次模型请求。工具执行轴的视图一般不带下游模型请求，于是把「视图里看不到」判成「没送达」。8 条「工具返回没进下一次模型输入」全是这样来的。在完整案卷上重算：26 达到 / 2 无法核 / 0 没达到。
2. **交付缺口出处**：出处只查了一部分记录；而且 reconcile 会把程序条目自动转成问题，与它自己 prompt 里「程序条目只是线索」的说法矛盾。
3. 同一事实按轴、按批重复算。

## v2 怎么做（program_checks_v2.py）

- 每个 case 在**完整案卷**（new_arm.build_case 的 dossier）上算一次，引用的都是真实记录 id。
- 只保留能逐字判定的三项：工具返回与下一次请求里同 tool_call_id 的 tool 消息逐字一致；各次模型请求里「[本轮执行余量]」块是否全部相同；交付 gaps/limitations 每条能否在模型产出、工具返回或 tool 消息里逐字找到。
- v2 判「没达到」的条目放在 problems/pass<N>.json 的 `new_program_v2` 里，盲 id 为 `V2-<case>-<条目>`。它们不进原来的洗牌，所以已归类的 86 条 id 不变（已核对）。
- v2 只依赖案卷，与 pass 无关，两遍用的是同一份。

## 已知局限（写在看归类之前）

- **D01**：交付里那条「本轮已停止继续查询…」是包裹步骤因预算停止而加的。本轮确实因 BUDGET no_progress 停止（D01-2），所以这条说明属实，v2 仍判「没达到」，应视为程序误报。之所以不改规则，是因为再改就是对着结果调判据。
- **B01**：5 条缺口里有 2 条在模型产出里有出处；没有出处的 3 条中有一条是与 AP-3 同句的模板假缺口（gold 没收 B01 这一条）。
- **执行余量**：8 个 case 都判没达到，但 gold 只在任言琳 case 收了 REN-3，其他 case 是否算清单外真问题，交给盲测归类。
- **模型上下文**：两遍新方案臂第二次调用看到的仍是 v1 程序条目（new_arm 未改）。所以「只看模型条目」这个口径并不完全独立于 v1。

## 报告口径

score.py 对新方案臂同时报三种口径：`new`（v1 原样）、`new_model_only`（去掉程序条目）、`new_model_v2`（模型条目 + v2）。现行臂不变。
