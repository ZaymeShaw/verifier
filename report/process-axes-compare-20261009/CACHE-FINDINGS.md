# 提示词缓存与输入 token：实测记录（2026-10-10）

给以后做六轴/judge 成本优化的人看。结论先说，过程和数据在后面，脚本在 `cache-probes/`。

## 结论

1. **primary 中转上的 Gemini（`gemini-3.8-flash-*`）有前缀缓存，但只在「消息轮次对齐」时稳定命中**：
   - 作为**新一轮**追加：`[系统, user, assistant, 新 user]` 命中 **6/6**，约 91%（2.4 万 token 的前缀命中约 2.17 万）。
   - 把追加内容**拼进同一条 user 消息**：命中 1/6。
   - 完全相同的请求重发：命中约 96%（稳定）。
   - 同前缀、不同尾部：不稳定（连发 12 次，前 4 次都不中，之后 7 次命中）；紧挨着发的几次基本不中。
   - 开头（user 最前面）改几个字：不命中。
2. **所以任何「第二次调用接在第一次后面」「纠错重试」，都应该做成新一轮消息（带上上一轮 assistant 输出），不要拼进同一条 user。** 现在仓库里的纠错轮、本实验里的引文重写，都是拼进同一条 user，几乎享受不到缓存（本实验 31 次重写只有 4 次命中；现行臂纠错轮 8/188）。
3. 显式缓存不可用：`/v1beta/cachedContents` 返回 404。原生接口 `/v1beta/models/...:generateContent` 能用，缓存行为与 OpenAI 兼容接口一致。
4. `fallback1`（`qwen3.8-flash`）是真前缀缓存：同前缀不同尾部直接命中 100%（5 万 token 里命中 50176）。换模型不是无损，只作情报。`fallback2`（deepseek-flash）当时 402 余额不足，没测。
5. 新方案（`new_arm_quotes.py`）输入多出来的主要来源是**同一批材料发了两遍**：第一次 1.26M、第二次 2.48M、重写 0.51M（8 个 case 一遍，共 4.24M）；系统提示词只有 2–4.5k 字符，不占。
6. 第二次材料里与第一次相同的比例约 34%（context_memory 11%、planning 58%、tool_execution 23%、knowledge 74%、model_capability 72%）。若做成「第二次 = 第一次全文 + assistant(冻结的本应清单) + 只含新增字段的 user2」，第二次按全价计的输入从约 2.48M 降到约 1.75M，另有约 1.15M 走缓存；重写改成新一轮后也基本走缓存。**估算折合约省 20%，未实现、未验证。**

## 实跑结果（new4，2026-10-11）

把第二次调用改成多轮追加后，8 个 case 两遍的实测：

- **命中门槛约 16k token**：第一次调用（前缀）≥ 约 16,400 token 的批次，第二次 11/11 命中，命中量正好等于整个前缀；≤ 约 15,600 token 的 0/24 命中。门槛是从数据观察出来的，不是文档。
- 引文重写（第三轮）只有在前两轮本身被缓存时才命中。
- 全价输入：new3 4.06M / 4.10M → new4 3.19M / 3.28M（约 −21%）；缓存 0.94M / 0.95M。问题清单质量在噪声内不变（见 RESULT.md）。
- 没命中的批次也不吃亏：第二次只发新增字段，重发的第一次部分加上新增部分，总量和 new3 的完整材料差不多。

## 更正（我自己）

调查过程中我先后下过两个错误结论，保留在这里避免后人重复：

- 「这个中转上做不了前缀缓存，只有完全相同的请求才命中」——错。我最初测的是「同前缀换尾部」和「拼进同一条 user」，恰好是最不容易命中的两种形态；测多轮追加后命中 6/6。
- 「message 里有 40–70% 的重复」——错。我测的是展开（`cmp_view.normalize`）之后的视图；实际发给模型的文本已经被 `shared_contents` 去过重，长字符串重复只有 0–1%。残留的是「被包含的转义副本」（`raw_attributes` 里有其他字段内容的 JSON 转义副本），占 context_memory 材料的 6–22%、其他轴更少。

## 数据

### 生产与实验里的缓存命中（551 次成功请求）

| 臂/阶段 | 请求 | 输入 token | 命中 | 命中率 |
|---|---|---|---|---|
| new3 第一次（本应清单） | 166 | 3.13M | 225k | 7.2% |
| new3 第二次（实际清单） | 166 | 6.18M | 0 | 0% |
| new3 引文重写 | 31 | 1.54M | 196k | 12.7%（命中时 92–95%） |
| 现行（含纠错轮） | 188 | 7.31M | 406k | 5.6% |

没有命中的请求，usage 里没有 `prompt_tokens_details` 字段；命中时 `cached_tokens` 通常是输入的 92–98%，缺的是末尾约 2000 token。

### 探针（脚本在 `cache-probes/`）

| 编号 | 做法 | 结果 |
|---|---|---|
| probe1 | system 相同、user 短且不同（约 1.7k token） | 0%（低于缓存下限，未深究） |
| probe1/2 | system+5.7 万 token 材料，换尾部 / 换开头 / 完全相同 | 尾部不同、开头不同都是 0%；完全相同 96% |
| probe3 | 端点；qwen3.8-flash | `/v1/models`、`/v1beta/models` 200；`/v1beta/cachedContents` 404；qwen 同前缀不同尾部 100% |
| probe4 | 原生 Gemini 接口 | 冷启动 0%、完全相同 96%、尾部不同 0% / 0% |
| probe5 | 同前缀 12 个不同尾部；多轮追加 6 次 | 前者 7/12 命中；后者 6/6 命中（约 91%） |
| probe6 | 同一 user 末尾拼接 vs 新一轮追加，各 6 次 | 拼接 1/6，新一轮 6/6 |

### 材料构成（`audit_*.py`）

- 每个轴的材料里，`exact_request`（被测系统的模型请求）占最大头：36k–98k 字符；`raw_attributes` 在 context_memory 里 47k–74k 字符。
- 第二次调用的字段里，与第一次相同的占 34%：见上面第 6 条。

## 没做 / 可做

1. **最小改动**：引文重写与现行臂纠错轮，从「拼进同一条 user」改为「新一轮 assistant + user」。
2. **多轮版**（`new4`）：已实现并跑两遍，见上「实跑结果」。
3. 去掉「被包含的转义副本」：约 3–6% 总输入，需逐项验证不丢信息。
4. 缓存是否有过期时间、中转怎么对缓存计费：**未测**。
5. 以上都只测了 `gemini-3.8-flash-medium` 一个模型、一个中转；换线路要重测。
