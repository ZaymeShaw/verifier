## A0. demand/process_axes.md 新增：每个轴在评什么（从 spec/alg §2.1 上移）——**已应用（2026-10-11）**

理由：「部件的输入 → 输出」定义的是每个轴评什么，与用哪种判法（子能力 × 行使、本应清单）无关；放在需求里，方案怎么换都有不变的锚点。spec/alg §2.1 改为引用需求，只保留"怎么用它"。

建议位置：§1「我们要什么」之后，新增 §1.1。拟写：

> ### 1.1 每个轴在评什么
>
> 每个轴对应被测系统里的一类部件，部件有固定的"输入 → 输出"。一个轴评的是：这类部件每一次被用到时，**在它实际拿到的输入下本应产出什么，实际产出了什么**。
>
> | 轴 | 部件 | 输入 → 输出 |
> |---|---|---|
> | 意图理解 | 表达 | 用户原文、被指代的历史 → 系统内部表达 |
> | 规划路由 | 编排 | 任务、当时状态、规则 → 路径、调用序列、重试、收尾 |
> | 工具执行 | 执行 | 已发出的调用参数 → 返回 |
> | 知识数据 | 数据源 | 已正确执行的查询 → 数据是否存在、是否匹配 |
> | 模型能力 | 模型 | 一次调用的实际输入 → 该次输出 |
> | 上下文管理 | 传递 | 一处产出 → 下一处输入（含组装、缓存、历史、交付） |
>
> - **子能力** = 输出里必须保住或产出的每一个方面，由上表推出，不手列（逐轴推导见 spec/alg §8）。
> - 输入本身已经坏了，说明的是上游，不是这个部件。
> - 一个运行事件可以同时属于多个轴（模型一次调用的输出既是模型轴的对象，其中的工具参数又是意图轴的对象）；属于哪个轴，看它查的是哪一段输入 → 输出。

不放进需求的：两次调用、本应清单、引文、schema 这些"怎么判"——留在 spec/alg。

## B. spec/alg/process-axes.md

1. **§2 判定单位**：§2.1「子能力从哪来」的表与规则上移到需求 §1.1，这里改为引用；「子能力 × 一次行使」→「本应清单里的一条」。两次调用的分界就是 §1.1 的输入 → 输出：第一次只给输入端、第二次再给输出端。子能力保留为第一次调用的写作提纲，不再作为展开规则。
2. **§3.2 取值与 §5 汇总**
   - 单条取值：做到 → 达到；没做到 → 没达到；缺证、需独立查证 → 无法核（`needs_external=是` 由程序锁成无法核）。
   - 「输入无效 / 缺判准 / 未发生」不再是单条取值：输入无效 = 没达到 + 归因「上游」；缺判准 = 不进清单（写不全的放 `not_covered`）；未发生 = 不进清单。
   - 轴 verdict：任一「没达到」且归因本轴 → problematic；否则有「无法核」→ not_evaluable；否则有「达到」→ sound；否则有归因上游的「没达到」→ untested；否则 not_applicable。
3. **§3.4 判准从哪来**：三种判准（通用义务 / 需求 / 设计规则原文）改为：每条本应自带 `basis`（输入里的原文片段或记录 id）；另有**通用职责**（固定文字，带入第一次调用，由模型写成本 case 的具体条目，`basis` 写「通用职责」）。设计规则按轴能用的范围表保留。
4. **§4 问题记录与输出结构**（实验里的实际 schema）
   - 第一次：`{expected: [{id, about, subcapability, statement, basis, needs_external}], not_covered: [string]}`
   - 第二次：`{actual: [{id, links, observed, quotes: [{ref, quote}], verdict}], unexpected: [{id, observed, links, quotes, why}], problems: [{phenomenon, items, attribution, impact}], reason, scope_note}`
   - 引文规则：verdict=没达到 的行和每个 unexpected 至少 1 段逐字短引文（一般 40 字以内）；要靠两处对比才看得出的，两处都引；「达到」行引文可选。程序核对引文确实在该记录里，不在则退回重写一次，仍不在则把该行降成「无法核」。
   - `problems.items` 只能引用没达到的条目或 unexpected；程序据引文所在记录补 `refs`。
5. **新增「调用方式」一节**（在 §13 改造任务里，或单列）
   - 第二次调用 = `[system, user1, assistant(冻结的本应清单), user2]`，user2 只放第一次没给的字段与新引用的内容；引文重写同样作为新一轮追加。
   - 两次 system 逐字相同，输出结构约束放到各自 user 末尾。
   - 第一次与第二次材料从同一份完整视图切出，编号一致；必须满足「user1 ∪ user2 = 完整视图」「user1 不含输出端字段」两条核对。
   - 理由：这条中转的 Gemini 前缀缓存只认"新一轮追加"，且前缀约 ≥16k token 才命中（CACHE-FINDINGS.md）。
6. **§13 改造任务 / §14 验收**：新增观察项「引文第一次核对通过率」「降级为无法核的条数」「缓存命中」「全价输入」。

- 需求 §2 四个使用角度、§6「不要什么」、归因三种写法、问题记录作为聚类成员的定位、reason / scope_note。

## D. 风险与没验证的

- 「输入无效必须指向上游问题」被放松（A 第 2 行 ⚠）。
- 通用职责只有两条，是看过 gold 后写的；在 4 个没见过的 case 上 5/5，但只有一遍、没有 gold。
- **引文只证明存在，不证明支撑**：B01 里"开场问题被丢掉"重写后的两段引文都是真的，但都没直接证明结论；「达到」行常只引一小段（画像那条只引了"33岁"）。
- 同一问题会在不同批里重复提出，汇总要去重；实验里按「缺口原文 / 余量提示 / 工具返回」归并，是针对这几类的写法，正式实现要换成通用去重。
- 引用能点开的比例约 85%，现行 98%。
- 少数问题现行抓到、新方案没提（如 D05 保费标错、C01 全字段倾倒）。
- 成本：全价输入约为现行的 1.1–1.2 倍，输出+推理少 31–45%，请求约 2 倍；单个 case 六轴串行耗时与现行相当（之前"墙钟快 3 倍"是把现行的重跑算进去了，已更正）。缓存 token 的计费折扣未知。
- 证据规模：8 个 case 两遍 + 4 个未见 case 一遍，单一模型，归类也用同一模型；召回/误报的差距有一部分在噪声里。

## E. 若你点头，实现的顺序（每步都先跑得通再往上加）

1. 第二次调用的输出结构加 `quotes` + 引文核对与一次重写（复用现有 enforce_output 与记录读取）。
2. 纠错 / 重写改成新一轮追加（这一条对现行六轴也适用，可以单独先做）。
3. 第一次调用带入通用职责。
4. 把现有六轴「子能力 × 行使」展开替换为本应清单（最大的一步）。
5. 第二次调用改成多轮追加 + 只发新增字段（带两条切分核对）。
6. 轴 verdict 汇总按 B-2。
7. 去重。
