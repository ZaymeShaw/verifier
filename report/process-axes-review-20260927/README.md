## 重点发现

### 1. 错产品条款：事实已经可见，工具轴仍同类不同判

**确定的漏判。** B02、E02 工具轴均 sound，理由分别声称“所有返回对象与请求完全对应”“无对象错位”。同表知识轴已明确列出这些返回属于其他产品。E01 工具轴对相同类型的返回正确判了对象不符。

- B02：`扩展轴明细!G431:G432` 明确初次召回无关险种；`E442:G446` 却全部 pass，强调 JSON 完整、可读、未报错。
- E02：`G730:G731` 列出五条都是其他产品；`E741:G745` 全部 pass，形态完整项断言对象与请求一致。
- E01：`E709:G709` 正确判错产品返回 fail。

已独立核对 SQLite 原文：B02 运行 `4a304387-c385-408f-ab0b-e5e3d9053e28` 的 product_knowledge 请求安佑福等待期，正文为 e生保等其他产品，hint 仍写目标产品相关知识。E02 第三轮运行 `b7c4bb4a-fa18-4668-99fb-abd7f833c3e9` 请求鑫瑞优享免责，五条标题分别属于福满分、盛世金越、失能险、e生保、盛世金越至尊版，没有目标产品。gaps 的“不能保证属于该产品”不能支撑“对象完全一致”结论。

### 2. 模型输出到交付：E02 确定漏判，主 judge 进一步把覆写解释成正常化

**确定的漏判。** `扩展轴明细!E718:G718` 将 E02 的“模型输出到最终交付”判 pass，第三轮理由是最终答复两端一致。这实际只核对了落库/交付，没有正确核对模型原文到 bridge 的变化。

同一 SQLite 运行中，模型 messages/4 的 answer_draft 明确说明：目标产品免责正文未取得，返回均为其他产品，不能套用，建议查合同原文或官方条款。agent_bridge 却把 answer_draft 改成“暂时无法确认相关信息，请补充更完整的信息后再试，或转人工渠道办理。”，gaps 变为泛化来源不足，needs_user_input 从 true 变成 false。最终输出确实丢掉了具体产品、知识缺口和不能套用的理由。

主 judge（`用例池候选区!I26:J26`）不但未纠正，还写“交付层最终规范化输出，未对用户产生负面影响”“交付端到端一致”。它的整体 not_fulfilled 是对的，但过程解释并不准确，不能算完整命中。

### 3. E01 已能发现桥接改写，但理由与最终状态没有形成可复核闭环

`扩展轴明细!G684,G686` 已具体指出 ask_clarify 的 NEEDS_CLARIFICATION/hint 在 bridge 中丢失、clarify 清空、needs_user_input 改 false、答复被替换。SQLite 运行 `dd6fd881-5d04-4c6c-a690-bdf0082d15bd` 证实这些变化。相比旧版只盯输入相关性，这是实质进展。

但这两项状态均为 insufficient_evidence，整个上下文轴为 not_evaluable；同时主 judge（`I25:J25`）又把上下文缺陷当作已确证事实。表中没导出对应 missing_evidence、读取回执和程序修复原因，无法判断是材料未读、引用不合规导致降级，还是模型本身判断矛盾。不能仅凭理由文字把该轴统计成已准确命中。

另须避免套旧裁定：本次 E01 模型实际调用了 ask_clarify；旧运行则是正确的最终答复草稿被换掉。两次都存在桥接改写，但不能说模型行为完全相同。

### 4. D01 工具轴虽然 problematic，尚不能证明旧解析盲区已修好

`扩展轴明细!E580:G584` 的 fail 主要来自第 5 次 customer_search 的 BUDGET 错误；此前 AMBIGUOUS 的拒绝依据仍为 insufficient_evidence（第 581 行）。这比无依据判 sound 更诚实，但没有自动确认旧裁定中的前缀匹配适配层问题。

SQLite 运行 `9e682125-e7de-4d90-b697-1841d5f6e997` 证实：前三次带姓氏请求未执行，第 4 次删去姓氏后实际返回 416 条客户，第 5 次才 BUDGET。工具轴“返回形态完整”只列出 tools/0、1、2、4、5，遗漏 tools/3，却仍给全项 pass；规划轴第 578 行称放宽条件、反复改参合理，但缺少对“不得删掉限制扩大查询范围”规则的充分核对。因此不能把这条整体 nf 当成已修复原问题。

### 5. 缺证边界与耗时口径仍不一致

- 上下文轴：E02 第 719–724 行因没有 exact_model_request 全部不可评；unknown-policy 第 199–200 行面对相同类型缺口却限定在重建消息范围给 pass。范围限定可以成立，但全批次缺少一致执行口径。
- 工具耗时：B01 第 413 行因缺单工具阈值判缺证；B02 第 445 行、E02 第 744 行却拿整轮硬上限当单工具依据；D01 第 583 行凭“三秒以内”判正常。后两种做法不符合当前“不可自行定阈值，不用整轮时限替代单调用时限”的标准。

### 6. 导出还不够支撑人工提升与定位

`扩展轴明细!H2:H958` 的引用列全部为空。理由中虽有文字编号，但缺少可机器核对的 evidence_refs、missing_evidence 和修复记录。

当前实现可解释该信息损失的一部分：`process_common.py` 的 AxisSummary.items 只保留 key/value/reason；`table_view.py` 从 summary.items 构造展示行，未把 checks 的引用和缺口带进去。这解释了为什么表里会出现“理由已认定缺陷、状态却缺证”，但看不到降级原因。未取得此次运行完整 eval_axes 输出，不能把某一格的降级原因直接归咎到具体代码分支。

### 7. 主 judge 的 blocking 标准仍有漂移迹象

两个负例最终 answer 完全相同，均为泛化的“未找到符合本次查询条件的保单记录，可调整或补充条件后再查。”，且 gaps 为空。

- wrong-empno（`用例池候选区!I7:J7`）：具体保单对象与缺口说明丢失被当 blocking，因此 not_fulfilled。
- unknown-policy（`I8:J8`）：同类丢失被当 non-blocking，最终 fulfilled。

两例测试目的并不完全相同，不能只凭文案相同断言总裁决必须一样；但当前解释的差异主要落在同一“空态对象/缺口丢失”要求被赋予不同阻断等级，未清楚说明业务依据。应固定这类负例的验收标准，再比较结果。

## 建议优先级

1. 优先修证据闭环：逐项导出引用、缺口及降级原因；交付检查必须拿模型输出、bridge、实收答复三处具体正文，不能只比较落库与实收。
2. 固定跨案例判准：错产品对象、正常拒绝、单工具耗时、负例 blocking 先做事件级裁定；不要靠“整体 problematic”掩盖检查项漏判或归错。
3. 在同一冻结 Trace、同一模型策略上验收上述七类；单列传输失败、材料缺失和语义误判。先让 B02/E02、E01/E02 的同类判断一致，再扩大批量。

本次没有计算准确率：全32条×六轴尚无完整独立真值，且新旧运行事实不同。上述结论以工作簿内全量状态统计、重点检查项原文，以及指定 SQLite run 的独立核对为依据。
