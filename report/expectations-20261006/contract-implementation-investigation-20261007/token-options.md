# 系统契约处理方案的 token 预算对比

日期：2026-10-07。模型口径：当前冻结运行记录中的 qwen3.8-flash。估算脚本：[estimate_tokens.py](estimate_tokens.py)，机器结果：[token-estimates.json](token-estimates.json)。无需外部调用即可复算。

## 口径

对同一条冻结业务 trace 的当前评测工作量比较，不通过少检查用户目标或少交付证据降低预算。使用已保存的 requirements/analysis/projection，离线调用实际批次编排；stub 客户端只记录请求然后明确拒绝，不生成被接受的评测结果。实际展开 13 批、86 个义务单位、39 个轴内位置、245 项判准检查；位置包含真实事件及用户期望展开的候选位置，不等于业务模型调用次数。本案实际业务模型调用为 2 次。

范围包含：当前 4 次案卷分析、用户期望/必要行动准备、系统契约处理、六轴判定。**不包含业务系统运行、重试/路由失败、最终主 Judge 和独立 verifier-ready 全文审阅**。13 批是用保存的旧投影得到的共同预算基准，候选语义重构后批次数、检查项数、上游问题长度仍可能变化。这些是条件预算，不是完整 live 报价或统计置信区间。

输入为发送的逻辑 token，包括缓存命中的部分；输出包含思考 token。缓存命中不从输入总量中扣除，不与实际付费账单等同。思考 token 不再额外加到 output_tokens 上。

## 已测量的锚点

原运行保存了 14 次有 usage 的响应，合计输入 **507,834**、输出 **131,426**，输出中 reasoning **88,779**。该运行失败，六轴并未完成全部批次；没有 usage 的失败请求不能估作免费，也不能把这些数字叫作完整成功运行成本。

| 部分 | 已保存调用 | 输入 token | 输出 token（含思考） | 其中思考 |
|---|---:|---:|---:|---:|
| 全局需求/规则提取 | 1 | 7,823 | 36,868 | 16,965 |
| 规则映射与数据需要 | 1 | 25,809 | 27,304 | 21,580 |
| 案卷整理/工具会话 | 4 | 230,849 | 27,205 | 22,559 |
| 已发生的六轴请求，含不合格重试 | 8 | 243,353 | 40,049 | 27,675 |

案卷整理的历史随着工具返回累积，重复输入已经计入 230,849，不是把最终上下文只计一次。这个共同开销相当大，系统契约改法即使省掉部分提取工作，也不会自动消除它。

## 五个可比较方案

单位为 **万 token / 本样本一次无重试评测预算**；调用数包括共同案卷整理及准备步骤。输出总量已包含右侧两项；不要再相加。

| 方案 | 执行方式 | 调用次数 | 输入 | 输出合计 | 可见输出 | 思考输出 |
|---|---|---:|---:|---:|---:|---:|
| A 当前方式 | 全局提取用户及系统期望 → 映射 → 13 批判断 | 19 | 62–72 | 13–17 | 4.1–4.7 | 8.7–12.6 |
| B 每位置分别两次 | 39 个轴内位置各自登记规则、各自判断 | 84 | 153–193 | 19–48 | 3.4–10.1 | 16.1–37.9 |
| C 每批分别两次 | 13 批各自登记规则，然后各自判断 | 32 | 64–78 | 10–22 | 2.8–7.5 | 7.0–14.5 |
| D 按可共享规则组登记 | 假设 2–6 个作用域明确的规则组登记，再作 13 批判断 | 21–25 | 60–73 | 7.5–16.6 | 2.2–4.9 | 5.3–11.7 |
| E 直接批量核对原文 | 用户期望独立，13 批各自在一次调用内读原文并判断 | 19 | 58–68 | 7.5–13.5 | 2.5–4.3 | 5.0–9.3 |

### A：保留当前全局提取

优点：当前有明确的挂接清单和逐项覆盖校验，改动最少。问题：163 条系统期望的生成及映射已有较大思考/输出开销，且声明版本适用性并未因此解决。表中使用两次准备调用的实测 usage，加上实际展开的全部批次估算；不是原失败运行的花费复写。

### B：每位置独立登记与判断

优点：局部输入、输出边界直接，问题容易定位。问题：反复发通用提示、原文和结构；每次还有思考开销。39 个位置包括未发生行动候选，机械地每个位置都做两次尤其浪费。预算用保留现有取证选择的未优化拆分，未声称这是精细裁剪后的理论最低值。作为独立诊断可以用，不建议作为常态执行方式。

### C：每批登记再判断

优点：隔离被判产出、按批冻结原文判准，实现比跨作用域复用简单。问题：同一规则跨批反复登记；调用变多，成本区间与当前重叠且可能更高。适合作为可测的质量基准，尚无成本优势证据。

### D：按可共享规则组登记再批量判断

优点：保留先定规则再判断的边界，同时减少重复登记。问题：需要证明组件、版本、条件、来源范围相同；两次请求文本相似不等于可以共享。**2–6 组是预算假设，尚未建立并验证安全分组算法**，不能当已测事实。请求中动态规则越多，可共享性越弱，可能退化为 C。冷启动预算见表；跨 case 复用只有在来源身份、版本和语义条件都验证相同后才能另算摊销。

### E：直接批量读原文并判断

优点：流程短，避免中间规则清单生成和再次交付，预算下沿较低。问题：模型同次看到规则与产出，可能选择性摘规则；登记了引用不证明全规则覆盖。不能只靠“prompt 要求读全”声称它和 D 等效，需要与 D 用同一人工核对表比较漏检、误判和责任归属。表中仍给每条检查的规则定位/作用域输出留预算，不假设只输出一个轴级结论。

## 估算方法与敏感性

- 输入校准：8 次真实六轴请求的 input_tokens / prompt_size 约为 0.396–0.410。候选结构改变后取更宽的 **0.36–0.46 token/字符**；不是使用“中文一字一个 token”，也不是官方 tokenizer 精确计数。
- A 使用实际编排 prompt，加当前 structured-output 约束。其他方案从相同材料中移除重述的 commitment 期望，保留原文；新登记表与准备调用另计。B 逐位置用真实 material_view 重组，保留现有 extra_refs，避免把未经验证的精准检索当免费能力。
- 输出不可在运行前精确计算：可见判断按原响应平均约 55.7 token/判准项，取上下浮动 20%；每次判断思考取 2,000–5,000 token。准备登记思考取 1,500–4,000/次，原文定位与作用域取 35–80/条。新用户准备两次共 2,500–7,000 输出 token。
- 为避免用“漏检查”虚构省钱，所有候选先保持 245 项检查及 163 条规则规模作为预算假设。B/C/D 的规则重复倍数分别假设 3–6 / 2–4 / 1–2；准备输入的原文重复倍数分别为 8–16 / 4–8 / 1–3。具体参数全部在脚本和 JSON 中，实际登记条目可能不同。
- 每多一次 4,000 思考 token 的调用，就多 0.4 万输出；每多一次输入 5 万 token 的重试，就至少再加对应输入和新输出。重试率无法靠当前失败例直接推成新方案分布，表中不暗设 10% 或 20%。
- D 与 A 的输入区间高度重叠：不能宣称共享规则一定省大量输入。当前较大的潜在节省来自缩短规则提取/映射的输出，以及降低思考重复；仍须实测。

## 独立完工门另计，不能忽略

五个方案都还需独立检查整个 verifier llmtrace。调用越多、材料越重复，门要读的原文也越多，所以门成本并非所有方案都相同的固定数。

预算方式：先实际生成方案 trace，统计审阅输入的去重前完整请求/可见响应及审阅协议，再按门的分片/工具会话实际累计计算。单次完整审阅的内容量通常与被审 trace 总输入加可见输出处于同一量级；pi 分块读取后的历史重复提交还会放大。模型内部未记录的思考不能当作可供审阅正文，也不能用裁掉已规定原文覆盖来降低成本。当前没有完整新门的真实审阅 usage，因此不虚报一个端到端门成本数字。

输出 token 的思考包含关系与输入缓存口径参考阿里云官方 [Chat API usage](https://docs.bailian.console.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions) 和 [Context Cache](https://www.alibabacloud.com/help/zh/model-studio/context-cache)。这里比较 token 量，未套用币种、地域或阶梯单价。

## 建议

以上 A–E 仅比较既有“案卷分析 + 用户准备 + 六轴分批”架构内部的变化，不是需求本身的必要成本。用户追问后，候选比较顺序修正：先增加下述整案审查基准，验证是否需要保留如此多的独立准备和分轴调用，再决定 D/E 的局部优化是否值得。当前估算不足以宣布胜出方案。

## 需求视角的架构基准（补充）

需求要求六轴能力结论与组成、独立问题及原文依据、必要行动遗漏、上游依赖、评测错误独立呈现。它没有要求六轴各跑一次模型、全部系统规则提前变成期望、每个用户目标逐轴展开、或为正常项重复写长解释。六轴可以是同一次整案审查的输出分类；问题可关联多项能力，仍保留各自判定单位与归属。

本样本完整 dossier 序列化 259,328 字符；当前 13 批轴请求连同系统/输出约束合计 982,141 字符，另外案卷整理已有 230,849 输入 token。两次真实业务模型请求加响应总计约 13,467 字符，但只审这部分会漏工具、规划和传递证据，因此不能拿它当整案材料量。现有完整 dossier 包含这些其他材料。

新增候选 F：程序整理并交付完整案卷及身份索引，一次整案语义审查输出各轴逐单位结论、问题和未决；仅对具体缺证/冲突做定向补查。复用已有确定性 links 与原文，不先调用模型再整理成六份语义视图。用户要求与系统原文独立标明；先不设置第二套全局系统期望或局部规则登记流水线。逐单位覆盖、来源定位、条件和上游问题校验仍由程序执行；语义漏检由原文人工核对与独立 gate 检验。

初始预算目标：完整 dossier 一次交付按经验系数约 9.3–11.9 万输入 token，加评测指令、schema 与少量补充预算，**首轮目标 10–15 万输入、1–3 万输出（含思考）**。输入有已测材料量作为依据，输出是待检验预算目标；多轮补查若重发完整历史，会突破该目标。未验证长上下文召回、输出覆盖、上下游问题一致性、模型上下文/输出限制、provider 可接受性和实际运行效果，不能当作已达到的成本或完整成功运行预测。独立完工门、最终主 Judge、业务调用与失败重试仍另计。

F 的关键对照是：同样证据、同样人工核对目标，是否能保住六轴组成和全部已知问题。如果漏检集中在局部，再依据失败证据决定如何分组或补一个审查阶段；不能仅因六个输出分类就预先安排六套完整上下文。若必须分块，应保持身份和跨块关系；字符去重只去完全相同的存储正文，不删除 provenance，不保证语义召回。
