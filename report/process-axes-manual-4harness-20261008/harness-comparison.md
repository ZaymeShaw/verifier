# 四套 Agent Harness 的过程对比：评测发现

> 批次：2026-10-08，4 套系统 × 120 题（174 个用户轮次）
> 原始数据：`package/llmtracing/eval_runs/comparison_20261008/results/new-run/`
> 读者：Claude Code、Pi、OpenCode、Insurance QA 四套 harness 的开发者。
> 只看 Insurance 的详细问题清单，请读同目录下的 `insurance-findings.md`。

## 1. 这次在比什么

四套系统用**同一个模型**（`deepseek-v4-flash-0731`，关闭 thinking）、**同一份保险业务题集**、**同一套业务后端**作答。所以结果的差异主要来自 harness 本身，也就是它怎么把工具结果交给模型、怎么管理上下文、怎么收尾和交付答案。

| 系统 | 类型 | 怎么接业务工具 |
|---|---|---|
| Claude Code（CLI 2.1.292） | 通用 coding agent | MCP，7 个业务工具，另有 20 个自带工具（Read、Bash、Agent 等） |
| Pi | 通用 coding agent | MCP，7 个业务工具，另有 bash/read/write/edit/mcp/mcpScript |
| OpenCode（1.18.35） | 通用 coding agent | MCP，只暴露 7 个业务工具 |
| Insurance QA | 业务专用 agent（Agno） | 自有工具层：7 个业务工具加 5 个专用工具（澄清、实体词典、无保单号查字段、两种清单卡片），带调用上限、结果投影、服务端渲染 |

MCP 工具从 Insurance 的同一个代码版本同步而来，7 个业务工具的说明和参数逐字一致。但有一点不同：**MCP 把工具的原始结果直接交给模型，Insurance 会先做一层精简投影**（第 5 节详述）。

## 2. 一页结论

| 系统 | 做得好的 | 主要问题 |
|---|---|---|
| **Claude Code** | 工具结果过大时转存成文件，模型能用 Read/Bash 读回来；规划和上下文几乎没出问题 | 条款查不到时用常识补结论；把两款名字相近的产品说成同一款；个别终答只有英文内部推理，没有给用户的答复 |
| **Pi** | 截断后也能用 bash 读回；遇到工具缺陷会主动写脚本探测原因 | 和 Claude 同样的内容错误；探测可能失控（一题 50 次模型调用）；调用过不存在的工具 |
| **OpenCode** | 结果没被截断时，表现和 Claude、Pi 相当 | **工具结果被截断后存到 /tmp，模型却没有读文件的工具**，导致同一工具反复调用、上下文缺失，个别题终答通篇是推理 |
| **Insurance QA** | 不乱编；识别出了另外三家都没识别的实体差异 | **交付环节会把模型的答案改写掉**（金额错、字段堆砌、内部思考被交付）；投影把条款正文整条丢掉；ask_clarify 被当作收尾工具用 |

三条共性结论：

1. **工具结果太大，是通用 agent 的头号风险。** 业务工具一次能返回 1.6 万到 18 万字。三家通用 agent 都触发了截断：Claude 82 次、Pi 105 次、OpenCode 312 次。截断后能不能读回来，直接决定了后面的表现。
2. **三家通用 agent 在内容上犯同样的错，Insurance 没犯。** 原因是 Insurance 的系统提示词里有明确的业务约束（"不编造"、"已购事实和产品规则分开"），通用 agent 没有。
3. **业务工具本身的缺陷会让四家一起失分。** 这些题不能用来区分 harness 的好坏（第 6 节）。
4. **效率与完整性是一对权衡。** Insurance 最快、最省（每题耗时中位数 39 秒，输入 token 是 Claude 的 1/4），但同样的上限和投影机制也造成了它丢内容；通用 agent 更慢更贵，但信息更全。用户最终拿到可用答案的题数：Claude 8、Pi 8、OpenCode 7、Insurance 3（11 道抽样题，第 3.1 节）。

如果 Insurance 模型写的 `answer_draft` 能原样交付，可用题数大约是 5–6 道。剩下的差距来自投影丢正文和误用澄清。

### 3.2 效率

全量 120 题统计。耗时为每题墙钟时间（多轮题为各轮之和）；token 为每题所有模型调用的合计。

| 指标 | Claude Code | Pi | OpenCode | Insurance |
|---|---:|---:|---:|---:|
| 每题耗时 中位数 | 45.2 s | 50.1 s | 54.4 s | **39.3 s** |
| 每题耗时 P90 / 最长 | 122.7 s / 502 s | 122.8 s / 473 s | 125.0 s / 275 s | **75.7 s / 116 s** |
| 120 题总耗时 | 2.1 h | 2.1 h | 2.1 h | **1.4 h** |
| 每题模型调用次数 | 6.3 | 6.9 | 7.6 | **5.1** |
| 每题工具调用次数 | 6.4 | 7.3 | 6.8 | **5.7** |
| 每题输入 token | 193k | 133k | 93k | **45k** |
| 每题输出 token | 2595 | 1955 | 1761 | **1596** |
| 输入 token 缓存命中 | 75% | 71% | 72% | 81% |
| 120 题输入 token 合计 | 23.2M | 15.9M | 11.2M | **5.4M** |

按题型看每题耗时中位数（秒）：

| 题型 | Claude Code | Pi | OpenCode | Insurance |
|---|---:|---:|---:|---:|
| A 串行取证 | 34.8 | 39.7 | 37.8 | 35.5 |
| B 客户事实 + 知识 | 51.9 | 48.4 | 69.8 | 42.8 |
| C 多对象并行 | 27.5 | 49.8 | 42.8 | 22.8 |
| D 条件与澄清 | 31.8 | 40.1 | 39.1 | 24.2 |
| E 多轮指代 | 68.2 | 68.9 | 73.0 | 49.9 |
| F 多轮纠错 | 69.7 | 68.1 | 73.9 | 62.4 |

读法：

- **Insurance 效率最高，尤其是长尾。** P90 只有通用 agent 的六成左右，最长一题不到 2 分钟；输入 token 是 Claude 的 1/4、OpenCode 的 1/2。原因是调用上限（不会无限重试）和结果投影（每次结果不超过 8000 字）。
- **但这和它的质量问题同源。** 同样的投影丢掉了条款正文，同样的上限在 A04 拦下了必要的调用。效率和完整性之间的这个权衡，目前偏向了"省"。
- **Claude Code 输入 token 最多**：它的系统提示词长、工具多（27 个），而且原始结果完整进入上下文。好处是截断后能读回、信息最全。
- **OpenCode 的耗时主要花在重复调用上**：B 类（知识题）中位数 69.8 秒，四家最慢，正是截断后反复检索那类题。
- **口径差异**：三个通用 agent 4 路并发运行，Insurance 单路逐题运行。共享后端在并发下可能更慢，通用 agent 的耗时可能因此略偏高；token 和调用次数不受影响。通用 agent 的耗时还包含 CLI 启动时间。

## 4. 各 harness 的具体发现

证据格式：`claude/A01 #4` 表示 Claude Code 在 A01 题的第 4 次模型调用，见该题目录下的 `llm_calls.jsonl`。

### 4.1 Claude Code

**做得好的**
- 工具结果超过上限时，转存到文件并告诉模型路径（`persisted-output`），模型能用 Read 或 Bash 加 python 解析回来。例如 `claude/A05`、`claude/E05` 的客户详情约 57–83KB，都完整读回，回访资料是四家里最全的。
- 多轮里改字段、保留子任务处理正确（F04）。

**问题**
- **用常识补条款结论**（B11）：条款没查到，却以"常见等待期 30–180 天"断言"等待期应已过"。题目检查点明确禁止这样做。
- **把名字相近的两款产品说成同一款**（B02）：用户问 1836 款，客户持有 1813 款，Claude 答"已购买"，并写"二者是同一款产品的不同叫法"，输入里没有任何依据。
- **终答没有面向用户的内容**（D01）：最后一条消息只有英文推理"Let me report this to the user transparently."，然后就结束了。
- **终答混入乱码**（A01）：开头出现 "voluptatem min. voluptatem min."。
- 把客户的"关注方向"说成"已有保障"（E05）。
- 暴露给模型的 20 个自带工具里，有些与业务无关，但模型在评测中调用过：Agent 2 次、ScheduleWakeup 1 次、TaskStop 1 次。

### 4.2 Pi

**做得好的**
- 工具结果截断（单行超过 50KB）后，会把全文存到临时文件，模型用 bash/grep/python 读回。例如 B02 里，它从截断的检索结果中找到了"险种代码 1813 vs 1836"的候选信息。
- 遇到工具缺陷会主动做实验定位。D01 里它用 mcpScript 批量测试，证明了"姓X"条件对所有姓氏都失败、只能取到第一页 100 条，这是四家里对工具缺陷定位最准的。

**问题**
- 和 Claude 同样的内容错误：B02 答"已购买"，B11 用"常规等待期 30–90 天"断言"可认定已过"。
- **探测没有上限**：D01 一题用了 50 次模型调用。harness 没有预算或无进展检测。
- 调用了不存在的工具 `insurance-tools_mcp`（A04）。
- A01 没查保单详情就收尾，反问用户要不要再查；终答夹带异语种碎片 "información"。
- C14 把"体检预约"交给了 general_qa，而工具说明指定的是 benefit_info。

### 4.3 OpenCode

**做得好的**
- 结果没被截断的题目表现正常，A01、D06、F04 第 2 轮都完全正确。
- E05 里换了措辞（"安有护 就医绿通"），是四家里**唯一**查到就医绿通申请规则的。

**问题（基本都源于同一个原因）**
- **截断后读不回来**：工具结果超限时，OpenCode 把全文存到 `/tmp/.../tool-output/...`，并提示模型"用 Grep 或 Read 查看"，但这次配置只暴露了 7 个业务工具，模型没有任何读文件的手段。全量 312 次、涉及 64 题。模型的原话是"由于我无法直接读取文件系统……"（`opencode/C03 #5`）。
- **于是反复调用同一工具**：A05 客户详情调了 4 次；B02 检索调了 8 次；C14 检索调了 11 次，每次都被截断。
- **终答通篇是推理**（C14）：没有面向用户的回答，还准备把"同类产品通用免责"拿来当这款产品的参考。
- 该查详情没查：F04 没调 policy_detail，就说"接口未提供累计已交保费"。
- 和另外两家同样的内容错误（B02、B11）。

**建议**：截断提示里引导模型去读文件，前提是模型确实有读文件的工具。两种修法任选其一：给模型开放只读工具；或者在工具层先把结果裁剪到上限以内，不依赖"事后读文件"。

### 4.4 Insurance QA

详细问题清单、代码位置和修改建议见同目录 `insurance-findings.md`。这里只列和其他 harness 对比时有意义的点。

**做得好的**
- B02 是唯一识别出 1836 ≠ 1813 并发起澄清的；B11 是唯一没断言等待期已过的；F17 是唯一没把工具的假"无结果"当成事实的。
- 有调用上限和无进展拦截（D01 第 4 次查询被 no_progress 拦下），不会像 Pi 那样失控。

**问题**
- **交付环节改写答案**：模型写了正确答案，交付给用户的却是服务端按 facts 重新渲染的内容。能解析出模型答案的 93 轮里，只有 8 轮的交付包含了它。典型情况有：金额渲染错（A01）、60–80 行原始字段堆砌并含个人敏感信息（A05、E05、F04）、内部思考被拼成答案（D01）、交付最后一行是"占位"（F04）。
- **模型不按规定格式输出**：105 条终答没有一条是纯 JSON，也没有一条声明了 `claims`，这正是触发服务端兜底渲染的原因。
- **投影丢掉知识正文**：单条正文里"必须保留的条件句"超过 1200 字时整条丢弃，70 次产品检索里有 32 次模型收到 0 条正文。
- **ask_clarify 被当成收尾工具**：74 次调用中，12 次参数为空或是"占位"，抽样里多数发生在已经拿到答案之后。
- 同一工具 4 次的上限拦下了必要的调用（A04，用户名下有 6 张保单）。

## 5. 同一套工具，模型实际看到的并不一样

这一节解释为什么相同的工具，四家的上下文表现差别这么大。

| | MCP（Claude Code / Pi / OpenCode） | Insurance |
|---|---|---|
| 工具说明、参数 | 与 Insurance 逐字一致 | — |
| 结果交给模型前 | 原样交付 | 经 `ModelView` 投影：只留关键字段，长正文按句摘录，总长不超过 8000 字 |
| policy_detail 返回字段数 | 75 | 29–30 |
| 一次 product_knowledge 的正文 | 1.6 万到 3.1 万字 | 约 1.2 千到 4.8 千字；32/70 次为 0 |
| `compact`、`fields` 参数 | 写在参数说明里，但**实际不起作用**（MCP 通道没有接投影） | 生效 |
| 调用上限 | 无 | 有 |

我们把参数完全相同的调用配成对来比（Claude 35 对、Pi 18 对、OpenCode 32 对）。三家 MCP 之间同参调用的结果逐字相同，说明差异全部来自 Insurance 的投影层，不是检索随机性。

这对各家的含义：

- **通用 agent 拿到的信息更全，但也更大。** 截断就是这么来的，OpenCode 的大部分问题也是这么来的。
- **Insurance 拿到的更精简，但会丢内容。**
- 这次对比**保留了这个差异**：投影属于 Insurance 自己的设计，按"各系统现有形态"来比较。如果以后要做"同一视图下只比编排能力"的对比，需要先在 MCP 通道接上投影并重跑。

## 6. 四家共同受影响的工具缺陷

这些问题在业务工具层（MCP 与 Insurance 同源），哪家都绕不过去：

| 缺陷 | 表现 | 受影响的题 |
|---|---|---|
| customer_search 不支持"姓X"条件 | 工具说明的示例就是"姓张的女性客户"，但所有含"姓X"的查询都返回 AMBIGUOUS；改写成"姓名以平开头"则返回假的"无结果"，而这位客户确实存在（E17 第 2 轮按尾号能查到） | D01、E17、F17 |
| product_knowledge 召回到别的产品 | 查"安佑福"，返回的是 e生保、意外险、守护百分百等产品的正文 | B02、B11、C03、C14 |
| benefit_info 召回依赖措辞 | "就医绿通怎么申请"返回无结果，"安有护 就医绿通"能查到 | E05 |
| 检索结果随措辞变化 | 同一产品，Claude 的查询没召回"投保年龄 0–52 周岁"，Pi 和 OpenCode 的查询召回了 | C03 |
| policy_search 后端偶发 UPSTREAM 错误 | 四家各 17–26 次 | 全量 |

在这些题上，各家的差别只体现在"如何应对"。例如 F17 里，三家通用 agent 把假的"无结果"转述成了"不存在姓平的客户"，Insurance 没有这么说。

## 7. 评测方法

**标准从哪来**：题集里每道题写了"预期协同"（应该调哪些工具、按什么顺序）和"检查点"（不能犯的错）。系统提示词和工具说明里写明的规则，也作为判断依据。某个 harness 没收到的规则，不拿来判它。例如通用 agent 终答里带英文过程叙述，因为它们没有收到格式要求，所以不算错。

**六个检查维度**：

| 维度 | 检查什么 | 例子 |
|---|---|---|
| 意图理解 | 用户的话有没有被正确转成内部要做的事 | 用户问 1836 款，被当成了 1813 款 |
| 规划路由 | 该调的工具调了没有，顺序、重试、收尾对不对 | 截断后反复调同一工具；已有答案还去澄清 |
| 工具执行 | 工具按请求正确执行并返回了吗 | "姓X"解析失败；后端报错 |
| 知识数据 | 正确执行的查询，数据源里有没有对应数据 | 字段在源数据中为空 |
| 模型能力 | 在模型实际收到的输入下，输出对不对 | 编造结论；不遵守收到的输出格式 |
| 上下文管理 | 信息在各环节之间传递有没有丢或变 | 结果被截断读不回；交付时答案被替换 |

**怎么归属问题**：只看"这一步在它实际拿到的输入下做得对不对"。上一步坏了导致下一步出错，记在上一步，不重复算到下一步头上。例如 OpenCode 的模型说"没有资料"，是因为它收到的结果被截断了，这记在上下文管理，不记在模型能力。

**表格符号**：✓ 已检查没问题；✗ 有问题；? 结果不对，但看不出是哪一环的问题；∅ 上游已经失败，这一环没机会执行。

**范围**：人工逐题判定 11 题 × 4 套（A01 A04 A05 B02 B11 C03 C14 D01 D06 E05 F04），E17、F17 只看工具；全量 480 条只做程序统计。题集做过实体替换（如"姓曹 / 9 月"换成"姓平 / 12 月"），题集中"数据前置"的张数对应原题，没有直接套用。

**复现脚本**：`scripts/digest.py` 生成每题的过程摘要；`scripts/scan.py` 做全量统计（`scan_signals.json`）；`scripts/pair_returns.py` 对比同参工具调用在 MCP 和 Insurance 两侧的返回。
