# Insurance QA 与三个通用 Agent 的过程对比：评测发现

> 批次：2026-10-08，4 套系统 × 120 题（174 个用户轮次）
> 原始数据：`package/llmtracing/eval_runs/comparison_20261008/results/new-run/`
> 本文给 Insurance QA 开发阅读。第 1–3 节是结论和问题清单，第 4 节说明评测方法，附录是逐题明细。
> 四套系统的对等对比见同目录 `harness-comparison.md`。

## 1. 一页结论

我们用同一个模型、同一份题集，跑了 Insurance QA 和三个通用 coding agent，并逐步检查了每套系统"查数、调工具、组织答案、交付给用户"的过程。

**整体水平：内部推理和效率是第一梯队，端到端交付垫底，现状不达可用标准。**

| | Claude Code | Pi | OpenCode | Insurance |
|---|---:|---:|---:|---:|
| 用户最终拿到可用答案（11 道抽样题） | 8 | 8 | 7 | **3** |
| 每题耗时中位数 / P90 | 45 s / 123 s | 50 s / 123 s | 54 s / 125 s | **39 s / 76 s** |
| 每题输入 token | 193k | 133k | 93k | **45k** |

- **内部推理是强项**：不编造、能识别实体差异、能遵守业务约束，这几点四家里最好（B02、B11、F17 是唯一做对的）。
- **效率领先**：耗时最短、长尾最短（最长一题 116 秒，其他三家 275–502 秒），token 用量是其他家的 1/4 到 1/2。这得益于调用上限和结果投影。
- **但用户拿到的结果最差**：11 题里只有 3 题的交付可用，其余要么答案被服务端改写（问题 1、2），要么知识正文被投影丢掉（问题 3），要么在已有答案时去澄清（问题 4）。
- **修复后的预期**：只修交付链路（问题 1、2），让模型的 `answer_draft` 原样交付，可用题数估计能到 5–6；再修投影丢正文（问题 3）和误用澄清（问题 4），才有可能追上通用 agent 的 7–8，同时保留效率优势。这是根据抽样题的逐条分析估算的，修完需要重跑验证。

下面是要点：

- **Insurance 做得好的**：不乱编、能识别实体差异。比如用户问的产品和客户实际持有的产品只差几个字，Insurance 是唯一识别出来并澄清的；条款查不到时，它也是唯一没有用常识去补结论的。
- **Insurance 最大的问题在交付环节**：模型写出了正确答案，但最终交给用户的内容常常被服务端改写成别的东西，比如金额错误、原始字段堆砌、内部思考过程，甚至"占位"两个字。能解析出模型答案的 93 个轮次里，只有 8 轮的交付内容包含了模型的答案。110 题被标记为 `completeness=partial`，主因在这里，而不是取数失败。
- **知识正文在交给模型之前常被整条丢掉**：工具检索到的条款正文，在投影（见第 2 节问题 3）这一步经常整条被省略。全量 70 次产品检索里，有 32 次模型收到的正文是 0 条，而同样的请求在其他三套系统里都能拿到正文。
- **工具层有几处缺陷**：这些缺陷会让四套系统一起失分，因为三个通用 agent 用的 MCP 工具就是从 Insurance 代码同步过去的（同一 commit `4cb7dba5`）。

## 2. 需要 Insurance 修的问题（按影响排序）

每条都给出现象、证据和影响。证据格式 `INS_A01` 指 `insurance-rerun/dual_datasetA_full/insurance/cases/INS_A01/` 目录；`#4` 指该题第 4 次模型调用，见目录下的 `llm_calls.jsonl`。

### 问题 1：交付内容被服务端改写，模型的答案丢失（最严重）

**现象**：模型生成的 `answer_draft` 没有被交给用户。用户收到的是服务端按 facts 重新渲染的内容，常见四种情况：

| 情况 | 例子 |
|---|---|
| 金额渲染错误 | `INS_A01`：模型答 P…415 累计已交保费 1320。交付变成"保单 P…415 · 保费:0.00"，因为交付层的 fact_refs 被换成了另外两条（取值 6300 和 0，推测是年缴保费，未核实）。 |
| 原始字段堆砌 | `INS_A05`、`INS_E05`、`INS_F04`：交付是 60–80 行"查询信息:xx"，包含密文、车牌、邮箱、身份证号明文。模型整理好的表格全部丢失。全量有 36 题出现这种堆砌，共 2124 行。 |
| 内部思考被当成答案 | `INS_D01`：模型没输出 JSON，服务端把每一步的独白（"让我思考是否需要澄清…"）拼成了答案。 |
| 内容替换或缺失 | `INS_A04`：交付首句是"详见上表"，但并没有表，还漏了一张保单。`INS_C14`、`INS_E05`：模型自己判定无关的知识库原文被放在答案最前面。`INS_F04` 第 2 轮：交付最后一行是"占位"，还附上了用户明确说"不看"的累计已交保费。 |

**连带问题**：这些渲染结果又会作为"助手历史"注入下一轮（见 `INS_E05` 第 2、3 轮请求里的历史块）。下一轮模型看到的是一堆字段，而不是上一轮的真实回答。`INS_E05` 第 3 轮，模型据此虚构了"用户已确认'是'"。

**影响**：用户看到错误或不可读的答案；还会泄露与问题无关的个人敏感字段。

### 问题 2：模型输出不符合 `AgentOutput` 格式要求，是问题 1 的触发点

**现象**：请求里配置了 `response_format=json_schema(AgentOutput)`，系统提示词也要求以 JSON 输出、`answer_draft` 为首字段、业务值写进 `claims`。但全量 105 条文本终答里：

- 0 条以 JSON 开头，都是"说明文字 + 代码块 JSON"；
- 0 条声明了 `claims`；
- 12 条连 `answer_draft` 都没有；
- 7 条混入了 `</think>` 和推理过程。

**判断**：服务端拿不到 `claims` 就走兜底渲染，于是出现问题 1。修的时候，建议两头都看：一头是模型侧为什么不遵守 schema（该模型在流式加工具调用时，`response_format` 可能没有被强制执行）；另一头是兜底策略。拿不到 `claims` 时，至少应该保留模型的 `answer_draft` 原文，而不是用 facts 重新拼一份答案。

### 问题 3：知识正文在投影时被整条丢弃

**背景**：工具结果交给模型之前，`app/tools/hooks.py` 的 `boundary_hook` 会调用 `ModelView`，生成一份"给模型看的精简视图"，原始结果不变。这一步分两段：

1. 业务字段投影（`model_output.project_business_tool_result`）：`compact=true` 时只保留主键、核心字段、`fields` 指定的字段和与问题相关的字段，并去掉 null 值。policy_detail 因此从 75 个字段变成 29–30 个。这一步符合预期。
2. 按长度裁剪（`output_shaper.preview_output`）：配置在 `harness_common_args.yaml`，单次结果上限 `max_chars=8000`，知识正文单条上限 `item_chars=1200`。超过 1200 字的正文由 `_sentences` 按句摘录。凡是含"不、未、无、否、除、仅、只、若、如果、须、必须、条件、限于、但"的句子，连同前后各一句都必须保留。**如果这些必须保留的句子加起来就超过 1200 字，整条正文直接丢弃**，只在 `omitted_items` 里计一笔。

**现象**：条款正文几乎句句带"不、无、须、除"，所以经常被整条丢弃。全量 70 次 product_knowledge 中，有 32 次模型收到的正文是 0 条，涉及 34 道题里的 24 道（B01 B02 B03 B04 B11 B19 B20 C02 C03 C04 C14 C16 C18 C20 D07 D15 D19 E01 E12 E14 F01 F03 F10 F16）。对照组：三个通用 agent 用完全相同的参数调用，拿到的是 1.6 万到 3.1 万字的完整正文；它们彼此之间同参调用的结果逐字相同，所以差异不是检索随机性造成的。

**例子**：`INS_C03`，"平安守护百分百（2026）两全保险"的检索结果里，facts 为空、`omitted_items: 1`。其他三套系统从同一次检索中拿到了"投保年龄 0–52 周岁"。模型据实回答"没有资料"，然后去澄清"产品名是否准确"。

**建议**：保护条件句的初衷是对的，但"超限就整条丢"这条退路太激进。可以改成超限时截取与问题最相关的几段，并标注"不完整"。

### 问题 4：ask_clarify 被用来收尾或占位

**现象**：系统提示词和工具说明都写着"已取得可回答的事实后不得调用 ask_clarify，应先作答并把未完成项写入 gaps"。但全量 74 次 ask_clarify 中：

- 10 次参数为空，2 次问题是"占位"；
- 抽样题里，多数是在已经拿到答案之后发起的。例如 `INS_F04` 第 1 轮三项金额都取到了，仍然问"请确认要查询哪张保单"；`INS_C14` 三个缺口都已确认，仍然问"希望我继续查哪一项"；`INS_C03`、`INS_B11`、`INS_E05` 也是如此。

**判断**：模型似乎把 ask_clarify 当成"结束本轮"的方式在用，可能和问题 2 有关（模型没有用 JSON 正常收尾）。建议结合问题 2 一起排查。

### 问题 5：同一工具的调用上限拦下了必要的调用

`INS_A04`：本轮工具总预算是 12 次，但 policy_detail 同一工具上限是 4 次。模型并行查 6 张保单详情，第 5、6 张被 BUDGET 拦掉，最终少确认了 2 张保单。改用 `run_policy_field_lookup` 补查也失败了（见问题 6）。建议重新评估这个上限：用户问"名下所有保单"时，6 张以上是常见情况。

### 问题 6：工具解析缺陷（三个通用 agent 也受影响）

这些工具代码与 MCP 同源，所以四套系统一起失分：

| 缺陷 | 证据 |
|---|---|
| `customer_search` 不支持"姓X"条件。工具说明的示例就是"姓张的女性客户"，但所有含"姓X"的查询都返回 AMBIGUOUS；"姓名以平开头"返回 EMPTY，而客户"平泽杰"确实存在。 | D01、E17、F17 四套系统全部失败；Pi 实测姓伍、姓邬、姓戴都一样（`pi/D01 #27`）。`INS_B11` 里"姓费名书洋的客户"也返回 AMBIGUOUS。 |
| `product_knowledge` 查某款产品，召回的是别的产品的正文。分不清是检索的问题，还是知识库里没有这款产品。 | B02、B11、C03、C14：查"安佑福"返回 e生保、意外险、守护百分百等产品的正文。 |
| `benefit_info` 的召回依赖措辞。查"就医绿通怎么申请"返回 EMPTY，查"安有护 就医绿通"就能召回完整规则。 | E05：OpenCode 用后一种措辞查到了内容，其余三家返回 EMPTY。 |
| `run_policy_field_lookup` 带上客户名和保单号仍然返回"客户定位尚未确认"或 AMBIGUOUS。 | `INS_A04 #3/#4`、`INS_E05 #6` |
| policy_search 后端偶发 UPSTREAM 错误。 | 全量 Insurance 26 次，其余三套 17–20 次。 |

### 问题 7：其他

- 调用了不存在的工具：`call_tool`、`task_confirm`、`function`、`carrier_Search` 各 1 次，另有 1 次调用 `benefit_info("test")`。
- 查询时删掉了用户给的条件：`INS_D01 #4` 把"姓平"去掉，只查"性别女、12 月生日"，违反工具规则"不得删条件扩大范围"。
- 该查的没查：`INS_A05` 中投保人姓名在搜索结果里是密文，而 policy_detail 能给出明文，模型没有去查，直接回答"未能确认"。

## 3. 四套系统横向对比

### 参与对比的系统

| 系统 | 说明 |
|---|---|
| Insurance | Insurance QA 服务（Agno 编排、自有工具层、投影、服务端渲染） |
| Claude Code | 通用 coding agent（CLI 2.1.292），通过 MCP 接入 insurance 工具 |
| Pi | 通用 coding agent，通过 MCP 接入 |
| OpenCode | 通用 coding agent（1.18.35），通过 MCP 接入 |

四套系统用同一个模型 `deepseek-v4-flash-0731`（关闭 thinking）。三个通用 agent 的 MCP 工具从 Insurance 同一个 commit 同步而来，7 个业务工具的说明和参数逐字一致。区别在于：

- Insurance 多 5 个工具：ask_clarify、entity_lookup、run_policy_field_lookup 和两个 present_*_card。
- Insurance 有调用上限：同一工具 4 次、知识检索合计 6 次、无进展拦截。
- **Insurance 对工具结果做投影，MCP 不做**：MCP 的 `itools/dispatch.py` 只接了核心函数，没有接 `ModelView`，所以通用 agent 拿到的是原始结果，`compact`/`fields` 参数在 MCP 侧不起作用。

几点说明：

- Insurance 模型能力轴的 10 题，大多是问题 2（没按 AgentOutput 格式输出）。三个通用 agent 没有收到这类格式要求，所以不存在这一项。它们的模型问题是内容层面的：用常识补条款、把两个产品说成同一款、调用不存在的工具。

- 三家通用 agent 共同犯的两个内容错误，Insurance 都避免了：

  - B11：条款没查到，三家都用"常见等待期 30–180 天"断言等待期已过。

## 4. 评测方法说明

### 评测标准从哪来

题集文件 `inputs/复杂协同与上下文问题集-120题(2).md` 里，每道题写了"预期协同"（应该调哪些工具、按什么顺序）和"检查点"（不能犯的错）。我们拿它判断"该做的做了没有"。系统提示词和工具说明里写明的规则，也作为判断依据。

### 六个检查维度

每道题都从下面六个角度分别检查，每个角度对应系统里的一类部件：

| 维度 | 检查什么 | 例子 |
|---|---|---|
| 意图理解 | 用户的话有没有被正确转成内部要做的事 | 用户问 1836 款，系统当成了 1813 款 |
| 规划路由 | 该调的工具调了没有，顺序、重试、收尾对不对 | 已经拿到答案还去澄清；该查详情没查 |
| 工具执行 | 工具按请求正确执行并返回了吗 | "姓X"条件解析失败；后端报错 |
| 知识数据 | 正确执行的查询，数据源里有没有对应数据 | 查到了保单，但所需字段为空 |
| 模型能力 | 在模型实际收到的输入下，输出对不对 | 编造输入里没有的结论；不遵守输出格式 |
| 上下文管理 | 信息在各环节之间传递有没有丢或变 | 正文在投影时被丢弃；交付时答案被替换 |

### 怎么归属问题

只看"这一步在它实际拿到的输入下做得对不对"。如果上一步已经坏了，下一步跟着出错，就算上一步的问题，不重复算到下一步头上。

例子：`INS_C03` 中模型回答"没有资料"。模型收到的输入里确实没有正文，所以模型这一步不算错，问题记在"上下文管理"（投影丢了正文）上。

### 表格符号

| 符号 | 含义 |
|---|---|
| ✓ | 已检查，没发现问题 |
| ✗ | 有问题 |
| ? | 判不了：能看到结果不对，但看不出是哪一环的问题 |
| ∅ | 没测到：上游已经失败，这一环没有机会执行 |

### 判定范围

- 人工逐题判定 11 题 × 4 套：A01 A04 A05 B02 B11 C03 C14 D01 D06 E05 F04。E17、F17 只判了工具轴。
- 全量 480 条只做程序统计（第 3 节）。
- 题集做过实体替换（例如原题"姓曹 / 9 月"换成了"姓平 / 12 月"），题集中"数据前置"给出的张数对应原题，判定时没有直接套用。
- 三个通用 agent 的终答里常带英文过程叙述，它们没有收到格式要求，所以这一点不算错。

### 复现脚本

`scripts/digest.py` 生成每题的过程摘要，`scripts/scan.py` 做全量统计（结果在 `scan_signals.json`），`scripts/pair_returns.py` 对比同参数工具调用在 MCP 和 Insurance 两侧的返回。

### A01 列出客户每张保单的累计已交保费（不合计）
