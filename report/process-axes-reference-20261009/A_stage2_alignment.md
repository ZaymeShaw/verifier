**M5 的三处**（读原文，系统提示词对照）：
1. 系统提示词要求「输出 JSON：answer_draft 必须是首字段、结论先行」；实际输出是一段带粗体的文字、一个列表，**之后**才是 JSON 对象——整段回复不是 JSON，首字段也不是 answer_draft。
2. 业务回答契约要求给出 `claims:[{subject_id,field,fact_id}]`；实际输出没有 `claims` 字段，只有 `fact_refs`。
3. 系统提示词要求「不要在 answer_draft/gaps 自行填写……客户或被保人姓名、状态」；实际 answer_draft 直接写了「任言琳」「交费有效」。

**问题 MP1**（归本轴）：第二次模型调用的输出违反系统提示词写明的输出契约（上述三点）。影响：间接，见 CP1。

### 上下文管理
| 条 | 结论 | 观察 |
|---|---|---|
| C1 | ✓ | 程序核：用户原话完整出现在调用 1 的输入里 |
| C2 | ✓ | 程序核：调用 2 输入里的 tool 消息与工具结果逐字一致（5012 字符） |
| C3 | ✗ | 交付的事实正确（投保人、被保人、状态都对）；但模型草稿 `gaps: []`，交付里却多了「部分内容未能在本轮证据中对应，请结合原始资料核实」，且 `completeness: partial`、`limitations` 同样一条。这条缺口既不是模型写的，也不在工具返回里 |
| C4 | ✗ | 程序核：调用 1 与调用 2 的「本轮执行余量」逐字相同（剩余 10 次模型调用、12 次工具调用、约 598 秒），调用 2 之前已用掉 1 次模型、1 次工具 |
| C5 | ✓ | 首轮没有历史注入 |

**问题 CP1**：交付给用户的答案正确，却附带一条与事实不符的「未能对应」缺口并标为 partial。因果推断（我没读 bridge 代码）：模型没给 `claims`（MP1），服务端无法逐条绑定，就补了一条通用缺口。若成立，这一条的**上游是 MP1**——bridge 对坏输入的反应本身不算它自己的失败，但「把缺 claims 变成对用户可见的 partial」值得单独看。归因：上游 model_capability（MP1），上下文轴不记本轴失败。影响：unknown。
**问题 CP2**：「本轮执行余量」不随用量更新（调用 1、2 读数相同）。归本轴（输入组装）。影响：本案无后果。

### 本 case 结论
- 找到 3 条问题：MP1（模型输出契约，实）、CP1（假缺口，依赖 MP1，因果待核）、CP2（余量提示静态）。
- 其余全部达到或无法核。无法核的集中在知识数据（外部真值）与耗时（无时限）。

## Case 2：D01 同姓客户澄清

实际产出概览：gate=AGENT → 模型调用 1 发出 `customer_search("姓平、12月份生日、女性的客户")` → 返回 AMBIGUOUS → 调用 2 换成「姓名姓平开头的女性客户且生日在12月」→ AMBIGUOUS → 调用 3 换成「平姓女性客户，生日12月」→ AMBIGUOUS → 调用 4 换成「筛选客户：性别为女，生日月份为12月，姓平」→ **未执行**（BUDGET / no_progress / finish_with_evidence，0.005 秒）→ 调用 5 发出 `ask_clarify` → 交付澄清问题与三个选项，带一条「已停止继续查询」的缺口。

### 意图理解
| 条 | 结论 | 观察 |
|---|---|---|
| I1 | ～ | 姓平、女、12 月三项在四次查询里都在；**「我名下」在所有查询里都没有**（模型的思考文字提到过，没写进查询）。工具有没有隐含的归属范围，trace 里看不出 → 这一项无法定性 |
| I2 | ✗ | 「按客户号升序」在四次查询里**全部静默消失**，也没有出现在澄清问题和交付缺口里 |
| I3 | ✓ | 只执行了第一阶段；没有调详情或保单工具 |
| I4 | ～（已更正，见文末） | 冻结条目要求 E2、E3 **保留在表达里**。四次查询都只含第一阶段；会话账本里挂起任务的 summary 只是澄清问题；交付里也没提后续两步。原话「确定后再查……」仍在会话历史中，下一轮可以再读到——是否足够本轮无法核 |
| I5 | ✓ | 「姓平」始终按姓氏表达（姓平 / 姓名姓平开头 / 平姓） |
| I6 | ✓ | 没有添加条件，月份始终是 12 月 |
| I7 | ✓ | 先取数，后澄清 |

**问题 IP1**：用户要求的「按客户号升序」在内部表达中丢失，全程没有任何地方交代；「我名下」同样未体现（是否有影响待查）。归本轴。影响：unknown——本轮没拿到名单，若拿到了，排序要求会直接落空。
**待查项 IQ1**（I4 更正后新增）：「确定选中后再查详情和保单状态」这两步没有保留在任何结构化状态里（账本只存了澄清问题）。多轮能否续上，取决于下一轮是否重读历史原话；本轮无法核，归因未定位。

### 规划路由
| 条 | 结论 | 观察 |
|---|---|---|
| P1 | ✓ | to_agent，首步 customer_search |
| P2 | ～ | 排序被去掉了（可接受的处理之一），但之后没有任何交代，见 IP1 |
| P3 | ✓ | 选定前没有调用详情或保单工具 |
| P4 | ✗ | 第一次 AMBIGUOUS 后，又换了两次措辞重试（均已执行，仍 AMBIGUOUS），第三次重试被预算守卫拦下。系统提示词明令「不得反复猜别名、改写同一问题或重复调用已失败来源」；工具说明写明 AMBIGUOUS 是「某条件不支持」 |

| P6 | ～ | 守卫返回的是「基于已有证据回答并明确未确认部分」（finish_with_evidence），模型却选了 ask_clarify。系统提示词两者都允许，我不判 |
| P7 | ～ | 用户得到一个澄清问题和三个选项（选项 2「放宽条件，按12月出生的女性客户先查」给了出路），但没说真实原因，也没提排序 |

**问题 PP1**：同一失败查询连续换措辞重试，2 次已执行，第 3 次被守卫拦下。违反系统提示词与工具说明。归本轴（规划），同一事件在模型轴也记（见 MP2）。影响：yes——用掉 3 次调用，没有换来任何信息。
