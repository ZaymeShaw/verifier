# 过程六轴「本应产出」手工走查（2026-10-09）

> 状态：探索，**未改需求、未改规格、未改代码**。目的：在动 `demand/process_axes.md` §4（判定单位 = 子能力 × 一次行使）之前，先看「把本应产出显式写出来」这条路到底行不行。
> 用户指示：名字就叫「本应产出」，与「实际产出」成对（出自 `spec/alg/process-axes.md` §3.1 的对照）；要加的是把它从一句隐含的话，变成**每个部件实例一份、先写先冻结的显式产物**。`pair_up` 没用 `situation` 字段的问题**不修**——方向一变它就跟着废。

## 1. 做了什么

两个真实 case（来自 job `fb5fda56…` 的导出）：
- **保单**（`smoke-policy-detail-renyanlin`）：任言琳保单，一次 `policy_detail`，答对了。
- **D01**（`main-D01-same-surname-clarify`）：找姓平、12 月生日的女性客户，`customer_search` 连续 AMBIGUOUS，最后澄清。

六个轴都按同一套步骤走：**只依据部件拿到的输入，写「本应产出」→ 冻结 → 再对照实际产出 → 差在哪 → 问题**。每条「本应产出」是一句可对着运行记录核对的陈述，标类型：
- **推出**：由输入、期望 E、业务系统自己写明的规则推出；
- **守恒**：参考就是上游产出本身，下游不得丢改、不得凭空多出；
- **外部真值**：必须独立查证（库里到底有没有）。

三个写法：
| 版本 | 谁写 | 怎么写 | 文件 |
|---|---|---|---|
| **A** | 我，手写 | 先读输入侧，写完冻结（哈希见 `FROZEN.sha256`），再读运行结果 | `A_stage1_frozen.md`、`A_stage2_alignment.md` |
| **B1、B2** | 独立模型（deepseek-flash），写两遍 | 阶段一**只给部件的输入**（模型轴按每次调用单独给，防止后一次的输入泄漏前一次的输出）；阶段二给冻结清单＋完整案卷，逐条核对 | `blind_pass.py`、`B_runs/` |

**A 不干净，必须说明**：保单 case 的 A 只读了输入侧，仅受本会话早先印象影响（T4、C3 带 ◇）；**D01 的 A 在冻结前读到了输出侧的内容**——五次工具调用的实际参数和会话账本里的澄清问题——所以可能受影响的 D01 条目共 15 条，不是最初标的 2 条。完整清单与理由见 `A_contamination_audit.md`（这是审查时补的更正；冻结文件本身一字未改，哈希复核一致）。真正不受污染的是 B。
**换模型的原因**：中转的 Gemini 线路今天被地区限制拒绝（`User location is not supported for the API use`），Claude 线路额度用完，只剩 qwen 与 deepseek 可用，所以 B 用 deepseek-flash。方法不依赖具体模型，但这意味着 **B 与线上六轴不是同一个模型**，不能把差异归结为方法。

## 2. 三个问题的回答

### 2.1 每个轴写不写得出来？—— 写得出来

12 个（case × 轴）三个写法都写出了清单，全部可核对（A 68 条，B1 248 条，B2 245 条）。类型分布（B1）：推出 169、守恒 56、外部真值 23。

| 轴 | 实际体验 |
|---|---|
| 意图理解 | 推出型为主，写得出。但这个系统里「内部表达」没有独立载体，只能落在工具参数和草稿上；多阶段意图（D01 的「选定后再查」）有没有被**保留**，没有地方可核（见问题 R6） |
| 规划路由 | 推出型。**B 的误报集中在这里**：保单 case 里分支该走哪条（to_direct / to_capability / to_agent），输入里没有任何规则指向，B 却硬写出「本应」，两遍还互相矛盾（B1 说 to_capability，B2 说 to_direct） |
| 工具执行 | 保单 case 很干净；D01 的难点是「AMBIGUOUS 算不算合约行为」取决于工具的字段登记，trace 里没有。A 判「无法核」，B1 却断言「对受支持条件返回了 AMBIGUOUS」——无依据 |
| 知识数据 | 几乎全是外部真值型：该轴自己的 8 条外部真值型条目全部判「无法核」，轴的结论基本是 untested。**另外** B 在别的轴上把 11 条外部真值型条目判成了「达到」（意图 3、规划 3、模型 5），而它没有任何独立来源——这类要由程序强制记「无法核」 |
| 模型能力 | 条目最多（D01 一个轴 67 条，5 次调用 × 约 13 条），也是**真违约最集中**的地方（输出契约、改写重试） |
| 上下文管理 | **守恒型为主，可以交给程序**：我用脚本逐字比对核掉了 8 条（保单 C1、C2、C4；D01 C1–C5）——用户原话、工具返回是否原样进入下一次输入，工具参数是否原样执行，执行余量提示是否更新，澄清是否原样进入账本和交付。不需要模型判断 |

### 2.2 结论是不是比现在那 21 道题有用？—— 找到的真问题更多，但有误报

我把全部问题收拢成 9 个真实问题（R1–R9，定义见 `problems_triage.md`），看各方找到了哪几个：

| R2 保单·交付附带假缺口并标 partial | ✓ | ✓ | ✓ | — |
| R3 两 case·「执行余量」提示从不更新 | ✓ | — | — | — |

**代价是误报。** 61 条 B 报出的问题（我逐条归类，可推翻）：

| | 总数 | 命中真问题 | 重复拆分 | 过度断言 | 被案卷/规则反驳 | 无法判断 |
|---|---|---|---|---|---|---|
| B1 | 29 | 17 | 2 | 3 | 5 | 2 |
| B2 | 32 | 18 | 5 | 4 | 3 | 2 |

即约 22%–28% 是错的或过度的。现行流水线在这两个 case 上几乎没有误报（7 条里 1 条存疑），但漏得多。

同一条归类规则下三方的精度：A 8 条问题全部命中（**我评我自己，最不可信**），现行流水线 7 条命中 6 条（错的一条是 D01 上下文轴的「未交付名单」，那是上游结果不是传递缺陷），B 是 17/29 和 18/32。明细见 `problems_triage.md`。

注意：R1–R9 是我读完 A、B、现行三方结果后收拢的，**没有独立的标准答案**，所以只能比较「谁找到了这几个」，量不出「还有多少没人找到」；谁的发现被收进清单，谁的命中数就更高（R3 只有 A、R8 和 R9 只有 B）。D01 上 A 的几个 ✓ 因污染需要打折（见审计），但 B 独立找到了 R4、R5、R7，整体方向没变。

**按需求 §6「不要让评测器自己的失败变成业务结论」看，这 22%–28% 不是小事**：B 的误报（如「本应走 to_direct」「本应调用 run_policy_field_lookup」）如果原样进入问题记录，就是评测器的错写成了业务系统的缺陷。所以方案里必须有独立复核这一步（见第 3 节），不能把盲写的问题直接当结论用。

形式上 B 的 61 条问题都带了归因、违反的清单条目和引用；159 个引用里 144 个是案卷里真实存在的记录 id、14 个是案卷原文片段，只有 1 个对不上，满足需求 §2.2「每个问题带可回查引用」的形式要求（引得对不对，我没逐条验）。

成本量级相当，不更便宜：每个 case 约 17.9–33.6 万输入、13.7–21.7 万输出 token（deepseek；其 completion_tokens 是否含推理不确定），现行六轴是 14.3–37.9 万输入、1.4–2.9 万输出外加 6.3–29.4 万推理。D01 模型轴一个轴就要写 67 条，阶段二的输出被 24000 token 上限截断过，要加到 64000 才写完。

### 2.3 写两遍是否一致？—— 问题层面基本一致，条目层面只有一半

- **问题层面**：B1 与 B2 找到的真问题 7/8 相同（R9 只有 B2 有）。
- **条目层面**：B1 的条目在 B2 里有等价条目的比例，取决于「等价」的口径，我跑了两种，又抽样校准：
  - 严格口径（核对会得到同样结论）：**39%**；宽松口径（盯着同一件事就算）：**94%**。**宽松口径是我看到严格口径只有 39%、并抽查发现配对器偏严之后才加的**，不是事先定好的两档；两个数都报了，但「事后加档」这一点读者应当知道。
  - 我对分歧区抽了 14 对，只有 4 对确实等价（宽松口径对了 29%）；又对严格口径判等价的抽了 10 对，约 85% 成立。校准后大约 **47%**，但样本只有 24 对，**不确定范围很宽（大致 30%–65%）**。
  - 说明清单本身**不可逐条复现**；稳定的是结论。
- **一致不等于正确**：两遍都犯的错——「本应调用 run_policy_field_lookup」「本应走 to_direct/to_capability」——引的原文是真的，错在用错了（那句话讲的是用该工具时 query 怎么写，不是必须用它）。所以我原先设想的「依据必须是原文引用，程序一查就能拦住站不住的条目」**不成立**：493 条里 182 条的依据根本没有可核对的原文片段，53 条的片段在输入里找不到，而误用真引文程序查不出来。

## 3. 对「判定单位改成部件实例」的建议

先说我对数据的读法，再说建议。

**数据支持的：**
1. 现行的「每个事件 × 每项职责出一道题」确实是笛卡尔积，且大量题答案固定。改成「每个部件实例一份本应产出清单」，条目数随情况变化，不是固定网格。
2. 显式的、先冻结的清单**能多找到现行漏掉的真问题**（R2、R3、R7、R8、R9），且 A 的核对过程可以追到每一条依据。
3. 「守恒型」（占 A 的 28%、B 的 23%）可以由程序核对，不需要模型，既省 token 又去掉了方差。

**数据不支持的：**
1. 直接把现行换掉。误报 22%–28%，条目级只能复现约一半。
2. 用「引用存在」挡住误报。
3. 让模型对外部真值型下「达到」。

**如果往这个方向改，我建议的形状（不含具体实现）：**
- **工作单位 = 部件实例 + 它的本应产出清单**；「子能力」降为写清单时的提纲和条目标签，不再用来出题。这会改写需求 §4 的一行：判定单位。
- **三类条目分别对待**：守恒型由程序核（不进模型）；推出型保留，但要求**每条带规则原文或期望编号，并且阶段二由另一次独立调用复核「依据是否支撑结论」**，而不是只查引用存在；外部真值型一律记「无法核」，除非接入独立来源（以前 authority / 能力空间干的就是这件事），由程序强制，不让模型判。
- **清单要有上限和合并规则**：D01 模型轴 67 条说明按「每次调用 × 每个方面」会重新长成笛卡尔积。同模式的调用要合并写。
- **轴 verdict 的含义要改**：现在的 `sound` 是「每一项都核过」；新方案下只能是「在本次冻结清单内没有 not_met，并且清单未覆盖的范围已写明」。

**最大的风险是需求 §2.1（verdict 要跨 case 可比）**。清单本身每次不同，分母不稳，直接比 `sound` 的占比没有意义。可行的补救是按子能力标签汇总 met / not_met / cannot_check 的**计数**，接受分母变化。这是需求层面的取舍，要你来定。

**需要你定的事：**
1. 要不要沿这个方向继续。如果要，需求 §4 的「判定单位」那一行得改，§2.1 的可比性要换锚。
2. 推出型的条目由谁复核：同一个模型独立再判一次，还是人工抽查。
3. 守恒型交给程序之后，是新建一个通用的「传递核对」模块，还是并入现有 `process_loop` 的证据校验。

## 4. 局限

- 样本只有两个 case、一种业务；保单 case 太干净（几乎无问题），D01 又偏失败路径，没有覆盖「多轮」「多工具」。
- B 用的是 deepseek-flash，不是线上的 Gemini；中转的 Gemini 线路恢复后应复跑一遍对照。
- 阶段二的核对是让同一个模型自己做，我只抽查了问题层面，没有逐条复核每条 met/not_met。
- 条目级一致性靠模型配对，抽检只有 24 对，抽检的等价判断是我做的（逐对判断保存在 `calibration_sample*.json`）。
- A 的 D01 部分在冻结前读到过输出侧内容（见 `A_contamination_audit.md`）；最干净的补救是找一个没见过结局的写手重写一份 A，本轮没做。
- R1–R9 由我定义，没有独立标准答案；「真问题」的判断里 R6、R8、R9 本身有争议，已在 `problems_triage.md` 注明。
- A 版有一次误判（D01 的 I4），在与现行结果对照后才发现，说明手写核对也会错。
