# A 版（手写）· 阶段一：本应产出（只依据输入写，写完冻结）

写法约定
- 每条 = 一句可对着 trace 核对的陈述，不是完整答案。允许只写一部分，没写到的部分在末尾「未覆盖」里说明。
- 类型：**[推]** 推出型（由部件实际拿到的输入、期望 E、设计规则推出）；**[守]** 守恒型（参考就是上游产出，下游不得丢改或凭空多出）；**[外]** 外部真值型（需要独立查证，trace 内给不出）。
- ◇ = 我写这一条时已经知道该 case 的部分结局（本会话早先看过），可能被影响，不能当作"干净推出"。
- 来源：E=冻结的期望；SP=业务模型系统提示词（两个 case 逐字相同）；TD=工具说明；WF=工作流定义（两个 case 相同）；U=用户原话。

## Case 1：任言琳保单（smoke-policy-detail-renyanlin）

用户原话：P260922000005855是谁的保单？投保人和被保人分别是谁？当前状态呢？（首轮，无历史）
E：applicant（告知投保人）、insured（告知被保人）、current_status（告知当前状态）；「谁的保单」未单列，应由投保人/被保人覆盖。

### 意图理解（表达：用户原文 → 系统内部表达，即工具参数与草稿）
- I1 [推] 对象 = 保单 P260922000005855，号码原样保留，不改写不补全。〔U，SP:保单号〕
- I2 [推] 三个问题都保留：谁的保单（投保人/被保人）、投保人、被保人、当前状态；「谁的保单」没有被丢掉。〔U，E〕
- I3 [守] 不添加用户没说的约束（时间范围、险种过滤、其他保单）。〔U〕
- I4 [推] 无历史、无指代、无歧义，不应触发澄清。〔U，SP:澄清条件〕
- I5 [推] 用户措辞映射到工具字段时，覆盖「投保人、被保人、保单状态」，不多不少。〔SP:可传 fields，TD〕

### 规划路由（编排：任务 + 状态 + 规则 → 路径与调用序列）
- P1 [推] 走单智能体取数路径（to_agent），取数工具 = policy_detail（已有完整保单号）。〔WF，SP:工具分工，TD:适用〕
- P2 [推] 一次 policy_detail 即可覆盖三个问题；不需要 policy_search、客户类工具或知识类工具。〔TD，E〕
- P3 [推] 取数返回后据结果作答，证据足够时不重复同参调用。〔SP:证据已足够不再检索〕
- P4 [推] 调用总数在预算内（工具 ≤12、同工具 ≤4、约 598 秒）。〔SP〕
- P5 [推] 以结论先行的答复收尾，未确认项进 gaps；不声称已挂起任务。〔SP〕
- P6 [守] 工作流按定义顺序执行（assemble → gate → 条件分支 → finalize），gate 选中的分支与输入一致（有保单号的取数问题 → to_agent）。〔WF〕

### 工具执行（policy_detail 一次调用：参数 → 返回）
- T1 [推] 调用无报错、无超时地完成。
- T2 [守] 返回的保单就是请求的保单（data.records 的保单号 = P260922000005855），没有把别的保单标成目标。〔TD:读结果〕
- T3 [推] 请求的信息（投保人、被保人、保单状态）要么出现在 data.records，要么在 execution 里明确说明未返回；PARTIAL / EMPTY 的含义按工具说明使用。〔TD〕
- T4 [守] ◇ 返回自洽：data.records 里已有值的字段，execution/gaps 不得声称"未返回"；同一保单多行字段冲突要披露。〔TD:多行冲突不能合成保单级结论〕
- T5 [推] 返回结构符合工具说明（data.records 险种记录、field_descriptions、projection.incomplete）。〔TD〕
- T6 [推] 耗时在适用时限内（本案没有配置时限 → 无法核）。

### 知识数据（数据源：已正确执行的查询 → 数据是否存在、是否匹配）
- K1 [外] 保单 P260922000005855 在库里存在。
- K2 [外] 返回的投保人、被保人、保单状态与库里一致。
- K3 [推] 多行（主险/附加险）时，保单级字段（投保人、被保人、状态）在各行一致；不一致要暴露而不是合并。〔TD〕

### 模型能力（一次调用的实际输入 → 该次输出）
调用 1（输入：系统提示词 + 用户问题）
- M1 [推] 决策 = 调用 policy_detail，不直接作答、不先澄清。〔SP，TD〕
- M2 [推] 参数：polno 原样；fields 覆盖三项；不带多余参数。〔SP，TD〕
- M3 [守] 取数前不陈述任何业务事实。〔SP:L3〕

- M5 [推] 输出契约：JSON；answer_draft 为首字段、结论先行；fact_refs 只填真实 fact_id；gaps；needs_user_input；claims 的 subject_id/field/fact_id 逐字复制自工具 facts；answer_draft 不自填姓名、状态等业务值。〔SP:输出 JSON、业务回答契约〕

- M7 [推] 无内部词（工具返回/EMPTY/BUDGET）与来源转述（根据资料/检索到）。〔SP〕

### 上下文管理（传递：一处产出 → 下一处输入）
- C1 [守] 用户原话完整进入调用 1 的输入。
- C2 [守] 工具返回正文完整、无截断、无改写地进入调用 2 的输入（tool 消息 = 工具结果）。
- C3 [守] ◇ 调用 2 的草稿经 agent_bridge → finalize → delivered_output：事实（姓名、状态）与限制/gaps 不丢不改。
- C4 [守] 执行余量提示与实际用量一致。
- C5 [推] 首轮不注入历史。

## Case 2：D01 同姓客户澄清（main-D01-same-surname-clarify）

用户原话：先找一下我名下姓平、12月份生日的女性客户，按客户号升序列出来让我选，确定后再查选中客户的详细资料和保单状态。（首轮，无历史）
E：list_…（查找名下姓平、12月生日的女性客户，按客户号升序列出供选）；query_selected_client_detail_info（条件：确定选中客户后）；query_selected_client_policy_status（条件：确定选中客户后）。
工具说明要点（TD）：customer_search「不支持年龄数值比较或区间、跨年生日区间、地址、排序及未登记字段；任一条件不支持时整条不查询，返回 AMBIGUOUS（不是零命中），不得删条件扩大范围」；ask_clarify「无可答事实时才澄清，须单独调用」。SP 另有：「不得反复猜别名、改写同一问题或重复调用已失败来源」。

### 意图理解
- I1 [推] 对象 = 客户；筛选条件：归属我名下、姓氏 = 平、性别 = 女、生日月份 = 12。〔U，E1〕
- I2 [推] 「按客户号升序」作为排序要求保留，不能静默消失；若系统/工具不支持排序，应表现为一个待处理的限制。〔U，E1，TD〕
- I3 [推] 「列出让我选，确定后再查」是分阶段意图：本阶段只列候选；详情与保单状态是选定后的条件步骤。〔U，E2，E3〕
- I4 [推] E2、E3 都保留，且带「确定选中后」的条件。〔E〕
- I5 [推] 「姓平」理解为姓氏是平，不是名字叫"姓平"；「我名下」是归属约束。〔U〕
- I6 [守] 不添加用户没说的条件（年龄、地区、等级），月份不被改成日或季节。〔U〕
- I7 [推] 条件已足够表达首步查询，取数前不需要澄清。〔U，SP〕

### 规划路由
- P1 [推] 走 to_agent，首步 = customer_search（定位/筛选客户）。〔WF，SP:工具分工〕
- P2 [推] 排序是工具不支持项：首次调用前就要识别并决定怎么处理（不带排序去查、查回后再说明或排序、或告知用户），不能把不支持条件原样塞进查询。〔TD，E1〕
- P3 [推] E2、E3 是选定后的步骤：用户选定前不得调用 customer_detail / 保单类工具；首步完成后以「列出供选、等用户选择」收尾。〔E，SP〕
- P4 [推] ◇ 若 customer_search 返回 AMBIGUOUS（= 某条件不被支持），不得换措辞重试同一意图（系统提示词明令不得改写同一问题、重复调用已失败来源）；应按工具说明做一次合法调整，或据实收尾/澄清。〔SP，TD〕
- P5 [推] 预算内（工具 ≤12、同工具 ≤4、约 598 秒）；接近上限前停止取数，用已有证据收尾。〔SP〕
- P6 [推] 无可答事实且缺关键信息时才 ask_clarify，且单独调用。〔SP，TD〕
- P7 [推] 收尾要给用户一个可行动的结果（候选清单，或清楚说明哪里做不了、需要用户怎么做）。

### 工具执行
对每一次 customer_search（参数：query 文本、compact、fields）
- T1 [推] 无报错、无超时地完成。
- T2 [推] 参数里所有条件都在支持范围内时，应返回匹配客户的搜索页记录或 EMPTY（total=0）；含不支持条件时，按工具合约整条不查询、返回 AMBIGUOUS 并说明——这是合约行为，不是故障。核对点：该次 query 里到底有没有不支持条件。〔TD〕
- T3 [守] 返回的客户满足 query 的条件（女、生日 12 月、姓平）。〔TD:读结果〕
- T4 [推] fields 请求项（姓名、生日、性别、客户号、客户中心ID）出现在 records，或 execution 说明未返回。〔TD〕
- T5 [推] 耗时在适用时限内（未配置 → 无法核）。
对 ask_clarify
- T6 [推] 返回 NEEDS_CLARIFICATION 并登记挂起任务。〔TD〕

### 知识数据
- K1 [外] 名下姓平、12 月生日的女性客户是否存在、有几位（仅当查询被正确执行时才对数据源说话）。
- K2 [外] 返回的候选是满足条件的全体（不漏）。
- K3 [推] 数据源语义：EMPTY = 确实无记录；AMBIGUOUS ≠ 零命中。〔TD〕
- 查询若没有被执行，本轴无从判断，应指向上游。

### 模型能力
调用 1（输入：系统提示词 + 用户问题）
- M1 [推] 决策 = 调用 customer_search，不先澄清、不直接作答。〔SP〕
- M2 [推] query 覆盖姓平、女、12 月三个条件，不夹带工具不支持项（排序），不加用户没说的条件。〔TD，U〕
- M3 [推] fields 含用户要看的列（至少客户号、姓名），可带客户中心ID 便于后续详情。〔U，TD〕
- M4 [守] 取数前不陈述业务事实。〔SP:L3〕
调用 2–4（输入：+ 前一次工具返回）
- M5 [推] ◇ 读懂上一次返回：若是 AMBIGUOUS，含义是"某条件不被支持"，不是零命中；不改写重试。〔SP，TD〕
- M6 [守] 不把 AMBIGUOUS 当成"没有这样的客户"来陈述。〔SP:L3〕
调用 5（若走澄清）
- M7 [推] ask_clarify 的问题与选项要对用户有用，且与已知限制一致（不要求用户提供他本不必提供的信息）。

### 上下文管理

- C2 [守] 每次工具返回（错误码、说明文字、execution/gaps）完整进入下一次模型输入，不丢"AMBIGUOUS 的含义"。
