# 四套 Agent Harness 的过程对比：评测发现（2026-10-12 批次）

> 批次：2026-10-11 ~ 2026-10-12，4 套系统 × 120 题（174 个用户轮次）
> 原始数据：`package/llmtracing/eval_runs/share_20261012.zip`（4 份自包含 `llm_trace.html`）
> 判定依据：`demand/process_axes.md`（按"每个部件在实际拿到的输入下本应产出什么、实际产出了什么"逐环检查）
> 上一批次：`report/process-axes-manual-4harness-20261008/`

## 1. 这次在比什么

四套系统用同一个模型（`deepseek-v4-flash-0731`，四家的 thinking 都被关闭）、同一份题集（数据集 A，120 题）、同一套业务后端作答。结果的差异主要来自 harness：怎么把工具结果交给模型、怎么控制调用、怎么收尾和交付。

| 系统 | 类型 | 怎么接业务工具 | 和上一批相比 |
|---|---|---|---|
| Claude Code 2.1.292 | 通用 coding agent | MCP，7 个业务工具 + 20 个自带工具 | MCP 返回格式改成了 facts 列表 |
| Pi 0.87.1 | 通用 coding agent | MCP，7 个业务工具 + bash/read/mcp 等 | 同上 |
| 旧 Insurance（insurance-qa-agent） | 业务专用 agent | 自有工具层，9 个工具 | **不再要求模型输出 JSON、也不再由服务端改写答案**，改成直接输出中文 |
| 新 Insurance harness（insurance-agent-harness，Agno） | 业务专用 agent | 自有工具层，17 个工具（多了 calculate、技能、run_policy_*、read_evidence 等） | 本批新增 |

OpenCode（81/120 暂停）和 dsh 没有跑完，不在本包里。

## 2. 一页结论

**新 Insurance harness 是这一批里综合表现最好的：答案内容正确的题数并列最多，交付最干净，速度最快。** 但它和其他三家一样，在"条款查不到"和"名字相近的两款产品"这两类题上失分；另外它会心算求和，违反了它自己"计算必须调用 calculate"的规定。

**旧 Insurance 上一批的头号问题（交付时把答案改写坏）已经修掉了**，金额都对了。但出现了新问题：用户收到的是模型每一步的过程叙述拼在一起的全文，174 轮里有 136 轮是这样，而不是只收到最终答案。

**这一批最大的共性问题出在模型自身，四家都受影响。** thinking 被关闭后，模型把思考过程直接写进了正文。轻的是答案前面多几段"让我整理一下"；重的是整段输出都是思考，最后一句是"让我给出最终回答"，然后就结束了，用户收不到答案。

| 系统 | 做得好的 | 主要问题 |
|---|---|---|
| **新 Insurance harness** | 搜索一页取 100 条，几乎没有"列表不全"；工具结果小；查不到时会给选项让用户选；正文里混入的思考最少 | 心算求和（F04、B02）；把名字相近的产品认成同一款（B02）；个别题停在"让我给出回答"（B11）；以澄清收尾时交付服务端拼的字段清单，B19 带身份证号明文 |
| **旧 Insurance** | 答案内容正确的题数并列最多；不乱编 | **交付的是全部过程叙述的拼接**（136/174 轮），里面还有英文；有答案后还调用 ask_user（E05） |
| **Claude Code** | 工具结果太大时会存到文件再读回来；查不到时不编造 | 正文混入英文思考和 `</think>`；名字相近的产品认成同一款；漏查保单详情，把累计已交保费说成 0（F04）；评测给它的附加提示让它反复解释"获取 ID"这件事 |
| **Pi** | 遇到工具问题会写脚本排查；个别题答得最完整（B11） | 漏查保单详情（F04）；错误推断"第 6 张就是季缴那张"（A04）；受附加提示影响，向用户索要"你的客户号"（D01）；读截断文件时编错路径 |

## 3. 用户最终拿到的答案

人工逐题判定 11 题（和上一批同一组题号），看用户最终收到的那段文字。

| | Claude Code | Pi | 旧 Insurance | 新 Insurance harness |
|---|---:|---:|---:|---:|
| 内容正确（允许如实说"查不到"） | 7 | 7 | 8 | 8 |
| 其中可以直接给用户看（没有大段思考或过程叙述） | 4 | 4 | 1 | 5 |
| 内容不正确的题 | B02、B11、D01、F04 | A04、B02、D01、F04 | B02、B11、C14 | B02、B11、F04 |

不正确的原因：

- **B02（四家都错）**：客户买的是"安佑福（惠享版）定期重疾"（险种代码 1813），用户问的是"安佑福重大疾病保险"（1836），这是两款产品。Claude、Pi、新 harness 都回答"已购买"。旧 Insurance 其实在思考里分辨出来了，但最终没写出答案。上一批只有 Insurance 答对了这题。
- **B11**：Claude、新 harness 的输出停在"让我给出完整回答"，没有给出答案；旧 Insurance 交付的是一大段内部思考。只有 Pi 给出了完整答复。
- **F04**：Claude、Pi 没有查第一张保单的详情，把累计已交保费说成 0（实际是 675）。新 harness 金额正确，但把同一保单两个险种的金额加成了 258.4，题目检查点明确要求"不跨险种自动加总"，而且这个加法是心算的，没有调用 calculate。
- **D01**：客户搜索工具解析不了"姓平 + 12 月生日"。Claude 试了 11 次后告诉用户"系统里没有姓平的客户"，这个结论并不成立；Pi 向用户索要"你的客户号"。新 harness 试了 4 次后列出几种放宽条件的选项让用户选，旧 Insurance 也如实说明了查询失败，这两家判为正确。
- **A04**：客户名下有 6 张年缴保单。Claude、Pi、旧 Insurance 的搜索每页只返回 5 条，都漏了"盈添悦两全"。Claude 和旧 Insurance 说明了"可能还有未返回的"，判为正确；Pi 断定第 6 张是另一张季缴保单，结论错误。只有新 harness 一次拿全，答案完整。
- **C14**：旧 Insurance 的输出停在"Let me write the final answer."，没有答案。

样本只有 11 题，看方向可以，不宜当成精确比例。新 harness 的 F04 如果不按检查点严格判，内容正确数是 9。

## 4. 按流程分层：问题出在哪一环

把每道题拆成"理解问题 → 安排调用 → 工具执行 → 数据源 → 模型输出 → 传递与交付"六个环节，记下哪一环有问题。数字是 11 题里该环节有问题的题数；归到上游的问题不重复算到下游。

| 环节（六轴） | Claude Code | Pi | 旧 Insurance | 新 Insurance harness |
|---|---:|---:|---:|---:|
| 理解问题（意图理解） | 0 | 1 | 0 | 0 |
| 安排调用（规划路由） | 2 | 1 | 1 | 0 |
| 工具执行 | 2 | 2 | 2 | 2 |
| 数据源（知识数据） | 0（4 题未定位） | 0（4 题未定位） | 0（4 题未定位） | 0（4 题未定位） |
| 模型输出（模型能力） | 3 | 3 | 3 | 4 |
| 传递与交付（上下文管理） | 0 | 0 | **10** | 0 |

各环节的具体问题：

**理解问题**
- Pi/D01：把"我名下的客户"理解成要先拿到用户自己的 ID，于是向用户索要客户号。诱因是评测给通用 agent 加的附加提示"请从 mcp 工具中获取我的 id 信息"（见第 7 节），这一条应同时算评测配置的问题。

**安排调用**
- Claude/D01：搜索条件解析失败后换说法连试 11 次。
- Claude/F04、Pi/F04：只看了搜索结果里的"续期保费"，没有调用保单详情查累计已交保费。
- 旧 Insurance/E05 第 2 轮：已经写出三个问题，又调用 ask_user 挂起本轮。
- 新 harness 没有记为问题，但有两处可以更好：D06 先用搜索查两个保单号、只返回一张再查详情，多了一次调用；E05 第 3 轮权益库为空后没有试通用问答，另外三家都从通用问答拿到了参考内容。

**工具执行**（四家共用的后端问题，不拉开差距）
- D01（四家）：客户搜索解析不了"姓X + 生日月份"的组合条件，返回"未执行查询"；有时又返回"0 条"，让模型误以为没有这个客户。
- A04（Claude、Pi、旧 Insurance）：搜索每页 5 条、没有翻页参数，返回"报告 6 条、读取 5 条"。全量统计里，这三家分别有 18、18、14 道题出现"总数大于实际返回"；新 harness 每页 100 条，只有 3 道题。
- 新 harness/B11：run_policy_field_lookup 返回上游错误。

**数据源**
- B02、B11、C03、C14（四家）：查产品条款，返回的是别的产品的正文（e 生保、守护百分百等），看不出是检索召回错了，还是知识库里本来就没有这款产品。按 P2 记为"未定位{工具执行, 知识数据}"。

**模型输出**
- 名字相近的产品认成同一款：B02 的 Claude、Pi、新 harness。
- 输出停在"让我给出回答"、没有写答案：Claude/B11、新 harness/B11、旧 Insurance/B02、旧 Insurance/C14。全量粗筛至少还有 Claude 2 题、旧 Insurance 3 题（第 6.3 节）。
- 数字错误：Claude、Pi 在 F04 把"续期保费为 0"当成累计已交保费 0；Pi 在 A04 推断错误。
- 违反规定的心算：新 harness 在 F04、B02 心算求和。它的系统提示写明"计算必须调用 calculate"，全量 120 题里 calculate 只被调用了 7 次。
- 事实张冠李戴：新 harness/E05 把客户"关注过的方向"写成了"办理的保险产品责任"。

**传递与交付**
- 旧 Insurance：交付的是本轮所有过程叙述拼在一起的全文，比如"我需要先找到客户……找到客户……现在查询……"，最终答案在最后。11 题里有 10 题是这样（只有 D06 例外），全量 174 轮里有 136 轮。多轮题里，这段拼接文本还会作为"上一轮回答"带进下一轮（F04 第 2 轮）。

## 5. 各 harness 的具体发现

证据格式：`insurance_harness/B11 #6` 表示新 Insurance harness 在 B11 题的第 6 次模型调用，可在对应 `llm_trace.html` 中按 `#用例/6` 定位。

### 5.1 新 Insurance harness

**做得好的**
- 列表查询一次拿全：搜索每页 100 条（另外三家是 5 条），A04 是四家里唯一列全 6 张年缴保单的。
- 交付干净：161/174 轮交付的就是模型最后一次输出，其余 13 轮主要是澄清问题；正文里混入思考的轮次是四家最少的（49/174，其余三家 86–102）。
- 查不到时处理得体：D01 解析失败 4 次后，用 ask_clarify 给出 5 个放宽条件的选项（`insurance_harness/D01 #5`）；C14 换问法从通用问答找到了体检卡预约方式，其他三家都没找到。
- 最快：每题耗时中位数 26 秒，最长 94 秒。

**问题**
1. **心算求和，违反自己的规定。** F04 把主险 216.7 和附加险 41.7 心算成"合计 258.4"（`insurance_harness/F04 #3`），B02 心算出"合计年缴约 170.8 元"（`insurance_harness/B02 #2`）。题目检查点要求不跨险种加总，系统提示要求计算必须调用 calculate。
2. **相近产品认成同一款**：B02 回答"已购买"（`insurance_harness/B02 #2`）。
3. **个别题输出停在思考**：B11 最后一句是"让我给出完整回答。"（`insurance_harness/B11 #6`）。系统没有检查"最终输出里有没有答案"。
4. **以澄清收尾时，交付的是服务端拼出的字段清单。** B03、B19、F01 三轮里，模型调用 ask_clarify 后，用户收到的是"保单 P… · 字段：值"逐行堆出来的内容，后面才是澄清问题。B19 一次列了 63 行，里面有投保人和被保人的身份证号、手机号明文（`insurance_harness/B19 #4`）。这和上一批旧 Insurance 的"字段堆砌、身份证外露"是同一类问题，只是现在只出现在澄清这条路径上（3/174 轮）。
5. **固定开销偏大**：17 个工具说明加系统提示，每次调用约 1.5 万 token，是旧 Insurance 的 2 倍，所以每题输入 token 反而比旧 Insurance 多（中位数 55k 对 32k）。新增工具里 read_evidence、run_policy_snapshot、control_workflow_task 在 120 题里一次都没用到。

### 5.2 旧 Insurance

**做得好的**
- 上一批的交付改写问题已经修复：A01 金额正确（1320 / 6300），F04 各险种金额正确，也没有求和。
- 内容正确的题数并列最多（8/11）；不编造。

**问题**
1. **交付的是过程叙述拼接全文**（136/174 轮）。例如 A05 用户收到的开头是 "I'll start by verifying the customer information…The search by customer number returned no results…"（英文过程），最终答案在最后。B02、C14 更严重：拼接的全是思考，没有最终答案。
2. 本轮已经作答后又调用 ask_user（E05 第 2 轮 `insurance_old/E05 #4`）。
3. 搜索每页 5 条，和 MCP 一样会漏列表（A04）。

### 5.3 Claude Code

**做得好的**
- 工具结果过大时转存成文件，再用 Bash/Read 读回（72 次 / 45 题），信息基本不丢。
- 查不到条款时如实说明，不编造（B02、C03、C14）。

**问题**
1. **正文混入英文思考**：79/174 轮有英文思考，13 轮带 `</think>` 标记（例如 A04、C14）。
2. **F04 漏查详情**：没有查第一张保单的详情，把"续期保费 0"说成"累计已交保费 0"，还对第二张做了加总（`claude/F04 #4`）。
3. **D01 重试过多**：换说法查了 11 次，最后得出"系统里没有姓平的客户"这个不成立的结论。
4. **读回大文件有阻力**：Read 读不了单行大 JSON（`claude/A05 #3`、`claude/E05 #3–#4`），要绕到 Bash/python，一题多花 3–5 次调用。
5. **评测附加提示造成干扰**：10 轮答复向用户解释"无法获取您的 ID 信息"，用户其实并没有提这个要求（第 7 节）。

### 5.4 Pi

**做得好的**
- B11 是四家里唯一给出完整、诚实答复的。
- 截断后能用 bash 读回（89 次 / 62 题）。

**问题**
1. **F04 漏查详情**：只用了搜索结果，没有拿到累计已交保费。
2. **A04 推断错误**：把搜索结果里没出现的"第 6 张"断定为另一张季缴保单，实际上漏的是一张年缴保单（`pi/A04 #7`）。
3. **D01 向用户索要客户号**：受评测附加提示影响。
4. **读截断文件时编错路径**：B02、B11 把临时目录名写错（`…0000gt` / `pUOpkH`），多花 2–3 次调用（`pi/B02 #2–#3`）。
5. 正文混入英文思考（72/174 轮）；以"需要我……吗？"结尾的轮次最多（57/174）。

### 6.2 读法

- **速度：新 harness 最快，长尾最短。** 调用次数最少（平均 4.1 次），工具结果不需要转存再读回。
- **token：旧 Insurance 最省，新 harness 第二。** 新 harness 每次调用的固定开销是旧版的 2 倍，抵消了调用次数少带来的节省。如果把用不到的工具说明去掉，还有下降空间。
- **Claude 的 token 主要花在固定开销上**：每次调用 1.95 万 token 的系统提示和工具说明（27 个工具里 20 个与业务无关），按每题 6.3 次调用算，约占总输入的六成。
- **通用 agent 的额外调用主要花在"大结果读回"上**：MCP 的保单详情一次返回约 3 万字符，客户详情 5 万–7 万，经常超过上限，需要 Bash/Read 读回。业务专用的两家没有这一步。
- **口径**：index 页没有写明并发情况；Claude 有 5 题没有耗时记录。token 和调用次数不受这两点影响。

## 7. 评测配置本身的问题（影响 Claude、Pi）

评测在 Claude Code 的系统提示末尾、Pi 的 addendum 里加了两句话：

> 请从mcp工具中获取我的id信息，通过id信息直接使用mcp工具进行查询。
> 除了mcp工具外，不要访问和使用本地的任何代码和数据。

两句都有副作用：

## 9. 建议

按影响从大到小：

1. **四家都需要：输出停在思考、没有答案时，不能直接交付。** 最终输出如果没有面向用户的答案（只有"让我…""Let me…"这类话），应该再让模型输出一次，或者在交付前把思考段落去掉。这是本批四家共同的头号问题，根源是 thinking 被关闭后模型把思考写进了正文。打开 thinking、让思考走单独的字段，是更根本的做法，值得单独做一次对照实验。
2. **旧 Insurance：交付只用最后一次输出**，不要把中间的过程叙述拼进去。修好之后，按抽样估计可直接交付的题数能从 1 题升到 6 题左右（估算，需重跑验证；它的最后一次输出本身也会混入思考）。
3. **新 harness：计算强制走 calculate**，模型自己写出的"合计"要拦下；同时清理用不到的工具说明，降低固定开销。
4. **工具层（四家共用）**：客户搜索要支持"姓X + 生日月份"；产品条款检索要按产品过滤，不要返回别的产品；MCP 和旧 Insurance 的搜索每页 5 条、又没有翻页参数，需要调大或提供翻页。
5. **评测配置**：去掉给 Claude/Pi 的那两句附加提示（第 7 节）。

## 10. 评测方法与局限

**标准从哪来**：题集 `复杂协同与上下文问题集-120题(2).md` 里每题的"预期协同"和"检查点"，加上各 harness 自己收到的系统提示和工具说明。某个 harness 没收到的规则，不拿来判它。例如通用 agent 没有收到"计算必须调用 calculate"，所以只对新 harness 判这一条。

**怎么归属问题**：只看"这一步在它实际拿到的输入下做得对不对"。上游坏了导致下游出错，记在上游。例如 D01 Claude 告诉用户"没有姓平的客户"，起因是工具返回了"0 条"，这记在工具执行；但"试了 11 次"是它自己的规划问题。

**哪些查实了，哪些是估计**

- 查实（对照 trace 原文或全量程序统计）：旧 Insurance 交付拼接的 136/174、各家耗时与 token、截断次数、分页不全的题数、calculate 的调用次数、评测附加提示的原文、第 6.3 节列出的"停在思考"的具体题目。
- 估计：11 题的"内容正确 / 可直接交付"题数是人工逐题看的；"修复后能到多少"是按抽样推算的。"正文含内部思考"用的是关键词匹配，会有少量误判。

**范围**：人工逐题判定 11 题 × 4 套（A01 A04 A05 B02 B11 C03 C14 D01 D06 E05 F04），和上一批同一组题号；全量 480 条只做程序统计。

**数据怎么来的**：zip 里只有 4 份 trace HTML，没有逐题 json。交付文本取自 trace 里的 `overview.turns[].final_text`，来源标注为 harness / 评测器产物，代表用户实际收到的文本；模型输出取自各次调用的 `assistant` 字段。

**复现脚本**（都在 `scripts/`）

- `extract.py`：从 trace HTML 里抽出内嵌数据
- `digest.py`：生成每题的过程摘要，并标出交付和模型输出不一致的轮次
- `scan.py`：全量统计，结果在 `scan_signals.json`
- `paging.py`：统计搜索结果总数大于实际返回的题
- `delivery.py`：给交付形态分类
- `monologue.py`：统计正文里的内部思考
