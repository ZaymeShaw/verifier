## 2. 一句话结论

- **新 Insurance harness**：最快、交付最干净、可用最多、答错最少，隐私控制也好。问题集中在模型不照提示词做（心算、编内容、乱澄清），以及提示词本身过于保守、互相矛盾。
- **旧 Insurance**：答错最少、最省 token。问题集中在"答案没交出去"：7 题没有答案，过程叙述拼接后交给用户，又被带进下一轮。
- **Claude Code**：完全正确最多（86），但每题输入是旧 Insurance 的 5 倍，速度最慢，一半答复夹着思考，隐私外露 26 题。
- **Pi**：成本中等，答错最多（12）。主要是数据没查全就下结论，或把别的东西当成用户问的；隐私外露最多（29）。

## 3. 四家共用的后端接口问题

按接口分，后端有 6 个问题，归下来是 3 件事。下表的统计来自四家全部调用记录，同一次调用只算一次（`scripts/backend_stats.py`）。

| 接口 | 问题 | 例子 |
|---|---|---|
| ① 保单搜索<br>`policy_search` → `policy_svc /policy/search` | 1. 查询里带了产品名，基本都会失败 | 带产品名的 93 次查询里（含重试），64 次报错，报错原文是"上游响应格式不符合接口契约，请联系服务维护人员"；另有 16 次返回空，只有 11 次正常。按题算，报错出现在 11 道题，返回空出现在 8 道题。不带产品名的 235 次里只有 8 次失败 |
| | 2. 有记录也返回"空"，而工具说明写的是"空 = 确实无记录" | E10：查"何承琪名下的平安鑫瑞养老年金保险"返回空；改查"何承琪名下所有保单"，结果里就有 2 张鑫瑞（P…2459、P…2460）。新 harness（E10）、旧 Insurance（A09）、Pi（B15）都相信了这个"空"，告诉用户"没有"，三题都答错 |
| | 3. 每页只返回 5 条，又没有翻页参数（MCP 和旧 Insurance 是这样，新 harness 每页 100 条） | A13：接口报告共 9 条，只返回了 5 条，Claude 和 Pi 都据此少列了保单 |
| ② 客户搜索<br>`customer_search` → `policy_svc /customer/search` | 4. "姓X + 生日月份 + 性别"这类组合条件解析不了 | D01、F17：要找"姓平、12 月生日的女客户"，接口返回"条件无法解析"或空，四家都给不出候选名单 |
| | 5. 返回的"总数"不管什么条件都是 417 | "三月生日""四月生日""四月生日的女性"等 9 种不同条件，总数都返回 417。但按三月查和按四月查返回的各 100 位客户完全不重合，说明月份条件生效了，只是总数报错。几家 harness 因此对用户说"共 417 位" |
| ③ 产品知识<br>`product_knowledge` → `product_svc /product/rag` | 6. 问 A 产品的条款，返回的多是别的产品的正文 | 246 次调用里，150 次返回"部分命中"，意思是正文没定位到所问的产品；正常命中只有 46 次。B02 问"安佑福重大疾病保险的等待期"，返回的是 e 生保等产品的条款。四家每家有 38–46 题因此答不全 |
| ④ 权益服务<br>`benefit_info` → `benefit_svc /benefit/detail` | （和 6 同类）常见服务名怎么问都返回空 | "就医绿通""住院陪护""健康体检"换多种问法都返回空。E09 里 Claude 连续查了 7 次，全部为空。分不清是库里没有，还是召回不到 |

归下来是 3 件事：

1. **保单搜索处理不了产品名条件（第 1、2 条）**：这条直接导致答错。接口识别不了产品名时，有时报格式错误，有时返回空。返回空最危险，因为四家的工具说明都把"空"定义成"确实没有"，模型就会如实告诉用户"没有这张保单"。修法是接口识别不了产品名时，明确返回"条件未识别"，不要返回空；或者在接口里支持按产品名筛选。
2. **知识类检索召回不准（第 6 条和④）**：影响面最大，每家近 40 题。`/product/rag` 和 `/benefit/detail` 要先确认两件事：知识库里到底有没有这些产品和服务；如果有，为什么召回成了别的产品。
3. **客户搜索的条件和总数（第 3、4、5 条）**：组合条件解析不了；总数字段不可信；保单搜索每页 5 条又不能翻页。影响相对小，但会让列表不全、人数报错。

**确定性**：
- 各接口的调用次数和成功率，是程序扫描全部调用记录统计的。保单搜索约 440 次调用中，有 328 次能对上查询语句，统计用的是这 328 次。
- E10、B02、F12 这三个例子对照原始 trace 核实过。
- "性别条件可能被忽略"没有核实，所以没写进表。
- 每页 5 条，是接口本身的限制，还是 MCP 和旧 Insurance 适配层的设置，需要后端确认。

## 5. 旧 Insurance

主要问题只有 1 个：**答案没交出去**。它沿着一轮问答的流程一路传下去：7 题没有答案；174 轮里 136 轮交给用户的是过程叙述拼接；拼接的文本又被带进了下一轮。其他问题题数少、彼此独立，算不上主干，放在表后。

| 环节 | 问题 | 例子 |
|---|---|---|
| ① 模型收尾 | 1. 数据查全了，最后一步不写答案，发一个参数为空的"向用户提问"，或者只写思考 | 7 题没有答案，四家最多。B10 三张保单的状态和保费都查到了，最后发了个空提问，退保流程一句没讲；C14 停在 "Let me write the final answer" |
| | 2. 数据拿到了还去问用户（8 题），违反它自己"已取得事实不得澄清"的规则 | B04 已经查到唯一一张对应保单，还让用户"确认是不是这张" |
| ② 交付 | 3. 交给用户的是每一步说明文字原样拼起来的全文 | 174 轮里 136 轮是这样，另外三家一轮都没有。A01 用户收到"我需要先找到客户伏云平……找到客户伏云平，客户中心ID为4F2873…。现在查询……"，最后才是答案。①发生时，用户收到的就只有这堆过程话 |
| ③ 服务端绕过模型 | 4. 有的轮次模型一次没被调用，服务端直接交付保单卡片 | B09 问"有哪些保单、电子保单怎么获取"，只收到卡片，电子保单那一问被漏掉；E01 第一轮用户要"客户资料和名下保单"，只收到两条保单摘要 |
| ④ 下一轮 | 5. 拼接文本和卡片被当成"上一轮的回答"带进下一轮 | F17 第一轮交付的是保单卡片而不是客户候选，用户说"选第一位"后，第二、三轮都把保单的被保人当成了客户，整题答错。E12 第二轮说"上一轮您已经确认了候选 2"，实际用户没确认过 |

不算主干的问题：

- **多轮里的指代和追加处理不好**（6 题）：E19 用户问"那项怎么办"，指代不明，它直接当成重疾理赔作答，答错；F08 把"服务改成住院陪护"理解成要办理服务变更；F20 用户追加一项后，前面的投保人和状态就丢了。
- **少量内容错误**：B11 凭投保日期断言"等待期早已届满"；B13 把 e 生保的条款当成安佑福的；E17 把保单号 P260922000009421 抄成 P260921000009421。

修法：
- 交付层只交模型最后一次答复；
- 最后一步如果是空提问，或者已取得事实还去澄清，程序打回让模型重写；
- 拿掉卡片捷径，或者卡片之后仍让模型回答其余部分。

这几步就能切断整条链。它模型本身的内容质量不差，答错 6 题，并列最少。

**确定性**：136/174 轮是拼接，是程序逐轮比对的。A01、B09、B10、F17 对照原始 trace 核实过。其余题数来自子 agent 标注加抽检。

## 6. 新 Insurance harness

新 harness 最快、交付最干净、可用最多、答错最少。它的问题分散在三处：模型、规则本身、服务端兜底文本，三处的修法完全不同，所以按"问题出在哪一边"分层。新 harness 自己的问题有 7 个，归下来是 3 件事。

| 出在哪一边 | 问题 | 例子 |
|---|---|---|
| ① 规则写清楚了，模型没照做 | 1. 心算求和（20 题）。规则写的是"计算必须调用 calculate"，120 题里 calculate 只被调用了 7 次 | B02 答复里写"两条记录的续期保费分别为 108.3 元和 62.5 元，合计年缴约 170.8 元"。A18 用户说了"别混成一条"，它仍写"两者相加为 1,762.5 元" |
| | 2. 写了工具里没有的内容（12 题，另外三家是 3–7 题）。规则写的是"答案只能来自工具返回的业务 data" | B04 条款没查到，答复里却出现"条款第 2.1 条责任免除"，章节号是编的；B08 写了"可通过金管家 App 修改，或拨打 95511"，检索结果里都没有；C19 一个工具都没调，凭记忆讲理赔规则 |
| | 3. 已经查到数据，仍只回一个澄清问题（7 题）。规则写的是"本轮一旦取得任何可用事实，不得再调用 ask_clarify" | B19 保单详情查到了，用户要的材料清单没回答，只问了用户一个问题；D15 用户给的是产品标准全称，一次没查就先问"是哪个版本" |
| ② 模型照做了，规则本身有问题 | 4. 查不到或报错就收尾，不换更宽的查法（约 10 题）。规则写的是"工具失败不硬答……证据不足如实收尾转人工"，"返回空时不要为同一意图反复猜别名重试" | E10 带产品名查保单返回空，它告诉用户"何承琪名下查无鑫瑞保单"；Claude 碰到同样的空，多查一次"名下所有保单"就找到了 2 张。旧 Insurance 的规则写的是"可改用职责覆盖缺口的另一个工具"，它就更常换个查法查到 |
| | 5. 补币种和时点（16 题）。规则写的是"已声明的保险金额默认人民币""金额必须带数据时点"，另一处又写"有来源日期才标注"，前后矛盾 | D12 写"保额大概率人民币"；B17 加上"数据时点 2026-10-12" |
| ③ 服务端兜底文本 | 6. 模型选择澄清、没写正文时，服务端用原始字段加问题拼一段文本交给用户（9 题） | B19 交付了几十行原样罗列的保单字段，其中有身份证号明文；B03 拼出的文本写着"保单资料未返回"，实际已经查到了保单；E16 追加的候选清单和正文表格顺序不一致，下一轮用户说"第二张"时指错了对象，答错 |
| ④ 模型能力 | 7. 读错事实（7 题） | B20 把 2 岁的被保人冯亦凡写成投保人；A07 把投保时约 31 岁的投保人写成 38 岁 |

归下来是 3 件事：

1. **模型不照规则做，也没人拦（1、2、3）**：这是它"完全正确"（73）低于 Claude（86）的主要原因。规则已经写得很清楚，再加字句作用不大，要靠交付前的程序检查：
   - 答复里的金额，在工具结果里找不到原值、也不是 calculate 算出来的，打回；
   - 没调工具就陈述业务事实的，打回；
   - 已经查到数据却只回澄清的，打回。
2. **规则本身要改（4、5）**：
   - 把"查不到就收尾"改成"先放宽一次，比如去掉产品名、改查名下全部保单，仍查不到再收尾"；
   - 币种和时点先由业务定怎么写，再统一提示词里矛盾的地方。
3. **兜底文本要改（6）**：澄清时也让模型写一段话，服务端只附选项，不再罗列原始字段。

第 7 条规模不大，不单独成事。另外，它每次调用固定带约 15k token 的提示词，约占全部输入的 80%（估算）。

**确定性**：
- 规则原文都是从请求里直接取的；
- 心算 20 题、calculate 7 次是程序统计的；
- B02、E10、A18、B19 对照原始 trace 核实过，其余题数来自子 agent 标注加抽检；
- "第 4 条是规则导致的"是根据原文做的推断，没有做对照实验。

## 7. Claude Code

Claude 答对得最多（完全正确 86），主要问题是贵：每题输入中位数 154k，是旧 Insurance 的 5 倍；耗时中位数 43 秒，最长 426 秒。看 token 花在哪就清楚了：

| token 花在哪 | 占全部输入 | 为什么 / 例子 |
|---|---:|---|
| ① 每次调用都重复带上的系统提示和工具说明 | 约 61%（估算） | 每次约 19.5k，其中有 20 个与业务无关的自带编码工具 |
| ② 读回存盘的工具结果 | 21% | 工具结果太大时被存成本地文件，用 Read 读不回，又改用 Bash 去解析。共 156 次调用，涉及 43 题。D08 用 Read 只读回 9 个字符，又用了 7 次 Bash；F05 直接放弃，用搜索页的几个字段拼了档案，也没告诉用户档案不全 |
| ③ 真正查业务数据 | 不到两成 | 其中还有一部分是反复重试：D01 同一个失败条件换说法试了 11 次，F17 试了 19 次，违反了工具说明"条件不支持时不得改写问法重试" |

前两项合计约八成，都来自 Claude Code 本身是为写代码设计的外壳。修法是关掉无关的自带工具，让工具结果按字段返回或分页、不触发存文件，并给重试设上限。

另一个独立的问题是答复不能直接给用户：能直接给用户看的只有 56 题，四家最少。B14、C18 以英文推理和 `</think>` 开头；B11、C15 停在"让我整理最终回答"，没有答案。另有 26 题带出了用户没要求的证件号或手机号，比如 F04 第二轮只问投保人和被保人，答复里带出了身份证号和手机号。修法是交付前过滤思考文字并做脱敏。

答错题里唯一反复出现的类型是把名字相近的产品当成一款：B02、D03、E14 里，客户买的是 1813 惠享版，用户问的是 1836，三题都答"买了"。

另外，评测给 Claude 和 Pi 附加的"请从 mcp 工具中获取我的 id 信息"造成了困惑，Claude 有约 10 轮在解释这件事。这是评测配置的问题，不算 harness 的。

**确定性**：
- 读回存盘的调用次数和占比、耗时是程序统计的；
- 固定开销占比是按每次调用的平均开销乘以调用次数估算的；
- D01、F04 对照原始 trace 核实过，其余题数来自子 agent 标注加抽检。

## 8. Pi

Pi 答错最多（12 题），拆开这 12 道错题，最能看出它的问题：

| 怎么错的 | 题数 | 例子 |
|---|---:|---|
| ① 数据没查全，就给出确定结论 | 5 | F04、C16 没查保单详情，把搜索结果里的续期保费当成累计已交保费，C16 把 6300 写成 3150；A04 推断没返回的那张保单是季缴，实际是年缴；A13 接口说共 9 条，它只看到 6 条，就断言"共 6 张"；B15 只看到 11 条里的 5 条，再加上后端假空，告诉用户"没有她的安佑福保单" |
| ② 把别的东西当成用户问的那个 | 4 | F10 把别的产品条款里的"90 日等待期"写成安佑福的；F16 把 1813 当成 1836；B05 把"安有医"手册当成就医绿通的申请流程；D18 凭空写出"金管家 App → 就医绿通 → 提交预约"的路径 |
| ③ 指代猜错 | 1 | E18 第二轮用户说"前面那个"，指的是先列出的投保人韦欣颖，它当成了被保人，只查了费书洋 |
| ④ 四家都错，或评测配置造成 | 2 | F15；D01（向用户索要"你的客户号"，是评测附加的那句提示诱发的） |

前三类合计 10 题，都是同一个毛病：证据不够就下结论。这在没答错的题里也常见，比如 E03 说"已通过网络确认重疾险有 90 天等待期"，这次环境根本没联网。修法是要求关键字段必须来自详情接口；明知没取全时，不许下确定结论；名称不一致时必须说明。

它还有两个和答错无关的问题：

- **读回机制浪费调用**：超过 50KB 的工具结果被截成 249 个字符，存成文件让模型自己去读。结果有 200 次调用花在 bash、read 和脚本读取上，涉及 64 题，占全部输入的 30%，比 Claude 还重。F01 一题就绕了 20 次，最后读到的还是别的产品。修法是不截断，改成工具端按字段返回或分页。
- **交付不把关**：隐私外露 29 题，四家最多。E07 第三轮只问投保人，它把整份客户画像都贴了出来，包括收入、资产、车辆和面访记录。另外 174 轮里有 57 轮以"需要我……吗？"结尾。修法是交付前做字段裁剪和脱敏。

**确定性**：
- 57/174 轮以反问结尾、本地读取调用的次数和占比，是程序统计的；
- A04、F04 对照原始 trace 核实过，其余例子没有逐题复核。
