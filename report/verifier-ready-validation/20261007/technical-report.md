# verifier-ready 审阅者探索性验证

最终正式模型：pi + DashScope `qwen3.8-flash`，现有百炼 Token Plan 北京端点，私有临时 pi 配置；全局配置未修改。官方模型 ID、工具调用和 1M 上下文支持已核对：[阿里模型页](https://help.aliyun.com/zh/model-studio/qwen3-8-flash)。公开按量价格不用于估算本次 Token Plan 的实际账单。

## 当前结论

五类明确构造问题两次均被识别，六个正常或修复后对照两次均无无依据的 high/blocking。但真实五条调用审阅给出的两条 blocking，独立复核均找到请求原文反证，现有理由不足以支持硬拦。最大不确定性已经验证为：**审阅者会把不清晰的约束或引用选择错误推断为任务必然无解，而规范不给 blocking 留争议处理通道。** 当前支持实施可观察的采集—审阅—回应流程，不支持直接将审阅者的 blocking 原样用于不可豁免的放行条件。

第一次用时 225.47 秒，17 次工具调用，输出 6 blocking、0 high、1 diagnostic；第二次 215.14 秒，9 次工具调用，输出 6 blocking、1 high、1 diagnostic。两次 JSON 均可解析、覆盖 C01–C12，临时任务目录内容哈希未变。此结果不能证明仓库或其他目录没有修改。

原预注册的“目标必须产生 finding”计数为 5/6、6/6。独立复核后的主要指标为 **五个明确问题两次 5/5，六个正常对照两次均零 high/blocking；一个重复装料升级目标有争议**。两次审阅使用同一组 12 个样本，不是 24 个独立样本，不能据此估算生产误报率。

五组明确问题的修复后对照未产生对应 finding。这些是构造修复，不能证明任何生产改动已经修好。

## 审阅输出本身的质量

- 第一次 summary 把分类数写反：写 7 个有问题、5 个成立；逐项正文及 findings 实际为 5 个有 finding、7 个无 finding。拟议程序的“可解析＋severity＋quote非空”检查会接受这一摘要。
- 两次都认为独立请求重供单条 dossier 合理，未机械执行“整份 dossier_view 再发一遍不行”。但“所有字段均最小必要”的表述过强。
- C08 第一次把重复视为去重能力的被测对象，第二次认为副本无必要。两种必要性推断均超出样本明确说明的目的，不能仅凭后者符合 Gold 就判后者正确。
- 缺证可以证明输出无依据，不能证明实际发生了跨调用泄漏。没有提供重试过程，也不能从错误反馈断言真的发生重试循环。

参见 `methodology-peer.md`。这些问题指向任务目的、严重级别与证据边界的明确化，不能直接归因底层模型缺陷。

## 历史原文审阅

范围固定为五条 llmtrace 全文（764097 bytes），两个 case，附账本及轴终态；不提供源码、历史诊断或完整案卷解引用，不宣称四例端到端验收。

会话完成，用时 **1154.32 秒（19分14秒）**，67 次只读工具调用、67 次助手模型消息，输出 **2 blocking、5 high、4 diagnostic**。访问了所有五份原文，通过只读 Python 提取请求、响应、共享正文、pending、期望覆盖和引用端点；这证明实际取证行为，不证明逐字符穷尽阅读或不存在漏判。最终 JSON、spawn_id、severity、非空引用和任务目录哈希检查均通过。

独立复核完成，关键结果如下（详见 `historical-peer.md`、确定性解引用证据 `historical-peer-checks.json`）：

- **F-01 的 blocking 理由不成立。** 审阅者说没有合法英文轴标识、只能输出 χ，但请求明确有 `dimension: tool_execution`，系统也没有强制输出希腊字母。轴映射及纠错提示不清晰可作为 high 候选；不能因此证明任务必然无解。
- **F-08 的 blocking 理由不成立。** 审阅者说没有实际输入的合法引用材料，但 dossier 交付三个 model_calls 记录，实际请求均有 system 消息；顶层 captured_tool_definitions 解引用后有 12 项工具 schema。通用出处规则与 μ 实际输入约束不互斥。未查验证器源码，不宣称任意引用都会通过。
- **F-05 的 κ 覆盖缺漏有直接证据。** 所选两次响应未核对 7 条期望，轴终态错误列出相同 ID；附带的其他轴因果归因尚未证明。
- F-03 的重复事实不等于不必要或无帮助；F-09 的笼统核对及当前调用覆盖不足可保留，但年龄、电话、可选追问的违约推断不足；F-11 缺少 reasoning 与 completion 包含关系契约，不能断言计量必然矛盾。其余候选未完成源码与全链路验证。

轴终态 failed 是真实事实，仍可被 U1 硬性检查拦截。两条语义 blocking 的反证不代表运行应放行，也不等于所有候选都无效。它们证明格式有效与使用只读工具都不能保证审阅结论准确。

额外发现一个确定的定位错误：F-05 的 call_id 带 `.txt` 后缀，不等于账本 ID，虽然旁边 call_note 自行写出了正确 ID。拟议程序的三项 finding 检查仍会接受它。不能从“格式有效”推导“所有引用准确”。

会话 usage 合计：未缓存输入 158987、输出 64768、缓存读取 4251392、totalTokens 4475147。累计 total 是多次模型请求之和，不能当作单次上下文长度，也不能用临时 registry 的 cost=0 推导免费。实际 Token Plan 账单未知。

## 已复现的机制问题

1. **验收 fixture 数字不一致。** 文档指定存档写的是 156 次调用、28 次重判。新 `llmtrace` 导出 schema 为 `llmtrace.calls/v1`、status complete、111 次；与旧统计的 call_id 集合完全一致。按本门“同 execution、同名非 ToolLoop stage 的额外 wire 次数”公式得到 24，旧统计另记录 19 次显式逻辑纠错，二者不能混用（wire 指标还包括 fallback 等重复尝试）。`:4` 原本即为 0 次网关调用、not_evaluable。应更正验收口径或明确另一个 fixture。
2. **git porcelain 不能做内容审计。** 临时仓库内，已是 M 的文件再次修改，前后 porcelain 完全相同，内容哈希不同。规范现有 scope_valid 检查会放过这类改动。
3. **同目录哈希不能证明结论不可篡改。** 仅改 review 会失配；同时改可写 meta 的 hash 后再次匹配。该机制可检测不一致，不能作为“实施者改不了结论”的保证。
4. **exit 0 不表示模型审阅成功。** 默认 anyrouter/claude-opus-5-5 在恢复所需 provider 适配器后仍 HTTP 400 停供，进程 exit 0，没有最终 JSON。审阅有效性须检查实际输出。

以上均有独立产物 `fixture-reconciliation.json`、`mechanics-results.json`、对应 runs/messages.json。没有修改 verifier、spec 或全局配置。

## 方法与执行边界

- Gold 由协调代理构造、独立 peer 复核，不是人工业务金标；同轮给全部配对样本可能存在配对推断。
- 材料、Gold 在正式审阅前冻结，执行后哈希一致；preregister 的模型选择按用户指示单独修订。
- pi 在新的证据目录启动，关闭会话保存、技能、项目上下文文件、扩展发现。与拟议仓库 cwd 的启动方式不同，尚未验证仓库上下文污染。
- 前面模型停供、未加载必要 transport adapter、OpenRouter/Max 的主动中断尝试均不计入评分。
- 运行时不新增 verifier LLM 角色，未实施 hook、live 采集或生产修复。

## 实施建议

先把完整采集、审阅与回应接成可观察的最小流程。实施前先明确 blocking 的证据阈值与反证裁决方式：不能把“某次输出被拒绝”直接升级为“任何合法输出都不可能”，也不能把“未找到材料”当成“材料未交付”。这需要调整当前 blocking 只能 fixed 的需求，不能靠要求实施者改掉正确代码来处理审阅错误。对于必要性无法从请求原文确认的重复材料，finding 应说明缺少的目的或约束，避免无依据升级。摘要计数从结构化 findings 生成。scope 审计应比较内容，结论哈希的保证应写为一致性；若需要防篡改，需要独立可信边界。校正 fixture 的可复算数字，再做全四例、大材料、正常运行与真实修复后的验证，才讨论硬性放行的可靠性。
