# verifier-ready 使用结论

pi + DashScope qwen3.8-flash 已在构造样本中显示出发现明显问题的能力。五类明确问题，两次都识别正确；六个正常或修复后对照，两次都没有被报成 high/blocking。

真实五条历史调用审阅给出两条 blocking，独立复核均找到原文反证：请求已经包含英文轴标识，却被说成没有；实际请求、系统消息和捕获的工具定义已经交付，却被说成缺失。因此，**当前最不确定的是审阅者能否准确区分“存在问题”与“任务必然无法完成”，以及如何处理错误的 blocking。** 规范要求 blocking 只能修复、不能争议，这会使审阅错误变成无从纠正的硬拦。真实轴终态失败仍可由 U1 检查拦截，这项复核不意味着运行应放行。

材料的必要性也存在歧义。重复账单两次都被看见，却一次认为是去重任务的合法输入，另一次报 high。样本未说明任务目的，不能只按预设答案把第一次算作漏报。真实 κ 期望覆盖缺漏则有直接证据，说明审阅仍能产出有用发现。

审阅输出也需要核对。一次摘要把有问题与无 finding 的样本数量写反，且附带出现“跨调用泄漏”“高成本”等超出明确证据的解释。这些结果仍满足拟议程序的格式检查。

这次试验支持最小采集—审阅—回应流程的实施。实施前应先补 blocking 的证据阈值及反证裁决方式。自动放行的可信度还需要真实正常样本、真实修复后重跑、大材料覆盖和严重级别校准；当前小样本不能给出生产误报率。

完整结果见 `technical-report.md`，历史候选裁决见 `historical-peer.md`。原始会话、独立复核意见和机制复现均保留，未改 verifier、需求文档或全局 pi 默认设置。

需求实施前另有三项确定的问题需要处理：指定历史 fixture 的调用数及重判口径不一致；git status 无法审计内容变化；同目录 hash 只能检查一致性，无法证明结论不可篡改。
