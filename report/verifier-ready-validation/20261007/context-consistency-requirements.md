# 整个 llmtrace 上下文的一致性验收要求

依据：用户在本次讨论中确认，核心目标是整个 llmtrace 实际上下文及其跨调用流转能自圆其说；结构约束是一部分，修改必须通过新运行验证。本文为交给实施者的需求补充，不代表门已经实现，也不代表现有运行已经通过。

## 1. 审查对象

审查指定 execution 范围内、经 llmtrace 完整导出的所有模型调用，以及这些调用实际形成的上下文流转关系。包括实际请求中的 system/messages、任务和判准、业务材料、历史、前序结果、工具定义、输出结构约束、错误反馈，以及同次响应被后续调用如何使用。只在记录确实包含相应内容时作出判断。

源码中的 prompt、内部 snapshot、预期配置和人工说明不能替代实际交付记录。响应本身不是先前请求的上下文；只有在后续实际交付时，才能说它进入后续上下文。没有捕获或导出缺失的部分记为不可核验。

不同调用可以承担不同任务，拥有不同范围、权限和判准；不同 case 不共享同一个业务事实身份。不能要求所有调用字面相同。需要解释的是差异是否有明确的任务、对象、阶段、条件、时点、版本或来源依据。

## 2. 核心问题

仅凭实际记录，能否解释清楚每一步要求什么、依据什么、允许得出什么，以及它与前后步骤为什么相容？不能靠模型猜符号、补规则、补材料或自行决定冲突来源的优先级，才能使任务成立。

审阅覆盖以下六类关系，而不只是 schema 字段：

| 类别 | 核验内容 |
|---|---|
| 概念与指代 | 同一名称、对象、ID 和符号是否保持含义；必须使用的术语是否已有解释；不同 ID 的映射是否明确。 |
| 任务与指令 | 全部适用要求能否同时满足；不同段落是否互相禁止；范围或优先级是否在实际上下文中讲清。 |
| 任务与材料 | 要求的判断是否有材料、可用取证路径及表达位置；只有材料目录或编号时不能当成已有正文。 |
| 结构与语义 | 字段、枚举、空值、覆盖、分组、引用与条件规则是否一致；完成语义要求是否会违反结构限制。 |
| 来源与事实 | 对象、单位、时点、版本、否定和不确定性是否保留；来源间的差异是否如实呈现；业务材料存在矛盾不等于必须删掉矛盾。 |
| 跨调用流转 | 上游材料、结果和规则被下游使用时是否变义、丢条件、换对象；推测是否变成事实，采集时定义是否变成当次已收到的规则；重试是否改变任务或偷偷增加门槛。 |

重复材料本身不是不一致。独立调用重供必要证据可以成立。裁剪后缺少规则的适用条件、把两个不同版本拼成一个事实，才是需要定位的一致性问题。

## 3. 证据与裁决

每个候选问题记录具体关系：call_id、请求或响应、消息/块位置、两端原文、共同对象与适用范围、不能同时成立的原因。缺少定义或材料的问题记录要求端、实际交付范围及缺口。摘引之后仍须检查邻近说明、来源差异和反证，不能因关键词不同直接判冲突。

裁决为：

- 已确认不一致：两端确实适用于同一范围，没有已交付的解释，存在具体冲突、变义或无法同时满足的要求。
- 已解释差异：范围、版本、来源或任务变化能够解释；记录解释和依据。
- 未决：材料不完整或含义无法确认；写出还缺什么，不能计为通过，也不能直接断言任务必然无解。

“某次输出被拒绝”不能单独证明上下文有矛盾；“审阅者没找到”不能单独证明材料未交付。一致性通过也不证明业务结论正确：一套错误规则仍可能内部自洽。

## 4. 指标与通过条件

不使用单个加权总分。报告至少包含：

1. 调用覆盖：指定范围总调用数、全文审查数、部分审查数、不可核验数及对应 ID。只打开文件或读取摘要不能记为全文审查。
2. 关系覆盖：每次调用上述六类检查的记录，以及已识别的上下游关系检查记录；不适用必须有理由。关系数只是可追溯清单，不宣称枚举了所有可能的语义关系。
3. 已确认不一致数：逐项可定位，不用大量正常项抵消一个冲突。
4. 未决项数：区分关键任务/结构/证据关系与其他问题，并列出缺口。

一致性验收通过需要：指定范围导出完整，调用及适用关系审查无遗漏，已确认不一致为零，关键关系未决项为零。非关键未决项保留披露和理由。审阅覆盖不完整时不能声称“整个 llmtrace 上下文一致”。该结论是本次范围内的有证据验收，不是不存在任何语义矛盾的数学证明。

## 5. 修复验收

不能以“改了 prompt”“删了符号”“测试通过”关闭问题。每项修复必须：

1. 重新运行原失败场景，获得新的完整 llmtrace，保留原记录。
2. 在新记录中定位对应两端，说明原不一致怎样消除；缺口类问题证明所需内容已经实际交付。
3. 检查变化影响的后续调用，确认未通过删掉任务或材料掩盖问题，也没有把不一致转移到下一阶段。
4. 验证至少一个邻近正常场景，保留正常的范围差异和必要材料。
5. 在冻结测试材料中制造一次明确冲突，证明一致性检查能定位；不得改写历史证据或线上业务材料来造样本。

验收结果绑定新运行和实际导出材料。前后对照、未决项以及审阅反证均保留；审阅自身的误判也允许通过证据复核纠正。

## 6. 对现有 verifier-ready 方案的调整点

- 将一致性作为核心验收目标；耗时和业务准确性保持各自结论，不能替代它。
- §4.3 的必读清单可用于安排顺序，不能用“其他调用按需打开”支持整个 trace 一致的结论。
- §5.4 从零散调用清单扩大为上述完整上下文与跨调用关系检查，移除对跨调用重供 dossier 的一概禁止。
- §5.5 记录覆盖、关系证据、已解释差异和未决项，不能只收 severity 与非空 quote。
- §6–7 增加基于原文反证的审阅纠错裁决；证据充分的冲突必须修复，审阅错误不能迫使实施者改掉本来成立的内容。
- §12 必须验收新 llmtrace 中的修复闭环，而不只是 finding 命中或文件已经修改。

本补充不要求新增在线治理 LLM，不建设通用治理平台。先在现有 llm_probe 真实流程上完成一轮可复核的最小闭环。
