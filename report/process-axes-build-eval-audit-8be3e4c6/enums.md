# 六轴枚举盘点：先验证区分能力，再确定候选协议

状态：只读分析与候选设计，未修改实现、未冻结新枚举、未启动模型评测。
依据：build-eval / eval-audit 的成功标准明确性、分类定义、错误分离、原子检查与评分器一致性。

## 1. 当前不是一套枚举，而是三层

|层|当前值|实际回答的问题|
|---|---|---|
|评判运行 status|disabled / blocked / not_applicable / succeeded / failed|评判器这次有没有执行并产出可用报告|
|具体义务 outcome|pass / fail / insufficient_evidence / not_applicable / contract_missing|某个环节的某条义务有没有做到，或为何不能判|
|整个轴 verdict|sound / problematic / not_evaluable / not_applicable|将整轴多条结果压成一个概览值|

来源：`impl/projects/llm_probe/eval_axes/types.py`、`adapters/process_common.py`。
`failed` 是评判运行失败；`fail` 是对被测环节的判断，不能混为一种失败。
同一个英文 `not_applicable` 还出现在运行、义务、轴三个层次，展示时需要明确其主体与范围。

已有明细还保存 expected、observed、source_refs、输入/输出证据、missing、flags；轴汇总保存 contract_missing 清单与 scope_note。不能说系统完全没有这些信息；问题包括定义重载、汇总压缩和消费端只用摘要。

## 2. 当前汇总函数的实测

直接调用当前 `aggregate_verdict`，不调用模型：

|明细组成|轴级输出|被概览值遮住的差异|
|---|---|---|
|pass|sound|—|
|pass + contract_missing|sound|仍有义务缺少判准|
|fail|problematic|—|
|fail + insufficient_evidence|problematic|已经发现问题，但仍有部分判断未完成|
|not_applicable|not_applicable|—|
|not_applicable + contract_missing|not_applicable|并不是所有义务都已证实不适用|
|只有 contract_missing|not_evaluable|缺判断规则，不是缺业务事实|
|只有 insufficient_evidence|not_evaluable|缺判断所需的事实|
|空结果|not_evaluable|没有结果，不等于已识别了证据缺口；此行为为函数探针，不声称存在相同实跑案例|

算法选择 fail 优先有合理性：不能用缺证冲掉已经发现的偏差。问题是输出一个主值后，没有同时显著表达剩余判定的状态。
排除 contract_missing 后对可评部分给 sound 也可以是一种有意设计；但公开描述是“适用义务都做到了，且有正面证据”，容易被读成完整背书。需要统一范围、名称和展示，而不是不看语境就改聚合算法。

## 4. 主要问题及所属层次

### E1｜一个 verdict 同时承载多种问题

“目标是否实现”“本环节是否违反义务”“证据/判准是否足够”“问题是否定位”不是同一个问题。
用户已明确要求：没取得所需数据的事实要记，是否数据源自身出错也要区分，不能二选一。

当前 `data_per_subquestion` 的 fail 既可记录查询未执行导致数据未取得，也可记录源数据确实缺失；若把整个 problematic 都解释成“该组件自身有缺陷”，就发生语义重载。
不能只新增一个 upstream_failure 单选值：同一案例可能同时受到上游影响且本环节也独立违约。

### E2｜事实已知，不代表原因已知

R39 的“数据没取得”与“尚不能排除适配问题”能够同时成立。不能为了表达原因未知，把已确认的未取得改成缺证；也不能因为已经 fail，就把局部责任或精确根因说成已确认。
这需要保留定位范围，而不是让 fail 负责表达所有确定性。

### E3｜缺事实、缺判准、评判失败不应合并

明细五值已区分前两者，轴级 not_evaluable 又将其合并。当前 Agno 的 salvage 还会把输出不合规/没回答补成 insufficient_evidence；llmtracing 新 loop 的运行失败处理不同。
这是部分汇总问题、部分执行分类问题，不是给 not_evaluable 换个名字就能解决。

### E4｜轴内允许多种状态同时存在

problematic 与“还有未判事项”并不冲突；sound 与“只覆盖有判准部分”也可能是当前有意语义。
如果一味扩充平面枚举，会出现正常但缺判准、有问题但缺证、有问题且两者都缺等组合膨胀。
更应保留明细组成和检查范围，再决定轴级展示形式。

### E5｜不适用不等于没做到，也不等于看不见

- 明确没有模型调用：模型义务未发生。
- 没发本该需要的查询：数据源没有执行实例，但系统的工作覆盖可能没做到。
- 取不到模型调用记录：不可见，不能据此认定没有模型调用。
- 某种附加约束没有出现：该条约束义务不适用，不代表整轴或整轮未发生。

新定义必须要求说明“什么对什么不适用”，不能把这些状态混作一个“无问题”。

### E6｜现象类别不应全部变成通用 verdict

TIMEOUT、EMPTY、字段映射错误、违规重试、历史未注入属于事实或情况类别；同一种现象在不同业务期望下可能合规、违规或尚不能判。
例如业务预期就是空结果时，EMPTY 不应自动意味着没满足任务。六轴共用的履责判定与各轴具体情形分类应分别定义。

### E7｜消费端的聚类单位比底层明细粗

`core/axes_clustering.build_material` 对 verdict_scope=axis 的六轴优先使用轴 summary.text；只有 text 为空才将 items.reason 拼接。底层已有的各项 outcome 不成为独立聚类成员。
因此还存在“明细其实有差异，聚类输入却是一整段轴 reason”的信息粒度问题。只加轴级枚举不能恢复被摘要合并的多个独立事项。

## 5. 候选设计方向（尚未定稿）

不要求保留现有四值，也不预设要为每轴发明完全不同的一套 verdict。先区分以下职责：

1. **运行状态**继续只表达评判器是否完成；发生失败时不伪装成业务证据不足。
2. **具体事项的结果事实**表达业务关注的产出是否取得、如何取得。例如知识轴要保留“所需数据已给出/部分未给出/未取得/尚不能确认”的事实，并结合业务期望判断其含义。空结果这一现象本身不直接决定符合与否。
3. **具体环节的履责判定**表达适用义务做到/没做到/缺证/缺判准/不适用。当前五值覆盖了相当部分需求，先校正定义和作用范围，不为凑细粒度随意加值。
4. **定位与限制**保留偏差落在哪个环节、上游影响有何证据、边界未知在哪里。局部职责可已判明而更深内部根因仍未知；二者不要混成一个置信标签。
5. **轴级输出**汇总实际组成，例如“已发现偏差；另有缺证项”“已核实范围未发现偏差；仍有判准缺口”。不必为每个组合定义一个新的枚举。

这不是立即确定五个新字段；1、3及部分4当前已经存在。需要先用下面的对照确认业务必须保留的区分，再选择最少的协议表达。

## 6. 按 build-eval 验证候选枚举的最小对照

先审核输入与预期区别，不启动付费实验。已有原判词只是材料，不自动作为新枚举的 gold。

|对照|必须保留的区分|不应得到的结论|
|---|---|---|
|上游没发查询 vs 源端确实缺少应有数据|两者都记录数据未取得，但本地履责与定位不同|两者统一解释为数据源自身错误|
|正常空结果 vs 应有数据却为空|返回形态相同，业务期望不同|看到 EMPTY 就统一 fail|
|已确认偏差且原因未知 vs 连偏差是否发生都未知|事实判断与定位程度分开|前者被抹成缺证，或后者被硬判偏差|
|pass vs pass+缺判准|已核实部分可以相同，完整性不同|都被解释为全部事项已通过|
|fail vs fail+缺证|已发现问题保留，未判部分仍可见|因为缺证抹掉fail，或因为fail忽略剩余缺证|
|缺事实 vs 缺规则 vs 评判器输出失败|补证、补规则、修评判器是三种不同动作|一概 not_evaluable / insufficient_evidence|
|未发生 vs 无法观察|不适用需要正面依据|无记录自动推断未发生|
|一个案例同时上游受阻与本环节违约|两种事实能同时表达|强迫单一归责或用一种状态覆盖另一种|

验收不是“新值更多/更好看”，而是：人在相同证据与规则下能稳定区分；合理等价表述不改变判断；合规与偏差都覆盖；未知不冒充正常；一个字段的确定性不能传播成另一个字段的确定性。

当前尚未批准这些候选值及逐例预期为最终协议。后续应先展示少量真实案例的旧输出与候选输出，由用户核对是否准确表达其业务含义，再决定字段与枚举定义。
