# 过程六轴与近期优化：build-eval 审计

## 结论

**已经具有辅助人工发现业务问题、定位证据与调查链路的价值；尚无足够证据把它当成稳定、已校准、能自动验收优化的评测器。**

工程可运行性、证据可见性、业务判定正确性、归因正确性、聚类完整性必须分别评价。测试通过、轴 verdict 有变化、缺证减少、聚类数减少、重叠降低，都不能单独证明语义质量改善。

本审计依据 `build-eval.md` / `eval-audit.md` 的任务、执行器、指标、评分器与统计分辨率要求，检查现有代码及已保存结果。没有新模型请求、业务运行、服务重启或实现修改；仅运行本地测试、读取证据并生成本文。没有计算新的总体准确率，也没有把助理审查意见认定为专家 gold。

## 1. 三个对象，不能混成一个成绩

|对象|真实输入与输出|应评价的目标|
|---|---|---|
|过程六轴判定|业务轨迹、当次规则、可见证据 → 环节×义务判断、理由与引用|检出真实偏差、不误报正常行为、正确归位、证据与判准使用成立|
|问题聚类|冻结的六轴 reason、原枚举、案例 → 语义目录|入类正确、独立情况不漏、共同描述适用于成员、不抹掉不确定性|
|试验台/执行器|配置、请求、工具、hooks → 可观察且可恢复的运行|能交付、预算正确、故障分类、尝试记账、状态与产物保真|

单次聚类并没有重新评测业务轨迹，不能从聚类页面的质量反推当前六轴判得更准或更差。也不能把被测业务系统的 fail 数当作 verifier 自身的错误率。

## 3. 六轴目前分别做到哪里

以下是能力和风险观察，不是按轴打分或排名。

|轴|已有价值|应优先验证的边界|
|---|---|---|
|意图理解|能检查对象、字段、子问题、限制与跨轮指代；已有 gate 将复合任务压成单一查询的发现|当前 `ι:<turn>` 输出仍包含首个步骤和首次模型决策。要分清表达环节未消解、上游没给历史、下游模型合理澄清；不能只因为澄清就判理解错误|
|规划路由|能检查覆盖、依赖顺序、停止、已有事实整合以及策略行为|D 的旧基线把一般“超时可重试”覆盖当次禁止规则；允许、建议、必须、禁止不可互换。同一个行为是否违规取决于当次契约|
|工具执行|能检查超时、对象错配、适配层误报及按契约拒绝；当前正常返回义务已排除执行错误外壳|要区分系统策略拒绝、真实执行错误、业务空结果。HTTP 200 或可解析 JSON 不能证明工具语义正确；没有调用适用时限不能借整轮时限判定|
|知识数据|能按子问题发现未取得、缺字段、未召回、对象不匹配|当前代码同时承担“所需数据未取得”与“数据源责任判断”。与数学文档中“已正确执行的查询→数据存在性”不同，见下一节；这先是判准问题|
|模型能力|按逐次实际输入评忠实、决策、输出契约，方向合理；能发现部分编造与格式违约|B/C 把受语义限制的字段值直接解释为确定结论却获 pass，且重复出现。需要检查值能否支持该业务推断，不只检查有没有抄对；格式 fail 也不能掩盖事实类漏报|
|上下文管理|已能关注历史注入、缓存、桥接和最终交付，比只看输入相关性更有价值|必须核对正确的两端及证据角色。旧 llmtracing 用工具请求或单侧模型收到的消息证明工具产出传递无损，仍有错误；API 实收不能冒充实际 UI 展示|

已读的历史裁定与人工核验支持“系统可以发现真问题”，但并未形成逐轴 precision/recall、误报率和拒判合理性的可靠总体估计。

## 4. 优先问题：会使评价结论误导的事项

### A. 判准尚未统一，不能用规则改动伪装准确率提升

当前可核对的差异：
- `spec/math-abstract/process-axes.md` §3：σ 是“已正确执行的查询 → 数据是否存在”。
- `knowledge_data.py`：所需查询未执行、数据未取得仍 fail，写“查询未执行”；`links._turn_links` 也仍按整轮组织 σ。
- 历史 9/24 裁定本就使用了较宽的数据供给视角。因此不是简单宣判某一份必然正确，而是两种目标必须明确选定。
- 数学文档 §5–6 允许各环节按独立义务同时出错；10/01 待确认方案又提出只在第一次出错环节记 fail，并用降重复、降低 new:N 等作为验收。
- 10/01 方案将中间轮 content 一概排除的方向也需谨慎：应按真实输出要求的作用范围判断，不能免除真实存在的中间轮参数语法或明确禁止事项。

建议：先锁定当前业务判准及例外边界，之后所有版本按同一口径比较。少报某轴、少报一个义务或改变标签，不是天然的质量收益。

### B. 原始六轴存在“评判器未正常交卷”与“证据不足”混用

当前 Agno `process_common.run_process_axis` 的 `ask(strict=False)` 会在结构化输出阻断后调用 `salvage(None, pending)`；未回答单元被补成 insufficient_evidence，轴可能成为 not_evaluable，详情放在 repaired。

`tests/test_process_axes_facts.py` 明确测试了：
- `test_protocol_layer_block_degrades_to_missing_evidence`
- `test_garbage_second_attempt_degrades_to_missing_evidence`

本次两项及相关回归通过，说明这是实际实现行为，而非猜测。这里不是说 API 故障都被吞掉，而是指出结构输出/解析失败的特定分支。

建议：外部质量评测至少将这些记录单列为评判器失败，不与真实业务证据缺失混算。已有合法结论的保留和整组无法解析的失败也应区别，不能笼统以“缺证率降低”当作优化目标。llmtracing 新 loop 的失败路径已有不同处理，不能把两条路线混报。

### C. 聚类的机械校验不是语义评分器

最新结果的已核实例子：
- model/problematic 的 19 条 reason 恰好各入一个类。重复失败来源类仅 R54，但 R5/R89 也有明确同参违规重试；终答契约类遗漏 R5/R26/R54/R61 的独立格式违约。
- R5/R12 的参数 JSON 语法错误没有清楚呈现。
- R165 原文含 turn1–turn3，却归到“单轮明确提问”。
- R39 保留“无法完全排除工具适配问题、原因未定位”，目录却概括为“数据源中确无该保单记录”。
- “适配、解析与归一层缺陷”把字段误报、条件解析未执行、错对象召回、桥接归一组合成一个宽类，其第一句并不适用于所有成员。

**本次实际负对照，零模型调用：**将该产物的每个轴×标签内所有类合并成一个“本标签下所有情况”，保留真实引用和摘录；40 类变为 15 类，不再区分现象。`validate_submission` 和 `OverlapGuard(threshold=.5)` 仍全部通过。

这不是模型实际进行了这种投机，而是证明该校验组合不能识别这种明显失去区分度的输出。降低重叠率既能通过合理组织实现，也能通过丢掉独立情况或揉成大桶实现。

建议：重叠率只作为目录诊断项/实验约束，不作为主质量指标。质量需核对“成员—独立现象”覆盖、入类支持性、共同说明适用性与不确定性保持。不直接断言当前遗漏由 Hook 造成：前后同时换了模型且没有同条件消融对照。

### D. 执行预算与性能解释仍有问题

- 工具预算 24→30 解决的是已有提交被第25次工具调用拦截，不证明语义更好。
- Qwen 历史运行 `88ae5a4d…`：聚类请求两次各1200秒，总约40分钟；客户端每次尝试重新设置 wall_deadline，外层循环只在边界检查，不能把1200秒描述成严格整案上限。
- 当前 `_run_agent` 单次时限是真实保护，但无法单靠边界检查保证取消后底层流已关闭；之前本地复现观察到重试与未停止流重叠的风险。
- 请求尝试有记录是优点；失败/取消流不一定有最终 usage，不能把未知费用记为零。
- 最新配置为 deepseek-flash 的聚类约278.7秒成功，只是本轮性能观测，不能推断所有任务都能这样完成或优于其他模型。

建议：质量、整案完成率、成功请求耗时、总墙钟、全部尝试消耗分栏。超时、配额、结构错误、语义错误分别记录。

### E. 外部审查与数据还不足以支撑发布结论

- A–E 已有输入确认与暂定评分，比只看 accepted 更接近 build-eval；但5条相关轨迹、3类问法不足以形成总体成绩。
- 既有业务集集中于保险查询及这些环境下的故障，不能直接代表所有业务项目。
- 已反复查看的案例不能伪装为 held-out；相近轨迹按独立 case 切分仍可能泄漏。
- 本助理之前也曾读错聚类标题字段、类数、未充分核对 R63 全文，并把共现误当语义重复。此类审查文本只能作为待核验材料，不能自动成为 gold。
- 当前没有足够证据说明已有外部评分器通过完整 oracle/null/全部fail/全部缺证/错误引用等验收；不能将工程测试数量代替它。

## 5. 对一系列优化的评价

|优化|可以承认的收益|尚不能声称的收益|
|---|---|---|
|环节×义务×出处、按实际输入判模型|把归属和判据显式化，便于逐项追查|六轴已经准确、边界已经统一|
|精确模型输入/工具定义、证据角色与读取回执|减少“材料不存在却判了”的工程可能性，能定位读了什么|编号合法或读过就说明论证成立|
|Agno 完整材料交付及按完整环节分组|当前代码和测试支持不裁掉必要端点、不混用别次输入|最新实现已在完整历史集上证明召回/精度提升|
|同会话拒绝与修正、核心完成检查|真实与脚本记录均有引用或格式错误获反馈后修正的实例|框架接入使字段语义误判自动消失；v2/B 的 G3 仍漏报|
|fail 不被程序抹掉|保持诊断可见性，避免机械后处理掩盖偏差|所有保留下来的 fail 都正确|
|快照、运行身份、前端理由、持久化与进度|可观察、可复核，减少重跑和来源混淆|单例判断或聚类本身更准|
|逐成员连续原文摘录|能阻止假引用，并降低人工核对成本|摘录支持该标题、共同情况或因果解释|
|重叠 Hook|约束集合重叠并反馈具体类对，接线已验证|语义边界更正确；已发现信息遗漏与宽类合并风险|

|更换模型与提高时限|得到若干不同性能和输出实例|单独归因某项 prompt/hook 收益，或证明新模型更好|

## 6. 下一步建议：沿用现有材料，先让评价可信

不新增多代理流水线，不凭固定类别数、重叠阈值、fail数量优化。

1. **先把六轴业务口径确认清楚**：尤其知识轴的供给结果与源头责任、跨轴独立义务、中间轮规则范围。不要直接把10/01待确认方案的计数目标当成 gold。
2. **复用 A–E 暂定校准**：逐项核对判定、论证、契约使用；正常项和应保留项同样重要。扩展输入与评分方法仍需两次明确确认，旧审批不自动覆盖新用途或数据外发。
3. **以原子事项评分，而不是只看整轴标签**：问题精确率/召回、正常行为误报、证据支持、归属正确、适当与不当拒判分开记录。不求一个混合总分。按业务轨迹汇总与估计区间，同一事实跨轴出现不增加独立样本量。
4. **给外部评分补负对照**：正确报告、空报告、全fail、全缺证、合法编号但错误证据角色；聚类另测一大桶、乱配成员、真实摘录但错误标题、删掉次要独立情况。不能只是让检查函数接受/拒绝预置字段。
5. **一次只比较一个变更**：冻结业务运行、完整原始输入、规则与模型设置；六轴看同版本前后，聚类单独看相同 reason 下摘录/Hook 的变更。相同条件重复，不把模型、规则、采集与prompt同时改变的结果归因到单个优化。
6. **先展示少量试评分供确认，再申请付费复测**。不假设当前已读样本是未见集，不为小幅变化编造统计显著性，不因缺证减少就宣布成功。

当前最合理的使用方式仍是“可追证据的辅助审查”，不是无人值守地根据六轴标签或聚类目录作发布/业务归责决定。
