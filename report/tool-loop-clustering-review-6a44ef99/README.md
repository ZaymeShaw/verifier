## 优先修正的具体问题

### 1. 模型能力：“工具选择错误（清单场景误用客户搜索）”与成员不符

成员为 R5/#24、R33/#28、R54/#31。

- R54 明确说误调的是普通 `policy_search`，应使用 `present_policy_search_card`；不是误用 `customer_search`。
- R33 的需求是保单累计已交保费，不应一概叫作“纯清单场景”。
- 共同说明写成“未调用卡片或 policy_search，反而调用 customer_search”，与 R54 直接矛盾；“传入不支持的保单号字段”也只是部分成员的特点。

可以保留较宽的“未遵循保单查询入口选择规则”，但必须说明两种不同偏差；如果第三层要求可直接定位的共同情况，应分别归纳“保单需求误走客户搜索”和“清单需求未走卡片入口”。R5 同时涉及两种约束，允许有证据地多归属。

### 2. 意图理解：“单一明确查询原义保留”错误地宣称无约束

该类说明写“无约束、指代或歧义情形”。然而：

- R17/#26 明确说保留了业务客户号条件与当前核对范围约束。
- R52/#31 明确说保留了“先列清单”的范围约束。
- R59/#33 明确说保留了对象、字段、子问题与约束条件。
- R66/#34 明确说保留了查找对应投保人客户资料的前置限定约束，而且是复合需求。

这些成员与“无约束”这一共同描述不符，也与相邻“带约束/复合诉求完整保留”的边界重叠。应统一两类边界后重分，而非仅美化标题。

### 3. 上下文管理：“历史未注入”基本成立，但“全都被迫澄清”不成立

“多轮追问时历史上下文未注入模型输入致指代断裂”包含 R157/#52。

- R157 的缺失是上一轮查询关注点未进入第二轮输入。
- 同案例 R158 明确记录第二轮已有新保单号，`policy_detail.fields` 为空；R160 更明确说实际发起 `policy_detail`、获取数据后作答，**没有多余重复或澄清**。
- 因而不能把所有成员共同概括成“缺少实体，被迫发起澄清”。有些是实体丢失，有些是字段/任务继承丢失。

建议共同描述为“历史实体或任务关注点未传入，导致后续追问缺失必要上下文”，澄清仅作为部分案例的后果。

### 4. 模型能力：“其他工具决策违规”是杂项桶，不是共同情况

R61/#33 是未经确认的保单号准入；R96/#38 是歧义后删减条件扩大查询范围；R119/#45 是实体明确时仍多余澄清。

原排序理由自己写了“各仅单案例、情形各异，归为一类”。它们仅共享“tool_decision 有 fail”，没有给出更具体的共同机制。应分别保留可理解的情况类别；不能因为都是单例，就把不同情况合并来凑目录。

### 5. 编排：“同参重试未拦截且失败结果被缓存吞掉”说明覆盖过头

成员 R6/#24、R55/#31、R90/#37。

- R6、R55 明确支持失败缓存与重试短路。
- R90 的这段 reason 只明确支持同参重试未拦截，没有提供被缓存吞掉或桥接覆盖缺口的证据。
- 原文 R90 还先称“不可重试失败”，后又说返回“可稍后重试一次”、未声明不可重试。这个输入内部的口径问题应保留为待核查，聚类不应将其抹平成同一确定机制。

建议保留共同点“同参重试控制不当”，将缓存短路与桥接覆盖写成有对应成员的子现象，而不是共同断言。

### 6. 服务错误不能自动升级为同一个已定位根因

工具轴和知识轴的大类把 TIMEOUT、OVERLOADED、UPSTREAM 放在一起，作为“后端调用失败/所需数据未取得”的现象级类别可以成立。

但以下延伸不成立：

- 知识轴排序说明称“同一后端稳定性根因”；R4 明确注明原始下游报文缺失、适配层与后端边界原因未定位。共同错误表现不等于相同根因已证实。
- 知识轴说明称“服务始终未恢复”；部分后续调用未真正发到后端，只命中失败缓存，不能据此证明服务一直没有恢复。
- 模型重复调用类排序理由称“放大后端压力”；被缓存拦截的调用没有发出后端请求，不能直接这么概括。

应描述实际观测到的失败、取数缺口与缓存行为，保留原因未定位的范围。

### 7. EMPTY 类推测用户输错保单号，证据不足

“保单号对象在数据源中不存在（EMPTY）”的成员确实均返回 EMPTY，分在同一现象类有依据。

但排序理由“更可能是用户侧保单号有误而非系统缺陷”没有对应证据。尤其 R39 已明确保留工具适配问题未排除的边界。建议标题采用“保单查询返回 EMPTY，具体原因存在未定位情况”，不把提示用户核对号码等同于确认用户输入错误。

### 8. 过程案卷轴的两类是计数分桶，不是实际情况语义聚类

“高可疑密度单轮案卷”和“常规单轮案卷”分别按可疑环节数 `≥10`、`<10` 划分：

- 这是模型自行引入的阈值，用户标准没有规定它。
- 用的是数量，不是密度；标题不准确。
- 案卷摘要主要给出记录数、调用数、环节数，单凭这些数不能推出问题链路相近、业务情况同质或阅读价值更高。
- 该轴可以保留“多轮”“无模型调用”等结构性目录，但需要明确它是案卷结构分类，不应伪装成业务现象的语义分类。

## 44 类逐类意见

“基本成立”指在已有 reason 层面有共同点和成员依据，不表示原业务裁决正确，也不表示粒度唯一最优。

## 为什么结构验收没拦住

当前结构包含类名、共同情况、排序理由、member_refs，程序会核对引用、覆盖与归属，但不验证：

1. 每个成员的哪一段原文支持这个类别；
2. 共同说明中的哪些命题由全部成员支持、哪些仅属于部分成员；
3. 相邻类别是否使用一致的划分边界；
4. 是否把现象升级成未经定位的共同根因；
5. 是否拿数量代替用户关心的影响与证据；
6. 一个复合 reason 已经被引用，是否仍有其中的其他独立情况被遗漏。

因此，本次 `accepted=true` 不能解释为语义审查通过。

## 建议方向（未实施）

- 先修明确反例，不通过改枚举、改原 reason 或放宽标准来让现有类别“显得正确”。
- 每个成员给出对应的原文证据片段或位置，说明它属于本类的具体情况；原始 reason 仍完整保留供核对。
- 明确共同点与部分案例的变体，不能把变体升级为全类断言。
- 用相邻类反例检查边界；单例可以单列，不设固定类别数，不以“其他”代替共同情况。
- 增加语义审阅环节，允许驳回、拆分、合并或改名；LLM 审阅也只是另一道检查，不是正确性保证。
