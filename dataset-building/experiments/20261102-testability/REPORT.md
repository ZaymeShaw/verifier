# 聚类采样流水线：当前环境适用性试验

已完成固定 28 题的配对探索：A 先按题意与工具清单筛选，冻结后 B 做真实只读取证并检查内容。七类各 4 题，来自人工对照保留池 1061 题。未运行被测 agent、未构造 gold、未改正式流水线。

## 最影响方案的发现

1. **“有返回”不够。** #25 问代理合同，召回保险产品合同；#27 问具体权益，只有本人使用一句；#23 问代际年份，却只有服务项。若以非空判定，这些都会放行。
2. **“返回错误”也不能淘汰。** #14 二次解析 HTTP 成功并返回条件，但工具校验报错，未请求客户数据接口。未知的是接口衔接，不是该客户集合存在与否。
3. **名称近似匹配会污染筛题。** #12 原题平安福被解析为全称/简称包含平安福，首页出现平安福满分。这是应保留的疑似系统缺陷；因源筛选字段与展示产品字段不同，尚不宣称已证明底层查询错误。
4. **有数据但欠可核对字段。** #9/#15 的返回页不带年龄性别/周年日等关键条件字段；#11 源请求确实按缴费日期过滤，但输出页未提供同一源字段。不能拿返回条数证明条件正确，也不该据此认定整个题目不可做。
5. **相同产品不代表回答依据完整。** #6 两次均命中正确产品，但免赔额指向缺失附录，案例中的某计划数值不能覆盖所有计划。
6. **环境元数据没有沿采样线传下来。** export_questions.py 只导出 id/source/scenario/turns；本轮从源题库补回后发现 28 条都是 env.data=none，源身份与当前账号不同。原始时间也未送入探查，#11 原始 HTTP 显示使用服务当前时间。源元数据不是当前事实，但必须保留来明确重绑定。

## 现在建议怎么继续

用“两道筛选”替代一次二元判断：先检查题意及环境前提；再对候选做必要证据探查，分别记录资源可得性与实际可验证范围。只把已确认的环境缺口移出主候选池；工具错误保留到问题池，检索不足留待确认。
这轮已经留下四个独立集合：ready-candidates.jsonl（2）、scoped-candidates.jsonl（11）、retain-problems.jsonl（2）、pending.jsonl（13）。限定范围集合不作为完整业务任务的通过样本。它们都是实验候选，不覆盖正式样本表。
下一轮优先在人审时对照这 28 条明确“本次验证到底接受哪些范围”：尤其是清单首页、澄清、空结果是否单独计数。随后使用新抽样、冻结规则复验。先不全量自动淘汰，避免把本轮未确认的难题当成环境不支持。

## 执行与局限

首轮 29 次只读工具调用，累计单次耗时之和 96.78 秒（并发执行，非墙钟时间）；二阶段 4 次定向重复，原结果未覆盖。首轮状态：{'PARTIAL': 20, 'EMPTY': 7, 'AMBIGUOUS': 1, 'ERROR': 1}。
初始沙箱两次失败单独保存在 sandbox-smoke，不计入实验。用户明确授权目的地和全部题目后完成联网探查。未进行业务写操作；解析接口里的 user_action=write 是现有查询适配器的协议字段，不是本实验发起业务写入。
环境：dev、账号1050900009、认证主体pi。读现有MCP工具封装，二阶段仅记录既有HTTP请求/响应，无请求改写。开放话术及核保等FAQ文本不被当作权威事实；本报告只评估资料可得性，不输出保险业务答案。
同一主代理先A后B判读，非盲评。样本等额分层，不估算全库通过率。部分题只探查必要前提，未完整执行多步任务；后续补查可能改变判断。
回退：删除本实验目录即可移除全部产物；原始题库、聚类/采样/过滤与业务代码不变。已发生只读调用的成本不可撤销。
