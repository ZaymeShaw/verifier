# 基于任务需求与信息源供给的不可测排除

状态：2026-11-04，按信息源职责及评估者缺失的信息源组合组织判断。需求前提已明确，判定方法仍待验证。

## 目标与范围

在评测集构建中，优先标记有明确依据确认无法在指定环境中完成原任务的题目。其余保留为不确定，随着取得更多信息继续筛选。

本阶段要回答：**是否存在一项完成原任务所必需的信息，已确认在负责提供它的信息源中不存在？** 已明确的系统权限或操作限制，也可以构成必要需求的阻断。

过滤后的集合是“尚未排除的候选集”，不是“已确认可测集”。不要求先解题、生成 gold 或运行 verifier。

## 需求侧：原任务必须具备什么

从 query 及完整对话识别完成原任务不可缺少的信息、上下文或操作能力。例如，客户保单检视需要定位客户并取得相应保单资料；产品条款问答需要对应产品及版本的条款信息。

必要性针对原任务，不针对标注者选定的解法。“需要知道等待期”是一项需求，“必须调用某个检索工具”通常不是。若已知事实可以推导出所需信息，不能仅因没有现成字段或同名文档就认定信息缺失。

缺参数、表达简略或没有唯一答案不自动构成不可测。原目标是澄清、空结果处理或开放生成时，按该目标判断；也不能把完整保单检视改成“查不到时解释原因”，再把较弱目标当作原任务。

## 供给侧：信息源及其职责

一次评估中，系统供给总范围固定。预先声明有哪些信息源、每个信息源负责哪类信息，以及适用的身份、权限、版本或时点。信息源不限于知识库，也可以是业务数据库、对话记录、附件集合或其他提供信息的资源。

**每类信息的归属预先明确，负责的信息源就是这类信息在当前环境中的完整供给边界。确认其中没有必要信息，即可认定当前环境无法提供该信息，不再逐题假设还有未声明的其他来源。**

例如，A 负责客户身份及家庭资料，B 负责保单及缴费记录，C 负责产品条款。这里的 A/B/C 只是说明职责的例子，不是预设所有项目必须有这三个源。

必须区分：

- **职责范围完整**：知道某类信息应归哪个源负责，环境内没有未声明的补充来源。
- **实际资料齐全**：该源是否真的保存了某个客户、某张保单或某版条款。职责明确不承诺资料齐全。

信息源职责是共享的环境前提，不是每道题重新探索的问题。逐题需要识别必要信息属于哪类，再对应到负责的信息源。实际接入时若某类信息的职责没有声明，或题目依赖无法可靠归类，应记录未确认部分，不能凭猜测补出归属或排除结论。

系统允许怎样使用资源，仍属于供给条件。只允许经指定 harness 访问，与允许直接访问源内容，是不同环境；单次工具失败不能证明系统的唯一允许路径一定无法取得信息。

## 评估者缺少哪些信息源

系统的供给范围固定，但评估者可能只能看到部分信息源，甚至拿不到任何源的内容。评估者知道全部源的职责，也知道自己缺少哪些源。

**“缺少 A”指评估者拿不到 A 的内容，不代表系统没有 A。** 源可获取也不等于已检查完：只读了一页、只看了部分字段或一次检索结果，都不能自动证明源内缺失。

每种评估条件用缺少的信息源组合描述，可以缺一个或多个。职责说明及原题是共同前提，不因某个源的内容不可见而消失。

| 对某项必要信息的掌握情况 | 本阶段判断 |
|---|---|
| 负责的信息源不可见 | 无法据此排除，保留不确定 |
| 源可见，但相关内容尚未查清 | 保留不确定 |
| 已确认负责的源内没有必要信息 | 确定不可测 |
| 找到了所需信息 | 该项缺失未成立；仍须看是否有其他阻断，本阶段不新增可测标签 |

例如，确认客户源 A 缺少必要客户资料后，即使保单源 B 不可见，也不妨碍据此排除；B 的职责不包含补足该客户资料。若只是 A 的一次查询没命中，则不能排除。

## 按条件组织同一批数据

保留同一批原题，在不同信息源缺失组合下分别记录判定，呈现时每个条件可以是一列。

- 缺失组合逐步缩小、已有证据保留时，可以组成递进筛选：在尚未排除的题中继续标记新增的确定不可测。
- 缺失组合互不包含时，是并列条件，不能当成固定的先后层级，也不能直接把一列的排除结果抄到另一列。
- 不必枚举全部组合，只建立实际需要评估的条件。

原始记录不物理删除。每个条件下的筛选结果从原题和判定记录生成；新证据暴露旧判断错误时允许撤销，保留修订依据。递进筛选期待增加有依据的排除，不以排除数量越多代表方法越好。

## 标签与判定依据

| 标签 | 含义 | 筛选动作 |
|---|---|---|
| 确定不可测 | 至少一项必要需求在指定环境中已有确定阻断 | 标记排除，保留原题、理由与证据 |
| 不确定 | 尚未确认上述阻断；包括缺少源、尚未查清或已经找到部分支持 | 留在候选集中，允许后续检查 |

“确定”只对声明的任务、环境及版本/时点成立。一个必要子目标被确定阻断即可排除整题；部分子目标有支持，不能证明整题可完成。

排除依据至少说明：**哪项信息必需、归哪个源负责、如何确认源内缺失。** 若依据是系统权限或操作限制，则说明该限制为何阻断必要目标。预算耗尽、工具报错、检索未命中、返回非空或当前 agent 做错，都不能单独决定标签。

## 信息增加与环境改变

评估者得到原本就属于系统供给的源内容，是信息增加，可以在新的评估条件下继续筛选。系统新增资源、信息源职责改变、源内容版本变化或系统权限变化，则属于环境改变，应另行记录环境下的判定，不能直接接续原来的排除结果。

评估者额外取得核实证据，不意味着系统自动获得同样的访问权限。评估者的检查能力与被评估系统的访问限制必须区分。

## 最小输出与验收

对外呈现保持简单：原题加各条件的判定列，单元格包含**结论与简短理由**，可追到证据。共享说明记录信息源职责和各列缺少哪些源；逐题记录必要信息、负责的源及实际检查范围。具体存储形式由方案决定。

验收要求：

1. 每个确定不可测都能追到必要需求及相应源内缺失证据，或明确的系统阻断。
2. 区分职责完整与资料齐全、源不可见与源内没有、源可获取与已经查清。
3. 按缺失组合组织条件，既支持递进筛选，也支持并列比较，不强制固定阶梯。
4. 保留原题目标，不通过换实体、缩小目标或换环境形成结论。
5. 未排除不等于可测，不确定比例不是可测率；判定可复核、可修订。

## 与现有流程的关系

既有无效题过滤处理题目本身的有效性。本阶段利用已有结果，检查任务需求与信息源供给的确定冲突。只有 query、职责说明和已知限制时，也允许先标注；若没有足够排除依据，保留不确定。

gold、评分器、被测系统能力优化和全量自动筛除不在本阶段范围内。当前方法重点仍是：**如何可靠识别必要信息，以及如何确认负责的源内确实缺失。** 详见[方案](../spec/testability.md)。
