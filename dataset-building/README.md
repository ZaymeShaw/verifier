# 评测集构建

本目录承载从原始题库到验证集的构建工作。目前聚焦“任务需求—环境供给”：寻找有明确依据的必要条件冲突，优先标记确定不可测的题目，其余保留为不确定。未排除的候选不等于已确认可测。

当前与 verifier 共用仓库，需求、方案和实验独立组织；未来可整体拆出为项目。

聚类采样流水线是可测性标注的调用方，verifier 是验证集的使用方。可测性标注不要求运行 verifier，也不要求先生成 gold。

## 当前判断方式

需求侧识别完成原任务必须具备什么；供给侧预先声明各信息源负责哪类信息，以及系统的身份、访问条件和相关版本。信息源不限于知识库，也可以保存客户、保单、对话或附件资料。

每类信息的负责源是它在当前环境中的完整供给边界。职责范围明确不代表实际资料齐全；确认必要信息在负责的源中不存在，就标“确定不可测”，其余保留“不确定”。不再逐题假设未声明的补充来源，但一次没查到不等于源内确认缺失。

一次评估中系统供给总范围固定。评估者知道源的职责，但可能拿不到一个、多个乃至全部源的内容。“缺少某源”指评估者不可见，不意味着系统没有该源；可获取也不意味着已经查清。

同一批原题按信息源缺失组合增加判定列。组合逐步缩小且证据保留时可以递进筛选，互不包含时是并列条件，不强制固定阶梯，也不枚举所有组合。各列保留判定、理由和证据；筛选结果从记录生成，不删除原题。系统供给改变则另记环境版本。

当前方法重点是识别原题的必要信息、确认负责的源内缺失。下一轮拟固定源职责及内容，只改变评估者可见的信息源做小规模对照，尚未执行。

## 当前工作流

题库整理 → 导出 → 两级语义聚类 → 分层采样 → 标 hard → 标场景类型 → 过滤无效题 → 不可测排除标注（当前探索阶段） → 后续标注、复核与冻结。

## 组织约定

需求记录要解决什么；方案记录怎么尝试解决；每轮实施与实验记录放在独立日期目录，保留当时的计划、样本、环境、证据和结果。新认识写入方案及实验解读，不追改冻结样本和历史证据。

先沿用已有脚本与数据，不额外建立配置平台、服务或 verifier 评测轴。未来拆出项目时再整体处理依赖路径；本机实验脚本目前仍依赖外部工具工程，不宣称已经可移植。
