# 按信息源缺失组合组织不可测排除

状态：2026-11-04，待验证。对齐[需求](../demand/testability.md)。信息源职责与数据组织方式已明确，自动判断方法尚未验证。

## 方案前提

先声明当前环境的信息源及其职责。每类信息有明确归属，负责的源是该类信息在当前环境中的完整供给边界；它的实际资料可以不齐全。因此，确认必要信息在负责的源中不存在，就可以据此排除，不再逐题搜索假想的其他来源。

这个前提由环境说明提供，不能从工具名或题目中的词语自行编造。题目需要哪类信息仍须逐题判断；未能确定归属时保留不确定。

源内容、系统身份、权限及相关版本/时点在一轮对照中保持固定。改变的是评估者拿到哪些源的内容。源可获取不代表已读完，也不代表能够完成原任务。

## 数据如何组织

先用可读文本、表格或简单记录组织，不引入配置平台或规则引擎。需要保存三部分内容：

1. **共享环境说明**：源标识、负责的信息类别、系统访问条件和版本/时点。比如 A 负责客户资料，B 负责保单资料，C 负责产品条款；具体划分由项目给出。
2. **评估条件**：本条件缺少哪些源，以及可见源实际提供的材料或访问范围。缺失集合可以包含零个、一个或多个源；query、已有对话和职责说明始终提供。
3. **逐题判定**：原题与条件引用、必要信息及负责的源、判定、理由、证据及实际检查范围。

一个展示示例：

| query | 缺少 A、B、C | 缺少 B、C | 缺少 A、C | 不缺信息源 |
|---|---|---|---|---|
| 某题 | 结论＋理由 | 结论＋理由 | 结论＋理由 | 结论＋理由 |

这些列是信息条件，不是置信等级。“不缺信息源”只表示都可获取，不表示每个源都已完整检查。可见源只有局部材料时，在证据中记录范围，不把局部可见写成全源已核查。

不要求枚举所有组合。缺失集合互不包含的列独立判断，不能相互继承排除；若选择一条缺失集合逐步缩小的路线，并保留前一条件的证据，就可以只对尚未排除的题继续筛选。

递进路线中已排除的题保留原判定及出处，不物理删行。若新列不复查，可以展示“沿用前列排除”并引用依据，不能伪装成本列新判断；尚未处理的单元格留空，不能自动填成“不确定”。这两者是处理状态，不是新增业务标签。

每个条件的候选集由原题与有效判定生成。并列比较使用同一原始题集；不能先用另一条件删掉样本，再宣称完成本条件的比较。证据纠错时允许撤销排除，保留原因。

## 最小判定过程

1. **读原题及已有上下文。** 沿用无效题过滤结果，保留多轮指代和原任务目标。
2. **提出必要信息。** 用一句话说明任务必须知道什么、为什么缺少它就无法完成。不要求列尽全部依赖；但不能把某种工具、字段或解法误当唯一必要条件。
3. **对应负责的信息源。** 按共享职责说明映射；不能确认信息类别或归属时记录疑问。
4. **检查当前条件的证据。** 源不可见就保留该项未知；源可见则检查相关内容。记录实体、版本、范围及结果，区分未查清、找到支持、确认缺失。
5. **给出判定。** 任一必要信息已被确认在负责的源中缺失，就标确定不可测；否则标不确定。明确权限或操作限制构成必要阻断时，也可据此排除。

不必取得所有源才能排除。客户信息由 A 负责，若已经确认 A 缺少原题必需的客户资料，则不需要读取仅负责产品条款的 C 来支撑该结论。反之，A 不可见时，不能因为 B、C 没有客户资料就排除。

找到必要资料只说明该项缺失未成立，不自动产生可测标签。模型能生成答案、返回非空或部分目标已完成，也不改变这条规则。

## 什么算确认源内缺失

职责边界已作为前提，具体缺失仍须有证据。这是方案需要验证的方法问题，不用“已经充分探索”代替。

可尝试的证据包括：对明确实体和版本的完整相关材料检查；语义、身份、范围及完整性得到确认的结构化查询；明确说明该类必要字段未被保存的源说明。它们是否足以支撑某道题，需要结合任务核实，不能机械套用。

以下情况单独出现时都不够：

- 一次 RAG 未命中或返回了别的产品。
- 查询为零，但实体解析、权限或过滤条件没有确认。
- 当前页或部分字段中没有，尚未覆盖相关记录。
- 没有现成答案字段，但已有事实可能足以推导答案。
- 工具报错、访问失败或调查预算耗尽。

停止检查与排除判定分开：本轮查不清就记录不确定及缺少的证据，不为了填满标签继续无限探查，也不把停止本身当作缺失证明。

## 对照例子

以下为假设性例子，不是实际题库标签。假设 A 负责客户资料，B 负责保单资料，C 负责产品条款，职责范围已确认。

| 情况 | 结论及原因 |
|---|---|
| 原题必需客户资料，当前缺 A | 不确定：负责的源不可见 |
| A 可获取，但只查了局部记录且未命中 | 不确定：源内缺失未确认 |
| 已确认 A 没有必需客户资料，B、C 不可见 | 确定不可测：必要信息缺失，其他源不负责补足它 |
| A 有客户资料，原题还需要保单数据，当前缺 B | 不确定：保单依赖未查清 |
| 所需资料均找到，未发现其他阻断 | 本阶段仍为不确定：不承担确认可测 |
| C 的一次检索未找到指定条款 | 不确定：检索结果不能证明 C 没有 |
| 已检查 C 中完整相关版本材料，确认无法得到原题必需信息 | 确定不可测：负责的源内确认缺失 |
| 原目标就是核实记录是否存在，完整查询确认没有 | 不能因零记录排除：确认不存在可能就是任务结果 |

系统只允许通过某一 harness 取得资料时，访问限制仍属于环境条件。源内容存在但一次调用失败，不能直接确定不可测；证明唯一允许路径存在必然阻断是另外的取证问题，不与源内缺失混为一谈。

## 下一轮如何验证

先准备少量可完整人工核查的材料，不重跑旧 A/B 或全量联网探查。实验尚未执行，实际模型、规模及预算待实施时确定。

1. 冻结 query、源职责、源内容和系统访问条件。职责可以完整声明，内容刻意保留有资料与缺资料的不同情况。
2. 选择实际需要的缺失组合，例如缺全部源、仅可见 A、仅可见 B、全部源可获取。不要求固定三层，也不枚举全部组合。
3. 在每个条件下独立形成判断，不向评估者泄露不可见源内容或其他条件的答案。先判断依赖识别是否成立，再检查缺失证据是否支持排除。
4. 对存在递进关系的条件，检查新增信息是否带来有依据的新增排除；对并列条件，检查差异是否来自负责的信息源是否可见。

材料应覆盖：必要信息藏在不可见源中；负责的源确实缺少必要信息；源只提供部分内容；信息存在但需要推导；查询空结果本身就是原目标；多项必要依赖中仅一项确认缺失。这样既检查错误排除，也检查有充分依据时是否仍漏掉阻断。

依据不足却碰巧判对，不算可靠排除。没有缺失证据时保留不确定是合理行为；完整材料支持任务时，仍不要求输出可测。小型材料只验证判定逻辑，不证明真实数据源已经满足职责与范围约定。

记录排除数量、依据成立情况、误排除、应排未排、不确定原因及成本。有明确参照时才统计相应指标；不以排除数量最大或不确定比例最低作为目标。

回到真实聚类采样题时，先使用 query、职责说明和已有上下文，明确列出当前缺少的源。没有资源内容时能排除很少也是允许结果。后续取得源内容，再增加对应条件列及判定，无须重建原始题集。

## 首轮 A/B 的定位

[首轮实验](../experiments/20261102-testability/README.md)探索了 A（题意＋静态工具清单）与 B（增加只读探查）。A 得到 24 条候选、4 条待确认；B 分为 2 条资料较明确、11 条限定范围、2 条疑似工具问题、13 条待核实。

它揭示了非空返回不等于需求满足、查询失败不等于供给缺失等局限。实验没有按当前约定声明信息源职责、确认相关源内缺失，也没有独立参照，不能证明 B 更优，不能把历史分组直接转换为当前两个标签。

## 当前待解决的问题与实施范围

需求及数据组织没有待澄清的阻塞项。方法上仍需验证两件事：如何从原题可靠识别必要信息并映射到负责的源；如何取得足以确认源内缺失的证据。真实项目的信息源职责、身份和版本需要在接入时填写，不假设已有工具清单就是完整供给说明。
