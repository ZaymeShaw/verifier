# 期望需求

> 状态：2026-10-20 上线（修订记录 `spec/implementation/demand-revision-20261020/`，旧版备份 `demand/backup-20261020/`）。2026-10-25 修订草稿：§3 主轴一行、§4 新增"写明判它还需要什么证据"。本文定义期望是什么、从哪来、不是什么、谁用、要满足什么。怎么产出归 `spec/`。

## 1. 期望是什么

期望是**用户和下游对业务系统的期望**：这一次，希望从业务系统得到什么。（2026-10-07 定）

来源有三类：

| 来源 | 说明 | 例 |
|---|---|---|
| 用户原话 | 用户说了什么；多轮时以整段对话为准，后面的更正、追问都算，结合历史理解指代和省略 | "这张保单是谁的？投保人和被保人分别是谁？当前状态呢？" |
| 下游要求 | 业务系统的交付物被谁消费、对方要求什么（格式、字段、口径） | 下游系统要求返回结构化字段，而不是一段文字 |
| 场景判准 | 业务方登记的：这个场景里"办成"指交付什么。说的是结果，不是评测怎么判 | 查询类场景：给出所问字段的值；咨询类场景：给出适用的条款内容和条件 |

业务层面的信息，例如"这个系统是干什么的、用户拿它办什么事"，写在业务描述里（`information_sources.md` §1.2），作为理解期望的依据。

## 2. 期望不是什么

| 不是 | 为什么 | 归谁 |
|---|---|---|
| 业务系统自己的设计规则（系统提示词、工具说明、输出格式声明） | 这是"系统打算怎么做"，不是"用户要什么"；它是评测时的证据 | 评测某一步时引用原文 |
| "拿不到时怎么做"的行为规范（应如实说明、应澄清、不得编造） | 这是系统的行为规范；用户要的是结果本身，如实说明不等于给到了（`main_axis.md` §2.1、§2.3） | 评测的通用义务；至多是附带要求 |
| 执行路径（"必须调用某工具""必须查一次"） | 期望描述要得到的结果，允许等价做法 | 过程评测判定 |
| 通用底线（"不编造""不改义"） | 对所有 case 都成立，不需要每个 case 列一遍 | 评测的通用义务 |
| 评测标准（怎么判、判成什么值） | 由评测自己定，不来自场景（2026-10-07 定） | 评测 |
| 被测系统对自身能力的声明 | 是被测方的自我描述，不能当成用户要什么 | 不作为期望 |

## 3. 谁用期望

| 使用者 | 用来做什么 |
|---|---|
| 主轴 | 判断用户和下游要的结果给到了没有；按每条写明的证据要求，决定用知识、trace 还是只凭交付判（`main_axis.md` §2.4） |
| 过程六轴 | 意图轴判断用户要求有没有被正确表达；其余轴据此发现"该做没做" |

**所有评测者用同一份期望。** 不能某个评测者在判定时自己再推一份，尤其不能看着实际答案写期望。

**谁来定这一份（2026-10-20 用户定）。** 有需要提前定下期望的评测（如过程六轴）在场时，期望单独提前定下，主轴也用这一份；只有主轴时，主轴可以自己定，但同样要先于看结果定下、满足 §4。单独提前定的那一步开了却没定出来，不能由主轴另推一份顶上，记为评测器失败。

## 4. 期望要满足什么

- **准确、完整**：不缺、不漏、不错。
- **先于运行结果定下来**：只依据用户原话、历史、下游要求、场景判准和业务描述，不看业务系统本次的输出，不对着答案倒推，也不按本次回答加条件。
- **描述结果，不描述路径**：说要得到什么，不规定怎么得到。
- **歧义显式标出**：同一句话有互斥的读法时，各列一条并标为同组，不替用户选。
- **一条只说一件事**：用户问了几件事，就分几条；不把一件事拆碎。
- **可回到原文**：每条期望都能指回它来自哪句原话或哪段描述。
- **写明判它还需要什么证据**（2026-10-25 用户定）：除了交付、用户原话、场景资料之外，判这一条对不对还需要哪类证据（知识、trace），写成"几组之间或、组内与"，例如"知识 或 trace"；只凭交付就能判的写空。凡是业务事实（保费、条款、产品规则、某个对象的属性）都要写证据要求；通用常识（算术、单位换算、公认的常识）不用。和期望本身一样，在看到交付之前写定，不能看了回答再降低要求。

## 5. 现在已经碰到的问题

需求必须覆盖的现象，方案拿它们验收：

| # | 现象 | 问题在哪 |
|---|---|---|
| Q1 | 一条查询 case 产出的期望绝大多数来自系统提示词和工具说明，来自用户的只有几条 | 把系统设计规则当成了期望 |
| Q2 | 同一份材料两次运行，期望条数差一倍 | 没有拆分标准；而且系统规则这部分本来就不该拆 |
| Q3 | 产出期望耗时极长 | 主要耗在生成不该有的那部分 |
| Q4 | 判定时又自己推了一份期望，内容里直接写着实际答案 | 期望有两份，且其中一份是对着答案写的 |
| Q5 | 多轮里用户第二轮更正了对象，期望只看了第一句 | 没按整段对话定期望 |
| Q6 | 对象不存在的 case，期望里出现"如实反馈未查到" | 把"拿不到时怎么做"的行为规范写成了期望；期望应是用户要的那个结果 |

## 6. 还没定的 ⟡

- ⟡ **业务描述怎么切。** 现有场景描述里，"用户要办什么、办成指交付什么"（期望）、"系统声称能做什么"（不是期望）、"拿不到时怎么做"（行为规范）三者混写，要定怎么拆或怎么标。
- ⟡ **下游要求从哪里来、谁维护。** 现在没有登记下游要求的地方；是否区分"确认无下游"与"有下游但未登记"。
- ⟡ **过程轴的轴说明归属。** 其中"业务方对过程的期望"可能属于下游要求，"评测怎么判"属于评测设定，需拆开。

## 7. 不要什么

- 不把业务系统的设计规则、行为规范、通用底线、执行路径写成期望。
- 不让同一个 case 存在多份期望，也不在看到答案后补写或改写期望。
- 不为了让清单看起来完整而硬拆。
- 不替用户在歧义读法中选一种。

## 8. 验收怎么看

- 用冻结样本对照：每条期望都能指回原话或描述；用户问了几件事就有几条，没有系统规则、行为规范混入。
- 同一 case 重复产出，期望条目稳定。
- 主轴和六轴引用的是同一份期望。
- 多轮 case 的期望能体现用户在后续轮次的更正和追问。
- Q1–Q6 在新实现下都不再出现。
