## 1. 信息源是什么

评测一个 case，流程上有五个位置：

```text
① 输入端        用户原话、历史、下游要求、场景判准   ──→  期望（expectations.md）
② 被测系统运行  产出回答，同时留下 trace
③ 信息源        评测方在判定过程中取来用的信息         ←  本文
④ 判定          主轴结论、过程六轴结论
⑤ 归因          优化建议
```

信息源是 ③：**既不是输入，也不是结论，是评测方在判定时取用的东西。**

开放文字类场景（回答是自由文本，里面有大量具体事实、条件、流程），光看问答文本判不了对错、也判不了过程哪里出了问题，评测方必须有信息源。trace 和知识是其中最重要的两种。

### 1.1 有哪几种

| | 被测系统自己产生的 | 被测系统之外的 |
|---|---|---|
| **case 级、动态** | **trace**：这一轮运行留下的记录 | **知识**：评测方到知识源查到的 |
| **项目级、静态** | 系统静态资料：代码、配置、能力声明 | **业务描述**：业务方登记的事实；**责任范围**：业务方登记的、系统不负责的限制；**参考答案**：人工或业务方给的标注 |

横轴的意义：被测系统自己产生的东西，只能说明"系统做了什么、怎么做的"，**不能证明系统做得对**。独立于系统的东西才能证明对错。

### 1.2 每种信息源

| 信息源 | 谁提供 | 能说明什么 | 不能说明什么 |
|---|---|---|---|
| **trace** | 被测系统运行时留下，评测方在跑完业务时取回、存档 | 业务这一轮做了什么：查没查、拿到什么返回、把什么交给了模型、模型输出了什么。配了 trace 的场景，主轴拿它作过程佐证：用户要的值是不是按对的对象、从系统数据里取到、如实交付的（`main_axis.md` §2.4） | 业务的数据本身对不对 |
| **知识** | 评测方自己到场景登记的知识源查 | 回答里的事实在知识源里有没有依据 | 业务有没有去查、过程可不可靠 |
| **业务描述** | 业务方登记 | 怎么读别的信息源：系统是干什么的、对象靠什么区分、数据单位、返回怎么读 | 不是结论的依据，只是读法 |
| **责任范围** | 业务方登记（`rule.md` 评估责任边界） | 哪些要求在被测系统责任之外、系统正常工作时也给不出：没有哪类数据、不接哪类系统、哪些字段本来就没有 | 本次做没做对。它是"做不了"的依据（`main_axis.md` §3.3），不是"做成了"的依据 |
| **参考答案** | 人工核定或业务方确认 | 对照用 | AI 生成的伪参考不构成依据 |
| **系统静态资料** | 被测系统的代码、配置、能力声明 | 系统设计上怎么做的 | 同 trace，证明不了对 |

被测系统运行时自己说的话（系统提示词、能力提示、自带护栏 / 评估的输出）不单列，它们就在 trace 里，按"系统自己说的"对待。

### 1.3 信息源在流程里的身份

| 身份 | 做什么 | 例 |
|---|---|---|
| **依据** | 被某条结论引用 | "没办成"指向 trace 里某次调用的返回 |
| **读法** | 帮着读别的信息源 | 业务描述告诉判定"两个代码不同就是两款产品" |
| **对照物** | 两个来源互相比 | 业务 trace 里查到的 vs 评测方在知识源查到的 |
| **缺口信号** | 它不在，本身就是信息 | 没埋点、脱敏、没登记知识源 → 下游知道缺的是哪一格 |

## 2. 信息源不是什么

- **不是输入。** 用户原话、历史、下游要求归 ①。
- **不是结论。** 主轴结论、六轴结论、每个事实的对错都是 ④ 产出的。
- **不是评判标准。** 判别法：一句话写进本文之前问一句，**把判定模型换掉、判法全部重写，这句话还成立吗？**成立才是本文的内容。

本文保证"缺了什么"这个信息存在；缺了怎么判，归判定。

## 3. 谁用信息源

| 用的人 / 环节 | 用哪些 | 拿来干什么 |
|---|---|---|
| 主轴 | trace、知识、业务描述、责任范围 | 结果有没有依据；没给到的能不能做；缺哪一格 |
| 过程六轴 | trace、业务描述 | 每一环做了什么、本应做什么 |
| 核事实 | 知识、业务描述 | 回答里每个事实有没有依据 |
| 业务开发 | 全部，经由 ④ 的引用 | 看到问题时能回查到原文 |
| 评测方自己 | 全部 + 评测器运行记录 | 确认每条结论依据什么判的、信息源采到什么程度 |

两个来源**对照**是开放场景里最有价值的用法：业务查到了没用上 / 业务没查、知识源里有 / 知识源里就没有。这要求同一件事在 trace 和知识两边都取得到。

## 4. 信息源要满足的要求

1. **取得到。** 每个 case 都能取到场景声明的信息源；取不到要有明确记录，不能静默跳过。场景配了 trace、而这个 case 有一整轮没采到（或整条没采到），这个 case 记运行失败、不出结论，可补跑；一轮之内缺了某些端点，照常评测，缺口按要求 4 标出（2026-10-25 用户定）。
2. **关联精确。** 这条 trace 必须就是这一轮；对不上唯一一条（零条或多条）都算取不到，不按时间、会话、正文去猜。
3. **只读。** 知识源只放开只读的工具；有副作用的不放开。带身份的查询照常放开，需要什么参数就给什么，身份随样本而变。
4. **完整性可见。** 采到多少、缺哪段、哪里脱敏、哪里截断、哪些调用没埋点，都标出来，传到下游。缺证不能悄悄变成通过，也不能悄悄变成失败。
5. **原文可回查。** 取回什么就存什么，不转述、不改写，程序能逐字回读。
6. **真查过才能说没找到。** 对一条事实一次都没查，不能报"没找到"。查证过程本身要有记录。
7. **评测器自己的失败和缺证分开。** 超时、预算耗尽、输出不合法是评测器失败，不是业务证据不足。
8. **改被测系统只为关联。** 为了让评测方找到这一轮的 trace，可以要求业务带一个关联标识；此外不为取证改业务、不补埋点。缺口写进报告，由业务方决定补不补。
9. **业务描述、责任范围只写事实，不写判法、查法。** 单位、对象标识、别名对应、返回怎么读、没有哪类数据，可以写；"回答写了单位就算对""查不到就算做不了"不能写。
10. **业务事实不进评测系统。** 评测系统里不内置任何具体业务的事实；由业务方写进业务描述，评测系统照着读，没写的对不上就是对不上。
11. **知识源内部矛盾不裁。** 知识源对同一问题口径互相矛盾时，两边原文都记，不判哪条对。
12. **新接一个信息源只需登记，评测器不改。** 不同场景的查法差别很大（按产品和条款查、先查客户再查保单、只能走业务自己的查询接口）；接新的 trace 来源或知识源、换一种查法，都只改登记，评测器代码和流程不动。
13. **知识源返回里要有原文。** 能被引用的东西必须以原文出现在返回里；只回答"是 / 否"的不能当依据。

## 5. 现在已经碰到的问题

| # | 现象 | 属于哪一格 / 哪条要求 |
|---|---|---|
| S1 | 业务工具内部有多步，trace 只记了外层入参出参，看不到实际按什么条件查的 | trace；要求 4、8 |
| S2 | trace 内容默认脱敏，并截断且不留标记，最先被截掉的是本轮问题和工具结果 | trace；要求 4 |
| S3 | 评测方没有连接某类数据源，回答里关于它的事实核实不了 | 知识；缺口信号 |
| S4 | 查证只读了长返回的开头，后面的关键字段没看到就说"没找到" | 知识；要求 5、6 |
| S5 | 一个工具都没调，直接说"查不到" | 知识；要求 6 |
| S6 | 知识源对问法敏感，查证拿了名字相像的另一个对象当证据 | 知识；依据须属于同一对象；业务描述要写清对象靠什么区分 |
| S7 | 业务数据里金额不带单位，回答写了单位，判定拿不准 | 业务描述；要求 10 |
| S8 | 读法说明里混进了判法、查法类的话，被判定当成依据或让查证多查 | 业务描述；要求 9 |
| S9 | 单次返回很大，模型只看了开头 | 知识；要求 5（原文完整保存，不因为大就丢）、要求 6 |
| S10 | trace 写入是异步的，刚跑完就取可能缺步骤；业务开了采样时有调用不在 trace 里 | trace；要求 1、4 |
| S11 | 评测器超时后，下游拿到的是"无法评估"，分不清原因 | 要求 7 |

## 6. 还没定的 ⟡

- **场景怎么声明自己需要哪些信息源（2026-10-25 定）。** 场景配了哪些信息源，就按哪些的标准判（`main_axis.md` §2.4）；每条期望需要哪类证据由期望写明（`expectations.md` §4）。期望要的证据场景没配，记"缺哪一类"，判不确定；配了没取到见要求 1。
- ⟡ **参考答案的站位。** 人工核定的标签能不能作为 ④ 的依据，还是只用于评测自检。目前只用于自检。
- ⟡ **trace 与知识对照什么时候启用。** 建议提前。
- ⟡ **用户后续反应。** 多轮里用户下一句能反映上一轮办没办成，归 ① 还是也算 ③。倾向归 ①。

## 7. 不要什么

- 不为取证改被测系统（关联 ID 除外）。
- 不把业务事实写进评测系统。
- 不把系统自己的输出、配置、能力声明当作"系统做得对"的证明。过程佐证说明的是"业务按需求做到了"，不是"数据对"，结论里要标明（`main_axis.md` §2.4）。
- 不让缺证悄悄变成通过，也不让它悄悄变成失败。
- 不让预算、超时、模型没跑完变成"没找到"。
- 本文不写任何"怎么判"。

## 8. 验收怎么看

- 每个 case 能列出：用了哪些信息源、各自采到什么程度、缺哪一格、缺在哪一步。
- 信息源里的任何一段都能由程序回读到原始记录，取回的和保存的逐字一致。
- 缺证的 case，下游能看见缺的是哪一格，而不是一个笼统的"无法评估"。
- 评测器自己失败的 case 和缺证的 case 分得开。
- 新接一个 trace 来源或一个知识源，只登记，不改评测器代码（要求 12）。
- "没查就报没找到"为 0。
- S1–S11 每条都能在方案里找到归属和处理方式。
