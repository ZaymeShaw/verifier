## 1. 要什么

**每个评测轴是一个标准化的任务；一个 case 由一个主 loop 完成它启用的全部任务。加减一个轴，只动配置和规范内的少量代码，不再写一条工作流。**

主 loop 的内核是现有的 tool loop（模型自己决定调什么工具、按什么顺序做事，程序用 hook 管约束）；在它之上搭一层"评测轴任务"专属的机制：任务怎么出现、能看什么、交什么、怎么验收、彼此怎么依赖。

给谁用：

| 谁 | 拿来做什么 |
|---|---|
| 写轴的人（评测方） | 用标准方式加、减、改一个轴，不碰主 loop、不碰别的轴 |
| 配场景的人 | 给场景挑要跑的轴、挑信息源和工具、写场景对各轴的说明 |
| 接信息源的人 | 新接一个知识源或 trace 来源，只登记 |
| 调评测效果的人 | 某个 case 判错时，回看评测器每一步看了什么、交了什么、被拒在哪 |

### 1.1 定位

- 这是一条**实验路线**（llm_probe_loop），与现有工作流方案（llm_probe 的 eval_axes）在同一批 case 上并跑对比；赢的留下，输的删掉，不长期并存。（2026-10-20 用户定）
- **结论口径不动。** 同一份交付、同样材料，两条路线要回答的是同一个问题、用同一套取值；能比较的前提就是口径一致。（2026-10-20 用户定）

## 2. 现在已经碰到的问题

需求必须覆盖的现象，方案拿它们验收：

| # | 现象 | 为什么 |
|---|---|---|
| L1 | 多一个评测轴，就多一条定制工作流：prompt、输出 schema、取数接线、依赖、校验、注册各写一遍 | 轴的形态没有标准，每个轴从头搭 |
| L2 | 一个轴判错，要去改段与段之间的投影和接口，调一处牵动多处，容易调崩 | 轴之间靠程序接线传数据，接线本身就是调参对象 |
| L3 | 判定时发现证据不够，不能自己再查一次 | 每一段只看上游投影给它的那部分，取证与判定被切开 |
| L4 | 流程顺序写死，不能按 case 调整 | 先做什么、什么情况下做什么，写在运行器和各轴代码里 |
| L5 | 一个 case 判错，很难回看评测器当时怎么想的 | 评测散在多次互不相干的模型调用里 |
| L6 | 调了半天效果还是不好 | L2、L3 的直接后果 |
| L7 | 运行慢、token 成本高 | 同一份材料在多段里反复灌给模型 |
| L8 | 加减轴没有标准方式 | 同 L1；没有"加一个轴只能动哪些东西"的边界 |

## 3. 任务

### 3.1 一个任务由什么组成

| 元素 | 含义 |
|---|---|
| 执行者 | 模型，或程序。程序任务就是全部输出都由程序算出的任务（如主轴四值） |
| 所属 loop | 这个任务在哪个 loop 里做（§3.5）；不写就是 case 开始时启动的那个 |
| 冻结 | 是否冻结型：交上去被接受后不许再改（§3.2.9） |
| 角色 | 分析类（产出给别的轴用的中间结果，如需求、说法）或评测类（缺省），决定展示时算不算评测结论 |
| 依赖 | 上游任务；分硬、软两种（§3.2） |
| 触发条件 | 上游的轴级 verdict 落在某个集合内，这个任务才出现；只有这一种形式，由程序判断 |
| 任务说明 | 这个轴固定的要求，只写判什么、怎么判；能结构化表达的一律做成配置，不写进说明 |
| 材料 | 这个任务能读的材料白名单（§3.6）：内置材料、它依赖的轴的结果，各自读哪些字段 |
| 工具 | 这个任务需要的信息源类别，标明必需或可选（§4.3）；以及选用的被调用启动的 loop（§3.5.6） |
| 提交物 | 轴级 verdict、reason，加上这个轴自定义的中间产物（§3.3） |
| 验收规则 | 标准校验加自定义校验（§3.4）；不过就打回并说明原因，模型改了再交 |
| 完成条件 | 什么算这个任务做完了 |
| 不适用出口 | 任务出现了，但这个 case 里没有可评的对象；声明不适用也要过验收 |

一个任务的全部元素都是配置，在页面上编辑；轴间依赖也是配置，属于全局的轴定义，场景只能开关某个轴，不能改它的依赖。要用上游的哪些结果，同样写进材料白名单，不靠任务说明去描述。（2026-10-21 用户定，取代当天早些时候"上游结果由任务说明写明"的说法）

### 3.2 任务之间

1. **依赖成 DAG。** 上游没完成，下游不出现。
2. **硬依赖与软依赖。** 硬依赖：场景开了 A 而没开 A 的硬依赖 B，加载时就报错。软依赖：B 没开，A 照常跑，按 A 的任务说明里写的"没有 B 时怎么做"；B 开了，A 必须等 B 完成并用它。例：兑现对核事实是软依赖（没开核事实时只凭交付判），兑现、过程六轴对需求是硬依赖。触发条件只能引用硬依赖。（2026-10-21 用户定；兑现不再自推期望，见 §7）
3. **该看不到的看不到，而且由程序保证。** 目的首先是防污染：例如期望定下之前不能看到交付，否则会被交付带偏（`main_axis.md` M1、M2）；其次是减轻负担。不能靠提示词劝模型"先别看"。程序保证的方式只有两种：
   - **整个任务都不能看某样材料**：靠出现顺序。那样材料只在后面的任务出现时才第一次进入上下文；
   - **这个判断要和别的东西隔开**（例：blocking 不能看交付；期望每轮看不到后面的轮）：放进单独的 loop（§3.5），它有自己的上下文，只拿到程序按白名单给它的材料。
4. **看过的收不回。** 同一个上下文里，已经出现的东西不能再藏起来，所以上面第二种情况只能放进单独的 loop。
5. **上游改了，下游必须重交。** 已完成的上游被改动后，依赖它的下游（传递地）全部作废、必须重新提交；触发条件按新结果重新判断，不再满足的下游撤下。之前的上下文照常保留，就跟普通 loop 一样。（2026-10-21 用户定）
6. **顺序由模型安排。** 同时出现的几个任务，模型自己决定先做哪个、交错着做，也可以在一次回复里同时提交多个。程序不规定顺序。
7. **领任务是程序推送，交任务是模型调工具。** 有任务出现时，由程序把它推进上下文；模型通过工具提交，每次提交都写明是哪个任务。
8. **任何一个任务失败，整个 case 记运行失败。** 预算耗尽、一直过不了验收都算。不出部分结论。（2026-10-21 用户定）
9. **冻结型任务不许重做。** 任务可以声明为冻结型：提交被接受后，再交一律拒绝。用在"后面会看到它不该看到的东西、看过之后不能回头改"的地方（例：过程轴的本应清单，实际出现后输出端已进上下文）。它的上游变了，按第 5 条作废时，它所在的整个 loop 重新起一个干净的上下文重做，而不是在原上下文里改。（2026-10-25 用户定）

### 3.3 提交

1. **verdict 是轴级的。** 每个任务交一个轴级 verdict 和 reason。轴里各分项自己的结论（每条说法的核实结果、每条期望给到没有）是中间产物，不是轴的 verdict。
2. **中间产物由轴自己定结构**，和 verdict、reason 一起交。
3. **能分条交的，可以分条交。** 中间产物是一组分项时，可以一条一条提交、一条一条验收、只打回错的那条，最后再交 verdict 和 reason 收尾。这要同时满足三条：分项之间完全独立（一条的结论不读别的分项）；任务定义里明确声明了允许分条交；每次提交写明是哪个任务、哪个分项。不满足的一次交齐。
4. **能由程序算的，不让模型写。** 任务的输出结构里逐个字段标明"模型填"还是"程序填"。有程序填的字段，就要配一个合成程序：读模型交的部分，算出完整结果。例如兑现的整体状态由各条 blocking 期望派生，六轴的轴级值由逐条结果派生。合成出的完整结果同样要合乎输出结构。（2026-10-21 用户定）
5. **程序任务**的全部字段都由程序填，模型看不到它；上游完成就自动算，上游改了就自动重算。

### 3.4 验收

现有各轴的校验归成七种。前六种是通用的，由内核提供，写轴时选用并填参数；第七种按轴定制，写成代码。

| # | 形式 | 例 |
|---|---|---|
| V1 | 形状、枚举：字段齐全、类型对、取值在枚举里、非空 | 几乎每个轴都有 |
| V2 | 条件字段：取某个值时，某字段必填或必须为空 | 查到时必须有引文；核实不了时必须写缺哪一格 |
| V3 | 逐条覆盖：对某个清单不增、不漏、不重 | 兑现覆盖全部期望；承载性覆盖全部没给到的 |
| V4 | 引用存在：引用的编号必须在某个集合里 | 引的说法编号在核事实结果里；环节编号在环节表里 |
| V5 | 逐字原文：引文必须逐字出现在某段原文里 | 说法的出处在交付里；引句在工具返回里 |
| V6 | 先看到再引用：只能引用此前已经返回、且没报错的调用 | 不能引用同一次回复里刚拿到的返回；报错的调用不算查过 |
| V7 | 业务规则：跨字段、跨任务的判法约束 | 引了被否定的说法就不能判给到；期望必须引本轮用户原话 |

1. **写代码只有三个固定插口**：业务规则校验（V7）、合成程序（§3.3.4）、分发脚本（§3.5.3）；另有新增内置材料的取值函数（§3.6）。发现一个新轴需要的东西这些插口表达不了，就去挑战框架、改框架机制，而不是在轴里或项目入口另写自定义代码。（2026-10-21 用户定；2026-10-22 补：一切围绕框架机制插拔，框架之外不加自定义代码）
2. **引用只有一种规则：** 引用 = 某一次工具调用 + 一段原文，原文必须逐字出现在**那一次调用中模型实际看到的返回**里。没看到的部分不能引。各信息源不再各自写核验方式。
3. **自定义代码只能看声明过的东西**：本任务交的、声明过的上游任务的结果、本任务和上游声明过的输入源、本次 loop 的工具调用记录。看不到声明之外的任务，否则依赖关系就会在代码里偷偷长出来、而配置上看不见。
4. **自定义代码要守规范：** 确定性、不调模型、不读写外部状态。验收结果要能复算。合成程序（§3.3.4）同样遵守。

### 3.5 loop：一个 case 跑几个 loop，每个做自己那组任务（2026-10-25 用户定，取代"主 loop / 独立运行的轴 / 公共 loop 工具"三种说法）

一个 case 不止一个 loop。主 loop、需要隔开的判断、可复用的 agentic 能力，都是同一种东西：**loop 定义**。每个任务属于一个 loop；loop 里的规则都一样（任务出现、推送、自由安排、submit、验收），主 loop 只是"case 开始就启动"的那一个。

1. **loop 定义只写三样：** 名字；怎么启动（case 开始就启动 / 它的任务依赖的别的 loop 里的任务都齐了，由程序启动 / 被模型当工具调用时启动）；可选的分发脚本（同一个 loop 按材料起几份）。全部是配置，与轴定义放在同一处、同一个页面编辑。
2. **什么时候起，由程序从任务的依赖推出来**，不另写：loop 里各任务依赖的、属于别的 loop 的任务，就是这个 loop 要等的。要守四条：loop 之间的依赖不能成环（加载时报错）；"齐了"指完成了或已确定不出现；全部齐了才起；它等的任务被改了，整个 loop 作废、重新起。
3. **跨 loop 只通过任务结果传东西**（`result.<轴>`），按白名单读。
4. **为什么要单独一个 loop，只有两种理由：** 要隔开可见性（例：blocking 不能看交付；需求每轮看不到后面的轮；过程六轴写本应时不能看到主 loop 里已出现的交付）；过程产物大、别的任务用不上。默认在主 loop 里做：信息不被切碎、判定时能当场补查，是选 loop 的初衷（L3）。
5. **分发。** 一个 loop 需要"一份材料一份"时（例：需求每轮一份），上传分发脚本：标准输入是这个 loop 里各任务白名单的材料，标准输出是每一份的材料**选择**（与白名单同一种写法）。每一份只看到给它的那份选择，跑这个 loop 的全部任务；各份被接受的结果收成列表，交给各任务的合成程序合并。分发脚本只能选已登记的材料，造不出新内容。
6. **被调用时启动的 loop（原"公共 loop 工具"）**：对调用方是一个工具，调不调、什么时候调、参数怎么填由调用方的模型决定；它的说明、规则、能用的信息源由它自己的定义决定。被调用的 loop 里不能再调这种 loop，只嵌这一层。
7. **几个 loop 一个一个跑**，不同时跑（2026-10-25 用户定，先做对；实测耗时后再议）。
8. 任何一个 loop 失败（预算耗尽、一直过不了验收、合成或分发出错），整个 case 记运行失败（§3.2.8）。
9. **按任务换模型**（§5.1）就是把它放进单独的 loop。

### 3.6 材料

1. **每样内置材料都有标准名**（如用户原话、交付、场景判准、责任范围），由评测器维护一张全局注册表：名字、值的结构、说明、取值函数。新增内置材料，就往注册表里加一项。内置材料不带参数，一个 case 一个值。
2. **每个轴的结果也是材料**，名字由轴 id 决定，结构就是它的输出 schema。
3. **谁能读什么，由配置里的白名单决定**：写明读哪几样、每样读哪些字段，还可以按字段值只取列表里的某些元素。名字和字段在加载时按注册表、schema 检查，写错就报错。声明（注册表）、选择（白名单）、取值（取值函数）三件事分开。
4. **读取范围：** 轴（不论在哪个 loop 里）读内置材料，以及它依赖的轴的结果；分发出来的每一份只读分发脚本给它的那份选择；被调用启动的 loop 只读内置材料，加上调用方传给它的参数；校验、合成、分发代码读的范围与所属的轴相同。
5. **材料由程序直接给**，放进上下文时用标准名标明每一段；引用材料原文时，也用标准名作为出处。
6. **大材料先给目录，正文按需读**（2026-10-25 用户定）：超过上限的材料，任务出现时只推目录（编号、类别、大小、一行摘要）；正文由 loop 内置的读工具按编号取，太大的先给结构、再带位置下钻，确需整段时整段取（沿用现有"先 outline 再读"的做法）。读工具能读到的范围，是这个 loop 里已出现任务的白名单的合集：白名单没选的部分读不到，所以可见性仍由程序保证。读回来的正文按 §5.3 归档。不因为材料大就丢，也不因为大就分批硬塞。

## 4. 信息源与工具

### 4.1 内部与外部

| | 是什么 | 怎么接 |
|---|---|---|
| **内部** | case 自己的数据（用户原话、多轮历史、请求、交付）；场景资料（场景描述、判准、业务描述、责任范围） | 由评测器内置，不作为扩展点 |
| **外部** | 知识源、trace 平台、以后的其他系统 | 一律通过登记 MCP 接入，评测器不为它写代码 |

这里落实的是 `information_sources.md` 要求 12：新接一个信息源，只登记，评测器不改。

### 4.2 三层登记

1. **类型**：一种信息源怎么连、怎么读。全局只写一次。
2. **全局实例**：某个具体的连接（地址、凭据、上限），登记一次，所有场景共用。
3. **场景选用**：场景从全局实例里挑（可以挑多个），并填写自己那部分参数（索引、关联字段、允许哪些工具……）。

连接信息不写进场景。读取方式只认类型，不认场景。全局登记里可以指定这个信息源的**检查工具**：评测时才实时去查的信息源（知识源），loop 启动前由程序调它一次，看这个 case 能不能用；报错就记运行失败，原因带上它的说明。检查工具不交给模型。（2026-10-25 用户定）
一条登记拿来做什么（查知识、读 trace）由它的类型决定；判断场景选了哪类信息源，查登记，不搜描述文字。知识源和业务 trace 都照资料管理页的做法：全局登记，场景选用。（2026-10-22 用户定）
一个信息源要提供哪些查询工具，写在这个信息源自己的 MCP 服务里；选用它的场景都拿到这组工具。

### 4.3 一个任务能用哪些工具

| 层 | 谁定 | 作用 |
|---|---|---|
| 任务定义 | 写轴的人 | 声明需要哪些类别的工具，标明必需或可选 |
| 场景里这个轴的配置 | 配场景的人 | 从场景选用的实例里挑给这个轴；不挑就是这个类别下场景选用的全部 |
| 工具池 | 自动 | 前面任务带进来的工具，后面的任务一直能用，不收回 |
| 场景和轴的描述 | 配场景的人 | 写"查什么用哪个"，模型照着读。这是指导，不是权限 |

必需的类别在场景里一个实例都没有，加载时报错；可选的按任务说明处理。

### 4.4 trace

trace 是一种特殊的信息源（`information_sources.md` §1）：由被测系统自己产生，只能说明系统做了什么；必须精确关联到这一轮。

1. **登记与选用同知识源**：全局登记 trace 源（类型 agno / langfuse / llmtracing，填连接配置），场景选用并填自己的部分（字段绑定）。（2026-10-22 用户定）
2. **关联在跑业务那一侧完成**（发请求前后记下这一轮的关联标识），这是 `information_sources.md` §4.8 唯一允许的业务改动。
3. **同一个 case，每次评测读到的 trace 必须一样。** 跑完业务就采集、等写完、存下来；评测读存下来的那份。冻结的评测集要能一直复跑，不受 trace 平台保留期和异步写入影响。（2026-10-21 用户定）
4. **外部的事归信息源，case 里的事归框架**（2026-10-25 用户定）：去 trace 平台取回这一轮，是 trace 源 MCP 的工具在跑完业务时做的；取回来的存进这次运行记录，和回答一样成为 case 的数据，评测时作为内置材料读（§3.6），loop 里不连 trace 平台。采集报错或缺了整轮，记进存档，这个 case 记运行失败（`information_sources.md` 要求 1）。
5. 哪个任务要读 trace，在它的材料白名单里写 trace 那份内置材料；场景开了这样的任务，跑业务时才采集。

### 4.5 输出形状

信息源和工具交给模型的东西，形状统一，照 MCP 的标准：程序放进上下文的照 MCP 的 resources，模型调用的工具照 MCP 的 tools（文本内容、可选的结构化内容、是否报错）。是否报错必须由返回本身标明，不靠猜。

### 4.6 case

case 有固定结构：标识、按轮的用户原话 / 请求 / 原始响应 / 交付、各 trace 的存档、业务调用本身是否失败。

**被测系统的返回命中场景预先维护的错误码，这条 case 记运行失败，不出任何结论**，不进统计，不算进任何轴的 verdict（`main_axis.md` §3.6，2026-10-22 用户定）。错误码按场景事先维护（HTTP 状态码、响应体错误码字段的取值）；没命中的返回——包括没登记的非 2xx——照常进 loop 评测。这段判断在框架外手写，统一一处。

## 5. 运行

1. **一个 loop 一个模型。** 要给某个任务换模型，把它放进单独的 loop（§3.5）。（2026-10-21 用户定）
2. **预算是全局的**，不按任务分。
3. **不能因为上下文超出模型窗口而失败。** 上限可以配置。超窗属于机制问题，不能靠删任务、删材料来规避。做法参照成熟 harness：大材料只给目录、正文按需读（§3.6.6）；旧的读取结果接近上限时归档、要用再取回（2026-10-25 用户定）。
4. **过程可以回看。** 每个 case 能按任务回看：何时出现、放进了哪些输入、调了哪些工具、交了什么、被拒了几次以及原因、因为上游改动重做了几次。这些记录接入 verifier 自己的 tracing。这是评测器自身的过程可视化，用来 debug，和 loop 的执行逻辑无关。

## 6. 加减一个轴要做什么

上面几节的要求，落到写轴的人身上就是这几件事：

| 要做的 | 形式 |
|---|---|
| 声明任务：依赖（硬 / 软）、触发条件、任务说明、材料白名单、工具类别、输出结构（逐字段标明谁填）、选用哪些通用校验、完成条件、是否允许分条交 | 配置，页面编辑 |
| 所属 loop、是否冻结、角色、选用哪些被调用启动的 loop | 配置，页面编辑 |
| loop 定义：名字、怎么启动 | 配置，页面编辑 |
| 业务规则校验（V7） | 规范内的代码，可选，页面上传 |
| 合成程序（有程序填的字段时） | 规范内的代码，可选，页面上传 |
| 分发脚本（一个 loop 要一份材料一份时，挂在 loop 上） | 规范内的代码，可选，页面上传 |
| 场景开不开这个轴、挑哪些实例、写对它的描述 | 场景配置 |

**不能做的：** 改主 loop；改别的任务的定义；为某个轴写专门的流程控制。如果一个轴用上面这些表达不了，就说明机制不够用，要改机制，而不是给它开特例。

加减一个任务不能要求改动其他任务的定义。（2026-10-21 用户定）

## 7. 还没定的 ⟡

- ⟡ **按上游结果分发**：分发脚本已能按字段值选上游轴结果里的元素；"按说法分、每份只看自己那条"之类真实用例出现时验证。
- ⟡ **loop 与分发出去的各份并发执行**：现在一个一个跑（§3.5.7）。
- ⟡ **代码工具。** 指工具本身是一段确定性计算、没有模型参与。目前没找到需要它的场景（计算由合成程序完成，读外部走 MCP），第一期不支持；出现真实需求时再作为一种规范内代码加进来。
- **兑现不再自推期望（2026-10-21 用户定）。** llm_probe_loop 里兑现硬依赖需求：开兑现必须开需求。原因是自推期望不能看交付，而兑现出现时交付已经在上下文里了。这改变了现有"只开兑现时自推期望"的行为（`spec/alg/expectations.md:97`）；软依赖机制本身保留（核事实、承载性仍是软依赖）。
- ⟡ **按任务换模型。** 如果成本压不下来，重新打开。
- **主轴综合过程六轴（2026-10-25 定，`main_axis.md` §2.4）**：六轴的结果交兑现，兑现逐条期望引用。用本文的任务形态表达：兑现依赖六轴（跨 loop 依赖）。

## 8. 不要什么

- 不改任何结论口径；本文不写"怎么判"。
- 不为某个轴写专门的流程；不为某个场景写专门的读法；不在框架机制之外加自定义代码。
- 不靠提示词实现"看不到"。
- 不让模型填程序能算出来的字段。
- 不让评测器自己的失败变成业务结论，也不出部分结论。
- 不为外部信息源写评测器代码。
- 不用固定顺序代替验收来换取可复算：可复算靠每个任务都经过验收、最终结论由程序合成。

## 9. 验收怎么看

在评测集加 holdout 上，与现有工作流方案并跑：

| 指标 | 要求 |
|---|---|
| 与人工核定结论的一致率 | 不低于现方案（硬门槛），目标是提升 |
| 误放行（不该做成判了做成）数 | 不多于现方案（硬门槛），目标是减少 |
| 同一 case 重跑多次的结论一致率 | 不低于现方案（硬门槛） |
| 每个 case 的 token 与耗时 | 必须下降 |
| 加一个轴要写的东西 | 必须下降：按 §6 清点，与现方案的一个轴对比 |

另外：

- 现有各轴（需求、说法抽取、知识查证、核事实、兑现、承载性、主轴结论、过程案卷、过程六轴）都能只用 §6 的方式表达，不需要动主 loop。
- 防污染：抽查 case 的过程记录，期望定下之前，上下文里没有出现交付。
- 加减一个轴之后，在冻结样本上回归；其他轴的结论变化逐条列出，由人核对。
- 抽查判错的 case，能从过程记录里定位到错在哪个任务、哪一步。
- L1–L8 每条都能在方案里找到对应的处理。
