## 1. 我们要什么

被测业务系统跑一个 case，会留下一条业务 trace。过程六轴读这条 trace，对业务系统的六项过程能力各给一个结论：

- 意图理解、规划路由、工具执行、知识数据、模型能力、上下文管理。

每个 case、每个轴，产出两样东西：

- **结论**：被测系统在这个轴对应的能力上，本次表现如何。它像一个评分，要能跨样本汇总。
- **问题**：这个轴看到的具体问题，每个问题要有 trace 里的依据。

给三处用：业务系统开发者（决定修哪里，分清功能问题和算法问题）；评测方自己（解释主轴为什么没做成）；主轴（只配了 trace 或同时配了 trace 的场景，用逐条结果判用户要的有没有按需求做到，`main_axis.md` §2.4）。

### 1.1 每个轴在评什么

每个轴对应被测系统里的一类部件，部件有固定的"输入 → 输出"。一个轴评的是：这类部件每一次被用到时，**在它实际拿到的输入下本应产出什么，实际产出了什么**。

| 轴 | 部件 | 输入 → 输出 |
|---|---|---|
| 意图理解 | 表达 | 用户原文、被指代的历史 → 系统内部表达 |
| 规划路由 | 编排 | 任务、当时状态、规则 → 路径、调用序列、重试、收尾 |
| 工具执行 | 执行 | 已发出的调用参数 → 返回 |
| 知识数据 | 数据源 | 已正确执行的查询 → 数据是否存在、是否匹配 |
| 模型能力 | 模型 | 一次调用的实际输入 → 该次输出 |
| 上下文管理 | 传递 | 一处产出 → 下一处输入（含组装、缓存、历史、交付） |

- 输入本身已经坏了，说明的是上游，不是这个部件。
- 一个运行事件可以同时属于多个轴；属于哪个轴，看它查的是哪一段输入 → 输出。

## 2. 四个使用角度

### 2.1 看整体：业务系统的各项能力哪些好、哪些差

对一个样本集汇总六轴结论，看出被测系统各项能力处于什么水平；对差的轴，直接下钻看具体哪些地方做得不好，形成对业务方有意义的反馈。

- 结论的含义要稳定、跨 case 可比，同一个值在不同 case 里说的是同一件事；
- 结论说的是**这项能力**。上游造成的结果不好，不能算到这个轴头上；
- 从轴的汇总能一路下钻到具体 case 的具体问题。

### 2.2 看单个 case：具体出了什么问题，依据是什么

- 问题要具体到"哪一步、什么现象、预期是什么、实际是什么"，不能只说"某模块有问题"（`demand/agent.md`）；
- 每个问题带可回查的 trace 引用；
- 该做而没做的事（例如本该查询却没发查询）也要作为问题记下来。

### 2.3 看聚合：把各 case 的问题聚类

- 聚类的成员应当是**一个个问题**，不是整段轴级说明；
- 同一个问题在不同 case 里要能被认出来是同一类。

### 2.4 看评测系统自己：确保上面三条做得对

- 评测器运行失败与"业务证据不足"分开记录（`information_sources.md` §4.7）；
- 每个结论和每个问题都能追到评测器当时看了什么材料、依据什么判的。

## 3. 现在已经碰到的问题

需求必须覆盖的现象，方案拿它们验收：

| # | 现象 | 为什么现在分不清 |
|---|---|---|
| P1 | 知识轴：A）上游没发查询，所以数据没拿到；B）查了，数据源确实没有 | 两种给的结论一样，看不出 A 不是数据源的问题 |
| P2 | 工具返回为空，看不清是工具丢了条件还是数据源没有 | 两轴都报问题、"原因未定位"只写在自由文本里 |
| P3 | 模型输入里关键提示被系统丢了，模型的回答因此不对 | 模型轴判没问题，"受上下文影响"只写在文字里，下游看不到 |
| P4 | 一个轴里既有判出的问题，又有判不了的项 | 轴级只剩一个"有问题"，判不了的那部分被盖掉 |
| P5 | 一个轴全部通过，但有些项缺判准 | 容易被读成"全部核实正常" |
| P6 | 评测器输出不合法被当成证据不足 | 和真正的业务证据不足混在一起 |
| P7 | 聚类输入是整段轴说明 | 一段说明含多个独立问题，聚类分不开 |

P1 的结构（结果不对，原因在上游）各轴都有。需求是对这种情况有**一条统一的口径**，而不是每个轴各写一套。

## 4. 已经定下的

| 事项 | 结论 |
|---|---|
| 结论的含义 | 这个轴对应的能力本次如何；有问题在问题列表里指出 |
| 问题从哪来 | 两条都要：从运行里发现的偏差；从期望和系统设计倒推"该发生什么"再去运行里核对 |
| 上游的问题 | 归上游的不算本轴问题；原因定不了的要明确标出"未定位"及候选轴 |
| 主轴与六轴 | 六轴的逐条结果交给主轴的兑现部分；兑现逐条期望判时可以引用六轴的条目作过程佐证，规则见 `main_axis.md` §2.4、§2.10、§2.11（2026-10-25 定） |

### 4.1 取值

轴级结论建立在逐条核对之上：每一条"在实际输入下本应产出什么"都要有自己的结果，轴级结论不能把它们盖掉（P4、P5）。

**每一条**：

| 值 | 含义 |
|---|---|
| 达到 | 实际产出符合本应产出的 |
| 没达到 | 实际产出不符合 |
| 无法核 | 材料不够，核不了；写清为什么 |
| 不适用 | 本应写的这一步这次没发生、也不需要（换了一条路办成了）；要拿出实际走的路的原文。该做没做不算，判没达到（2026-10-25 用户定） |

**轴级**：

| 值 | 标识 | 含义 | 后续动作 |
|---|---|---|---|
| 有问题 | `problematic` | 有归到本轴的问题 | 修本轴 |
| 看不清 | `not_evaluable` | 用到了，但有核不了的、或原因没定位的 | 补证 |
| 没问题 | `sound` | 核实过的范围内没问题 | 无 |
| 输入全坏 | `untested` | 本应用到这项能力，但每一次的输入都已被上游弄坏，本次对它没有结论 | 修上游；记评测覆盖缺口 |
| 不适用 | `not_applicable` | 本次不需要这项能力 | 无 |

五个值对应五种不同的后续动作，这是它们存在的理由。

轴级结论要带上组成（几条达到、几条没达到、几条无法核），不能只给一个值（P4、P5）。评测器自己没跑成不是上面任何一个值，记为运行失败（P6）。

## 5. 还没定的 ⟡

- ⟡ 六个轴本身是不是最合适的划分，不锁死；目前以这六个为准推进。
- ⟡ 引用的原文只证明原文存在，不证明它支撑结论。

## 6. 不要什么

- 不要为了区分 P1 给每个轴硬加一串故障类型，分不出"为什么是这几个"的枚举没有信息量。
- 不要用一个结论同时表达"能力如何"和"结果如何"。
- 不要让评测器自己的失败变成业务结论。
- 不要为了让汇总好看而改口径（例如把该判的问题改成不适用）。

## 7. 验收怎么看

- P1–P7 每一条，新方案的输出能让人一眼区分开，并且说得出为什么这样分。
- 用冻结样本做旧输出、新输出并排对照，由人核对是否准确表达了业务含义；不以通过率为目标。
- 2.1–2.3 三个角度各走一遍：能从轴汇总下钻到 case 问题，能从 case 问题回到 trace 原文，能把问题而不是整段说明送进聚类。
