# 2026-11-03 demand 修订草稿：按 trace 回放评测（只给 trace id，不调业务）（2026-11-03 用户确认，已并入正文）

起因：

- 现在每个 case 都要评测方现场调一次业务，拿到这一轮的输出和 trace。有些情况只有业务已经跑过的 trace：线上真实流量、没法从评测环境调用的系统、想复评某一次的结果。希望只给一个 trace id，评测方自己去 trace 平台把这一轮取回来再评。
- 2026-11-03 核实：
  - Langfuse 官方建议把整轮的请求和答复写在根步骤上（[Migrate ingestion to v4](https://langfuse.com/integrations/native/opentelemetry/migration-to-v4)：*"Trace input/output is deprecated. Use `langfuse.observation.input` and `langfuse.observation.output` on the root span instead."*）。这是推荐做法，不是强制要求（[Why are trace input and output empty?](https://langfuse.com/faq/all/empty-trace-input-and-output)）。
  - 本机实测 5 种常见上报写法：显式写 trace 级、根步骤写 Langfuse / OpenInference / GenAI 属性，这 4 种都能取到本轮的请求和答复；根步骤只是 HTTP 自动插桩、内容只记在模型子步骤里的，取不到。
  - Insurance 现场跑的 14 轮对比：用户原话 14 轮全部一致；交付有 6 轮在 trace 里被业务脱敏，`trace_id` 字段被业务改写过。trace 里记的交付，不一定等于用户实际收到的。

用户定（2026-11-03）：

- 做；按"如果做"的完整范围出方案。
- 无论加不加这个模式，已有的现场评测效果、效率都不变。

## 一、新增 `demand/trace_replay.md`

```markdown
# 按 trace 回放评测需求

> 状态：2026-11-03 草案（记录 `demand/draft-20261103/README.md`）。
> 上游：`demand/demand.md` 第 3 条、`information_sources.md`。标 ⟡ 的条目还没定。

## 1. 要什么

一个 case 只给一个 trace id：评测方不调业务，从 trace 平台取回这一轮（用户原话、对话历史、交付、过程记录），照常评。一个 case 对应一个 trace，评的是这一轮；多轮对话里前面的轮次只当这一轮的上下文。

## 2. 要满足什么

1. **现场评测不受影响。** 加了回放以后，现场跑的 case 发给评测模型的材料、提示词逐字不变，效果、效率不变。
2. **两种来源显式区分。** case 写明是现场还是回放，二者只能选一种；不按"有没有请求体"去猜。
3. **能不能回放由 trace 源自己声明。** 评测器只问"这个场景的 trace 源支不支持回放"，不认具体是哪一家平台。不支持的，回放 case 直接拒绝。
4. **取不到就不评，不猜。** trace 里没有记本轮的用户原话或交付，这个 case 记运行失败、不出结论；不拿内部步骤（如模型调用的输入输出）顶替。
5. **交付标明来源。** 回放的交付是"业务记录的交付"，不一定等于用户实际收到的；这一点随材料交给判卷，结论里看得见。不靠文字特征去猜记录有没有被脱敏、改写。
6. **记录靠不靠得住可以校准。** 同一个场景，可以用现场评测的结果对比"实际收到的"和"trace 记录的"，得出这个场景回放的一致程度。这个办法对任何业务都适用。
7. **不为回放改业务、不补埋点**（`information_sources.md` 要求 8）。业务记了多少就用多少；没记，就是这个业务不能回放。
8. **接入只需登记和配置，不写代码**（`information_sources.md` 要求 12）。trace 按业务的通行写法记录时，回放不需要额外配置。

## 3. 不做

- 不生成追问；只评 trace 里已经发生过的那一轮。
- 不把回放结论写回 trace 平台。

## 4. 还没定的 ⟡

- ⟡ **回放时"业务这次有没有正常返回"怎么判。** 现场看 HTTP 状态；回放时没有 HTTP，要从 trace 里判。
- ⟡ **校准是不是门槛。** 倾向：不做门槛，允许回放；没校准或一致性低的，结论里标出来。
- ⟡ **多轮历史从哪来。** trace 里本轮的请求带着历史就用；不带（业务在服务端存历史）时，从同一会话更早的 trace 拼。

## 5. 验收怎么看

- 现场模式：同一批固定输入，改前改后发给评测模型的材料、提示词逐字节一致；现有测试全过；8036 回归结论与效率和改前持平。
- 回放模式：拿已经现场跑过的 case 的 trace id 回放，和现场结论对照，一致或差异说得清（差异主要应来自交付记录与实收的差别）。
- 不支持回放的 trace 源、trace 里没记本轮请求或答复的，都明确拒绝或记运行失败，不当成通过。
```

## 三、不改

- `information_sources.md`：回放是"取得这一轮"的另一种办法，不是新的信息源。trace 照旧是信息源，要求 2（关联精确）、8（只为关联改业务）、12（只登记）都不变，新需求直接引用。
- `business_trace_langfuse.md`：不变。Langfuse 支持回放，是方案层的事。
- 评估轴、主轴、真实性等需求：不变。回放不改判法。

## 四、方案另记（写进 spec）

- trace 源以可选能力的形式提供回放，和现有的"投递前要发什么头"同一种写法。Langfuse：原话和交付优先取根步骤，没有再取 trace 级。
- 框架 live 协议里，"不调业务、用给定产出"的路径从项目级开关改为按 case 选。这是协议改动。
- 现场模式不变的做法：没带回放标记的 case 走原来的代码路径；回放来源只写在回放 case 的材料内容里，不改材料的通用说明。
- 服务端、前端：试取回放、校准、候选区按 trace id 生成 case、结果里标明来源。

## 五、已知局限

- 能不能回放，取决于业务有没有按通行写法记录本轮的请求和答复。目前只在 Insurance 和本机模拟的 5 种写法上核实过。
- 回放评的是业务记录的交付，证据比现场弱一档；Insurance 的记录有脱敏和字段改写。
- 现有 Langfuse 读取代码里写死了几个脱敏、截断标记的字符串去匹配，属于已有的过拟合，另记，本次不动。
