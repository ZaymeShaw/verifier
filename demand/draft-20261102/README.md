# 2026-11-02 demand 修订草稿：业务 trace 关联默认走行业标准（W3C Trace Context）（2026-11-02 用户确认，已并入正文）

起因：

- 想在不同场景里都能接 Langfuse 的业务 trace。现在的关联方式是评测方给一个自己的标识，业务把它写进 trace 的指定字段，评测方再按这个字段查。这要求每个业务都为评测改一处；Insurance 能用，是因为评测分支上专门加过这一处（`e433d80d`）。业务一多，挨个适配做不过来。
- W3C Trace Context 是行业通用标准：调用方在请求头 `traceparent` 里带上 trace 标识，按标准接入的业务会沿用它记录本轮。2026-11-02 实验（`scratchpad/w3c_exp/`）：按标准接入的最小业务，Langfuse 里本轮 trace 的标识就是评测方发的那个，按它直接查得到；现有 Langfuse 读取代码不改就能采全。现在的 Insurance 不沿用这个头（实测查不到），要换成标准做法。

用户定（2026-11-02）：

- 关联默认走 W3C：业务只要支持这个标准就能接入，不需要专门适配。
- 指定关联字段的办法保留，作为可选，用在不支持 W3C 的业务上。
- 本次只做 Langfuse 信息源；Agno、模型中转（llmtracing）的关联方式不动。Agno 有自己的 run 标识，不靠 W3C。
- 发不发 W3C 标识跟着信息源的登记走，不放在各个场景里。
- Insurance 评测分支换成标准做法，仍按 rebase 方式管理。

## 四、需求不改，方案另记（写进 spec）

- Langfuse 信息源登记默认按 W3C 关联。默认方式下，评测方每次请求在头里发一个新的 `traceparent`（采样位为"要记录"），按它的 trace 标识直接查本轮 trace，场景里不用配取标识的位置。
- 指定关联标识的方式保留：场景里写明标识从请求或响应的哪里取，按 trace 里记的这个字段查。这种方式下不发 `traceparent`。
- 业务根节点的上一级是评测方发出的那个标识时，读取时把它当成根，不算记录不全。
- 涉及的代码层、Insurance 评测分支怎么换、8036 实例数据怎么改，都写进 spec。

## 五、已知局限

- 业务自己按比例抽样时，本轮可能根本没记录。按要求 1 记"没采到"，不猜。
- "支持 W3C"指两件事都做到：业务入口沿用请求头里的标识，并且上报 Langfuse 时用的是同一个上下文。只用了 Langfuse 的装饰器、入口没接 OTel 的业务，不算支持，要走指定标识的方式。按 Langfuse 官方 SDK v3 加自动插桩接入的业务能不能自然沿用，还没实测。
- 用 Agno 自带 tracing 的业务，根节点沿用外部标识后，Agno 可能不再把它当根来建索引（读 Agno 3.0.6 源码得出，未实跑）。所以本次只对 Langfuse 信息源发 W3C 标识。
