> 上游：`resources-pilot.md`（P1，已做完）、`spec/alg/resources.md`、`axis_loop.md` §3.4 第 2 条（引用只有一种规则）。

## 1. 起因

P1（离线复核，结果见 `report/resources-pilot-20261104/README.md`）：

- 过程六轴（实际）910 条引用，现有核对误拒 102 条（宽松口径；严格口径 81 条），换成资源核对后消掉，真错误 2 条照样拦下。
- 资源是最小引用单位（记录是直接资源，字段是模板资源 `<记录地址>/fields/<字段名>`）。原文在所引资源里找到就过；但引用都写在记录这一级，有 173 条命中好几个字段，分不清引的是请求还是返回。

提交点重放（只改对话副本，`report/resources-pilot-20261104/replay.py`）：

| 改法 | 结果 |
|---|---|
| 只在引文规则里说"可以写到字段" | 0 条写到字段：提交格式里还写着"只写编号" |
| 再改提交格式 | 模型照抄材料里字段自带的来源 `ref`（`…/10/input`），11 / 35 条地址不存在 |
| 再从材料里去掉字段来源 `ref` | 第一次提交 22 次：71% 的引用写到字段，跨字段从 16% 降到 6%，地址写错 0；抽 20 条人工看，字段都选对了 |

后续提交不受影响：对话里留着模型自己的老写法，重放测不出来。

由此可见：**材料里同一个字段有两种长得像地址的写法**（来源 `ref` 和资源地址），违反"一件事只给一份"。字段来源 `ref` 是程序内部用的（取值、按来源去重、证据编号），不是字段的名字（如字段 `end_time` 的来源是 `…/endTime`）。

## 2. 目标

过程六轴（实际）的引用以 trace 资源为唯一来源：出处写记录或字段，核对拿资源本身比，范围按侦探分发。

要回答的问题：

1. 第一次提交写到字段、跨字段减少的效果，在用新代码真实渲染的材料上还在不在；
2. 地址写错、原文找不到会不会变多（尤其是材料展示和资源原文还有出入的地方）；
3. 被动受影响的过程六轴（本应），结果会不会变；
4. （隔离实例真跑时）后续提交、最终结论、成本怎么变。

## 3. 原则

1. **引用一律写资源地址**（长期目标，写进 `spec/alg/resources.md`）。**这次只做 trace 记录与字段**；环节、各轴产出、工具返回、知识库原文等，每一类以后单独决定、单独迁，不被这次带着迁。
2. **资源是最小引用单位**：原文在所指资源里出现即过，出现几处都算过，如实报出各处在哪、是什么角色；一条引用够不够撑结论由使用方判（P2 之后定）。
3. **读的与核的是同一份**：材料里展示的字段内容与资源原文一致；不一致的地方是展示层的问题，修展示，不在核对里迁就。
4. **资源层不管"读没读过"**：写出逐字的原文本身就是读过的证明；资源层只回答资源在不在、原文在不在、在哪、是什么角色。
5. **引用范围按侦探分发**：本轴能引的是侦探分发给本轴的记录（`views[axis].full`：本轴环节两端、侦探指出的、侦探从别轴借给本轴的）；没分发的不能引，并在提示词和被拒原因里说清楚。
6. **一件事只给一份**：材料里不再出现长得像地址、却不是地址的写法（字段来源 `ref`、与 `id` 重复的记录属性 `ref`）。
7. **资源是源数据的一种组织，组织方式登记在资源层**（符合 MCP：资源把文件、API、数据库等来源的数据按提供方定的形状、用 URI 提供出去，例如官方 Postgres 服务把数据库元数据组织成每张表一个 schema 资源）。同一份源数据可以有几种组织方式，每种是一个登记的类型、一套自己的地址；类型复用资源层的通用工具（转文本、找原文、切字段），不各写一份。这次只登记 `case_trace`：信息源交的原样快照 → 信息源自带的翻译器（`open_reader`）读成统一记录 → 按 case 整理成案卷，每条记录一个资源；每个资源在 `_meta` 记出处（在原样快照里的位置），以后登记偏源数据的类型时据此对应。偏源数据的类型等用到再登记。
8. **资源挂在材料上**：哪份材料提供资源，由材料登记时自己声明；框架在启动检查（取内置材料，取不到整个 case 运行失败）时把资源一起挂进这个 case 的资源表。资源与材料同生同灭，不新增依赖：过程轴硬依赖侦探、侦探白名单读 `case.trace`，都是现有的。
9. **资源的存在与可见分开**：资源表是这个 case 的全部资源；交给校验的只有本任务可见的那部分——本任务按白名单裁剪后的材料里出现的记录（记录 `id` 等于资源 `name`），记录可见则其字段可见。所以"引用范围按侦探分发"（第 5 条）由白名单自然得到，不在各轴另算；校验仍只看得到白名单里的东西（`axis_loop.md` §3.4 第 3 条）。

## 5. 实验

### 5.1 怎么做

- **改动在副本里真改**（§4），不是替换对话文本。分三步，前一步过了再做下一步：
  1. **只搬家**（`case_trace` 接管组织、材料挂资源，引用规则不动）：22 条 run 的各轴材料、读取工具返回与搬家前逐字节相同；`render_value` 深度 8 → 16 单独算，列出变了哪些。
  2. **加可见性**：框架算出的每个任务的可见资源，与复核脚本的严格口径（侦探分发）逐条一致。
  3. **引用改动**（§4 的 ④ 与材料去 `ref`）：按下面重放。
- **用新代码重放第一次提交**：取 8037 那 22 条 run 存下的同一份 trace，用新代码重新生成那次请求的上下文——推送按新代码渲染，当时模型调过的读取（同样的 ids）交给新代码执行得到新返回——发给当时同一个模型（gemini-3.8-flash-medium）一次，模型的工具调用不执行，取它的提交用新代码核对。
- 样本：过程实际 22 次 + 过程本应 22 次（各 run 的第一次提交）。不同 case 之间可并行，同一 case 内串行。
- **噪声基线**：同一批请求用**老代码**原样再重放一次，量出模型本身的波动；新老差异要和这个波动比，不能只和当时的老提交比。
- 规则文字、地址写法在实验前定好，不按结果回头改；结果不好先报原因再讨论。

### 5.2 对照

- 老提交（当时实际交的，按新 `cite` 核）；
- 噪声基线（老代码再重放一次）；
- P1 之后第③种重放（只改对话副本）的结果。

### 5.3 看什么

| 指标 | 说明什么 |
|---|---|
| 写到字段的比例、跨字段比例 | 问题 1 |
| 地址不存在、原文找不到、不在本轴材料里的条数 | 问题 2；"找不到"逐条看是不是展示与资源不一致 |
| 引用条数、提交条数 | 有没有交少 |
| 过程本应：期望清单与老代码基线的差异 | 问题 3 |
| 材料字符数变化 | 去掉 `ref` 后的长度 |

### 5.4 怎么算有效（⟡ 待定，草拟）

1. 过程实际第一次提交：写到字段 ≥ 50%，跨字段 ≤ 10%；
2. 地址不存在 + 原文找不到（真错误除外）不多于噪声基线 + 2 条；
3. 过程本应：与老代码基线的差异不超过噪声基线自身的波动；
4. 引用条数比老代码基线少不超过 30%（超过就逐条看是不是该引的没引）。

### 5.5 实验说明不了的

后续提交、最终结论、成本、对其他轴的影响 → 有效后在隔离实例上真跑 22 条 case、全部轴，新老各一遍，结论翻了的逐条看谁对；不该受影响的轴结论比对一致。
