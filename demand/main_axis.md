## 1. 要什么

评测对每个 case 给一个最终结论，回答一个问题：

**用户（和下游）这一次要的结果，被测系统给到了没有；没给到的，系统正常工作时本来能不能给出。**

给谁用：

| 谁 | 拿来做什么 |
|---|---|
| 业务开发 | 找出该修的 case；没做成的触发归因（`demand.md` attribute） |
| 产品 / 业务方 | 看哪些是系统做不了的，决定要不要补能力、补数据 |
| 评测方 | 看哪些判断不了，补材料；看期望、核事实有没有出错 |
| 跨 case 汇总 | 统计被测系统办成了多少、没办成的各是什么原因 |

## 2. "给到了"是什么意思

用户要的结果，在交付里有，并且是对的。用户要什么以 `expectations.md` 为准。

1. **要的是结果本身，不是态度。** 用户要一个值、一段条款、一份名单、一个办理结果，交付里就得有它。如实说查不到、无法确认、请用户补充信息、反问澄清，都不是给到；如实、礼貌、没编造都不能让它变成给到了。信息源里确实没有，也一样不算给到。（2026-10-19 用户定）
2. **用户问的是"有没有、能不能"时，答复本身就是结果。** 答复属不属实，看核事实。
3. **场景描述里"拿不到时怎么做"的要求，不能替代结果。** "信息缺失应如实说明""应发起澄清""不得编造"是系统的行为规范，至多是附带要求，不能把结果本身挤掉。
4. **对不对以场景配了的证据为准，有什么用什么，配了的都要过。**（2026-10-25 用户定，取代"只以核事实为准"）
   - 每条期望在定下时就写明：除了交付、用户原话、场景资料之外，判它对不对还需要哪类证据（`expectations.md` §4）。写法是"几组之间或、组内与"，例如"知识 或 trace"；不需要额外证据的写空。
   - **知识**：以 `claims.md` 的核事实结果为准。
   - **trace**：以过程六轴对这一条的逐条结果为准（**过程佐证**）：用户要的值是系统按对的对象、从它自己的数据里取到、如实交到用户手里的。这说明业务按需求做了，不说明数据本身对不对，结论里要写明是过程佐证、不是独立核实。
   - 某一组要的证据场景都配了，这一组就可用。**可用的组都要过**才算给到了；一组可用的都没有，这一条就是不确定，并写明缺哪一类。按场景配置定标准，不在单个 case 里因为某类证据没核成就改用别的（2026-10-25 用户定）。
   - 被测系统自己的说法不算依据。评测模型可以用通用常识（算术、单位换算、公认的常识），业务事实（保费、条款、产品规则、某个对象的属性）一律不能凭评测模型自己的知识认定；哪些是业务事实，在定期望时就标好（2026-10-25 用户定）。
5. **交付里的事实都要属实，用户没问的也算——作为一条隐性期望。** 用户要的事实被信息源否定 → 没做成；核实不了 → 不确定（2026-10-14 定）。用户没问、回答顺带说的事实，不再直接挡结论（取代 2026-10-20 的"附带说法错 / 查不到也挡"）：用户除了点名的几样，还要一个靠得住的回答，所以每轮固定有一条隐性期望"回答里说的事实都正确、不误导"，和其他期望一样由兑现判达到没有（2026-10-25 用户定）。这条隐性期望看的是和本轮用户要办的事有关的说法：本轮其他期望涉及的对象和事项，用户没点名问、回答顺带说的也算；和用户要办的事无关的说法，对不对、核不核得了，都不影响它。相不相关由兑现看着期望和回答定，不按说法的类别写死。（2026-10-28 用户定）
   - 它挡不挡结论看这次错成什么样：错一句无关紧要的，和错一句会误导用户办事的不一样，定期望时看不到回答、判不了。所以每条期望的 blocking 有三种：挡、不挡、**待定**（空）。待定的期望没达到时不决定结论，做成 / 没做成都算对，但结论里要列出"待定项没达到"及原因，让人看得到（2026-10-25 用户定）。
6. **值对了、单位核实不了，不算给错。** 一个数的值和它的单位、币种、时点是不同的事实，各有各的核事实结果（`claims.md` §2.3）；值核实了而单位核实不了，不挡。（2026-10-20 用户定）
7. **值对了、格式没照做，不算没给到。** 如要求"只回答金额"却答了整句，值对就是给到了；格式是另一回事。（2026-10-20 用户定）
8. **编造的比如实说没有更差。** 对象已查实不存在，回答却给了值，是给错了，不是没给到。（2026-10-20 用户定）
9. **用户要几样，就看几样。** 每一样给到没有都要能单独看到；一样的结论只受和它有关的事实影响，不被别的事实牵连。
10. **蒙对的不算对，过程像样但被证伪的也不算对。** 知识核实了值对、过程却表明这个值不是查来的（没查、查错对象、模型自己写的），不算给到；过程每一步都像样、知识却表明值不对，同样不算给到。两样都配了，两样都要过（2026-10-25 用户定）。
11. **交付的值没有来源，是给错了。** 过程表明交付的值不是来自系统取到的数据（编造、查错了对象、传丢后自己补的），判没做成，同 §2.8（2026-10-25 用户定）。

## 3. 最终结论有哪几种

| 结论 | 含义 | 谁拿它做什么 |
|---|---|---|
| 做成了 | 用户要的结果都给到了，且有依据；注明依据档位：独立核实（知识）、过程佐证（trace）、只凭交付（不需要额外证据的那几样） | 不用动 |
| 没做成 | 没给到或给错了，而系统正常工作时本可以给出 | 业务开发修；触发归因 |
| 做不了 | 没给到，且有独立依据表明系统正常工作时也给不出 | 产品决定补不补；不算本次故障 |
| 不确定 | 材料不够，判断不了给到没有、对不对 | 评测方补材料 |

四个值对应四种不同的后续动作，这是它们存在的理由。

1. **被测系统是一个整体。** 智能体、工具、数据、下游服务都算被测系统；最终结论不替系统区分是哪一块的责任，那是过程六轴和归因的事。（2026-10-20 用户定）
2. **"做不了"按系统正常工作时能不能给出来分。** 能力里本来没有、数据里本来没有，是做不了；这次服务出错、没取到、数据在却没拿到，是没做成。外部服务出错不改变"没给到"。（2026-10-19、2026-10-20 用户定）
3. **"做不了"要有独立依据。** 依据只有两处：业务方登记的责任范围（`information_sources.md` §1.2；`rule.md` 评估责任边界），或评测方从信息源查实"这个对象 / 这一项本来就没有"。被测系统自己说"做不到、查不到"不算依据；trace 里系统自己查了说没有，同样不算，只靠 trace 不能判做不了。（2026-10-20 用户定；2026-10-25 补）责任范围写在场景的承载性框里（`axis_loop.md` §3.7）：框里的原文就是登记的责任范围，承载性可以逐字引用它作依据；所以框里只写责任范围的事实（不接哪类数据、哪些要求不由本系统负责），系统自称能做什么写进场景总述，不写进这个框。（2026-10-27 用户定）
4. **没有依据区分时，只有三种结论。** 没登记责任范围、也没查实的，没给到就是没做成，并注明"能不能做没区分"；不能因为区分不出就改成不确定。（2026-10-20 用户定）
5. **不确定只用于材料不够。** 没给到是确定的、只是分不清能不能做，不是不确定。
6. **命中预先维护的错误码，不出结论。** 每个场景事先维护一份"调用失败"错误码（HTTP 状态码、响应体里的错误码字段取值）；返回命中其中之一，这条 case 记运行失败，不是上面四个值中的任何一个，不进统计。没命中的返回——包括没登记的非 2xx——一律照常进入评测流程。没维护错误码的场景，没有返回会被判为调用失败。与第 2 条不同：第 2 条是系统给了答复、只是内部某个服务出错没取到，那仍是没做成。（2026-10-22 用户定）

## 4. 结论要满足什么

1. **唯一、可复算。** 同一份交付、同样的期望和核事实结果，结论唯一；不随评测走哪条路线、用哪个信息源来源而变。
2. **每个结论都有依据，依据能回读。** 给到 / 没给到能指到期望条目、交付原文和核事实结果；做不了能指到登记的责任范围或信息源原文；不确定写清差在哪、缺什么材料。
3. **能看出结论是怎么来的。** 哪几样给到了、哪几样没给到、哪些是被顺带说的事实挡的、哪些分不清能不能做，都要能从结论里读出来，不只给一个值。
4. **评测器自己失败不是结论。** 超时、出错、输出不合法，与"材料不够"分开记（`information_sources.md` §4.7）：评测器没跑成时不出上面任何一个值，记为运行失败。

## 6. 不要什么

- 不把"区分不出能不能做"当成"不确定"。
- 不把被测系统自己的说法当作"做不了"的依据。
- 不让评测模型自己的知识替代核事实结果。
- 不把态度、格式、行为规范的满足当成结果给到了。
- 不为某个 case 写专门的判法；判法从本文推出，案例只作验收。

## 7. 还没定的 ⟡

1. ⟡ **只给到一部分时，最终结论怎么说。** 用户要几样、给到其中几样：最终是一个值还是分项各一个值；若是一个值，怎么汇。§4.3 已要求分项可见，这里只差汇总口径。
2. ⟡ **有依据来源、但仍分不清能不能做时，结论是什么。** 倾向：没做成，注明能不能做没分清（与 §3.4 同口径）。
3. ⟡ **"数据本来没有"的依据要多强。** 评测方按该对象查过一次就够，还是要业务方声明数据是全量的。

## 8. 验收怎么看

- 用人工核定的评测集对照；不该做成判了做成（误放行）单独计数。
- 同一份交付、同样材料，在不同评测路线下结论一致（M3）。
- 每个"做不了"都能指到依据；没有依据的"做不了"为 0。
- 每个"不确定"都写清缺什么。
- M1–M9 在新实现下都不再出现。
- 每个"做成了"都能看出依据档位；过程佐证的能指到它引用的六轴条目。
