# 第一章：协议标准

## 1. 我们在评什么

三个角色：

- **被测系统**：业务系统，一次运行留下一条业务 trace；
- **消费者**：业务系统开发者（决定修哪里，分清功能问题与算法问题）、评测方自己（解释主轴为什么没办成）；
- **我们**：过程六轴。

六轴对被测系统的六项过程能力各下一个结论。每个 case 每个轴产出两样东西：

```text
verdict   这项能力本次如何（枚举，可跨样本汇总）
reason    归到这个轴的问题，每条带 trace 依据；以及本轴的组成（几条达到、几条没达到…）
```

两样东西分别服务需求里的两类用途：verdict 服务"看整体哪项能力好哪项差"（需求 §2.1）；问题服务"看单个 case 出了什么"和"把问题聚类"（需求 §2.2、§2.3）。**一个值不同时表达两件事。**

## 2. 判定单位：本应清单里的一条

每个轴、每批材料，判定者先写出**本应清单**，再逐条写**实际**。判定单位 = 本应清单里的一条。

### 2.1 子能力从哪来

部件与"输入 → 输出"的定义见 `demand/process_axes.md` §1.1（各轴部件表、子能力的生成规则、一个事件可属多个轴）。本协议按它生成子能力：子能力 = 输出里必须保住或产出的每一个方面，不手列；§8 逐轴推一遍。

子能力是写本应清单时的**提纲**：每条本应标一个子能力；不再按"子能力 × 每一次行使"展开成网格。

**环节按轮排序装批，需求按轮对号。** 程序先定每个环节属于哪一轮（跨轮的环节归较晚的一轮，只引用共享正文的表外环节归该正文最早出现的一轮，单轮 case 即第 1 轮，多轮 case 算不出轮次是评测器错误），按轮次排好再按材料大小切批；一批可含几轮，批次记下含哪几轮。每批只拿**它含有的那几轮**的需求（E 中轮次属于这几轮的条目及其出处），每条需求带轮次。本应清单每条标所属轮次（必须是本批含有的轮，否则纠错），只依据同一轮的需求和该轮材料写，不拿一轮的需求去要求另一轮的材料。否则第 1 轮的材料会被拿去对第 2 轮的需求（用户第 2 轮改口时成片冤判）。依据 `report/multiturn-needs-20261012/`：实验 3–4 一批一轮后串轮条目 13 → 0；实验 9 几轮合批、需求按轮标注后未见串轮条目，多轮批数 150 → 96（与不分轮时相同）；单轮 case 的分批不变。

两次调用的分界就是 §1.1 的"输入 → 输出"：程序把本轴各环节（部件实例）的输入端字段交给第一步，输出端字段到第二步才给。第一步看不到任何输出端字段，这是材料切分保证的，不靠判定者自觉。

### 2.2 本应从哪来、实际里多了什么（需求：两条来源都要）

- **从需求和输入写本应**：第一步拿到本轴输入端材料、需求清单 E（`spec/alg/expectations.md`）、子能力提纲和场景写的过程职责（§3.4），写"在这样的输入下，做对时必须成立什么"。要求系统**应该发生**的动作（例如必须取数），按四问写：
  1. 要满足它，需不需要外部数据（依据需求本身、时效和任务性质，不能由"有工具"推出）；
  2. 系统有什么办法拿到（读设计原文中的工具说明，只证明候选办法）；
  3. 当时是否仍必须行动：已满足（有效数据、缓存、等价路径）则不写；必须做则写成一条本应；说不清则写成一条本应并标"必须独立查证"。
  4. 实际做了没有——留给第二步判。

  完整定义见 `spec/alg/expectations.md` §6.2。
- **从运行里召回**：第二步拿到输出端材料（含分析轴标出的可疑点），除了逐条判本应，还把本应清单没料到、但实际发生的行为写成"意外"（多调了不该调的、改措辞重复查询、交付覆盖了模型产出等）。

没有第一条来源，"该做没做"看不见；没有第二条，清单没想到的问题看不见。

## 3. 一条怎么判

### 3.1 唯一的对照

```text
实际产出了什么   vs   在它实际拿到的输入下，本应产出什么
```

"本应"相对于**实际拿到的输入**。理由：verdict 评的是能力，一次行使只有在输入有效时才说明这项能力；输入已经坏了，这次说明的是上游。这条对照是全协议唯一的归属规则，六轴共用，各轴义务文本里不再各写归属分句。

### 3.2 一条的取值

| 取值 | 什么时候 | 后续动作 |
|---|---|---|
| 达到 | 实际符合本应；至少一段对得上的引文证明它，引不出就是无法核（10-27 定） | 无 |
| 没达到 | 实际不符；写归因方向（§3.3） | 归本轴的产生一条问题；归上游、未定位的见 §3.3 |
| 无法核 | 看不见产出、证据不足，或这条必须独立查证（第一步标"必须独立查证"的，trace 只证明不了"没做是错的"：判没达到的由程序锁成无法核；trace 里看得到做到了的照判达到。llm_probe_loop 改为提交时打回、模型自己改判，10-27，`axis_loop.md` §12.4） | 补证 |
| 不适用 | 本应写的这一步这次没发生，也不需要——系统换了一条路办成了（例如走直达工具、没调大模型）。必须引原文说明实际走的路，没引文或引文对不上的降为无法核；该做没做不是不适用，判没达到。第一步看不到实际走了哪条路，这一值让"未发生 → 不进清单"在第二步落地：程序把它移出逐条结果（列在组成的 not_applicable 里），不计入轴级、不进兑现；全部条目不适用时轴级为 not_applicable（2026-10-25） | 无 |

原先的几种取值去向：

- 输入无效 → 没达到 + 归因"上游:\<轴\>"。
- 缺证 → 无法核；产出不符但不知道怪谁 → 没达到 + 归因"未定位:\<候选轴\>"。
- 缺判准 → 不进清单；第一步写不全、拿不准的放 `not_covered`。
- 未发生 → 不进清单。应发生而没发生的，本身就是一条本应（§2.2），判没达到并按证据写归因，不预设责任方。

### 3.3 归因

没达到的每一条写归因方向，三选一：

- **本轴**：这个部件在有效输入下做错了。
- **上游:\<轴\>**：它依赖的输入已被上游弄坏；不算本轴问题。只作用于依赖那份输入的那一条：模型输入丢了提示，"输出忠实"可以归上游；但模型同时编了一个输入里没有的数字，"不编造"不依赖那份提示，照判本轴。
- **未定位:\<候选轴\>**：看得出结果不对，说不清是哪一段。

不强制指向一条已记录的上游问题（2026-10-11 用户确认；实测 8 个 case 两遍归上游 5/122 条，逐条核对无误；样本小，继续观察）。同一事件允许多轴各记问题，不去重：工具把别的保单标成目标返回（工具轴没达到），目标保单在库里也确实没有（知识轴没达到），两条问题。同一轴内同一问题只记一条。

剩余缺口说清楚：归上游时，我们不知道这个部件在正常输入下会不会做对。协议不假装知道，记成"未检验"（§5）。

### 3.4 本应的依据

每条本应自带依据（`basis`）：输入里的原文片段或记录编号。依据有三种来源：

| 来源 | 例子 | `basis` 写什么 |
|---|---|---|
| 场景过程职责 | 配场景的人为本轴写的职责（`axis.note`，`spec/alg/axis_loop.md` §2.5），判定者写成本 case 的具体条目 | 职责原文 |
| 需求 | 需求清单 E 中适用的条目 | E 的编号或原文 |
| 设计规则原文 | 业务模型收到的系统提示词中"输出 JSON：answer_draft 必须是首字段"；某个工具的说明 | 记录编号或原文片段；条件、例外在别处时一并引 |

没有所有场景共用的固定职责：轴定义里只写对任何被测系统都成立的子能力；只对某个被测系统成立的要求（它自己的字段、提示、状态值），写进该场景本轴的过程职责，和需求、设计规则一样按本次材料写成具体条目，涉及几轮写几条，本次不涉及就不写。

设计规则**不进需求清单**，是判定时的证据。能用在哪一步，按轴区分：

| 轴 | 能用的设计规则 |
|---|---|
| 模型能力 | 只能用该次调用**实际收到的**规则；没收到的规则不能拿来判它违约 |
| 上下文传递 | 比较**本该送到的**与**实际送到的**；本该送到而实际没有，就是漏传 |
| 工具执行、规划 | 已确认适用于**这一次执行**的规则（来源、角色、版本对得上） |

设计原文由程序按步交付、每段只交付一次（优先该步实际收到的那份）。只有采集时定义、没有实际收到的那份时，只能作参考，不能单独认定违约或漏传；原文中的数据、示例不是规则；引用原样完整（不截掉范围词、条件、否定）。判定者挑漏规则不靠它自我声明来防，靠独立审阅与对照样本发现。完整定义见 `spec/alg/expectations.md` §6.3–§6.5。

## 4. 输出结构与问题记录

第一步：

```text
expected:    [{id, about, subcapability, statement, basis, expectations, needs_external}]   至少一条
             expectations：这条做错了，会让哪几条需求没给到或给错（只写会被它直接影响的；都影响不到时为空）。兑现按它强制引用过程条目（漏挑即退回），所以填的是"影响谁"，不是"照着谁写的"（2026-10-29）
             怎么拆按唯一性原则（`demand/axis_loop.md` §3.8，一份只装一件事），写在 loop 系统提示里，本应说明不另写（2026-11-01）
             statement 写这一步必须成立什么（要拿到哪项数据、交付里要有什么），不写"如某某调用"这类实现猜测；材料写明由哪个工具负责时才点名工具
not_covered: [string]                                                          写不全、拿不准、本次看不到的范围
```

第二步：

```text
actual:      [{id, links, observed, quotes: [{ref, quote}], verdict}]   id 与本应清单一一对应，不得增删改
unexpected:  [{id, observed, links, quotes, why}]                        清单没料到、实际发生的行为
problems:    [{phenomenon, items, attribution, impact}]                  items 只能引用没达到的条目或 unexpected
reason       给读者的本轴说明（写法见 §5 末）
scope_note   这次没覆盖到的范围
```

**引文规则**：

- verdict=达到、没达到、不适用的行和每个 unexpected 至少一段逐字短引文 `{记录编号, 原文}`（一般 40 字以内，只摘支撑结论的那一句，不改写、不用省略号拼接）；要靠两处对比才看得出的（上游写了什么、下游变成了什么；前一次请求与后一次请求里的同一句），两处都引。达到也要引（10-27 定：之前"达到引文可选"，trace 里看不见的事也能判达到，例如后端返回内容没记却判"返回与请求一致"）。
- 程序逐段核对引文确实在所引记录里（去空白后逐字包含）。不在的，作为新一轮消息退回重写一次；仍不在的引文丢弃；达到、没达到、不适用的行丢光引文的，降成无法核。llm_probe_loop 里不在的引文一直打回到改对为止，不丢、不降（10-27，`axis_loop.md` §12.4）。
- 程序按引文所在记录给每条问题补 `refs`。

**问题记录**（需求 §2.2、§2.3 的成员单位）由 problems 生成：

```text
轴 / 子能力（取所引本应条目的 subcapability） / 环节（links）
预期（所引本应条目的 statement + basis） / 实际（observed + 引文）
归因：本轴 ｜ 上游:<轴> ｜ 未定位:<候选轴>
影响：对最终交付的影响（impact）
来源：本应清单（items 指向本应条目） ｜ 运行召回（items 指向 unexpected）
```

问题是聚类的成员单位（需求 §2.3），不是整段轴级 reason。已知局限：引文只证明原文存在，不证明它支撑结论（需求 §5 ⟡）。

## 5. 轴 verdict

verdict 回答"这项能力本次如何"。对本轴所有条目与问题汇总，取第一个成立的：

| verdict | 条件 | 含义 | 后续动作 |
|---|---|---|---|
| problematic | 有任一归本轴的问题（来自没达到或意外） | 有归到本轴的问题 | 修本轴 |
| not_evaluable | 否则，有任一无法核，或有归因"未定位"的没达到 | 用到了，但看不清 | 补证 |
| sound | 否则，有任一达到 | 已核实范围内没问题 | 无 |
| untested | 否则，有归因"上游"的没达到 | 本应用到，但每一次的输入都已被上游弄坏；本次对这项能力没有结论 | 修上游；记评测覆盖缺口 |
| not_applicable | 否则（清单为空，或只写了本次不需要） | 本次不需要这项能力 | 无 |

五个值对应五种不同的后续动作，这是它们存在的理由。untested 不是"没问题"，是"没测到"，在六个轴上都成立（历史没注入则指代解析未检验；没发查询则数据能力未检验；输入被弄坏则模型未检验；预算拦截则执行未检验）。

**verdict 永远和组成一起出，组成是输出的一部分：** 几条达到、几条没达到（各归本轴 / 上游 / 未定位）、几条无法核、几条意外、`not_covered` 几项。这是 P4（problematic 盖掉看不清的项）和 P5（sound 被读成全部核实）的解法：不加枚举，不丢组成。

**轴级说明（`reason`）怎么写**（2026-10-29）：让读的人只看这一段，就知道本轴在这个 case 里哪里出了问题、是什么问题、为什么算问题，或者为什么没问题——目标是 `基于评测系统的ai递归自迭代体系探索-v6.pptx` 第 7 页"问题①②"的信息量。
- 有问题：每个问题一两句——第几轮、哪一步；原文里看到了什么（引最关键的一小段，加引号）；违背了哪一条本应；对用户要的结果造成了什么。上游带下来的，写明来自哪个轴的什么问题。
- 核不了：哪一件、为什么（缺什么材料）。
- 没问题：核了哪几件关键的事、凭哪段原文。
- 不复述计数（程序给）；不写原文撑不住的概括；条目里没判过的事不写。

曾试过由程序按问题与条目拼（10-29 当天）：条目的 observed 多半复述本应（用字重合中位 0.86），拼出来"达到 8 项：……"没有信息量，撤回。离线试模型按上面写法写：E01 能写出"意图漏了客户资料 → 规划只走直连 → 交付缺客户资料"且每步带原文，F01 写出最终答复漏内部字段、多余追问（与"意外"条目一致）。

归因未定位（P2）的汇总后果：两个轴都落 not_evaluable，问题记录归因写"未定位{工具, 知识}"。一个问题不会同时抬高两个轴的缺陷率。相应地，不变量从"结果坏 ⇒ 至少一轴 problematic"改为"结果坏 ⇒ 问题列表里至少一条记录"。

## 6. 评测器自身的失败

模型没给出合法输出、超时、预算耗尽，是评测运行的 error，记在运行状态上，**不进条目取值，不写成无法核**（需求 P6、§2.4）。

## 7. 主轴

主轴（扩展轴 fulfilled）最终基于六轴综合判断，方向已定（需求 §4），规则与启用时机另行约定。本文不定义。

## 8. 子能力逐轴推导

按 §2.1 规则，从各部件的输入 → 输出推子能力，对照现有义务：保留的注明对应，删除的说明原因。

**意图理解**（用户原文 → 内部表达）。原文里有五样东西必须被表达保住：对象与字段、子问题、约束、指代、不确定性。第 N 轮的内部表达 = 第 1..N 轮的全部步骤产出、交给 Agent 的任务、各次模型调用发出的工具调用；不能只看本轮首个步骤与首次决策——依赖前一步结果才能发出的查询（先查到客户再查保单）必然不在首次决策里，只看首次会把它判成遗漏（实验 5、7a）。
→ 对象与字段一致、子问题均识别、约束保留、指代解析、歧义识别。现有五条全部对应，保留。

**规划路由**（任务 + 状态 + 规则 → 决策）。输出是一组决策，每种决策都要与输入一致：选路径、给每个子问题安排工作、分支、失败后的动作、重复调用、工具返回后的整合、收尾、系统自身策略。
→ 路径选择、工作覆盖、分支按声明条件、失败分支有产出、重复调用有依据、工具返回后的整合与交付、结束时机、系统策略。现有八条对应。`decision_matches_rule` 保留为"表外决策"的兜底形式。

**工具执行**（调用参数 → 返回）。返回必须：执行完成、就是请求的对象且完整、在时限内。
→ 调用无执行错误、返回对象与请求一致（含"按请求条件执行，未丢条件"）、耗时在限。
删 `empty_or_rejection_expected`：它的内容是"空结果归工具还是归数据源"的归属判断，由 §3 的对照取代。工具侧原因（解析丢条件、适配层不支持）并入"返回对象与请求一致"；系统策略拒绝使调用未发出，判没达到、归上游:规划。

**知识数据**（已正确执行的查询 → 数据）。数据必须：存在、匹配。
→ 数据存在（对象存在、字段有值、条目存在）、对象版本时点匹配。
删 `data_per_subquestion` 义务文本里的原因清单（查询未执行 / 原因未定位 / 服务不可用）：查询未执行 → 没达到、归上游:规划；原因未定位 → 没达到、归因未定位；服务不可用 → 执行失败，是工具轴的问题。

**模型能力**（该次输入 → 该次输出）。输出必须：忠实于输入、不添加输入没有的东西、决策与输入一致、遵循输入写明的契约。
→ 输出忠实（不改义、不丢关键信息）、不编造、工具调用决策一致、输出契约遵循。
把现有 `output_faithful` 拆成"忠实"和"不编造"两条：按 §3.3，"不编造"不依赖缺失的输入，必须能独立判。

**上下文管理**（一处产出 → 下一处输入）。传递必须：原义到达、组装正确、历史与缓存来源正确、交付完整。
→ 传递保留原义、模型输入组装、历史与状态使用、交付保留原义。现有四条对应。删 arrives_intact 里"上游本就错误而被如实转交不算本项偏差"的分句：由 §3 对照取代。

## 9. 需求里的 P1–P7 在本协议下的输出

| # | 现象 | 输出 |
|---|---|---|
| P1-A | 没发查询，数据没拿到 | 规划轴："Q1 必须取数"没达到，归本轴 → 问题归规划。知识轴："Q1 数据存在"没达到，归上游:规划；若无其他达到的取数，verdict untested |

| P3 | 提示被系统丢了，模型答错 | 上下文轴："提示送达"没达到，归本轴。模型轴："输出忠实"没达到、归上游:上下文；"不编造"达到 → verdict sound，组成显示 1 条归上游 |
| P4 | 有没达到也有无法核 | problematic；组成写明 n 条无法核 |

| P7 | 聚类输入是整段 reason | 聚类成员改为问题记录 |

## 10. 分层样例

形式：轴 → verdict → 子能力 → 样例。各轴 verdict 层相同，只列有代表性的分支。

知识数据

```text
problematic
  ├── 数据存在         ── 业务材料说这张保单应存在，库里没有
  └── 对象版本时点匹配 ── 要 2024 年版条款，返回的是 2023 年版
not_evaluable
  └── 数据存在（未定位） ── 返回为空，看不清工具还是库；问题归因未定位{工具, 知识}
sound
  └── 组成：Q2 达到；Q1 没达到·归上游:规划
untested
  └── 所有子问题都没发查询；组成：2 条没达到·归上游:规划
not_applicable
  └── 本轮问题不需要外部数据
```

模型能力

```text
problematic
  ├── 输出忠实         ── 输入说"未查询到"，输出写"已失效"；输入说"结果里没有客户号，需用详情核实"，输出说成确定的身份
  ├── 不编造           ── 输入没有出生日期，输出写了一个
  ├── 工具调用决策一致 ── 输入已有有效结果，无理由再查
  └── 输出契约遵循     ── 输入写明 JSON，输出自然语言
sound
  └── 组成：不编造 达到、决策 达到；输出忠实 没达到·归上游:上下文（提示丢失）
untested
  └── 唯一一次模型调用的输入被系统弄坏，各条都归上游:上下文
not_applicable
  └── 本轮走直连，没有模型调用
```

意图理解

```text
problematic
  ├── 对象与字段一致 ── "退保金额"被表达成"保费"
  ├── 子问题均识别   ── 用户问两个，只表达一个
  ├── 约束保留       ── 用户限定 2024 年，内部没带时间
  ├── 指代解析       ── 历史在，"那个保单"仍解析到错的一张
  └── 歧义识别       ── 历史里有两张，内部直接选定一张当事实
sound
  └── 组成：四条达到；指代解析 没达到·归上游:上下文（历史未注入）
not_applicable
  └── 指代解析：用户没用指代
```
