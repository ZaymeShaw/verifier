# 需求轴协议（需求侧材料 → 需求清单 E）

> 状态：v2 定稿（2026-10-07），依据 `demand/expectations.md`，取代 v1（v1 把系统提示词、工具说明等"承诺的一侧"也提取为期望）。2026-10-20 补：需求轴何时必须跑、兑现轴何时自推（§2.3）；场景判准只写"交付什么"；"拿不到时怎么做"的行为规范不进 y_need（§2.1）。
> 与需求冲突以需求为准，回来修本文。本文只写方案（协议、产物、消费接口）；判准来源与应发生单位在过程六轴中的落点见 `spec/alg/process-axes.md` §2.2、§3.4；实施进度记在 `spec/implementation/process-axes.md`。
> 轴名"需求轴"是口头叫法，type_id 为 `expectations`。

## 0. 一张图

```text
y_need（需求侧材料，程序投影；本轮运行产出进不来）
 ├─ 用户原话（本轮）＋历史（只解指代与省略）
 ├─ 下游要求（场景配置 downstream 字段；占位，暂缓实现）
 ├─ 场景判准（业务方登记：这个场景里"办成"指交付什么；不含怎么判）
 └─ 业务描述（理解依据，不单独产需求）
   ✗ 不进：系统提示词、工具说明、能力声明、"拿不到时怎么做"的行为规范、本轮运行产出
 ▼
① 需求轴  e(y_need) → E：一份需求清单，每条 = { 出处, 关于, 陈述, 条件, 歧义组 }
 ▼ 定格；主判与过程六轴共用这一份，按 E 的 ID 与内容指纹引用
② 消费
   兑现轴    有 E 就读 E，逐条判"给到了没有"（blocking 由兑现轴投影给出）；没有需求轴时自推一份（§2.3）
   过程六轴  E → 意图单位＋候选行动单位
             设计原文（系统提示词、工具说明、格式声明等）作为证据与判准来源，不进 E
```

## 2. 内核：e : y_need → E

### 2.1 y_need

| 成分 | 内容 | 是否必需 |
|---|---|---|
| 用户原话 | 本轮用户消息；请求是对话消息形状时取最后一条用户消息，否则整份请求体就是用户这一轮发来的东西，原样作为用户原话（不靠猜字段名）；历史轮用户与助手消息只用于解析指代和省略，本身不产需求 | 必需 |
| 下游要求 | 交付物消费方对格式／字段／口径的要求，来自场景配置 `downstream` 字段 | 占位，暂缓实现（见下） |
| 场景判准 | 业务方登记的"这个场景里办成指交付什么"（例：查询类给出所问字段的值；咨询类给出适用条款与条件）；只写结果，不写评测怎么判；整案的判准，多轮时归最后一轮。用法：拿它把用户这一轮的要求落到具体交付上，不把判准条文逐条改写成期望；用户这一句不在判准设想的业务里时，按用户实际要的写 | 已配置则必收 |
| 业务描述 | 业务是干什么的、用户拿它办什么事；只作理解依据 | 已配置则收 |

**不进 y_need**：业务系统的系统提示词、工具定义、输出格式声明、编排注入的规则模板；被测系统对自身能力的声明；**"拿不到时怎么做"的行为规范**（"信息缺失应如实说明""应发起澄清""不得编造"——这是系统行为规范，用户要的是结果本身，`demand/expectations.md` §2、`demand/main_axis.md` §2.3）；verifier 自己的传输封装；本轮运行的任何产出（模型输出、工具返回、最终交付）。由程序投影保证；行为规范混在场景判准文字里时，由维护者拆出，不由模型逐 case 过滤。

**下游要求先定占位，暂缓实现。** 现有代码里没有登记下游要求的地方：主判输出的 `downstream_consumer` 是模型判定时现填的；场景 `capability` 文字里混写了下游信息（如"下游按标签路由"），要等它拆分；client_search 的 `downstream_search` 是运行时服务依赖，不是需求。

- 占位字段：场景配置新增 `downstream`，类型为字符串列表，**每个字符串是一条下游要求**（例："交付物是意图标签＋必要槽位，下游按标签路由、按槽位执行"）。
- 实现后：非空时每条字符串作为一个出处（`downstream[i]`）进入 y_need；空列表或未配置表示没有登记下游要求。
- 暂缓期间：不读取该字段，下游要求不参与需求轴 verdict。
- 项目已有的 live schema 输出形状不能自动当作下游要求：它可能是业务系统自身的声明或 verifier 的传输封装，需要时由维护者摘成 `downstream` 字符串登记。
- ⟡ 是否需要区分"确认无独立下游"与"有下游但未登记"、由谁维护，留到实现时再定。

**`capability` 字段**目前把"用户要办什么事、办成指交付什么"、"系统声称能做什么"和"拿不到时怎么做"三类混写。由**配置维护者**在配置中拆开（第一类进场景判准，业务背景进业务描述，能力声明和行为规范留在需求外），并确认拆分已覆盖原字段里的验收要求，不让模型每个 case 重新分类。维护者确认之前，`capability` 不进 y_need，且**不论是否已有用户原话**，verdict 都记 `partial` 并写明"capability 未拆分"：它里面可能有其他来源没有覆盖的验收要求，不能静默丢失后报 `complete`。

**多轮按轮写。** 每一轮各写一份需求：材料 = 这一轮的用户原话 + 这一轮请求里带的历史（只含此前各轮）+ 业务描述（多轮时最后一轮另加场景判准）。写第 t 轮时看不到第 t 轮之后的任何内容。用户在后面的轮次改口（更正对象、撤销、缩小、放弃）时，前面轮次的需求不被改写：第 1 轮按第 1 轮的话判，第 2 轮按第 2 轮的话判。依据 `report/multiturn-needs-20261012/`：整案一次写成一份时，改口类题 31 道里 18 道丢掉前面整轮的需求，同一题多次写结构不稳；按轮写时结构稳定、改口各类都写对。

### 2.2 E

| 字段 | 含义 |
|---|---|
| 出处 | y_need 中的精确位置，可多处；程序校验 ⊂ y_need |
| 关于 | 这条需求说的是什么东西（对象），用原文自己的话 |
| 陈述 | 要得到什么结果；只写结果，不写路径 |
| 条件 | 何时适用，默认"总是" |
| 歧义组 | 同一出处的互斥读法共享组号，默认空 |
| 轮次 | 属于哪一轮（t1、t2…），由程序按写它的那一轮标注；出处只能是这一轮或整案的材料 |
| 需要 | 判这一条对不对，除交付、用户原话、场景资料外还需要哪类证据（2026-10-25，`demand/expectations.md` §4）：证据组的列表，组之间是"或"、组内是"与"，类别取 `knowledge` / `trace`；只凭交付就能判写 `[]`。例：`[["knowledge"], ["trace"]]`（知识或 trace） |

E 的编号全案唯一，由程序加轮次前缀（如 `t2.查余昕雅保费`）。

拆分粒度：一件事一条。用户一句话问几件事就几条；不把一件事拆碎；不加总括条目。一条只说一个可独立验证的结果维度，多维度拆成多条。用户原话明确表达的语义（等值/前缀/包含、范围与边界、数量与单位、逻辑关系）原样保留，不放大、不缩小、不改写。两条都沿用原轴1 的派生原则（2026-10-20）。

**每条期望都要落在用户这一轮的话上**：出处必须含本轮用户原话；场景判准、历史、业务描述都只能帮着把它写具体，不能独立产生期望（程序校验）。用户原话没取到的轮次不写期望，记缺口，不拿判准凑。

"需要"怎么写：这条要的结果是业务事实（保费、条款、产品规则、某个对象的属性），就要写证据组，通常是 `[["knowledge"], ["trace"]]`；只靠用户原话、场景资料和通用常识（算术、单位换算、公认常识）就能判对错的（如"检索条件里年龄等于 45""只回答金额"），写 `[]`。e 看不到交付，所以这一格不会因为回答看起来像样而被写低。程序校验：类别在枚举里、组非空、组内不重复。

e 不做的事：不判系统做不做得到、不判有没有做到、不写执行路径、不读设计规则、不裁决冲突、不替用户在歧义中择一。

### 2.3 什么时候跑需求轴

需求轴在**除兑现轴外还有别的轴需要它时必须跑**（现在是过程六轴，必需依赖），由运行器自动补上；这时兑现轴和主判也读这一份，不另推（`demand/expectations.md` §3）。

- 只开兑现轴时不强制跑需求轴：兑现轴对它是可选依赖，自己推一份期望。自推同样先于看交付定格——先只看需求侧材料（用户原话含历史、场景判准、业务描述）写出期望，再看交付判；"拿不到时怎么做"的行为规范、被测系统的能力声明不写成期望。
- 需求轴开了却没跑成：兑现轴不自推顶上，记运行失败（`demand/expectations.md` §3）。
- 无 trace 场景也可以手动开需求轴（`requires_business_trace` 去掉）；开了兑现轴就读它。y_need 取法：

| 成分 | 从哪取 |
|---|---|
| 用户原话（含历史） | 样本请求体里的用户消息；多轮取各轮请求 |
| 场景判准 | 场景配置（`capability` 拆分后的判准部分） |
| 业务描述 | 场景引用的业务描述资料 |
| 下游要求 | `downstream`（实现后） |

### 2.4 需求轴 verdict

只说材料齐不齐，由程序按 y_need 成分判：`complete`／`partial`（附缺料清单）。v1 中"缺工具定义／系统提示词 ⇒ partial"删除，这些不是需求材料；新增"capability 未经维护者拆分确认"这一缺料原因。下游要求暂缓期间不参与 verdict。

## 3. 承诺表

| 承诺 | 形式 | 把关 |
|---|---|---|
| 需求不是对着实际倒推的 | 本轮运行产出 ∉ y_need | 程序投影；审计实际发出的材料 |
| 需求不含设计规则与能力声明 | 系统提示词、工具定义、格式声明、能力声明 ∉ y_need | 程序投影 |
| 判定前已定格、只有一份 | E 在所有消费者之前产出；主判和六轴按 E 的 ID 与内容指纹引用；消费者输出不回流 E | 依赖图；主判输出不得含自推需求 |
| 每条能回到原文 | 出处 ⊂ y_need | 程序校验 |
| 歧义不被静默择一 | 互斥读法各成一条、共组号 | 程序校验组内 ≥ 2；合并靠人评审 |

## 4. 谁用 E：先看一个例子

以冻结保险样本为例。用户问："P260922000005855 是谁的保单？投保人和被保人分别是谁？当前状态呢？"

需求轴产出 4 条需求，即 E：

| 编号 | 需求 |
|---|---|
| E1 | 告知这张保单是谁的 |
| E2 | 告知投保人是谁 |
| E3 | 告知被保人是谁 |
| E4 | 告知当前状态 |

拿 E 做判断的评测者（消费者）有两个：**主判**和**过程六轴**。它们用的是同一份 E，按 E 的编号引用，不改写、不另写。

E 由**独立的需求轴**产出：已有实现，最容易保证"先于运行结果定下来、多方共用"。

## 5. 消费者一：主判

**只回答一件事：最终答复里，每条需求交付了没有。**

| 需求 | 主判看最终答复 |
|---|---|
| E1 是谁的保单 | 答了"任言琳" → 交付了 |
| E2 投保人 | 答了 → 交付了 |
| E3 被保人 | 答了 → 交付了 |
| E4 当前状态 | 答了"交费有效" → 交付了 |

每条需求缺了算不算没办成（`blocking`），由主判自己定，不写进 E。llm_probe_loop 里由 blocking 轴逐条投影，取 true / false / 空（待定：挡不挡要看这次具体错成什么样，定期望时看不到回答判不了），待定项不决定主结论（`spec/math-abstract/judge.md` §3.1，2026-10-25）。

隐性期望（2026-10-25，`demand/main_axis.md` §2.5）：每轮在用户明说的期望之外固定加一条 `t<n>.implicit_correct`——"本轮回答里说的事实都正确、不误导用户（含用户没问、顺带说的）"，出处引本轮用户要求，needs 为知识或 trace。只加这一条，其余通用底线仍不是期望。

和现在的区别：主判不再在判定时自己另写一份"用户要什么"（现在那份是看着答案写的，例如"输出明确该保单归属于任言琳"），改为直接用 E。这一条对有无 trace 的场景都成立（§2.3）。

## 6. 消费者二：过程六轴

六轴用 E 做两件事；判断时还要用到设计规则，但设计规则不来自 E。

### 6.1 第一件：意图有没有表达对（意图轴）

每条需求对应一个"这条需求被表达"的单位，意图轴的五个子能力（对象与字段、子问题、约束、指代、歧义）各判一次。

例：系统内部的查询参数是"投保人姓名、被保人姓名、保单状态"。看 E1–E4 有没有被漏掉、改写或理解错。

### 6.2 第二件：该做的有没有做（其余几轴）

对每条需求，依次问四个问题，每个问题各自给证据，不由前一个直接推出后一个：

```text
                        以 E2「告知投保人是谁」为例
① 要回答它，需不需要外部数据？        需要：投保人信息只能从保单数据里来
② 系统有什么办法拿到？                工具说明里有 policy_detail，能按保单号查（引用说明原文位置）
③ 当时是不是真的必须去取？            此前没有取过，也没有可用缓存 → 必须
④ 实际取了没有？                      取了一次 policy_detail → 做了
```

几条规则：

- **①不能由②推出。** "有工具能查"不等于"需要查"。
- **②只说明有哪些可选办法。** 工具说明缺失时，不取消对这条需求的检查，而是记"设计或材料有缺口"。
- **③有三种结论：**
  - **已满足**：已有有效数据、缓存，或走了等价的路径。附证据，不算没做到，不报问题。
  - **必须做**：这一步成为一个"应发生单位"。是否必须，与④实际有没有发生无关。
  - **说不清**：同样保留为单位，记"缺证"并写明缺什么，不能让它消失。
- **④没做时，不预设是谁的责任。** 按六轴协议的归属口径找证据：
  - 可能是规划漏安排，也可能是需求在上游漏传、意图没识别出来。
  - 找到具体、有证据的上游问题，依赖它的单位才可记"输入无效"。
  - 找不到就记"缺证"，问题记录写"归因未定位"并列出候选轴。
- 应发生单位不能用"不适用"跳过（同现行规则）。

### 6.3 判断的依据从哪里来

六轴判任何一步时，依据（判准）有三种：

| 依据 | 例子 | 怎么引用 |
|---|---|---|
| 通用义务 | "不能编造"——对所有 case 都成立 | 义务编号 |
| 需求 | E1–E4 | E 的编号 |
| 设计规则原文 | 业务模型收到的系统提示词里写着"输出 JSON：answer_draft 必须是首字段"；policy_detail 的工具说明 | 原文位置＋原样摘录 |

**设计规则能用在哪一步，按轴区分：**

| 轴 | 能用的设计规则 | 例 |
|---|---|---|
| 模型能力 | 只能用**那次调用实际收到的**规则；它没收到的规则，不能拿来判它违约 | 业务模型那次调用的输入里有"输出 JSON"，才能据此判它输出不是 JSON 是违约 |
| 上下文传递 | 比较**本该送到的**规则和**实际送到的**规则 | 本该送到"输出 JSON"，实际输入里没有 → 这是漏传，不是模型的错 |
| 工具执行、规划 | 已确认适用于**这一次执行**的规则 | 用 policy_detail 当次版本的说明，判返回对不对 |

**引用设计规则时要核对三件事：**

1. **是哪个版本、什么角色。** 程序优先交付该步实际收到的那份原文（模型调用的实际输入、当次执行记录的工具说明）。只有采集时定义、没有实际收到的那份时，只能作参考，不能单独认定违约或漏传。原文里被引用的数据、示例不是规则，不能当判准。
2. **原样、完整。** 摘录必须是完整的句子，不能截掉"整个响应""仅最终响应"这类范围词、条件和否定（B 样本里"整段输出 JSON"被缩成"字段齐全"，就是这种错误）。
3. **条件不在同一句时一并带上。** 一条规则的条件或例外写在别的句子、上级章节或关联的格式定义里，就作为同一条判准的另一处原文一起引用。程序只核对每处原文逐字一致，不自己补写条件。

某个 source=trace/case 的义务，既没有适用的需求、也没有可引用的设计规则时，记"缺判准"。

### 6.4 设计原文怎么交给判定者、挑漏了怎么办

- **按步交付，每段一次。** 程序只交付该轴各步涉及的原文：模型轴是那次调用的实际输入，工具轴是当次被调用工具的说明，上下文轴是应交付端与实收端。同一段原文在一次判定里只出现一次，放在案卷里，用案卷编号引用。总量受 `demand/context.md` 的上下文预算约束（判定约 40k）。
- **判定者只引用用到的规则**：案卷编号＋原样摘录，可多处。程序核对摘录逐字出现在该编号的原文里。
- **不做逐块标注。** 判定者把块标成"不适用"同样可能漏，标注证明不了没挑漏，却会让提示词和输出成倍增长（实测见修订记录）。挑漏规则靠独立审阅和对照样本发现；判定结论不声称"规则已全部核实"。

### 6.5 判断结果怎么往下传

- 每个单位保存每条依据的引用（E 的编号／义务编号／设计原文位置和摘录）、结论和看到的事实。
- 问题记录里的"预期"，由程序从引用的依据原样拼出：需求带上陈述和条件；设计规则带上它的全部原文位置（规则、条件、例外）。不能只留陈述（现行实现会丢条件），也不由程序改写。
- 结论、引用和条件从单位一路传到问题记录和汇总，中间不被改写。

## 8. 验收

- E 只含用户、已登记下游、场景来源；用户问几件事就几条；同一 case 重复产出条目稳定。
- 需求轴耗时：目标为显著低于 v1 的 8.5–34 分钟，以实测为准。
- 主判与六轴引用同一份 E；主判输出不含自推需求。
- 对照样本（真实冻结样本与人工构造变体分开标注）：

| 对照 | 必须观察到 |
|---|---|
| B 样本：格式规则已送达，整段输出非 JSON | 模型轴引用该次输入中"整段输出 JSON"的完整原文，判出违约 |
| P1-A：用户要的数据需要取数，系统没取 | 候选行动判为"仍必需"；按证据定位到规划漏安排时，规划工作覆盖没做到，知识轴落 untested 并指向该问题；证据定位不了时落缺证、归因未定位 |
| 必要性无法确定 | 单位保留在覆盖中，落缺证并写明缺什么，不消失 |
| 规则的条件写在另一句或父级章节 | 判准关联多个原文位置，问题记录的"预期"原样带上条件 |
| 交付原文中有一条适用规则被判定者忽略 | 独立审阅对照交付的原文能检出；判定结论不声称规则已全部核实 |
| 上下文预算 | 每次六轴判定调用的提示词在 `demand/context.md` 预算内；同一段原文不重复交付 |
| 规则在组装时漏传 | 上下文轴比较应交付端与实收端定位漏传；模型轴依赖该规则的义务落输入无效 |
| 仅采集时定义与运行版本不同 | 不认定漏传或违约，保留版本未决 |
| 有效缓存／等价路径 vs 明确要求刷新却未执行 | 前者候选行动"已满足"，不报问题；后者报没做到 |
| 下游要求（实现后） | `downstream` 中每条字符串都在 E 中有对应需求，出处为 `downstream[i]` |
| 条件保留 | 带条件的判准生成的问题记录，"预期"中保留条件 |
| Q5 多轮更正 | 第二轮更正对象后，第二轮的 E 指向新对象，第一轮的 E 不被改写 |
| Q6 行为规范 | 对象不存在的 case，E 里没有"如实反馈未查到"一类条目；只有用户要的那个结果 |
| 只开兑现轴 | 不跑需求轴；兑现轴自推的期望不含行为规范、能力声明，且推期望那次调用看不到交付 |
| 需求轴开了却失败 | 兑现轴记运行失败，不自推 |
