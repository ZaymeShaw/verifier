## 1. 输入与输出

```text
输入  E       期望集：需求轴（expectations）跑了就用它的；没开需求轴时本轴自推一份（§1.1）
      d(x)    本次交付：最终答复（output_text / 结构化输出）、多轮时各轮答复
      K       核事实结果（truthfulness 的 claims：verified / refuted / unverifiable），可选，场景开了才有
      P       过程六轴的逐条结果（各轴实际清单：本应、实际、达到 / 没达到 / 无法核、归因），可选，场景配了 trace 才有
      业务描述  读法（单位、对象标识、返回怎么读），不是依据
输出  每条期望一个结果 + 整体一个结果（程序派生）+ 每条引用了哪些 claim
```

### 1.1 期望从哪来（`demand/expectations.md` §3）

- **需求轴跑了**（除本轴外有别的轴需要它，如过程六轴；或场景手动开了）：用它冻结的 E，本轴不另推。
- **需求轴开了却没跑成**：本轴记运行失败，不自推顶上。
- **没开需求轴**：本轴自推一份，这一份就是本案唯一的期望。自推分两步，第一步只看需求侧材料——用户原话（多轮看各轮）、场景描述——写出期望并定格，看不到交付；第二步才看交付判。场景描述里混着的"拿不到时怎么做"行为规范（如实说明、澄清、不编造）和被测系统的能力声明不写成期望（`demand/expectations.md` §2）。

| 每条期望的结果 | 含义 |
|---|---|
| `fulfilled` | 这条要的结果在交付里有，且（能核的）核实为对 |
| `not_fulfilled` | 没给到，或给错了 |
| `not_evaluable` | 材料不够判：交付为空 / 不可读，或这条依赖的事实核实不了 |

歧义组（同一句话的互斥读法，`demand/expectations.md` §4"不替用户选"）：交付按其中任一读法给到，这一组就算给到；没被采用的读法标 `other_reading_fulfilled`，不进整体派生，也不进主轴合成。一种读法都没给到时照常各自计。

整体结果由程序从 blocking 期望派生：任一 `not_fulfilled` → `not_fulfilled`；否则任一 `not_evaluable` → `not_evaluable`；否则 `fulfilled`。没给到是确定的，不被"说不清"盖掉。blocking 由本轴按期望内容投影（用户直接要的结果为 blocking；下游格式要求等为非 blocking），不写进 E。
⟡ 用户要几样只给到几样时整体怎么说（`main_axis.md` ⟡1）未定，暂按上面派生；无论怎么定，每条期望的结果都单独保留并输出。

## 2. 判法：每条需求对应一条

对应 `main_axis.md` §2 的九条。左列是需求，右列是本轴怎么判出来。

| # | 需求（`main_axis.md` §2） | 判法 |
|---|---|---|
| 1 | 要的是结果本身，不是态度 | 在交付里找这条期望要的那个东西（值、条款原文、名单、办理结果）。找到 → 候选 `fulfilled`，进第 4 条核对。交付是"查不到 / 无法确认 / 请补充 / 反问澄清"→ `not_fulfilled`，evidence 写明"以说明代替结果"。信息源里确实没有，本轴照判 `not_fulfilled`；能不能做是 carryability 的事 |
| 2 | 问"有没有、能不能"时答复就是结果 | E 的陈述是"告知有没有 / 能不能"时，答复本身是结果，进第 4 条核对属实 |
| 3 | 行为规范不替代结果 | 期望里没有行为规范：读需求轴的 E 时，混进去是需求轴材料拆分的问题，按 `expectations.md`（方案）§2.1 由维护者拆出，本轴不补救；自推时第一步就不把"如实说明""澄清""不编造"、系统能力声明写成期望（§1.1）。判的时候也不把满足这些规范当成给到 |
| 4 | 对不对以场景配了的证据为准 | 按 §2.1：期望的"需要"决定要哪类证据，场景配了哪类就用哪类，可用的组都要过。任何情况下都不得凭模型自己的知识判业务事实对错；通用常识可以用 |
| 5 | 交付里的事实都要属实，含用户没问的 | 隐性期望 `t<n>.implicit_correct`（需求轴每轮固定一条）按本表其他行一样判：`claim_refs` 只引和本轮用户要办的事有关的说法——本轮其他期望涉及的对象和事项，用户没点名问、回答顺带说的也算；和用户要办的事无关的不引。相不相关由模型看着期望和回答定，不按说法类别写死（2026-10-28，`main_axis.md` §2.5）。blocking 待定，没达到时不决定结论，由 M 列进待定项（`judge.md` §3.1） |
| 6 | 值对了、单位核实不了不算给错 | 值的 claim `verified`、修饰它的单位 / 币种 / 时点 claim（`qualifies` 指向值那条）`unverifiable` → 这条期望仍 `fulfilled`；单位 claim `refuted` → `not_fulfilled` |
| 7 | 值对了、格式没照做不算没给到 | 格式要求若登记为下游要求，在 E 里是单独一条（非 blocking）；核心值那条不因格式判 `not_fulfilled` |
| 8 | 编造比如实说没有更差 | 期望对象的 claim `refuted` 且理由是对象不存在，而交付给出了值 → `not_fulfilled`（给错了） |
| 9 | 用户要几样就看几样，单项不受牵连 | 每条期望只看自己的交付片段和自己引用的 claim；别的期望、别的 claim 的结果不影响它 |

### 2.1 按证据组判（2026-10-25，`demand/main_axis.md` §2.4、§2.10、§2.11）

模型只判交付本身：这条要的东西交付里**给了**、**没给**（以说明代替结果、反问、空）、还是**交付不可读**，并引用交付原文、相关的 claim（`claim_refs`）和过程条目（`process_refs`）。结果值由程序按下面派生，不让模型写：

```text
没给                                  → not_fulfilled
交付不可读                            → not_evaluable
给了：
  需要 = []                           → fulfilled（档位：只凭交付）
  可用组 = 需要里、组内每类证据场景都配了的组（knowledge ⇔ K 存在；trace ⇔ P 存在）
  可用组为空                           → not_evaluable（缺：列出需要的组）
  逐组判，可用组都要过：
    knowledge 组：引用的 claim 有 refuted → 不过（给错了）；结果值的 claim verified → 过；
                  否则（unverifiable，或没有对应 claim）→ 判不了
                  （修饰数值的 claim 例外同 §2 第 6 条）
    trace 组：    引用的过程条目有没达到 → 不过（过程不对：蒙的、查错对象、编造、传丢，§2.10、§2.11）；
                  都达到 → 过；有无法核、或没有可引用的条目 → 判不了
  任一组不过 → not_fulfilled；否则任一组判不了 → not_evaluable；否则 fulfilled（档位：所过各组）
```

- `process_refs` 由兑现自己挑：对这条期望要的结果有关的过程条目（查没查、查的对象、返回、模型照没照抄、交付有没有传丢）。程序检查：本应清单里依据（basis）写明是这条期望的条目，必须全部在 `process_refs` 里，不许只挑达到的。
- 两样都配了时，蒙对（知识 verified、过程没达到）和过程像样被证伪（过程都达到、知识 refuted）都不算给到（§2.10）。

## 3. `not_evaluable` 只有三种来源

1. 交付为空、不可读、必要的答复取不到。
2. 这条期望需要的证据场景一类都没配（§2.1 可用组为空），写明缺哪一类。
3. 可用的证据组判不了：对应 claim `unverifiable`，或过程条目无法核。

以下**不是** `not_evaluable`：

- 职责外、能力边界外、"系统不支持"——本轴照判给到没有；能不能做由 carryability 用责任范围登记判，M 合成为"做不了"。
- 用户问的事和产品无关——E 照常写出那条期望，交付没给就是 `not_fulfilled`，责任范围登记后由 carryability 判做不了。
- 不知道系统支不支持——不是本轴的输入。
- 评测器自己失败（模型输出不合法、超时）——轴 `failed`，不出任何值（`information_sources.md` §4.7）。
- 样本输入本身坏了——样本无效，运行层标记，不出值。

## 4. 输出结构与程序检查

每条期望输出：`expectation_id`、`delivered`（给了 / 没给 / 交付不可读，模型填）、`status`（程序按 §2.1 派生）、`evidence_tier`（所过的证据组，程序填）、`missing_evidence`（缺的组，程序填）、`blocking`、`actual_evidence`（交付原文位置）、`claim_refs`、`process_refs`（引用的过程条目，可空）、`status_basis`（程序为什么得出这个 status，程序填，10-27）、`reason`。

`reason` 写这条最终为什么是这个结果，包括程序按证据组算出的部分；status 由程序算，模型在说明回合里看到它（`axis_loop.md` §5.3 第 6 步）后写清原因。认为所引 claim 或过程条目的结论不对，在 reason 里写明依据挑战，不改结论（需求 `axis_loop.md` §3.3.6，10-27）。

程序检查（`validate.py`）：

- `claim_refs` 里的 id 必须存在于 K；K 不存在时必须为空。`process_refs` 同理对 P。
- `claim_refs` 引的每条说法，`spans` 里必须有一处的 `turn` 等于这条期望的轮次；否则退回重交（2026-10-29（二））。为此给兑现的说法材料带上每条的出处轮次。
- 本应依据写明是这条期望的过程条目，必须全在 `process_refs` 里（§2.1）。
- 引用了 `unverifiable` 的 claim 且该 claim 是这条期望的结果值 → `status` 不得为 `fulfilled`。
- 引用了 `refuted` 的 claim → `status` 必须为 `not_fulfilled`。
- 需求轴开了却没跑成，或期望为空（读来的、自推的都算）→ 轴 `failed`，不出整体结果。
- 自推期望的那次调用输入里不得有交付（程序组装输入时就不放）。

## 5. 不许

```text
1. 把"如实说明"等行为规范、被测系统能力声明写成期望（含附带期望）        ✗
1a. 有需求轴的 E 时另推一份；自推时看着交付写期望                          ✗
2. 凭模型自己的知识判一个事实对不对                                    ✗
3. 把职责外 / 不支持 / 完全无关判成 not_evaluable                        ✗
4. 把"该出结果没出"判成 not_evaluable                                    ✗
5. 一条 claim 的结果影响不依赖它的期望                                   ✗
6. 单位核实不了拖垮已核实的值                                            ✗
7. 用态度好、格式对替代结果给到                                          ✗
8. not_evaluable 不写缺什么                                              ✗
```

## 6. 对照需求现象

| 现象（`main_axis.md` §5） | 本判法下 |
|---|---|
| M1 对象不存在、如实说未检索到、被判做成 | E 里只有"告知被保人是谁"（需求轴、自推都不收行为规范）；交付以说明代替结果 → `not_fulfilled`；carryability 查实对象不存在 → M 合成做不了 |
| M2 反问澄清被判做成 | 第 1 条：澄清不是结果 → `not_fulfilled` |
| M3 三条路线三种结论 | 本轴输入只有 E、d(x)、K，与路线无关；M 是纯函数 |
| M4 服务出错、数据在，被说成做不了 | 本轴 `not_fulfilled`；carryability 查到数据在 → 做错了 → M 合成没做成 |
| M5 核事实没出结果、模型凭常识判对 | 第 4 条：K 不存在或无对应 claim 时不得判对；程序检查 `claim_refs` |
| M6 值对单位核实不了整项被挡 | 第 6 条 |
| M7 只接了 trace 的场景几乎全是不确定 | §2.1：trace 组可用，过程条目都达到即给到 |
| M8 没查、模型写的数碰巧对，判做成 | §2.1：trace 组里引用的条目没达到 → 不过 |
