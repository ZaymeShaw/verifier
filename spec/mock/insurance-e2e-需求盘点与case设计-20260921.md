## 1. 维度一：工具与能力载体（实物 11 个入口 + 4 hook + 8 Skill + MCP）

| 载体 | 实现 | 契约要点（直接来自 docstring） |
|---|---|---|
| `policy_detail` | `app/tools/policy_detail.py` | 完整号/纯数字尾号；尾号多匹配返候选；工号由运行时注入（empno 优先回退 user_id，**模型不填身份**）；未提供当前金额/币种/时点保持未知，**禁止补"元/万元/CNY/截至今天"**；已命中但目标字段缺失 = PARTIAL，EMPTY = 实际无记录；用户明确问字段时须逐项传 `fields` |
| `customer_detail` | `customer_detail.py` | 只吃内部 `customer_id`；**业务客户号 ≠ customer_id**；不猜测/构造/转换标识；未取得标识先 `customer_search`；数量未知 ≠ 0；嵌套资料 ≠ 完整关联全集；等级/达标标签不得推断资格 |

## 3. 维度三：过程六轴（定义原文在 `capability_map.json`）

六轴不是自创的，`insurance-agno-e2e.axes` 已写明判定口径与 `not_evaluable` 条件：

| 轴 | 判定口径要点 |
|---|---|
| ① 理解意图 `intent_understanding` | gate / agent_input / 可见任务或工具参数是否保留对象、目标、时间、条件、比较关系、格式约束；复合查询须覆盖所有子目标；指代须能追溯到本轮相关历史；**只有最终答案而无理解过程证据 = not_evaluable** |
| ② 编排路由 `planning_routing` | 路由/步骤/工具轨迹是否覆盖所需工作、先决条件是否满足；简单保单查询允许 Direct，复合允许 Agent/并行等**等价路线**，不强制 Skill 数量与顺序；未消歧就执行依赖查询、反复无效调用 = problematic；**仅缺显式规划文本不能判错** |
| ③ 工具执行 `tool_execution` | 参数与对象约束一致、实际返回内容、状态与后续解析；区分参数错误 / 工具业务失败 / 合理错误处理；**span OK 不代表返回成功或参数正确**；不得把失败、空结果、错误返回当成功事实继续作答；脱敏导致不可判断 = not_evaluable |
| ④ 上下文与状态 `context_memory` | 逐次看传给模型的上下文是否恰到好处：缺当前所需目标/对象/约束/前序结果，或多出无关、重复、过时、其他对象内容；指令与资料冲突是否组织清楚；**完整采集证明无模型调用则不适用** |
| ⑤ 知识与数据 `knowledge_data` | 对象、产品版本、数据时点、适用条件是否对应；泛化规则不得冒充已核实的特定保单条款；必要不确定性须保留；**不得把任一测试保单金额或等待期硬编码为通用真值**；缺来源内容 = not_evaluable |
| ⑥ 模型能力 `model_capability` | 只评可观测的输入输出对；是否正确整合已有事实、完成推理与约束遵循；**不由单例判断模型固有能力、不做换模型归因**；Direct 无模型调用则不适用；脱敏导致无法对应 = not_evaluable |

## 4. 维度四：功能需求

- **FR-1** 统一理解层（改写消解指代、实体抽取标准化、多意图、结构化理解结果）
- **FR-2** 分层路由（快轨 workflow / 主轨 agentic / **可升级可回退且不重复已完成工作** / 判据可配置 + shadow）
- **FR-3** 场域能力（产品知识三态、产品对比多维度、服务权益与资格边界、保单资料含无号定位、通用兜底）
- **FR-4** 澄清与交互（fuzzy 候选 ≤5、多候选锁定、**澄清轮次上限 ≤2**、澄清结果会话内生效不重复澄清）
- **FR-5** 工具体系（8 个 operation 全封装、统一信封、**超时/重试/幂等/错误归一（业务错误 ≠ 系统错误 ≠ 无权限）**）
- **FR-6** 兜底与转人工（触发条件、带结构化上下文）
- **FR-7** 会话管理（窗口策略优于"3 轮截断"、流式输出）
- **NFR-1** 时延（快轨 P95 ≤3s、主轨 ≤8~10s、硬上限强制降级）/ **NFR-2** 成本（单轮工具 ≤6、LLM ≤4、token ≤20k）/ **NFR-3** 可溯源不编造 / **NFR-4** 合规红线与出口脱敏 / **NFR-5** 越权 0 / **NFR-6** 故障不宕机、分级降级 / **NFR-7** 全链路 trace 可回放 / **NFR-8** 评测门禁 / **NFR-9** 改动局部化 / **NFR-10** 渠道扩展
- **SOUL 七条红线**（L1 不承诺收益、L2 不预判核保理赔、L3 不编造、L4 不心算、L5 不贬低同业不诱导退保换购、L6 不隐藏来源与不确定性、L7 不做写操作）—— 这是**可直接判定的功能需求**，旧表没单列
- 部署文档：工具配置 `tools-v6` 热更新、分环境与热更新

### 5.3 过程六轴（每轴 10–11 点，共 61 点）

**① 理解意图**：对象与角色 / 字段与近义词 / 编号片段匹配 / 条件与逻辑边界 / 否定与修正 / 时间与单位 / 子目标拆分 / 比较维度 / 歧义与信息不足 / 指代与省略 / 显式格式约束

**④ 上下文与状态**：目标与约束传递 / 前序事实可用 / 无关内容 / 重复内容 / 过时内容 / 指令与资料冲突组织 / 跨轮指代 / 同问缓存复用 / 澄清后补参 / 上下文裁剪（SOUL 不裁）/ 脱敏导致缺证
**⑤ 知识与数据**：对象归属（保单↔客户）/ 产品版本 / 数据时点 as_of / 适用条件（泛化 ≠ 特定）/ 不确定性保留 / 召回完整性边界 / 来源可指认 / 冲突原值保留 / 资格不得推断 / 缺来源 → not_evaluable
**⑥ 模型能力**：事实整合 / 引用约束（fact_refs、不转写数值）/ 不心算 / 不以常识补齐 / 抗诱导（免查确认）/ 格式约束遵循 / 复合先答可得（不得整轮只剩澄清）/ 不重复无效检索 / 忠实不夸大 / 可观测边界（脱敏 → 缺证）

## 7. case 设计

见下一节。

## 8. case 怎么挂

**一行一个 case；case 挂在需求点下；Case ID = 需求点 ID + 追加序号。**
一个需求点下有 1~3 个 case，不强制"单项/组合"配对——需要几个写几个，只有一个就一行。

| 列 | 内容 | 约束 |
|---|---|---|
| Case ID | `T-Q01`、`B-PS02`、`A-C03`、`F-R02`；同点第二个 case 用 `-2`、`-3` | 与需求点 ID 同源，一眼能对回需求 |
| 一级分类 | 四维度下的分类（普通业务 Tool / 客户搜索 / ① 理解意图 / 身份与权限 …） | 沿用盘点表 |
| 二级分类 | 需求点英文名或场景名（`policy_detail 保单详情`、`到底保谁`、`工具事实传递`…） | 沿用盘点表 |
| 类型 | 单项 / 组合 / 多轮 | 多轮需真实前轮，标"暂缓" |
| 用户输入 | **真人会敲的字**（见 §9） | 不写场景铺垫、不写验收、不写故障注入提示 |
| 测什么 | 本 case 在这条需求点下具体验的点 | 指向维度，不指向实现细节 |
| 预期结果 | 可判定的通过条件（可含 SUCCESS/PARTIAL/EMPTY/DENIED 等信封状态） | 判不了的一律不写 |
| 判定证据 | 在 trace 的哪一处看（gate / route / 工具入参返回 / 模型输入输出对 / 出口信封） | 六轴的 not_evaluable 条件同时写这里 |
| 前置条件 | 授权身份、样本编号、配置、故障注入 | 含"待建"的资源不得当正向样本 |

**同一 case 被多个需求点复用时写同一个 Case ID**：例如 `079 现在退能拿多少钱`
既是 `B-PD02`（金额与时点）、又是 `A-I02`（口语→字段）、又是 `A-D06`（数据时点）。
三条需求点下 query 相同、`测什么/预期/判定证据` 各写本维度的。**覆盖按去重 ID 计。**

## 9. query 怎么写

标准只有一句：**我自己要用这个工具，会往输入框里敲什么字。**

| 需求点 | 不要这样写（旧表/我上版） | 就这样写 |
|---|---|---|
| B-CS01 客户定位 | 「下午要给皮奕辰回访，先帮我把他的客户资料和保单核一遍」 | `皮奕辰的资料查一下。` |
| B-PD02 金额 | 「客户急用钱，问 079 现在退能拿回多少，注意不要用保额代替」 | `079 现在退能拿多少钱？` |
| B-PK01 条款 | 「客户刚买了鑫祥17，问是不是买完第二天出事就能赔」 | `鑫祥17 的等待期多久？` |
| B-PC01 对比 | 「客户五年后可能要用钱给孩子，平时也不想缴费压力太大……」 | `鑫祥17 和盛世金越差在哪？` |
| A-I05 纠正 | 「查 079 的投保人，不对，是被保人」（把答案写在 query 里） | `079 的现金价值……哦不，先说投保人是谁。` |
| A-I10 多轮 | 一轮把两件事都问完 | 轮1 `079 的被保人是谁` 轮2 `那投保人呢` |

规则：
1. 一句话就是一个人真的会敲的话，短就短（`079 保的是谁` 就够）。
2. **不写场景铺垫**：不写"我是代理人""客户刚打电话来""下午要回访"。
3. **不写验收**：不写"注意别用保额代替""金额没数就说没确认"——这些进"预期结果"。
4. **不写故障提示**：超时、坏配置、注入伪指令都由测试驱动做，query 保持自然。
5. 需求点要求的多条件/依赖/纠正，用真人会用的说法带出来（`找 10 月生日、45 岁以上的女客户`）。
6. 写完回读一遍：**我会不会这么敲？不会就重写。**

## 10. 数据与前置

**只用两组已授权真实身份**：`EMP000000 / P260000000000001`、`EMP000006 / 皮奕辰 / P260000000000079`。
其余对象（王敏、李伟、陈建国、陈静怡、尾号 6688…）**没有授权数据**，写进前置条件时要明确
`待建：<需要什么数据>`，并且**不能当正向 case 执行**。

现有 `mock_cases.json` 里 25 条 `llm-probe-insurance-real-*` 是**已跑通的真实 case**，
按 `baseline / intent / routing / data / model / scenario / direct / ctx` 分桶。case 集从它们起手，
映射到新 ID（例：`routing-name-search` → `B-CS02`；`data-cash-value-unavailable` → `B-PS04`；
`model-pressure-confirm-without-query` → `A-M10`；`ctx-ellipsis` → `A-I10`），再按维度补齐缺口。

**MCP（`T-M01`–`T-M06`）**：写设计 + 接入前置（server/transport、认证、schema、错误超时、关联 ID、
故障隔离、trace），状态标 `待接入`，**不计入覆盖**——沿用你的要求。
