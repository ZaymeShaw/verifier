# 需求草稿（2026-10-20）

这里是需求文档的调整稿，供审阅。原文件未动；审定后再替换，并把拿出去的内容落到 spec/。

## 目标

每份需求都要有一个和做法无关的内核：对象是什么、结果必须成立什么、用户已经定了什么、哪些现象必须覆盖。方案和实施怎么偏，拿内核能把它们拉回来。`process_axes.md` 已经是这个形状，其余几份按它改。

## 调整原则

1. **逐句归类，不按章节。** 一句话说的是"结果是什么、算不算"，是需求；说的是"怎么查出来、怎么拆、用什么结构"，是方案；说的是代码现状、具体样本、运行数据，是实施。句子里有没有"判"字、原来在哪一节，都不看。
2. 判别法（`information_sources.md` §2）：把判定模型换掉、做法全部重写，这句话还成立吗？成立才是需求。
3. **用户的决定一条都不丢。** 原稿里带日期的"用户定"，要么在新正文里有对应句子，要么在 ⟡ 里写明被重新打开及原因。逐条追踪见 `去向.md` 末尾。
4. **⟡ 和正文不两头占。** 标了 ⟡ 的事，正文任何地方不写成已定；一个 ⟡ 只住在一份文档里，别处引用。
5. 从用途写起；具体样本抽象成一句现象留下，样本进评测集；同一条需求只在一处写。
6. 结论的取值只在"结果必须成立什么"一节出现，每个值对应一种不同的后续动作；中间态、标识名不进需求。
7. 往上接 `demand.md`（judge、attribute 的定位）、`rule.md`（评估责任边界）。

## 统一骨架

要什么（对象的硬定义）→ 给谁用 → 结果必须成立什么 → 已碰到的现象 → 不要什么 → 还没定的 ⟡ → 验收（对着现象和使用者）。
