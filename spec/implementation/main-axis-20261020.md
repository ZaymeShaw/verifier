## 0. 背景一句话

主轴现在有四处和需求反着：fulfillment 自己从能力描述派生期望（M1、Q1、Q6 的根源）；附带说法规则写在 fulfillment 提示词里（C4 守不住、单项被牵连）；"做不了"的依据来自场景 description 里系统自己的能力声明（main_axis §3.3 落不下来）；核事实的 unverifiable 不带缺口类型（C2）。M 函数骨架、承载性判后派生、过程六轴整条链都不动。

### 更正（2026-10-20，用户指出）：需求轴不是兑现轴的硬依赖

T1、T2 和方案原写"需求轴对所有场景运行、兑现轴不许自推"，实现时还用自动补轴把依赖坐实、删了兑现轴自推和场景里兑现轴的描述。需求 `demand/expectations.md` §3 只要求"只有一份、先于结果定下"，由谁产出原是 ⟡；以前的实现也是需求轴只服务过程六轴（有 trace 的场景），无 trace 场景兑现轴自推。用户定：

- 除兑现轴外有别的轴需要需求轴时（现在是过程六轴），需求轴必须跑，兑现轴读它；
- 只开兑现轴时不强制跑需求轴，兑现轴自推一份（先只看需求侧材料写期望、再看交付判；行为规范、能力声明不写成期望）；
- 需求轴开了却没跑成，兑现轴记运行失败，不自推顶上；
- 无 trace 场景也可以手动开需求轴。

已回改：需求 `expectations.md` §3（原 ⟡ 关掉）；方案 `expectations.md` §2.3、`fulfilled.md` §1.1 与 §2 第 3 条、§4、§5、§7，`judge.md` §6。代码：兑现轴对需求轴改为可选依赖并恢复自推，`description` 字段恢复（选填），五份配置从备份还原。
