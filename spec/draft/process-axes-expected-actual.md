# 过程六轴：本应清单 / 实际清单（方案草稿）

> 状态：**草稿，未采纳**（2026-10-09）。未改 `demand/process_axes.md`、`spec/alg/process-axes.md` 与代码。
> 来源：与用户的讨论，以及手工走查 `report/process-axes-reference-20261009/`（README 为入口，实施记录见 `spec/implementation/process-axes.md` §14）。
> 若采纳，需要改动的需求与协议条目列在第 8 节，由用户决定。

## 1. 为什么

现行六轴把「职责 × trace 里的每个事件」配成固定网格，每格一道题（例：D01 的工具执行轴 5 次调用 × 3 项职责 = 15 道，加需求倒推 6 道）。问题：

- 题是程序提前定死的。定得不好就判不准，判不了又可以写「缺判准」；
- 大量格子的答案固定（例：没配时限的「耗时」58/58 缺判准，「历史与状态」70/73 不适用），成本花在确认没问题上；
- 每一行的 `expected` 是通用职责原文加期望原文，所有 case 一样；这次具体该怎样，是模型看着实际时在 `observed` 里临时想的。

方案 §3.1 的对照本身不变：**这次实际产出了什么 vs 在实际拿到的输入下本应产出什么**。改的是怎么把这两边写出来。

## 2. 抽象

对一个 case 的一个轴：

1. **先**只看这个轴能看到的输入，写出「做对时必须成立什么」——**本应清单**，写完冻结；
2. **再**看完整运行，逐条写出实际是什么、落在哪个环节、达没达到——**实际清单**；
3. 问题由「没达到」的条目、以及清单没料到的实际行为生成。

不再有「职责 × 事件」网格。条目数随 case 变化。原来的子能力（方案 §8）从「出题依据」变成「写清单时的提纲」和「条目标签」。

## 3. 每个轴第一次调用能看到什么

第一次调用只给这个轴的**输入**。实际跑出来的环节，属于哪个轴的输出，就不能在那个轴的第一次调用里出现。

| 轴 | 第一次调用看得到 | 必须藏起来 | 本应条目「关于」什么 |
|---|---|---|---|
| 意图理解 | 用户原话、历史；系统提示词与工具说明（表达能落到什么上） | 系统形成的表达：工具参数、改写后的任务 | 原话里的对象、条件、子问题、指代、歧义 |
| 规划路由 | 用户原话、冻结期望 E、工作流定义、系统提示词、可用工具、开轮时的预算 | **调了哪些工具、调了几次、怎么收尾**（环节列表本身就是规划的输出） | 任务层面：每条 E 需要什么工作、失败后怎么办、何时收尾 |
| 工具执行 | 这次调用的参数、工具说明 | 返回、报错、耗时 | 这一次调用 |
| 知识数据 | 已执行的查询、工具说明 | 返回的数据 | 这一次查询 |
| 模型能力 | 这一次调用收到的全部消息（每次调用单独一个请求） | 这一次的输出 | 这一次调用 |
| 上下文管理 | 上游的产出 | 下游实际收到的 | 这一处传递 |

已知的泄漏：工具执行轴若一次看到全部调用的参数，能看出规划层面的故事（例：D01 换了三次措辞），但看不到返回。若要堵，按调用逐个请求。

## 4. 输出形状

一个 case、一个轴一份：

```
第一次调用（冻结）
expected: [
  { id,
    about,          # 关于什么：输入里可见的对象，如 E1、tools/0、模型调用2、原话里的「排序」
    subcapability,  # 子能力标签，取自方案 §8 本轴清单；都不合适时写「其他」
    statement,      # 做对时必须成立的一句话，具体到能核对；不要求完整
    basis,          # 依据：期望编号 / 规则原文片段 / 输入里的位置
    needs_external  # 是否必须独立查证（如库里到底有没有）
  } ]
not_covered: [ … ]  # 写不全的部分

第二次调用
actual: [
  { id,             # 与 expected 一一对应，不得增删改
    links,          # 落在哪些实际环节（link id）；为空 = 该做没做
    observed,       # 实际是什么
    refs,           # trace 记录 id 或原文片段
    verdict         # 达到 / 没达到 / 无法核
  } ]
unexpected: [       # 清单没料到、但实际发生了的行为（例：多调了不该调的工具）
  { observed, links, refs, why } ]
problems: [         # 来自 verdict=没达到 的条目或 unexpected
  { phenomenon, items, attribution, impact, refs } ]   # attribution：本轴 / 上游:<轴> / 未定位:<候选轴>
reason, scope_note  # 不变
```

## 5. 程序负责的部分

- **切输入**：按第 3 节切第一次调用的材料；每个 case 做泄漏检查（输出侧的原文不得出现在该轴第一次调用里）。
- **冻结**：第一次调用的结果原样保存并记哈希，第二次调用只能引用其 id。
- **对齐校验**：`actual` 的 id 与 `expected` 一一对应；`refs` 必须是案卷里存在的记录 id 或原文片段；`problems.items` 只能引用没达到的条目或 `unexpected`。
- **外部真值**：`needs_external = 是` 的条目，结论由程序锁成「无法核」，除非接入了独立来源。
- **传递检查独立做**：参数是否原样执行、工具返回是否原样进入下一次模型输入、交付是否保留草稿的事实与缺口、执行余量提示是否随用量更新。这类由程序逐字比对，作为程序判定的条目并入 `actual`，不经过模型。
- **归属规则不变**：方案 §3.1–§3.3（按实际拿到的输入判；输入无效必须指向已记录的上游问题；同一事件多轴各记）。

## 6. 轴结论与汇总

- 有归本轴的问题 → problematic；没有问题，但本轴有「无法核」→ 写明哪些没核到；本轴没有可看的输入（这类部件本轮没被行使）→ 不适用。
- `sound` 的含义变为：**在本次冻结清单内没有没达到的条目，且未覆盖范围已写明**。不再是「每一项都核过」。
- 跨 case 看整体（需求 §2.1）：按 `subcapability` 汇总 达到 / 没达到 / 无法核 的计数与问题数。清单每次不同，分母不稳，只能比计数和问题率，不能比「sound 的占比」。

## 7. 与现行输出的对应

| 现行 | 本草稿 |
|---|---|
| 一行 = 职责 × 环节 | 一条 = 本应清单里的一项 |
| `expected`（通用职责＋期望原文） | `expected[].statement`（针对本 case 写，先写后冻结） |
| `observed`（一段话） | `actual[].observed`（逐条对应） |
| `link_id`、`evidence` | `actual[].links`、`actual[].refs` |
| `outcome` | `actual[].verdict` |
| `issues` | `problems`（来源多了 `unexpected`） |
| 程序判定的单位（如上游原文完整到达即通过） | 程序传递检查条目 |

## 8. 若采纳要改的地方

- `demand/process_axes.md` §4「判定单位」一行（现为「子能力 × 这个子能力的一次行使」）；§2.1 的可比口径。
- `spec/alg/process-axes.md`：§2 判定单位、§3.4 判准来源、§5 轴 verdict 的含义；§3.1–§3.3 不变。
- 代码：`process_output.py` 的输出结构、单位构造（`build_units`、`pair_up` 不再需要）、三条入口的提示词与校验。

## 9. 已知风险（来自走查，样本小）

- **本应写错**：走查中独立模型写的问题有 22%–28% 是错的或过度断言（例：「本应走 to_direct」「本应调用 run_policy_field_lookup」——引文是真的，用错了）。这些会以「业务缺陷」的面目出现，违反需求 §6。「依据须为原文引用」挡不住误用。
- **清单不可逐条复现**：同一方法写两遍，条目约一半能对上（样本校准，范围约 30%–65%）；问题层面较稳（7/8 相同）。
- **成本不更低**：走查中每 case 的 token 量与现行六轴同量级。清单要按模式合并，否则会重新长成网格（D01 模型轴单轴 67 条）。
- **事后看答案只在第一次调用里被挡住**：第二次调用写 `actual` 时已经看到全部，判定仍可能偏。

## 10. 对比实验设计（未执行）

目的：在**同一个模型**上，比较现行六轴与本草稿，回答三件事——找到的真问题多不多、误报多不多、两遍是否一致。

- **模型**：两边相同。Gemini 线路恢复则用它；否则两边都用 deepseek-flash（现行流水线经 fallback2 网关跑，并发不超过 3）。
- **上游固定**：需求轴的期望 E、分析轴的案卷都复用已记录的结果，只换六轴这一段。
- **样本**：选 2026-10-08 逐 case 核实时已确认有业务缺陷的 case（agent_bridge 模板改写覆盖了正确草稿；customer_detail 传了空的客户 id；答案漏了一张保单），加上 D01 与保单 case，约 8 个。**当时记的是批次内序号（25、26、27、30、31、35），执行前须先换算成 case_id 并核对缺陷仍然成立。**
- **事先登记**：跑之前写下「已知问题清单」与「归类规则」，跑完不再改。已知问题清单来自此前的逐 case 核实，不来自任一方的结果。
- **指标**：
  1. 已知问题的召回；
  2. 误报率：问题按事先定的规则归类为 命中 / 重复拆分 / 过度断言 / 被案卷反驳 / 无法判断，**归类时隐去是哪一方产出的**；
  3. 一致性：每一方跑两遍，比问题层面的重合；
  4. 成本：token 与耗时；
  5. 问题是否具体到「哪一步、现象、预期、实际、引用」。
- **判优（建议，待用户定）**：已知问题召回不低于现行；误报率不高于 15%；成本不高于现行的 1.2 倍。达不到就不改需求 §4。
