## 1. 核心定义

**ToolLoop 是框架型工具；llmtracing provider 通过配置 prompt、tools、hooks、必要的子 loop 等框架内组件，将它实例化为过程评判任务。**

模型自主选择工具、组织调用并处理返回。工具与提示词提供任务路径，hooks 约束什么算合法、什么算完成；不在框架外另写一套模型循环、补查控制器或重试评判管线。

核心结束语义：

> 模型不再调用工具，只是触发结束检查。只有核心完成 hook 确认任务满足要求，整个 loop 才正常完成。

优化的默认范围是 provider 实例里的组件，而不是框架本身。现有框架无法支撑需求时，先说明具体缺口、现有挂点为什么不足、涉及哪些调用方，再与框架作者确认，不自行绕过或修改框架。

## 2. 分层与职责

|层|负责|不负责|
|---|---|---|
|ToolLoop 框架|模型请求与工具执行循环、hook 调度、继续/结束/失败、上下文与调用历史、预算、子 loop 调用|六轴义务、Insurance 政策、llmtracing 日志含义|
|llmtracing provider 实例|准备冻结证据、暴露工具、任务 prompt/skill、六轴提交方式、核心完成条件、其他 hooks、交付结果|另造执行引擎、改公共模型路由或全局业务主流程|
|业务场景描述|业务期望、规则、输出字段用途、允许的重试/信息披露等政策|规定框架内部如何驱动循环|
|项目接入 adapter|在正确 provider 分支调用实例，向现有报告协议交付结果|在实例外补一套“模型再判断—修正—重试”流程|
|build-eval|离线准备样本与独立评分、运行被测实例、比较结果|运行时控制 loop；把自己的预期答案泄漏给待测模型|

这里的 provider 实例是逻辑职责，不要求所有代码放进采集模块。`collect` 等采集函数继续保持确定性；六轴 LLM 任务在 provider 的评判实例中组装，不让一次采集隐含触发模型评判。

Insurance 仅是当前校准业务。工具与 hooks 不得因这批样本而硬编码某个字段、客户或预期结论。

## 3. 执行模型

```text
实例准备：任务说明、工具、核心完成 hook、其他 hooks、预算
  ↓
请求模型
  ├─ 模型给出工具调用
  │    → pre_tool
  │    → 执行被允许的工具
  │    → post_tool / 失败处理
  │    → 工具结果进入会话
  │    → post_batch
  │    → 再请求模型
  │
  └─ 模型不再给出工具调用（申请结束）
       → 核心完成 hook 检查当前任务状态
            ├─ Done：正常完成，提取最终结果
            ├─ Continue(reason)：反馈未完成事项，再进入模型循环
            └─ Failed(reason)：失败结束，保留诊断
```

执行约束：

1. 工具调用路径由模型选择，不以固定脚本逐轴代替模型决策。前置依赖只表达合法条件，不强制无关调用顺序。
2. 模型仍在调用工具时，正常推进工具循环；不能只依赖结束检查控制失控调用，预算和中止仍需在框架已有挂点生效。
3. 模型已满足任务但还在调用工具时，仍由原循环语义与预算约束管理；核心完成 hook 不是每一步强制抢占模型的调度器。
4. `Continue` 返回具体事实和未满足的条件，不只说“再检查一遍”。
5. 允许从原文中确认某项无法评价并完成任务；不为了结束而编造证据，也不强制找到当前快照中不存在的内容。
6. 异常、预算耗尽和完成条件长期不满足应暴露为执行失败，不静默回退旧执行路线或补造部分业务结论。
7. 子任务需要独立 loop 时，使用框架的 `ToolLoop.as_tool()` 嵌套能力，不在外层手写第二套请求循环。

## 4. 核心完成 hook

### 4.1 定位

核心完成 hook 是实例对“什么算完成”的声明，应在实例构造时显式提供并可一眼识别。框架只调用这个 hook，不硬编码它的业务规则。

当前参数名为 `completion_hook`，是必填的独立构造参数，只绑定“模型不再调用工具”时的stop检查。它与辅助hooks分开传入。

### 4.2 llmtracing 实例的完成条件

当前任务是本次启用的六轴评判。默认六轴全部启用；单轴入口或显式子任务只检查其声明的轴集合，不能硬编码为任何 loop 都必须交六轴。

核心完成 hook 根据可审计的提交状态检查：

- 启用的轴是否全部提交；
- 提交是否按实例规定被接受；
- 是否仍有未解决的必需检查或无效提交。

“被接受”的具体条件由提交 tool 和相关 hooks 实现，例如结构合法、义务覆盖、引用已读取、必要的来源/关系检查。核心完成 hook 消费这些检查状态，不默认再启动一个独立审核 LLM。

以下不是完成条件：

- 六轴都判 pass；
- 找到固定数量的问题；
- 调过某个工具一次，无论返回了什么；
- 模型在自然语言里说“完成了”。

`fail`、`not_applicable`、`insufficient_evidence`、`contract_missing` 都可能是合法完成结果。必须区分“被测业务有问题”和“评判任务没完成”。

### 4.3 反馈示例

模型申请结束时，只交了五轴：

> 尚未完成 model_capability 的有效提交；其余五轴已有被接受结果。

某轴提交未满足引用检查：

> 当前引用只有模型收到的工具消息，没有独立的工具原始产出。该传递无损主张尚未获得所需证据；可以补查有记录的另一端，或按实际可见范围提交缺证结论。

后一个反馈是否成立由实例中的检查组件负责。框架不认识“工具原始产出”是什么。

### 4.4 完成与质量的边界

`accepted` 表示通过了实例已实现的检查，不证明所有自然语言推理都正确；六轴交齐同样不等于结果准确。

改善语义质量仍在实例的 tools、prompt/skill、hooks、子 loop 中进行，效果由独立 build-eval 验证。不得将框架的“完成”状态直接用作质量分数。

## 5. 其他 hooks 的分类

按事件组织辅助 hooks，避免把所有策略混成一个无法辨认的列表。事件字典是建议的管理形式，不是要求照搬外部产品的全部事件。

|事件/位置|职责示例|当前本地框架|
|---|---|---|
|`start`|注入实例初始上下文和规则|已有|
|`pre_tool`|允许/拒绝调用、检查依赖、调整参数|已有，`Allow / Deny / Abort`|
|`post_tool`|记录回执、检查返回、附加反馈或投影返回|已有|
|工具失败处理|把失败事实及可采取动作反馈给模型|目前可在 `post_tool` 检查 `call.error`，没有单独事件|
|`post_batch`|批量调用完成后更新共享状态、补充反馈|已有；这是本框架的批级挂点，不宣称与 Claude Code 完全对应|
|核心完成 hook / `stop`|模型申请结束时判断 Done / Continue / Failed|已独立为必填 `completion_hook`；辅助stop另行注册|
|`end`|从已完成状态提取对外结果|已有独立回调；不是另一个循环控制器|

Claude Code 的 `PreToolUse`、`PostToolUse`、`PostToolUseFailure`、`Stop` 等可作为命名与生命周期参考。官方 [Hooks reference](https://code.claude.com/docs/en/hooks) 本次访问返回403，未核实最新版完整事件表；本文的“已有”均以本地实现为证据。

不因外部产品存在权限通知、会话恢复、压缩等事件，就为当前实例预先增加这些能力。

### 5.1 字典组织建议

```python
# 当前框架 API；省略号表示实例自行提供的组件。
ToolLoop(
    id="llmtracing_evaluation",
    system_prompt=provider_prompt,
    tools=provider_tools,
    client=client,
    completion_hook=SixAxesCompleted(enabled_axes),
    hooks={
        "start": [...],
        "pre_tool": [...],
        "post_tool": [...],
        "post_batch": [...],
    },
    budget=...,
    end=...,
)
```

字典值使用有序Hook对象列表，事件之间的时序由框架统一定义。只调用对象被注册事件的方法，不自动注册它的其他方法。多个挂点需要共同状态时可显式注册同一个对象；可变状态必须按case/loop隔离，不用模块全局变量串案。

核心完成hook不能重复注册到辅助stop列表。允许 `hooks['stop']` 提供额外检查，按Failed > Continue > Done与核心条件合成；辅助Done不能覆盖核心Continue/Failed。

### 5.2 必须明确的组合语义

建议保留当前已有语义，不因为改成字典而改变行为：

- `pre_tool`：中止高于拒绝，拒绝高于允许；允许的参数调整按顺序传递。
- `post_tool`：处理器按顺序处理返回；证据原始值须保留，不能静默改写事实后仍冒充原文。
- `post_batch`：整批后更新状态；同批读取与提交不能假设模型已经看到这一批刚返回的正文。
- 正常结束：核心 hook 必须确认完成，预算/失败等硬性中止不能被 Done 覆盖。
- 多个结束检查：核心完成条件先执行，辅助stop按注册顺序执行，按 `Failed > Continue > Done` 合成。
- 工具异常和 hook 自身异常如何传播必须明确，不能把检查失败视为检查通过。

## 6. llmtracing 实例内部组件

|组件|当前职责/形态|允许的改进方向|
|---|---|---|
|冻结证据准备|从已有快照确定性构建对话稿及来源，不调用模型|修正原文投影、来源、调用归属，不伪造缺失记录|
|读取工具|`evidence_read` 分页取原文，`call_inputs` 查实际输入成员|按真实任务需要改进可用证据的获取方式，不为工具调用数凑流程|
|轴提交工具|六个 `eval_<axis>` 接收评判并返回接受或具体问题|改进提交表达与可执行检查；不按样本答案硬编码结果|
|prompt / skill|任务目标、六轴职责、工具用法、完成约定|指导模型如何工作；不是与框架并列的执行引擎|
|辅助 hooks|读取回执、依赖、重复提交管理等|在对应事件内落实约束与反馈|
|核心完成 hook|检查本次启用轴是否完成|明确未完成事项；不要求所有结论都是 pass|
|结果交付|将实例结果交回现有 AxisResult 报告|保持项目接入协议，避免在外面再次生成或改写已完成判断|

具体需要哪些工具、某类核验是否值得拆成子 loop，须由任务和实证决定。本文不预先批准一套新的“主张核验引擎”，也不把某个失败案例转化为永久提示补丁。

## 7. 当前代码与目标的差异

当前代码位置：

- `impl/core/tool_loop/`：`runtime.py` 驱动循环与 `as_tool`，`types.py` 声明协议，`hooks.py` 提供通用完成／预算组件，`outputs.py` 提取结果。统一从 `impl.core.tool_loop` 导入。
- `impl/projects/llm_probe/process_loop/llmtracing.py`：provider 的评判实例。
- `impl/projects/llm_probe/business_trace/providers/llmtracing_evidence.py`：证据工具与检查。
- `impl/projects/llm_probe/process_loop/llmtracing_report.py`：项目报告接入。

当前 provider 实例已经显式分出核心完成与辅助挂点：

```python
self.completion_hook = SixAxesCompleted(specs)
self.pre_tool_hook = DependsOn({name: until_accepted() for name in names})
self.post_batch_hook = EvidenceReceipts(self.evidence)

self.loop = ToolLoop(
    ...,
    completion_hook=self.completion_hook,
    hooks={"pre_tool": [self.pre_tool_hook], "post_batch": [self.post_batch_hook]},
    end=self._finish,
)
```

`SixAxesCompleted` 继承并复用框架 `RequireDone` 的完成谓词，只增加已完成清单、最近未接受原因和结束检查回执；不另写循环、不改变六轴业务判断。原 EvidenceGate 的前置拒绝逻辑改用框架现有 DependsOn/until_accepted，批尾读取回执由独立辅助 hook 维护。

当前ToolLoop已要求独立 `completion_hook=`，`hooks` 是事件字典。旧匿名列表、未知事件、非Hook处理器和非法stop返回均不会被静默放行。

当前实例只要求每条义务至少有一组合法提交，并不自动证明所有语义上的发生位置都已覆盖。后续如果需要加强“完成”的语义，应改实例的提交检查/工具和完成 hook，不能把它误称为框架天然保证。

现有主裁决仍使用旧入口，不在本次六轴实例范围内。本文不授权迁移主裁决，更不允许因为它还在外面，就新增框架外的循环来修补它。

## 8. 变更边界与作者确认

### 8.1 可在 provider 实例内推进

在经过具体任务设计与评测授权后，可增减或修改：
- tools 与工具描述；
- prompt / skill；
- hooks 的具体业务实现；
- 通过已有嵌套能力组成的子 loop；
- 本实例的任务范围、预算和结果提取方式。

这些仍应按单一假设评测，不捆绑无关改动。

### 8.2 框架授权与后续边界

用户已明确授权本次框架更新，落实如下：

1. `completion_hook: Hook` 为独立必填、仅关键字参数。
2. `hooks` 为事件名到有序Hook对象序列的字典；不接收旧列表或回调函数混合接口。
3. 支持辅助stop，不能覆盖核心条件的Continue/Failed；预算仍内置于pre_tool首位。
4. 保留批次可见性；复制注册字典与序列；Hook自身异常传播，不当作放行。
5. 工具失败仍通过post_tool中的call.error处理，不新增本次任务没有必要的失败事件或异步模型。

当前全部在用调用方已更新，不保留兼容层。未来新增框架能力仍需先确认；不能在provider里构建影子框架。

## 9. 对其他项目和场景的隔离

- llmtracing 实例由项目中的 provider 分支选择，不替换全局 judge/runner。
- Agno、无 trace 场景和其他项目继续各自原路径。
- 不改变业务投递、session、公共模型路由或默认模型参数。
- 与在建 ToolLoop 任务的公共文件修改需先协调，不覆盖作者工作。
- 框架接口若获准变更，影响评估、调用方更新与回归必须独立列出，不能混在 provider 优化里。
- 模型端点额度仍可能共享；执行隔离不等于资源隔离，真实测试需授权并限制并发。

## 10. 验收方式

### 10.1 机制验收（本地假模型）

|情形|应观察到的行为|
|---|---|
|模型连续选择多个工具|框架正常执行并回放，不在外部手写推进流程|
|模型无工具调用，但有轴未完成|核心完成 hook 返回缺少事项，模型得到反馈继续|
|六轴已完成，模型停止工具调用|正常结束，end 提取已接受结果|
|合法缺证或业务 fail|可以正常完成，不要求改成 pass|
|同批读证据与提交|遵循批次可见性，不伪造已读事实|
|前置条件永远无法满足/预算耗尽|失败并留轨迹，不自动回退或补造结果|
|两个 case 并行运行|history、回执、提交状态互不混入|

### 10.2 效果验收（build-eval）

独立评价最终报告的判定、证据支持、误报/拒判和业务契约使用。工具次数、提交打回次数、Stop 拦回次数只作机制诊断，不当质量分数。

当前真实运行已有工具拒绝后的修正例，但已观察的这些运行 `segments=1`；不能由本地测试或“存在 RequireDone”推断真实模型已经经历并正确利用过 Stop 反馈。两种机制需分别验证。

每次试验固定输入、判准、模型设置与被测版本；原文和旧结果不被候选改动覆盖。样本量小、没有未见测试集时，只报告有限校准结果，不宣称总体提升或正式晋升。

## 12. 阶段一历史验收：provider组件显式化（当时未修改框架）

该阶段生产源码仅修改 `impl/projects/llm_probe/process_loop/llmtracing.py`，另外更新其测试与本文：

- 核心完成 hook 是显式实例组件，按启用轴集合检查，不要求所有结果为pass。
- 模型申请结束但任务未完成时，反馈缺少的轴、已经完成的轴，以及最近一次未接受的具体原因。
- `completion_checks` 记录每次 stop 检查的decision、blocked次数、reason及accepted_tools；成功时进入view，失败时进入usage诊断。
- 框架通过end调用 `_finish` 提取被接受的结构化提交，不采用模型最后一句自然语言作为结果。loop外只附运行记账，不再次评判或驱动重试。
