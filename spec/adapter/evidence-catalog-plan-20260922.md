# 侦探改造方案：目录有真信息 + 先规划后取（2026-09-22）

> 前置：`spec/adapter/evidence-index-plan-20260921.md`（B3 主线，机制与验收线不变）。
> 本方案只改**侦探（trace_analysis 整理员）的交互形态**，不动六轴、判官、闸门、回执、requires。

## 1. 要解决什么（实测数字，非估计）

以 ctx-cache 案例的真实运行（verify-b3i1）为例，44 次近期运行同规律：

| 现象 | 实测 |
|---|---|
| 侦探内部轮数 | 8~44 轮（中位 17） |
| 侦探累计发送 | 145万~1015万字符/案例（中位 ~600万），其中 **95% 是重复发送**（开场×轮数 45% + 工具结果反复 50%） |
| 末轮会话 | 23万~66万字符 |
| 清单（目录） | 429 条目 / 11~16万字符，**401 条是 `content#N`，预览为 `None` 或半截 JSON，没有信息量** |
| 工具结果 | 单条最大 5.4 万字（整页读取），读一次后每轮都背着 |
| 单案例总耗时 | 4~20 分钟（中位 ~9 分钟），30 案例串行 ~4.5 小时 |
| 容量保护盲区 | prompt 预检只查第一发（19万），侦探内部滚到 61万无人查 |

病根三条（与 2026-08-30 验证过的 material_tools「outline 模式」对照）：

1. **目录没信息量** → 侦探只能开盲盒，读一个才知道下一个读啥，轮次一环扣一环；
2. **边逛边拿** → 无法一次规划，批量受限；
3. **会话即仓库** → 取回的正文永久留在会话里，每轮全量重发，成本 ≈ 轮数²。

## 2. 目标与验收线

- **发送量**：单案例侦探累计发送 ≤ 100万字符（现中位 ~600万，目标 −80% 以上）。
- **时长**：单案例 ≤ 6 分钟（现中位 ~9~14 分钟）。
- **判定质量不降**：3 样本校准 → 30 样本同批验收，沿用 B3 验收线——**缺证率不升**（对基线 `results/`）、结论一致率在噪声地板（±2 轴/样本）内不劣于现状。
- **不破坏的契约**：单一闸门（评委只能看到侦探读过并选中的）、回执留痕、needs 塌缩审计、requires 需求声明、轴视图按回执渲染。

## 3. 设计原则（沿用 08-30 验证过的三条）

1. **标签从内容自身的结构提取，不编造；提取不了就明说**（material_tools 的 AST/键/标题 → 本案的按 kind 从结构化字段提取）。
2. **目录压缩决策空间**：看菜单能点菜，不用开盲盒。
3. **先规划后取**：决策（选什么）与执行（取正文）分离，执行由程序批量做。

## 4. 新数据流

实现采用「批量取件工具」形态（比原稿的两次结构化调用少一层协议）：

```
案卷（build_dossier，不动）
  │
  ├─ 阶段0【程序】build_catalog：两级目录（§5.A）
  │
  ├─ 调用1【侦探】看 目录 + 六轴 requires → 一次 dossier_collect(ids=[...]) 取回要的正文
  │        （一次可带几十条；总量 >120k 的编号在 deferred 里列回）
  │
  ├─ 调用2..n【侦探】只看取回正文，增删后用 dossier_read 下钻超大节点（≤12 次工具调用）
  │
  ├─ 机械核验：输出里出现没有读取回执的编号 → 打回重做一次（补取或删掉），仍不改才剔除
  │
  └─ 阶段3【程序】回执闸门（不动）→ evidence_audit → 轴视图按回执渲染（不动）→ 六轴/判官（不动）
```

实测（verify-cat1，3 样本）：侦探工具调用 38~45 次 → 13~14 轮，末轮会话 15~23 万字符（旧 23~66 万），
单案例总耗时 386s/349s/374s（旧 683s/813s/1170s）。

## 5. 改造明细

### A. 目录（build_catalog 替代 build_manifest 给侦探的用途）

两级结构：

- **类别区**（≤15 行）：类别 + 条数 + 总大小 + 固定说明文案（15 种 kind 写死文案）。
- **条目区**：每条一行 ≤100 字 = `id | 语义摘要 | 大小 | [副本/异常标注]`。

语义摘要**按 kind 确定性提取**（只提取，不总结、不评判）：

| kind | 摘要内容（全部来自结构化字段） |
|---|---|
| tool_calls | 工具名 + 成功/失败 + 耗时 + 关键参数（如 polno）+ 返回大小 |
| model_calls | 模型名 + 输入/输出 token + 重建状态 + 耗时 |
| messages | 序号 + role + 开头首句（标注"开头："） |
| steps | 步骤名 + 成功/失败 + 耗时 + 输出大小 |
| states | 顶层键清单（ledger/entities/budget/evidence/route…）+ 大小 |
| reasoning | 开头首句 |
| final_output / runs / sessions | 类型 + 大小 + 开头首句 |
| **content#N** | **反查引用**：哪个记录的哪个字段引用了它 → "步骤gate的输出正文" + 开头首句 |
| gap | 缺口原因（现状已有，保留） |

规则（与 material_tools 相同）：
- 只从结构化字段提取（名字、状态、耗时、大小、引用关系、正文首句）；**不说"重不重要"**，选择权全在侦探。
- 正文首句预览标注"开头："，截 ~60 字。
- 去重/副本：同一正文多个编号（span/persisted 表示、copy_of）在条目上标注"同 X"，读一等于读全部。
- 目录总量预算 **≤40k**（现 157k）：摘要每条 ≤80 字；超预算时按类别折叠（先折 definitions/sources，折叠行注明"N 条配置定义，可 read 展开"——**不删除任何编号**，全部仍可 read 到达）。

### B. 批量取货（EvidenceIndex.collect）

- 入参：编号列表（每轴分组）。出参：取货包 = 每编号一段正文（record_body 渲染，单条 ≤6k）+ 超限给 shape+下钻路径（沿用现有 EVIDENCE_NODE_CHARS 机制）。
- 侦探标注"要全文"且超大 → 本轮先给 shape，侦探在调用2 确认后走 full-read（沿用 EVIDENCE_FULL_READ_CHARS=80k）。
- 总量预算 ≤120k/包；回执照旧（read_ids / read_paths / shape_only），**闸门与轴视图渲染零改动**。
- 现有单读 read / search / timeline / verify_quote **保留**，作为补充手段（逐字核对、补漏）。

### C. trace_analysis 两段制

- prompt1 = 系统（职责不变：需求→材料映射）+ 目录 + 六轴 requires + 购物单格式说明。
- 购物单 / 最终选段都走现有 StructuredOutputSpec（结构化协议 + 打回重试）。
- 最终输出契约**不变**：`{route, information_needs, coverage_note, selections{axis:{refs,why}}}`。
- route（业务叙事线）由侦探在定稿时基于目录+取货包写；接受"比现在浅"的风险，用 3 样本验证。
- TOOL_CALL_LIMIT 概念弱化：补取最多 1 轮；单读类工具预算保留 16 次兜底。

### D. 不动的清单

requires 需求声明、回执闸门（enforce_receipts）、needs 塌缩审计、轴视图渲染（build_axis_view / read_paths）、六轴 adapter、判官、A1~A6 全部端点保护。

## 7. 验收方案

1. **离线干跑（不花模型）**：3 个样本（snap-cash-value / ctx-cache / ctx-ref）只跑阶段0，人工看目录摘要质量——目录不准，后面全歪。
2. **3 样本端到端**：同批对基线（`results/`）与现状（`verify-b3i*`）：缺证数、逐轴结论、发送量、耗时、审计异常。
3. **30 样本验收**：串行 `--workers 1`，对基线算缺证率与结论一致率（噪声地板 ±2 轴/样本）。
4. 全量测试保持绿（既有 9 个无关失败除外）。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 摘要写错/误导侦探 | 只提取不总结；首句预览标"开头："；摘要生成器全单测 |
| 购物单漏材料（没看到正文就点菜） | 补取轮兜底；目录摘要质量是地基（验收步骤1 先把关） |
| route 变浅（不再边读边写） | 接受，3 样本验证评委是否受影响；受影响再把 route 拆成程序生成的时间线 |
| 折叠后侦探找不到 definitions | 折叠行保留"可 read 展开"；model_capability 的 requires 已点名系统提示词，侦探会去找 |
| 两轮输出协议模型不适应 | 复用现有结构化协议+打回；3 样本观察协议失败率 |

## 9. 实施步骤

1. 摘要生成器 + build_catalog（含 content#N 反查、去重标注、折叠）+ 单测 → **验收步骤1 离线干跑**
2. EvidenceIndex.collect（批量取货+回执）+ 单测
3. trace_analysis 两段制（prompt×2 + 结构化协议 + 复用闸门）+ 单测
4. 3 样本端到端校准（预算定稿）
5. 30 样本验收 → 更新 evidence-index-plan 的 B3 行

## 11. 实施记录与实测（滚动更新）

### 落地内容（2026-09-22）

- `business_trace/dossier.py`：`build_manifest/manifest_ids/_manifest_summary/build_overview` 删除，改为
  `build_catalog`（每编号一行程序摘要：kind 定制提取 + 外置正文反查宿主 + 深嵌正文按直接宿主归并）
  与 `render_catalog`（分轮次/类别渲染；超预算按 `CATALOG_FOLD_ORDER` 折叠；最后一档只留编号，编号永不丢）。
- `business_trace/tools.py`：新增 `dossier_collect`（一次取回多条；大记录按体积从小到大装回小片段并逐段留回执，
  装不下的登记路径）；`tool_calls` 改为统计工具调用次数而非回执条数；修复 source 编号读不出正文的老缺陷。
- `eval_axes/adapters/trace_analysis.py`：目录进 prompt；`TOOL_CALL_LIMIT` 64 → 12；
  **机械核验打回**：输出里出现没有读取回执的编号就重做一次（补取或删掉），仍不改才剔除。

### 目录尺寸（25 个真实样本，按运行态 trace 测）

旧清单平均 83,554 字（最大 167,063）→ 新目录平均 25,003 字（13,431~46,868，中位 22,545），
**−70%**；每个编号都出现在目录文本里（折叠时编号也逐条列出），全部在预算内。

### 三轮 3 样本实测（ctx-cache / ctx-ref / snap-cash-value）

| 项 | 旧（b3c / b3i1 / b3d） | cat1（仅目录+批量取件） | cat3（+打回重做+状态摘要） |
|---|---|---|---|
| 单案例耗时 | 683s / 813s / 1170s | 386s / 349s / 374s | 348s（snap） |
| 侦探取回编号 | 33 / 49 / 39 | 33 / 20 / 31 | 34（snap） |
| 缺证合计 | 0 / 4 / 5 | 3 / 2 / 2 | 3（snap） |
| 无回执被剔的引用 | 0 / 0 / 1 | **10 / 0 / 0** | **0**（snap） |
| catalog_chars | 72k / 157k / — | 29k / 14k / — | 23k（snap） |

结论：**成本与耗时降了一半以上，缺证在 ctx-cache/ctx-ref 上下降**；cat1 在 snap 上因「引用了没取回的编号被静默剔除」
退化两个轴，加机械核验后无回执引用归零。剩下 snap 的 `tool_execution` 仍缺证，原因定位为：
时限/耗时证据在 14 万字的会话状态记录里，而侦探的工具预算（12 次）在「拿结构图 → 再下钻」的两轮模式里被烧光
→ cat4 用「大记录一趟装回小片段」修复（已落地、待实测）。
