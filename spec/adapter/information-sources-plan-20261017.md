# 信息源：两条工作线按位置重新对位（2026-10-17）

依据：`demand/information_sources.md`（信息源需求）、`demand/process_axes.md`、`demand/expectations.md`、`spec/alg/fulfilled.md`。
对位的两条线：知识查证 bench（verifier-notrace，`report/knowledge-evidence-20261014/`）、业务 trace Langfuse provider 与分歧 case（主线，`spec/implementation/business-trace-langfuse.md`）。

## 0. 要解决的问题

两条线最近都卡住了，卡法一样：**用一个数、一套规则同时修三层的问题。**

- 知识查证 bench 六个版本盯判对率，总分在 86%–92% 之间晃，分不出好坏。每一版实际动的层不一样（v4 加搜索工具动的是取证；v6 一条边界动的是判官；读法说明补回来动的是业务描述），却用同一个数衡量。
- Langfuse 分歧 case（客户号 C92200000884 对应谁：Agno 判 ne、Langfuse 判 fulfilled）争了几小时"谁对、该谁判、要不要补埋点"，立场换了四次。

`demand/information_sources.md` 把评测流程分成五个位置（① 目标 → ② 运行 → ③ 信息源 → ④ 判定 → ⑤ 归因），③ 又分四格（trace / 知识 / 业务描述 / 系统静态资料）。按位置拆开，两条线的问题各自落到不同的格，每格有自己的尺子和归属。本文把这件事落成两份工作清单。

## 1. 总体思路

1. **先归位，再动手。**每个问题先定它在哪个位置、哪一格，再决定用什么尺子、改什么。
2. **每格各报各的数。**取证看漏查率和归属错误数；业务描述看多少"无法确认"是因为没写；判官看冤枉率和一致率。不再报一个总判对率当唯一指标。
3. **判法改动走需求 → 方案 → 实现。**一个 case 不立规则；case 先登记到 `demand/information_sources.md` §5（信息源层）或 `demand/process_axes.md` §3（判定层），再谈改。
4. **交叉用法补位。**trace × 知识对照是开放场景的主用法，目前两条线都没在做（见 §4）。

### 2.2 要做的

1. **bench 报表分层。**在现有打分脚本上，把每条判定的错误归到上表的格，分别报：漏查率、归属错误数、因业务描述缺失的"无法确认"数、变义条数、冤枉率、一致率。总判对率照报，但不作决策依据。
2. **解决拆说法与隔离检查的冲突。**按定义："前提"里只放对象标识（姓名、保单号、产品代码），不放任何被断言的数量和属性。改完 4 个报错样本单独重跑。
3. **读法说明清理。**删掉判法、查法类的句子，只留数据事实。改完先看耗时和工具调用数是否回落到 v4 水平，回落了就不做逐项开关实验。
4. **业务描述资料定稿。**"产品按险种代码区分、简称别称以产品查询为准""金额单位"写进业务描述资料；不写任何"怎么判"。资料放哪、谁维护，按 `demand/information_sources.md` ⟡3 的倾向先做，等裁决。
5. **B02 登记为已知 case，不加规则。**它是 S6 + 判官偶发不按业务事实认（3 轮错 1 轮）。等上面 1–4 做完、报表分层后再看它落在哪格。
6. **落主线路径。**上面站得住的三处（拆说法要能单独成立、判官一条边界、业务事实进业务描述）写成 `spec/alg/knowledge-evidence.md` 的条目；`demand/knowledge_evidence.md` 合到主线时，按 `demand/information_sources.md` 的位置重写其 §1、§2（它现在是方案写法）。实验补丁随落地删除，不留副本。

### 2.3 不做

- 不再做"改一句判官提示词 → 跑全量 → 看总分"的循环。
- 不在评测系统里加任何业务事实。
- 一致率不涨不急着上多采样；先等 1–3 做完，看剩下多少真属于判官。

## 3. 业务 trace 与分歧 case（Terminal 2）

### 3.1 case 归位

| 位置 | 这个 case 里是什么 | 结论 |
|---|---|---|
| ① 目标 | 客户号 C92200000884 对应谁 | 要结果 |
| ③ trace | 搜索内部四步，中间两步只记字节数和状态码，看不到按什么条件查的 | S1：缺口信号，写进报告；不补埋点 |
| ③ 知识 | 评测方没连客户数据源，核实不了 | S3：缺的是这一格 |
| ④ 主轴 | 缺知识格 → 说不清（缺料：客户数据源） | `fulfilled.md` §2.3 "事实核实不了"（已加） |
| ④ 六轴 · 模型能力 | 搜索返回已提示"需核实请用 customer_detail"，模型未调即断言 | 违反"不丢关键信息""工具调用决策一致"，两次评判漏判 |
| ③ trace | Langfuse 脱敏 + 4000 字截断不留标记 | S2：provider 按长度等于上限标 truncated |

这个 case 对开发的正确输出形状：

> 结果：无法核实（缺客户数据源）；过程：模型能力——搜索返回已提示需核实，未调详情接口即断言；可观测性：搜索内部查询条件未埋点。

两次评判一个给 `not_evaluable`、一个给 `fulfilled`，都没把这三句说出来。

### 3.2 要做的

1. **核对已做的文档改动**与需求一致：`fulfilled.md` §2.3 新行只在启用真实性轴时触发（D18 开关）；`process-axes.md` 不加新定义，§10 补样例"输入说需核实，输出说成确定结论"；`demand/demand.md` 第 7 条只说能力不说判法。
2. **查模型能力轴为什么漏判。**两次评判都判"忠实"。看它当时拿到的模型输入里有没有那句"需核实"提示（可能是材料没给到，属 ③），还是给到了没判出（属 ④）。先定位再改。
3. **缺口信号落地。**provider 把 S1、S2 这类缺口以结构化方式交给下游（哪一步、缺什么、为什么缺），不只写在 limitations 文字里。分几级按 `demand/information_sources.md` ⟡2，先用现有的"部分采到"雏形。
4. **Langfuse provider 代码按原计划提交**，和这个 case 无关。
5. **主轴稳定性。**Langfuse 那次主轴推翻了知识数据轴的"无法核"。D18 补了规则；是否还需要用同一份快照重跑 3 次确认偶发还是系统性，等 2 查完再定。

### 3.3 不做

- 不为这个 case 给业务补埋点。
- 不在主轴写"业务没核实 → ne"这类规则。
- 不为 Langfuse 单独加客户号类规则。

## 4. 交叉：trace × 知识对照

`demand/information_sources.md` §3 把两格对照列为开放场景最有价值的用法：业务查到了没用上 / 业务没查、知识源里有 / 知识源里就没有。§3.1 的 case 正是"业务没查、知识源里有"，没有这个对照就只能判说不清。

现状：`demand/knowledge_evidence.md` ⟡4 "有业务 trace 的场景是否也启用"标为暂缓。两条线一条在建知识格、一条在建 trace 格，交叉处没人做。

建议：
1. 需求层把 ⟡4 从暂缓改为排期，位置在 `demand/information_sources.md` ⟡6。
2. 前提是知识查证合到主线（§2.2 第 6 条）。合完后，第一个验证样本就用 §3.1 这个 case：接上 insurance-tools MCP，看能否输出 §3.1 那三句。
3. 对照结果意味着什么（结果正确但过程不可靠怎么归）归 `demand/process_axes.md` ⟡"主轴怎么基于六轴综合判断"，不在本文定。
