# 过程六轴的子分类抽象：按过程期望对账

> 讨论稿，未生效；完整替换此前按轴固定枚举的草案。撤回此前“那些子类互斥穷尽”“只有工具与数据轴允许未定位共担”的断言。
> 本文只讨论子分类的生成依据，不修改现行五态、六轴归属与汇总协议，不增加模型调用或审查阶段。

**核心：Judge 按“用户期望办成什么”逐条判；过程六轴按“本次过程中的哪项关系应当成立”逐条判。失败子类来自该关系的具体违背方式，不来自预先列好的故障词典。**

```text
运行现场 x                         需求与适用规则 y
  ① 采集、召回：取得有界运行证据 R       ┆
                    ↓                  ┆
  ② 具体化期望 O：在什么范围、什么情形下，哪项关系应成立，依据是什么
                    ↓
  ③ 对账 K：逐项比较过程期望与事实
       正常 / 偏差 / 看不清 / 不适用 / 契约缺失
       同时保留：要求、实际关系、证据及定位边界
                    ↓
  ④ 展示：沿用轴结论；子类按“同一期望关系的同一种违背方式”组织
```

## ① 取证：先固定本次到底看到了什么

沿用现有采集与召回：`R = S(t(x))`，包括选定环节、原文、机器事实与可见性缺口。
“没有调用记录”只有在相关执行范围完整可见时，才能支持“没有调用”；查不到记录本身不是未执行的证据。规则 y 保留出处及适用范围，不与观测事实混同。

## ② 具体化期望：六轴中对应业务期望的东西

**过程期望就是现有义务在本次运行中的具体化，不是另一套义务。**

`O : 运行证据 R × 需求与规则 y → 本次过程期望集 P`。

一条过程期望写成：

> 在【范围】内，当【情形】成立时，【应成立的关系】必须成立；依据是【出处】。

“关系”可以约束信息含义、决策、先后顺序、数据条件、时限或交付，不限于输出值相等。例如：取得对象标识后才能调用依赖该标识的接口；传递后仍保留来源中的不确定性；返回数据的时点满足请求条件。它不是固定的关系枚举。

生成与拆分规则：

1. **先找要求，再找反例。** 要求出自需求、适用的通用义务或当次契约；实际行为帮助定位检查对象，不能凭失败倒造一个“必须”。允许、建议不得加强为必须。
2. **按可独立验收的要求拆。** 两项要求能一项成立、另一项不成立，且各有独立依据与判据，就分别对账；共同定义一个条件的值、单位、时点不能拆散后丢掉它们的关系。
3. **既检查已做的，也检查应做却没做的。** 后者必须放在可观察的流程范围内检查，不能虚构一个已发生调用。
4. **不从目标推出唯一实现。** 目标允许缓存、替代工具或其他等价路径时，期望必须保留这些合法实现；不能没调某个接口就认定任务没处理。
5. **缺判准仍保留问题。** 不能因为缺少时限或规则，就把待检查要求悄悄从范围中删除。模型局部期望仍只用本次收到的规则及适用通用义务。

六轴提供不同的提问方向，而不提供封闭的失败类型：

| 轴 | 从本次材料中提取什么过程期望 |
|---|---|
| 意图理解 | 哪些用户含义、约束及未定信息，应如何出现在内部任务中？ |
| 规划路由 | 哪些工作应被覆盖，哪些决策、先后关系与结束条件应成立？ |
| 工具执行 | 对实际收到的指令，工具承担哪些有据的执行与返回保证？ |
| 知识数据 | 本题需要哪些有据的数据条件，对象、时点、适用范围应满足什么？ |
| 模型能力 | 对本次实收事实与规则，哪些推导、决定和输出要求应成立？ |
| 上下文管理 | 哪些既有信息应原义到达何处，哪些状态或来源约束应保留？ |

## ③ 内核：判结果，保留能证明结果的具体差异

白话：**先问这条要求做到了没有，再说明事实在哪一点与要求不符。**

`K : 过程期望 × 范围内事实 → 现行五态 × 对账说明`。

五态沿用现行 K，不在此重新定义；对账说明包含要求、实际关系、引用及尚未定位的边界。K 不按保单、订单等业务名字另设判法；期望和事实如何取得，由 O 与采集负责。

偏差的最小表达是：

> 【有据的关系要求】在【已核验范围】内，被【具体事实】违反；证据能定位到【这里】，还不能证明【那里】。

偏差成立与原因已定位是两件事。偏差已证实、原因不明时，保留偏差，不编原因；仅有证据缺口时不能用故障子类补齐。评测器调用失败仍是运行失败，不冒充业务五态。

## ④ 子类如何生成：把具体差异提升成可复用的关系模式

`分型 : 过程期望 × 对账说明 → 关系模式或明确的未细分项`。

分型是结果的组织规则，不是新增诊断阶段。现有按“同一义务、同一结论、同一理由”分组提供了起点，但不能把宽泛的义务编号当作最终类别。

生成一个子类必须交出一句**纳入条件**：

> 当【同类期望关系】适用，且证据证明【同一种相反事实关系】，并且【定位条件】一致时，属于本类。

只将不影响判定的对象身份、实例编号替换成角色变量；保留会影响判定的条件、否定、单位、时点要求和不确定性。类名只是这句话的简称。

- “信息不完整”不足以成类；“源记录中的任务相关限制语已存在，但在下游实收内容中消失”有明确判据。
- 名字相似不够：同为“数据没拿到”，未发起取数与源端已证实缺数不能合成同一个已定位原因。
- 证据只能证明共同现象时，停在现象级；不得把尚未定位的项塞进某个确定原因类。
- 一条宽义务包含多个独立偏差时分别保留，不能强制只选一个子类。
- 类别空间开放；五态需要封闭，业务偏差模式不需要预先穷尽。新增 case 可以产生新模式，而不扩充内核状态。

全链：`展示({(p, K(p,R)) : p ∈ O(R,y)})`，其中 `R=S(t(x))`；展示消费逐项结果，沿用 Agg，并按上述分型规则组织子类。规则与现场先定格；分型不能回写要求或改变判定。语义拆分与归类仍需核验，公式不保证模型必然分对。

## 边界例：没拿到数据，不等于数据源出了错

若本题的有效要求是“取得对象在指定时点的数据”，则：

| 已核验事实 | 可生成的模式条件 | 不能推出 |
|---|---|---|
| 完整流程证明必要取数未发起，且无可用缓存或等价来源 | 必要数据未取得，已确认获取动作未发生 | 数据源不存在该数据 |
| 正确查询已到达源端，可信源证据确认所需数据不存在 | 必要数据未取得，源端缺数已确认 | 工具执行有错 |
| 本应取得的数据未得到，但工具与源端交接不可见 | 必要数据未取得，缺失位置未定位 | 两侧各自故障已获证明 |

这些是从同一要求与不同证据生成的三个例子，**不是新的三值枚举**。若任务只是“查明是否存在”，可信的不存在答复可能已经满足期望，不能沿用“缺数即失败”。

现行 σ 的抽象写“正确执行的查询→数据是否存在”，实现又检查“本轮所需数据有没有取得”。二者范围不同。要同时记录，必须分别注明**本轮数据取得要求**与**数据源自身要求**；不能靠加一个子类把系统范围的失败偷换成源端故障。其归轴与汇总需要单独确认，本文不暗改现行协议。

## 承诺、分层与归位

| 承诺 | 形式 | 把关者 |
|---|---|---|
| 不能看到失败才编要求 | 出处支持情形与关系要求 | O 的材料与语义核验 |
| 不漏掉应做却未做 | P 不限于已发生调用 | 需求覆盖核对；不是仅枚举 trace |
| 类型有纳入依据 | 每类有关系谓词及支持证据 | 分型的逐项核验，不能只验类名 |
| 不以现象冒充原因 | 定位不超出证据可支持范围 | 对账与分类语义核验 |
| 分类不修改已判结果 | 分型结果不回流 K | 单向消费边界 |

不变的是“有据期望→事实对账→按违背关系分型”；可换的是 t/S/O 的供料与具体化方式，以及分型对已证差异的概括。新场景改变期望与材料，不预装新故障词典。“因为是某个 case 就特殊判”“没报错即正常”翻译不成供料变化，属于不接受的判法例外。

现有机制归位：reader/案卷/分析轴→①；六轴义务模板、项目声明与 expected→②；逐项评判、observed 和引用→③；Agg 与结果分组→④。跨 case 聚类仍是后续消费者，不能倒过来决定本案发现什么。

演化方向只有一条：先让每项结果能回答“违反了哪条具体期望、证据证明到哪里”，再讨论如何稳定合并同类；不先建设子类注册表。
