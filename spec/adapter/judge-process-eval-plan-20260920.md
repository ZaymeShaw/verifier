# 方案 2026-09-20：过程评测从"拉取 + 事后审计"改成"整理案卷 → 各判一题 → 一份裁决"

状态：已实现（A 测试环境、案卷+选段、六轴、主轴接线、干净重跑均完成；E 冻结样本复评见 report/process-dossier-20260920/README.md）。范围只在 llm_probe 的 Judge / 六轴 / 分析轴 / 测试环境；不碰多轮 mock、MCP、存储结构。

## 0. 问题

现在过程轴的判法：程序给 Judge 一张目录 + 4 个翻阅工具，Judge 自己决定翻哪几页，输出结论和引用；程序事后查它引的页存不存在、翻过没、翻全没（`process_common.py` 里 covers / seen_refs / unread_refs / fabricated_refs / _demote / precheck 覆盖 / unaddressed_findings 那一层）。"翻没翻过"程序查不准，所以补丁越打越多。

病因：从原始 trace（Agno 的 runs / spans / messages / session_state / raw_runs 几张表，半数重复，顺序靠时间戳拼，模型请求正文要从持久化消息拼回）到"这一轮按顺序发生了什么"的还原工作没人做，六个轴各自拿工具翻，翻出六个版本，还互相打架。

## 1. 三个角色

| 角色 | 只回答 | 输入 | 输出 |
|---|---|---|---|
| 分析轴 | 发生了什么 | 原始 trace（能拿到什么拿什么） | 案卷 |
| 六个过程轴 | 各自一题：做得对不对 | 完整案卷 | checks（现有格式） |
| 主轴 | 最终怎么判 | 案卷 + 六轴 checks | JudgeResult（现有格式，不改） |

### 1.1 分析轴 = 整理案卷，不下结论

1. 拉全：步骤、模型调用、工具调用、消息、状态、历史 run 全部读出来，对照采集器报的覆盖情况确认没漏。业务侧给什么拿什么，不等业务改。
2. 排时间线：用户问 → 步骤 1 → 模型调用 1（实际输入全文、输出）→ 工具调用（参数、返回）→ 模型调用 2 → … → 最终答复。每个节点带原文。历史轮单独一段。
3. 列缺口：该有但没有的（模型请求正文是拼回的、某步没落盘、直达路径后端调用只在步骤输出里），如实写。
4. LLM 用在哪：**分析行动路线、判断下游需要哪些信息、从步骤输出里认出"哪段是后端调用/参数/结果"**——这是理解结构，不是产内容。案卷里的每一段原文都来自 trace，LLM 不生成、不改写、不摘要正文。
5. 删：`observations.py` 里 repeats / handoffs / kept_ratio / model_saw 这套程序统计，以及"找异常点"式的 findings。

### 1.2 六个过程轴 = 读完整案卷，各答一题

- 意图理解：系统把用户要什么理解对了吗（结合历史：目标、对象、约束）
- 规划路由：路径对吗，该做的做了吗，该停的停了吗
- 工具执行：参数对吗，执行成了吗，返回合契约吗
- 上下文管理：**逐次模型调用**，对照"这一步要干什么"，判实际输入缺不缺（目标/约束/对象/前序工具结果）、多不多（无关历史/重复/过时/别的对象）、乱不乱（指令资料历史分不清、冲突没处理）。一次有问题就是有问题。删现有 5 个 check（projection / cache_reuse / per_call_goal / history_faithful / no_contamination）和"同名同参重复才查缓存"之类前置条件。
- 知识数据：拿到的数据能回答问题吗，对象、时点、来源对吗
- 模型能力：在它实际拿到的输入下，决策和输出做对了吗

每轴输出沿用 checks 格式：status / finding / evidence_refs / missing_evidence。refs 指案卷编号（如 call#2.msg5）。

结论口径统一：看到问题 → problematic；该判但案卷没材料 → 缺证（写缺什么）；本轮没这件事（如 0 次模型调用）→ 不适用；都有依据 → sound。缺证、不适用都不算通过；一项缺证整轴不能 sound（去掉 critical=False 这类固定标签）。

其他五轴定义不动，提示里写明已发现的错误判法：历史查询 EMPTY 不证明本轮后端没数据；"本轮没查"≠"查了没采到"；不能拿"这归别的轴"当本轴通过的理由。

事后只剩两样校验：输出格式对不对；引的案卷编号在不在。covers / seen_refs / unread_refs / fabricated_refs / _demote / precheck 覆盖 / unaddressed_findings 整层删。

### 1.3 主轴 = 法官，格式不变

- 不开 trace：现有主 Judge 一字不动。
- 开 trace：顺序改为 采集 → 案卷 → 六轴 → 主轴。主轴输入 = 案卷 + 六轴 checks，输出**现有 JudgeResult 格式不变**（fulfillment_assessments + reasoning_summary 等），只是 reasoning 里必须写清四件事：用户目标达成没；过程哪里有问题、对结果什么影响；六轴打架的地方按案卷怎么解释；定不了的为什么。
- 一致性检查就是上面"分歧解释"那一段，删 `consistency.py`。
- 页面主状态只显示这一份裁决，取消扩展 fulfillment 轴和主 Judge 并列。
- 开了 trace 但采集失败：结果标缺证，不默默退回无 trace 流程判通过。

## 2. 测试环境（A）

- A1 会话污染：用例不再写死 session_id，每次执行生成新的业务 session。
- A2 多轮顺序：4 组 T1/T2 显式分组，同组共用同一个新 session，T1 业务执行完再发 T2，T1 失败 T2 不跑。
- A3 重试边界：业务已跑完只是评测失败时，用已存 trace 重评，不再打后端。
- A4 留存：模型调用记录上限 200 → 500，不动存储结构。

## 3. 验证（E）

固定样本 = report/ 下已冻结的 5 份快照 + A 做完后干净重跑的 29 条，冻结 trace。每条先由我独立看 trace 下标准答案，你抽查。改完的 Judge 对着样本跑，看该报的报了没、不该报的乱报没；不以通过率为目标。以后改 Judge 都在同一批冻结 trace 上重评。

## 4. 不做

多轮 mock 探索页、MCP、新存储、独立一致性轴、规则引擎。业务系统自身问题（60s 上限、召回错产品、模板覆盖草稿）如实记，不修。

## 5. 顺序

A → 分析轴（案卷构造器，先对 5 份快照量体积）→ 六轴（删审计层、接案卷、上下文轴重定义）→ 主轴接案卷+六轴、删 consistency → 干净重跑 29 条 → E。
